Offline queue — readings the server rejected need attention

Story 11.16 (audit C4, the epic's Ask First: where does it surface and how does it look). A reading typed offline that the server later refuses is no longer deleted; it waits on the Dashboard in one card directly under the Status card and above the Tariff Check line. The card renders nothing when no reading needs attention (frame e), so the Dashboard stays exactly as it is today. Token values come from key-dashboard.html and DESIGN/colors.md; nothing new is introduced in option A.

Decisions to confirm
  • Surface tier. Recommended: the QuietCard tier (near-transparent, no blur), the same material as the Tariff Check card, so the Status card stays the single highest-weight element (Story 2.5 AC).
  • Accent. A (recommended): neutral card, TriangleAlert icon in the muted green-grey, reason in normal text. B: warm amber border and icon (the glass-confirm hue). C: red; colors.md reserves red for genuine system errors and critical messages, so C only if you rule a lost reading critical. Compare the three at the bottom.
  • Density. One compact block per reading: value and timestamp on one line, the server's reason below it (verbatim, English), then two pill buttons. On the wide layout the buttons sit on the right. Text buttons rather than icon-only: Correct and resend and Discard are not guessable from an icon, and each carries an accessible name with the value and timestamp. In the dialog the unit sits inside the kWh field.
  • Discard is two-step and inline (the row's buttons swap for "Discard this reading? It can't be recovered." with Discard and Keep), no second modal. The confirming Discard is an emphasised outline, not red.
  • German. Labels are translated; the server's reason stays English (known limitation, recorded as an open item).
