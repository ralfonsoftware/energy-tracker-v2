Household members and revocable invites — Settings › Household

Story 11.9 (audit A2 and S10, AD-26). Settings gains a members list (Remove / Leave) and an Open-invites list (Revoke) inside the existing Household section, next to the existing “Invite a member”. AD-26 means full, equal trust: every member sees the same actions, there are no owner or admin roles, and the only refusals are “last member” and tenant scoping. Every frame is rendered in Dark and Light, at ≥660px (704px, the narrowest width of that layout) and at 400px; key frames also in de-DE (informal “du”, ~15% longer). Tokens are copied from wide-settings-tariff-2026-09-28.html, the error red from key-profile-preferences.html; no new design language.

Constraints that shaped the design
  • Compact, icon-first (your standing preference): Remove and Revoke are 36px icon buttons with an accessible name that includes the person or the invite’s created date. Only Leave carries a label, because it is the one control with a visible disabled reason.
  • No fabricated names (UX-DR21): a member without a display name gets the generic label, never an e-mail or id. “You” is a chip from isCurrentMember.
  • The list never contains a token: an invite row shows only created and expires dates (the API stores a hash, so the link cannot be shown again).
  • Red is reserved for errors (DESIGN/colors.md): it appears only on the confirm buttons of the two destructive dialogs, the Leave label, and error lines. See Open decisions.
  • Accessibility: lists are <ul>; one polite live region announces completed actions; after a removal or revoke focus moves to the section heading (the row that held it is gone); DOM order is reading order.

For your review (Task 1.4) — Sally’s recommendations

  1. Layout: Household goes full width at ≥660px, AI Plausibility Check stays full width above it. Reason and Tab-order consequence are in the Layout decision. Spines amended as “proposed” until you confirm.
  2. Leave = icon + label, Remove/Revoke = icon only. Alternative: Leave as an icon too, with the disabled reason in a tooltip only — rejected, a tooltip is not a visible reason and not reachable by touch.
  3. Error tint on the two destructive confirm buttons. DESIGN/colors.md reserves red for “genuine system errors and critical messages”; removing a person is critical but not an error. It extends the existing precedent (Log off is already error-tinted in the Profile menu and Settings). Alternative: a neutral teal confirm — safer visually, but then the irreversible button looks like every other primary. If you agree, DESIGN.md gets one sentence: “irreversible access changes use the error tint”.
  4. Below 660px, “Invite a member” becomes the flat bare block inside the Household card (as chosen for the restore panel) instead of the nested glass card, so the new list and the invite action read as one section and the new invite lands in the list right above it. Small change to InviteMemberRow (its ≥660px row is unchanged). Alternative: leave it as built (card-in-card on phones).
  5. Initial avatars (a 32px circle with the first letter, a person glyph for unnamed members) help tell rows apart at a glance and cost no extra data. Say so if you would rather have none; the rows work without them.
  6. Dates use the locale formatter without times (the API returns UTC instants; an exact hour adds noise and a time-zone question). “Expires Oct 21, 2026” is day-accurate.
Layout decisionHousehold section: paired half-width, or full width?

Rendered at 704px, the narrowest width where the ≥660px layout applies (portrait tablet). The real column is up to 900px, which only makes Option 1 less bad, not good.

Option 1 (pairing stays)
Zero change to the page structure; the pairing already exists and is tested. But each half is ~320px wide at 704px: member names, the “You” chip, the joined date and the action no longer fit on one line, de-DE dates and the Leave label wrap, and the AI card stretches to the Household card’s height with an empty lower half.
Option 2 (full width) — Sally recommends
The pairing was justified in 2026-09-28 because both sections were “short and mutually unrelated”. Household is now three stacked blocks (members, open invites, invite row) and grows with every member, so it stops being short. Full width keeps each row on one line in both languages. Tab-order consequence: none for reading order — DOM order stays AI toggle → Household controls — but the pair becomes a stack, so tab-order.spec.ts must be extended: after the AI toggle come the Remove/Leave/Revoke buttons in list order, then “Invite a member”, then the Rooms tree. The EXPERIENCE.md pairing sentence is amended to AI Plausibility Check alone, full width, then Household (marked proposed until you confirm).
Option 1 — keep the pairing (half width next to AI Plausibility Check, as built today)

Failures stay where the action was. A generic failure keeps the dialog open with an inline role="alert" line and re-enables the buttons (the logoff-error precedent). 409 last-member has its own copy and a dead confirm button. 409 members-changed (and a 404 member-not-found on Remove, which means the same thing) closes the dialog, reloads the list and says so in a polite status line; a 404 invite-not-found on Revoke is “already gone”, same pattern. Behavior notes for the build (Task 7)

  • Loading: two skeleton rows per group, aria-busy on the card; no spinner text. Both lists load in parallel; if either fails the section shows the single load-error line with Try again (as rendered), not a half-filled section.
  • Remove: icon → dialog (focus on Cancel) → confirm sends DELETE /api/household-members/{id} with the clicked row’s id → on 204: dialog closes, list reloads, status “Mira was removed.”, focus moves to the section heading.
  • Leave: button → dialog + pending-readings check → confirm sends the same DELETE with your own member id → on 204: delete this household’s queued readings (only if the count was above zero and the member confirmed), then full navigation to /. A failed request deletes nothing.
  • Revoke: icon → immediate DELETE /api/household-invites/{id} (no dialog: it is cheap to undo by creating a new link, and nothing is lost); on 204 the row disappears, status “Invite revoked.”, focus to the heading.
  • In flight: every button in an open dialog is disabled; row buttons in the list are disabled while any request runs (the rate limit is 10 per 10 minutes, so double submits must not burn it).
  • Live regions: one role="status" element for success and “changed/gone” lines; role="alert" only for failures.
  • Stale tab: a removed member’s other open tab keeps its old screen until reload; every API call from it fails (backend guard). Not designed beyond the existing generic error lines.
