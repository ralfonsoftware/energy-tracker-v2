# Layout & Spacing

Mobile-first, responsive web — the primary authored surface is a phone-width screen, because meter-side reading entry (UJ-1) is the product's highest-frequency, highest-stakes interaction and it happens standing at a meter with a phone in hand. Browser/tablet width is the secondary authored surface, used for the calm-evening trend-browsing context (UJ-3) where a wider frame legitimately helps (trend chart, Room → Power Point → Device tree).

Spacing reflects "says less, on purpose": generous, calm gaps rather than a dense grid. `{spacing.card-padding}` (24px) is the standard interior padding for a glass card; `{spacing.card-gap}` (18px) separates stacked panel elements; `{spacing.mobile-margin}` (19px) is the phone-screen edge margin; `{spacing.5}` (24px) is the gap between major sections on a surface (e.g., between the Status card and the Tariff Check card on Dashboard). Tailwind's base 4px scale (`{spacing.1}`–`{spacing.6}`) is inherited as-is for anything not named above — no exotic scale, just used generously rather than packed tight. The app background itself sits on `{colors.surface-base}` / `{colors.surface-base-dark}`, one shade back from every glass panel so the panel stack has somewhere to cast its depth against.

Single-column layout on phone width. The drill-down surfaces (Trend History) widen to a browser/tablet frame but stay single-column-**of-cards** internally — the card stack never splits into a dense multi-column dashboard grid; that would work against the product's discipline of the Status card as the one thing that matters most. (2026-09-28: this still governs the *card stack*. It does not extend to the list of individual entries inside a single card — see the Entry-grid pattern below, which is a narrower, deliberately-scoped exception.)

**Responsive breakpoint (amended 2026-09-23, Epic 8):** `{spacing.breakpoint-wide}` = 660px. Below it, every surface renders the single-column phone layout described above, edge-to-edge. At 660px and above — one rule covering both tablet and desktop, not two separate treatments — content is constrained to a single column, centered in the available viewport, on **every** surface (Dashboard, Trend History, Tariff Radar, Settings), not only Trend History as originally scoped here. The column stays single-column-of-cards internally at the wide breakpoint too — this is a width constraint plus a nav-chrome swap (`{components.nav-chrome}`, see DESIGN/components.md), never a dense multi-column grid. This corrects a gap found in a 2026-09-23 UX review: the wide-viewport constraint was documented but had not actually been applied to any shipped surface, which rendered the mobile layout ungoverned across full desktop/tablet width. → See [mockups/critique-desktop-breakpoint-2026-09-23.html](mockups/critique-desktop-breakpoint-2026-09-23.html) for the full before/after per surface.

**Column width increased (amended 2026-09-28, post-Epic-8 desktop feedback):** the column's cap grows from 660px to `{spacing.content-max-wide}` (900px), on the same four surfaces, still governed by one shared rule rather than a per-surface exception. `{spacing.breakpoint-wide}` (660px) stays the trigger for the phone→wide layout switch and the nav-chrome swap — only the column's own max-width changed. Below 900px viewport the column still simply fills available space up to the cap (existing `w-full`/`max-w` mechanics, unchanged), so a mid-size tablet window isn't stranded with gutters it doesn't need. Motivation: Ralf's live-feedback review of the shipped Trend History page found the fixed 660px cap left most of a desktop viewport empty and squeezed the trend chart's usable drawing width. Dashboard's Status card keeps its existing proportions — nothing about its content changed, it simply sits in a column with slightly more margin either side.

**Entry-grid pattern (new 2026-09-28):** Trend History's Meter Readings and Events cards, and Tariff Radar's Tariff History list — previously single-column tables at every width — reflow their individual entries into a fluid grid at `{spacing.breakpoint-wide}` and above: `grid-template-columns: repeat(auto-fill, minmax(260px, 1fr))`. This yields 2 columns on a narrower wide-layout window and 3 on a full desktop width, without a second hard-coded breakpoint — column count falls out of available width, not a designed per-device-class decision, directly answering the "two or even three column" ask. Each entry renders as a compact bordered tile (primary line + secondary context line + timestamp + action) rather than a table row; below 660px, today's single-column stacked list is unchanged. The rule for which lists qualify: flat, independent, timestamp/period-ordered entries with **no manual reordering affordance**. That last clause is what excludes the Rooms/Power Points/Devices tree's Device level (see the Grid-with-expand pattern below) — a drag handle makes "move" ambiguous in two dimensions. The Room → Power Point → Device tree's hierarchical levels and Tariff Radar's Add/Compare-Tariff form fields (paired-field rows, not independent entries) are untouched by this pattern. → See [mockups/key-trend-history.html](mockups/key-trend-history.html) and [mockups/wide-settings-tariff-2026-09-28.html](mockups/wide-settings-tariff-2026-09-28.html) for the rendered treatment in both Dark and Light.

**Grid-with-expand pattern (new 2026-09-28, Settings' Rooms/Power Points/Devices tree only):** collapsed Room and Power Point summary rows — today a plain single-column list, the source of a long scroll of mostly one-line rows once a household has many of either — sit in the same `repeat(auto-fill, minmax(220px, 1fr))` grid as the Entry-grid pattern above. Opening a Room or Power Point spans that one tile to the full grid width (`grid-column: 1 / -1`) and reveals its children inline below the summary row — the identical `details`/`summary` accordion interaction already in place, just reflowed into a grid when collapsed, not a new interaction to learn. **Device rows (the leaf level) are deliberately excluded and stay a plain single-column list at every width** — they carry a drag handle for manual reordering (Story 2.6), and reordering via drag is a materially more ambiguous gesture across a 2D grid than down a vertical list. This is the same "no manual reordering affordance" test the Entry-grid pattern uses, applied to the one case in the product where it currently excludes something. → See [mockups/wide-settings-tariff-2026-09-28.html](mockups/wide-settings-tariff-2026-09-28.html).

**Section pairing (new 2026-09-28, Settings only):** "AI Plausibility Check" and "Household" — each a short, self-contained, mutually unrelated block that previously sat alone on a full-width row with most of the row empty — pair side by side at `{spacing.breakpoint-wide}` and above. "Yearly Baseline" is not paired with anything (its own preset-icon row already uses the width), and the Rooms/Power Points/Devices card stays full width (it is the one section that actually needs the room, per the Grid-with-expand pattern above). Pairing is reserved for genuinely short, unrelated sections — it is not a rule to apply to every Settings section uniformly. → See [mockups/wide-settings-tariff-2026-09-28.html](mockups/wide-settings-tariff-2026-09-28.html).

**Comparison-panel pairing (new 2026-09-28, Tariff Radar's Compare-Tariff form only):** the current-vs-candidate summary panels (`DESIGN.md` → Components → Tariff comparison card) move from stacked to side by side at `{spacing.breakpoint-wide}` and above — a direct comparison reads better in two columns than stacked one above the other. The verdict card stays full width below both panels: it is the shared conclusion both feed into, not a third comparison panel, so it does not join the pair. → See [mockups/wide-settings-tariff-2026-09-28.html](mockups/wide-settings-tariff-2026-09-28.html).
