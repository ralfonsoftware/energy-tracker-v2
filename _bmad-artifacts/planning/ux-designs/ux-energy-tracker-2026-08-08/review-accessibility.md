# Accessibility Review — energy-tracker

## Overall verdict

Mostly ready, with real and fixable contrast gaps, not just theoretical ones. The behavioral contract (motion/`prefers-reduced-motion`, focus-trap-and-return, offline capture, gap-flagging language, colorblind text-pairing) is genuinely well specified and, where I could check it against the mockups' actual CSS, correctly implemented. The color *system*, however, has a systemic problem: several secondary/quiet text tokens and multiple mockup-rendered text elements measure well below 4.5:1 against their actual composited (tinted-glass-over-base) backgrounds — this isn't a hypothetical edge case, it's the load-bearing microcopy (Tariff Check status line, FR-13's explanatory sentences, "last reading" footer). None of this requires a redesign; it requires re-tuning specific token values against measured, composited contrast rather than against a flat swatch.

### Findings

- **critical** Secondary/quiet body text fails AA systemically, in both modes, across real functional copy. Measured against actual composited backgrounds (surface-base → surface-glass/-quiet → text token): light-mode `tariff-quiet`/`text-quiet` ≈2.1–2.5:1, dark-mode ≈2.7–2.9:1; light/dark `secondary-footer` ("Last reading Aug 3", date label) ≈2.1–2.9:1 — all well under the 4.5:1 required for normal text at 10.5–12px. (`DESIGN.md` Colors — `text-quiet`, `text-secondary` tokens; rendered in `mockups/direction-green-eco.html` `.tariff-quiet`/`.secondary-footer`/`.date`, and the same low-alpha pattern recurs in `key-smart-plug-import.html` and `key-tariff-radar.html`.) *Fix:* re-tune these tokens' lightness/alpha against their actual composited background (not a flat swatch) until every real-copy use clears 4.5:1; the Tariff Check "nothing due" line and the trend/import footnotes are functional messages, not decoration, so they don't get a lower bar.

- **critical** Status badge label text, if implemented literally per `DESIGN.md`'s own spec ("badge... colored from the status triad" using `{colors.status-within-range}` / `-below-baseline` / `-trending`), fails AA: measured 2.85–3.98:1 against the badge's own `-bg` tint or the card's glass background. The actual mockup avoids this by quietly substituting *different*, better-contrast, undocumented hex values for the badge text specifically (`#B9EFC7`/`#F5CE93` dark, `#1F7038`/`#8A5A14` light — 4.86–7.72:1, genuinely AA-clean) that appear nowhere in `DESIGN.md`'s token table. Since `EXPERIENCE.md`/`DESIGN.md` state the spine wins on conflict with any mock, a dev building strictly from the documented tokens would reproduce the failing colors, not the working ones. (`DESIGN.md` Components → status-card; `mockups/direction-green-eco.html` lines 196–238.) *Fix:* add explicit `status-*-badge-text` / `-dark` tokens capturing the mockup's actual values, and point the component prose at them instead of the raw status-triad swatch.

- **high** `direction-green-eco.html`'s "Within range" frame is rendered using the hex values `DESIGN.md`'s own token table assigns to "below baseline" (`#4FCA72` dark / `#2F9E52` light), while the documented `status-within-range` sage tokens (`#9FBB8A`/`#6B8656`) never appear in any rendered mockup, and "below baseline" itself is never shown at all. This creates real risk that an implementer wires the wrong hue to the wrong state — which would also undercut the memlog's colorblind-safety decision, since that decision leans on three *visually distinct* states plus text, not two. (`mockups/direction-green-eco.html` vs. `DESIGN.md` Colors — status triad.) *Fix:* render (or at least spec-correct) an explicit "below baseline" frame using the sage token, and reconcile the file's own header comment (which correctly lists sage separately) with its CSS (which never uses it).

- **medium** FR-13's own explanatory copy in `key-tariff-radar.html` — the plain-language sentences that are supposed to be *why the user should trust the verdict* — falls short of AA in the one state rendered: `.signal-detail` ≈3.88–4.35:1, `.signal-frame-label` ≈2.48:1, and the "Not worth it" `.signal-amount` figure ≈3.49:1, all against their own row-tint backgrounds. The verdict pill itself (`.signal-badge`, solid-fill) is fine at 5.4–11.1:1 — the gap is specifically in the supporting sentences carrying the nuance the two-way signal exists to communicate. *Fix:* lighten/darken `.signal-detail`/`.signal-frame-label` per-mode and re-check against the actual composited row background.

- **medium** Trend chart (Moderate density — the only shipped default per this session's decision) has only a partial text alternative. A single snapshot sentence exists ("Currently 240 kWh under baseline...") plus incidental SVG `<text>` axis/gap labels, but the polyline's actual multi-point trajectory — the real information a trend chart conveys — has no structured equivalent, and the `<svg>` has no `<title>`/`role="img"`/accessible-name grouping, so a screen reader encounters disconnected text nodes ("0", "+40", "−40", "Jan", "Apr", "Aug", "No reading", "Apr 3–17") with no containing label. The rejected Dense variant already prototypes a `<table>` equivalent (`density-trend-history.html:363`) that Moderate could reuse behind a visually-hidden/expand affordance. (`EXPERIENCE.md` Component Patterns → Trend chart; `mockups/density-trend-history.html` "2 · Moderate" section.) *Fix:* wrap the chart in a labelled `role="img"` with an `aria-label`/`aria-describedby` summary, or add a collapsed text-table equivalent.

- **medium** No documented focus-indicator visual token. `EXPERIENCE.md`'s Accessibility Floor correctly specifies focus-trap-and-return *behavior* for the Log Reading sheet and Meter Regression prompt — that part is genuinely handled, not just implied. But `DESIGN.md` defines no `focus-ring` color/width/offset token anywhere in Colors or Components. The only rendered example, `motion-demo.html`'s `.log-btn:focus-visible { outline: 2px solid #8FE9CE }`, is a one-off in a motion demo file, not referenced as canonical, and its color isn't in the token table. *Fix:* promote a `focus-ring`/`focus-ring-dark` token into `DESIGN.md`, verified against both glass and base surfaces (WCAG 2.4.7/2.4.11).

- **low** The PRD's i18n/locale NFR (Cross-Cutting NFRs: launch locales `de-DE` + `en-US`, no hardcoded locale-specific formats) is not referenced anywhere in `DESIGN.md` or `EXPERIENCE.md` — a genuine silent gap, distinct from the offline-capture NFR, which *is* correctly carried into `EXPERIENCE.md` (Component/State Patterns, Log Reading sheet). No note addresses German text-expansion tolerance for the tight uppercase status pills/badges (`{typography.label-badge}` at 11.5px with 1.1px tracking) or the primary action button, and every rendered mock hardcodes English date formatting ("Thu, Aug 8"). *Fix:* add a line to `EXPERIENCE.md` Accessibility Floor (or a new i18n note) acknowledging locale-format handling and confirming badge/pill components have layout headroom for `de-DE` label lengths.

- **low** The primary action button ("+ Log reading") renders at ~42px effective height in `motion-demo.html`'s actual CSS (13px padding × 2 + ~16px line-height at 13.5px bold) — a hair under `EXPERIENCE.md`'s own stated 44×44pt-equivalent minimum, though it still clears WCAG 2.2 AA's actual 2.5.8 Target Size (Minimum) criterion (24×24px) comfortably. Not a conformance failure — just a minor mismatch between the spine's self-imposed minimum and the one control that matters most (UJ-1, highest-frequency interaction).

**Well-handled, checked and confirmed, not re-flagged:** the `prefers-reduced-motion` contract is complete and correctly gated in both `motion-demo.html` (global `* { animation: none !important }` fallback) and `key-smart-plug-import.html`'s processing-dot pulse — every animated property has a real, instantly-legible fallback. FR-13's two-way signal correctly pairs color with a plain-language verdict word on the badge itself (no color-alone reliance). Gap-flagging language (FR-8, FR-24) is consistently plain-language, not color/icon-only. The specular sweep is implemented as a `::before` pseudo-element, so it's correctly invisible to the accessibility tree without needing explicit `aria-hidden`. The colorblind-safety decision on the Status triad (memlog) is not re-litigated here — no new angle emerged beyond the state/color-mapping inconsistency already noted above.
