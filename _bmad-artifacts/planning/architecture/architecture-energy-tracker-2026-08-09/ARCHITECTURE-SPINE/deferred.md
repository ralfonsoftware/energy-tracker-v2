# Deferred

- **FR-20 generic Smart-Plug column mapping.** PRD itself flags this as low-confidence (Open Question 1). `ISmartPlugParser` (AD-9) leaves the seam open, but no generic/config-driven mapper is designed or built yet — revisit after a feasibility spike against real-world export variance.
- **FR-19 custom event/plausibility rules.** No rule format or evaluation engine designed yet. Whatever's built must stay behind a port consistent with AD-1, not a bespoke scripting layer.
- **FR-21 broader tunable thresholds** beyond the single FR-6 trending threshold. No settings-surface design yet.
- **FR-18 proactive weekly recap.** Needs a real externally-triggered scheduler per AD-7 (Container Apps scheduled Jobs or a KEDA cron rule) plus a decided notification delivery channel (PRD Open Question 2) — neither is designed yet.
- **Worker/API process split.** AD-6 currently runs API and job processing in one process/container. If Smart Plug import volume or AI-correlation load ever justifies independent scaling, split the worker into its own Container App with a queue-depth KEDA rule — same image, different entrypoint/command. Not needed at current expected household-scale volume.
- **Local OIDC provider for dev/test.** Docker Compose currently expects a real OIDC issuer (Entra ID/Auth0/etc.) even in local dev. Whether to bundle a lightweight local OIDC container (e.g. for offline dev) is left open — not blocking, since self-hosters typically already run one.
- **Multi-Main-Meter UI/logic.** The data model allows more than one Main Meter per Household (PRD Glossary), but v2's Pattern Detective and dashboard operate on a single Main Meter per Household — multi-meter flows are explicitly out of scope for v2, not designed here.
- **Storage growth on Azure SQL Basic (2 GB cap).** Fine for relational rows (readings, tariffs, events) at personal-household scale; dense Smart Plug interval data over many years could approach it. Not a concern at MVP scale — revisit if a household's import history grows large enough to matter.
- **NFR1 Tier 3 concrete time budget.** ~~Currently only "fully asynchronous with a completion notification" — no concrete number. Deliberately left open until AD-23's technical spike produces real throughput numbers on Azure SQL Basic to base a budget on, rather than picking one now.~~ **Resolved by Story 3.8's spike (2026-09-04):** recommend **15 minutes**. Derived from the slower provider's (Azure SQL Basic, 5 DTU) worst measured single-operation time on the sanctioned `[PowerPointId, IntervalStart]` bulk-write path — a 120,000-row full-device-history import against an already-large (~590,000-row) table took 459.1s (≈7.65 min) — rounded up with roughly a 2× safety margin for real-world concurrent-traffic contention the isolated spike run didn't have. See `_bmad-artifacts/implementation/spike-results/3-8-bulk-write-throughput-spike-results.md` for the full throughput table and derivation.
- **Device swap under the same Power Point name.** A different physical device continuing to report under an existing Power Point name, at timestamps the watermark hasn't seen yet, isn't caught by AD-22's value comparison and doesn't collide with any uniqueness constraint. A pattern/usage-plausibility check against historical data was discussed as a possible future mitigation but explicitly deprioritized — not designed here.
- **Narrow recovery from a mis-mapped Power Point's contaminated readings.** No delete/clear mechanism scoped to one Power Point or date range exists today. Epic 7's whole-household wholesale restore (FR-22/FR-23) is the only planned recovery path, and it isn't built yet either — a real gap, not designed here.
- **AD-23's bulk-write contract is coupled to the current one-row-per-reading storage grain.** `BulkInsertOrUpdateAsync`'s `UpdateByProperties`/`PropertiesToExclude` configuration is written against `SmartPlugReading`'s current shape — one row per reading. If a future "storage-grain rethink" (row-per-reading vs. batched/packed storage, motivated by the Meross/Eve interval-granularity mismatch) is ever pursued, AD-23's bulk-write mechanism would need to be reworked, not just re-pointed at a new table shape. Flagged by an independent reconcile-against-source-input check during AD-23's drafting — a real latent dependency, not covered elsewhere.
