# Invariants & Rules

## AD-1 — Ports & Adapters dependency direction

- **Binds:** all
- **Prevents:** Domain or Application code taking a compile-time dependency on EF Core, a specific cloud SDK, or a specific OIDC/AI vendor — the exact drift that would make swapping any of them require touching core logic instead of adding an adapter.
- **Rule:** Domain has zero external package references beyond the BCL. Application defines interfaces only; it never references `Infrastructure` or `Api`. All framework/vendor packages live in `Infrastructure`/`Api`.

## AD-2 — Dual database-provider persistence shape

- **Binds:** all persistence (FR-1–FR-28 data)
- **Prevents:** the two providers drifting into different schemas, or a feature landing that only works against one of them.
- **Rule:** One shared `EnergyTrackerDbContext` (never a per-provider subclass). Two migrations-only projects, `Infrastructure.Migrations.Postgres` and `Infrastructure.Migrations.SqlServer`, each wired via `.MigrationsAssembly(...)`. Provider is chosen once, at the composition root, from a single `Database:Provider` config value (`Postgres` | `SqlServer`) — never branched on elsewhere. A migration is added to both projects in the same commit via `scripts/add-migration.sh <Name>`, never to one alone. Portable subset only: plain relational columns (`string`, `int`, `decimal`, `DateTimeOffset`, `bool`, `byte[]`), standard LINQ translated identically by both providers. No LINQ query, raw SQL fragment, or column mapping may rely on a provider-specific feature — explicitly banned: Postgres `jsonb`/`ILike` operators, SQL Server `rowversion`, Postgres `xmin`, JSON-typed columns for anything queryable (see AD-4 for the portable alternative to native row-versioning).
- **[ADOPTED]** User explicitly chose dual-provider support (Postgres, Azure SQL Basic DTU) over a single engine, accepting the added migration-maintenance cost for near-zero Azure cost and self-host ARM compatibility. Provider is a config choice, not a strict environment lock — but SQL Server's Linux container image is x86-only, so self-hosting it on an ARM NAS (common consumer hardware, e.g. Synology/QNAP) isn't viable; Postgres runs on both architectures and is the only provider that works everywhere. Azure can run either provider.
- **[AMENDED 2026-09-04, Story 3.9] One narrow, named exception to "never branched on elsewhere":** `SmartPlugImportRepository.AddAsync`'s `AwaitingPowerPointMapping` upsert (AD-23) is a genuine single-statement-atomicity requirement (insert-or-update against the `(HouseholdId, IntervalStart) WHERE PowerPointId IS NULL` partial index, racing a concurrent completion for the same batch) that no portable LINQ/EF Core API can express — an `INSERT ... ON CONFLICT` (Postgres) or `MERGE` (SQL Server) statement is inherently provider-specific SQL text, and EFCore.BulkExtensions' `UpdateByProperties` was tried and empirically fails here (Story 3.8 spike Finding #2 — it can't scope its own match to the partial index's `WHERE` predicate on either provider). Decided with Ralf after the portable-LINQ-two-phase-upsert alternative (query-then-`AddRangeAsync`/`ExecuteUpdateAsync`, no raw SQL, weaker atomicity) was raised and explicitly declined in favor of true single-statement atomicity. **The exception is scoped to exactly this one method, this one narrow path** (never the primary `[PowerPointId, IntervalStart]` match-key path, which stays on `BulkInsertOrUpdateAsync` and is provider-unaware, per AD-23): `SmartPlugImportRepository` branches once, at the top of its `AwaitingPowerPointMapping` upsert helper, on `dbContext.Database.IsNpgsql()` vs. `dbContext.Database.IsSqlServer()` (both extension methods from the provider packages, now directly referenced by `EnergyTracker.Infrastructure.csproj` for this reason), executing one of two hand-written, provider-native raw-SQL upsert statements — one multi-row statement per `AddAsync` call, not a per-row loop (the whole point of a single-statement upsert), built via `ExecuteSqlRawAsync` with positional `{n}` placeholders EF Core itself parameterizes into the provider's native parameter syntax (never string-concatenated values; `ExecuteSqlInterpolatedAsync`'s single-`FormattableString` shape can't express a dynamic row count, hence `ExecuteSqlRawAsync` here specifically) — each statement's own `WHERE PowerPointId IS NULL`/equivalent predicate made explicit in the SQL text itself, and each also filtering `HouseholdId` explicitly (AD-3: raw SQL bypasses the global query filter, so tenant scoping must be written by hand here, not assumed). This is a second, narrower precedent alongside the one `SmartPlugReadingConfiguration.cs`'s own comment already documents for the partial index's migration-only raw SQL — both exist because the exact same partial-index shape has no portable representation in EF Core's own model or query surface. No other method, class, or future feature may cite this bullet as license for a third provider branch — a new one needs its own explicit AD amendment, the same way this one got one.
- **[AMENDED 2026-09-04, Story 3.9] A second, smaller Postgres-only branch inside the SAME method, for the primary match-key path this time — also within this bullet's scope, not a new exception.** Getting `BulkInsertOrUpdateAsync`'s primary `[PowerPointId, IntervalStart]` path to participate in the required ambient transaction on Postgres needed two further empirically-discovered fixes, neither of which is documented anywhere in `EFCore.BulkExtensions.PostgreSql` 10.0.1's own XML docs: (1) `BulkConfig.UnderlyingConnection`/`UnderlyingTransaction` must be set explicitly (`config.UnderlyingConnection = _ => dbContext.Database.GetDbConnection(); config.UnderlyingTransaction = _ => dbContext.Database.CurrentTransaction!.GetDbTransaction();`) — without it, the call doesn't join the ambient transaction at all; and (2) even after promoting `IX_SmartPlugReadings_PowerPointId_IntervalStart` to a genuine `pg_constraint` (the migration this bullet's own primary-path text references), the library's own internal constraint lookup still resolves the target schema to an empty string on this call path rather than `"public"`, so the lookup matches nothing and it falls back to its `CREATE INDEX CONCURRENTLY` helper-index step anyway — confirmed via direct Postgres server-side statement logging, not guessed. The workaround is `BulkConfig.CustomDestinationTableName = "public.SmartPlugReadings"` (Postgres-only — gated on `dbContext.Database.IsNpgsql()`; SQL Server's own default-schema resolution already returns `"dbo"` correctly and needs no such override), which forces the schema the lookup uses without changing the actual destination table name. Both fixes live in `SmartPlugImportRepository.AddAsync`'s primary-path branch, next to the code they patch.

## AD-3 — Data-layer tenant isolation

- **Binds:** all Household-scoped entities, including background job processing (AD-6)
- **Prevents:** a query handler forgetting to filter by Household and leaking one household's data into another's view — the PRD requires this enforced below the UI, not by convention in each handler. Also prevents the specific bypass where a job processor, having no HTTP principal to resolve `ICurrentHouseholdAccessor` from, reaches for `IgnoreQueryFilters()` or a raw/`Find()`-style lookup as the obvious workaround — silently reopening the exact leak this AD exists to close.
- **Rule:** Every Household-scoped entity carries `HouseholdId`. `EnergyTrackerDbContext.OnModelCreating` applies a global query filter (`HasQueryFilter(e => e.HouseholdId == _currentHousehold.Id)`) for each of them, sourced from `ICurrentHouseholdAccessor`. No repository or handler applies its own household filter — the DbContext is the single enforcement point. `DbSet<T>.Find()`, `FromSqlRaw`, and `.IgnoreQueryFilters()` are never used against a Household-scoped entity. `ICurrentHouseholdAccessor` has two resolution paths only: from the authenticated principal (HTTP requests) or from the enqueued job's `HouseholdId` field (AD-6 job processing, set before any query executes) — no code path is exempt from having one of these two set.

## AD-4 — Optimistic concurrency via portable version column

- **Binds:** Meter Reading, Tariff, Household settings (FR-1, FR-10, FR-2) — anywhere concurrent edits are plausible per the PRD's "no silent lost update" NFR
- **Prevents:** two concurrent edits silently overwriting each other, and (per AD-2) reliance on a provider-specific concurrency mechanism (SQL Server `rowversion`, Postgres `xmin`) that would fork behavior between providers.
- **Rule:** Each concurrency-sensitive entity carries a plain `int Version` column, mapped as an EF Core concurrency token, incremented on every update. A conflicting write throws `DbUpdateConcurrencyException`, mapped to an HTTP 409; the client reloads and retries. Never last-write-wins, never a silent merge.

## AD-5 — Shared Bonus-Decay Normalization module

- **Binds:** Pattern Detective (pace threshold), Tariff Savings Radar (FR-12–FR-14)
- **Prevents:** the two features' savings/threshold math diverging over time (FR-14's explicit requirement).
- **Rule:** Bonus-Decay Normalization lives in exactly one place — `Domain.Calculations.BonusDecayNormalizer`, a pure function of (rate, bonus terms, elapsed time) — called by both features. Neither feature may reimplement or locally adjust the formula.

## AD-6 — Async job processing shape

- **Binds:** FR-4 (Smart Plug import), any future Tier-3 async work
- **Prevents:** self-host needing an extra broker container it doesn't need yet, the cloud/self-host paths requiring different application code, and a push-based completion signal that fights scale-to-zero.
- **Rule:** One `IBackgroundJobQueue` port, generic over a single pinned envelope shape — `JobEnvelope<TPayload> { JobId, HouseholdId, JobType, PayloadJson }` — never a delegate/closure-based executor (a delegate can't serialize across the Azure Storage Queue adapter, so it would work on one adapter and silently fail on the other). `TPayload` is always a plain JSON-serializable record; `HouseholdId` on the envelope is what AD-3's job-processing path resolves `ICurrentHouseholdAccessor` from. Two adapters: `InProcessChannelJobQueue` (default; `System.Threading.Channels`-backed, runs inside the same ASP.NET Core process via a hosted `BackgroundService` — zero extra containers, used for self-host and local dev) and `AzureStorageQueueJobQueue` (cloud). Selected the same way as AD-2's provider (one config value, composition root). The API and the worker are **one process, one container** in both environments — no separate worker deployment exists yet (see Deferred). The client learns a job finished by **polling** a `GET /api/jobs/{id}` status endpoint, never via WebSocket/SSE — a persistent push connection would either prevent scale-to-zero from ever triggering or break outright on a cold start.
- **FR-32 extension (Smart Plug Import Job Status & History enrichment, 2026-08-26):** Today `BackgroundJob` goes straight from *no row exists* to `Status = Processing` — `BackgroundJobProcessor` creates the row only once a message is dequeued, so a job still sitting in `AzureStorageQueueJobQueue` (a scale-to-zero cold start, or several files from one multi-file upload still waiting their turn) has no persisted row and is invisible to any list query. To back FR-32's *Waiting* state, add a `BackgroundJobStatus.Queued` value; create the `BackgroundJob` row at enqueue time (wherever `IBackgroundJobQueue.EnqueueAsync` is called) with `Status = Queued`, and have `BackgroundJobProcessor` transition `Queued → Processing` on dequeue instead of creating the row fresh. FR-32's 30-day retention of completed job records is a **lazy, read-triggered sweep, not a scheduled job**: the query backing FR-32's list deletes its own household's expired `BackgroundJob`/`SmartPlugImport` rows (`CompletedAtUtc` older than 30 days) before returning results — never touching the `SmartPlugReading` rows those jobs wrote (AD-20's data stays permanent). This deliberately sidesteps the AD-7 hazard (an `IHostedService`/`Timer`-based sweep silently going dark once the container scales to zero) without needing FR-18's heavier externally-triggered-scheduler mechanism: nothing here has a wall-clock deadline, it only needs to be gone by the next time someone opens the view, so piggybacking on the existing read path is the zero-new-infrastructure answer. If a future requirement ever demands guaranteed deletion on a real clock regardless of whether anyone looks, revisit with FR-18's already-deferred scheduler (Container Apps scheduled Jobs / KEDA cron) instead of building a second one-off mechanism here.
- **[AMENDED 2026-10-10, codebase audit C7/C8; revised after reviewer gate] Job liveness: no job stays non-terminal forever, and every status transition has exactly one owner.** Audit finding: a restart loses in-process messages (and a temp-file payload is lost on any replica replacement — AD-24), leaving `BackgroundJob` rows `Queued`/`Processing` forever, which permanently blocks restore-confirm and cleanup for that Household. Rules:
  - **Conditional transitions only.** Every `BackgroundJob` status change — by the processor, the staleness check, the dequeue limit or the startup sweep — is a single conditional update (`ExecuteUpdateAsync … WHERE Id = @id AND Status IN (@expected…)`, plus `AND StartedAtUtc = @token` for transitions out of `Processing`), never a tracked-entity save. Zero rows affected means the caller no longer owns the job: log, delete the queue message (Azure), stop. A terminal status (`Completed`/`Failed`) is never overwritten. All transitions go through one Application service (e.g. `IBackgroundJobLifecycle`) — no second writer of job status.
  - **Ownership token + heartbeat.** `BackgroundJob` gains nullable `StartedAtUtc` and `HeartbeatAtUtc` (expand-only migration). `Queued → Processing` sets both to now; `StartedAtUtc` is the ownership token for that attempt (a redelivered message that legitimately restarts the job gets a fresh token). While a job runs, the processor refreshes `HeartbeatAtUtc` every **1 minute** from its own short-lived DbContext scope (independent of the job's own long transaction, e.g. a chunked restore).
  - **Staleness is evaluated lazily, at read time, never by a timer** (AD-7 reasoning, as for the 30-day retention sweep above). Every read that decides something — `GET /api/jobs/{id}`, the job list, restore-confirm's one-active-restore check, cleanup's one-active-cleanup check — first fails the Household's stale jobs. Stale means `Processing` with `HeartbeatAtUtc` older than **5 minutes**. A long but live job keeps heartbeating, so it is never falsely failed and the restore-confirm 409 guard holds for its whole run. `Queued` rows are not failed for being slow: on Azure the queue is durable (failures arrive via the dequeue limit or a missing payload file); in-process, the startup sweep covers them. **[AMENDED 2026-10-11, Story 11.3, Ralf]** The one exception is a backstop for a `Queued` row whose queue message no longer exists (crash between the enqueue-time row insert and the queue send, a failed send whose cleanup also failed, a database rolled back to a restore point, a purged or expired queue message): no dequeue will ever happen for it, and it would block restore-confirm and cleanup for the Household for good. The same read-time check therefore also fails a `Queued` row whose `CreatedAtUtc` is older than **12 hours** with `job-interrupted`. 12 hours is deliberately longer than the worst legitimate wait (a serial batch of imports, plus five 60-minute redelivery cycles before the dequeue limit fires); a message that is still in the queue after its row was failed is skipped and deleted by the processor's existing "terminal row" rule. Thresholds are operational constants in one place, not Household config (AD-15 covers household-specific values only).
  - **Startup sweep — in-process adapter only, AD-3-compliant.** At startup, iterate `Households` (an AD-3-exempt entity) and, per Household, set `JobHouseholdContext` and fail that Household's `Queued`/`Processing` rows whose `CreatedAtUtc` is earlier than the process start time (so jobs enqueued by the new process are never swept). Never `IgnoreQueryFilters()`. The Azure adapter never runs this sweep.
  - **Redelivery and missing rows.** A dequeued message whose job row is already terminal, or whose row no longer exists (e.g. deleted by Smart Plug cleanup), is deleted without doing any work. The processor's former "row missing → insert a `Processing` row" fallback is removed — it resurrected jobs that cleanup had deleted.
  - **Azure consumer (C7):** the whole receive loop body (including `CreateIfNotExistsAsync`/`ReceiveMessagesAsync`) runs inside `try/catch` with backoff — a transient storage error never escapes `ExecuteAsync` (the default `BackgroundServiceExceptionBehavior.StopHost` would take the web app down). Receive **one** message per poll. After **5** dequeues (`DequeueCount`), conditionally fail the job (non-terminal only) and delete the message — no separate poison queue (the `BackgroundJob` row is the record; a poison queue is infrastructure nobody watches at this scale).
  - **Cancellation that is not shutdown is a failure.** Only `OperationCanceledException` with `stoppingToken.IsCancellationRequested` may bypass the `Failed` transition.
  - **Missing payload file is a terminal failure, not a retry** (C3 under AD-24).
  - **Failure reasons are stable error codes, not English text** (`job-interrupted`, `job-retries-exhausted`, `upload-missing`), translated by the frontend's i18n catalogs (AD-18) like every other job error.

## AD-7 — Current Status/Reminder are computed at request time; history is persisted at computation time

- **Binds:** FR-6, FR-7, FR-8, FR-15
- **Prevents:** a naive recurring-timer implementation that silently stops firing once the Azure Container App scales to zero (`IHostedService`/`Timer`-based cron does not survive scale-to-zero, and the failure would be invisible until a household missed a reminder) — **and**, separately, a builder taking "compute live" to mean *history* is also recomputed live, which would silently rewrite past Status/pace whenever the Yearly Baseline or threshold changes, violating the PRD's explicit no-retroactive-rewrite requirement (FR-2, FR-8).
- **Rule:** The **current** Status (FR-6/FR-7) and Tariff Check Reminder due-ness (FR-15) are pure, synchronous computations evaluated on every relevant read — never precomputed by a background schedule. Separately, every time Status is (re)computed — on a new Meter Reading or a completed Smart Plug import, per FR-6 — the result is also written to an immutable `StatusSnapshot` row. **Exactly one** application service, `IStatusRecomputeService`, owns this write; the Meter-Reading-create handler, the Meter-Reading-edit handler (Story 4.3, a real value correction only — never for a no-op save), and the Smart-Plug-import-completion handler all call into it rather than each building its own snapshot writer (a second, independently-built writer is exactly the kind of divergence this spine exists to prevent — see the Capability Map, where Smart Plug Import is bound to this AD for that reason). FR-8's Trend History view reads persisted `StatusSnapshot` rows, never a live recomputation against current settings, so a later Yearly Baseline/threshold edit cannot rewrite history. FR-18's proactive weekly recap (deferred, post-MVP) is the one feature that genuinely needs an externally-triggered wake-up; when it's built, it must use an externally-triggered scheduler (Azure Container Apps scheduled Jobs, or a KEDA cron scale rule), never an in-process timer.

## AD-8 — AI Wattage Plausibility as one config-selected adapter

- **Binds:** FR-17
- **Prevents:** building two separate adapter implementations (local vs cloud) when one suffices, and the feature becoming a hard dependency it's explicitly not allowed to be.
- **Rule:** One `IAiPlausibilityClient` port, one adapter (`OpenAiCompatibleClient`) speaking the OpenAI-compatible chat/completions HTTP shape — LMStudio and essentially every cloud LLM provider implement this shape, so the "local vs cloud" choice is just a base-URL + API-key config pair, not two code paths. When unset, the port resolves to a no-op implementation and FR-17 correlation is simply absent from the response — the rest of the product must not branch on whether AI is enabled.

## AD-9 — Smart-plug import parser port

- **Binds:** FR-4, FR-24
- **Prevents:** vendor-specific parsing logic leaking into the import pipeline or the domain layer.
- **Rule:** One `ISmartPlugParser` port; one adapter per vendor format (`EveHomeXlsxParser`, `MerossCsvParser`), each producing a common `SmartPlugReading` shape. Eve Home timestamps are parsed as local time, never UTC-converted (addendum's documented behavior, reproduced deliberately). Meross device identity comes from the documented filename pattern, not file-body metadata. FR-20's generic column-mapping is explicitly **not** built against this port yet — see Deferred.

## AD-10 — Historical tag integrity for Room / Power Point / Device

- **Binds:** FR-9, FR-16, FR-28
- **Prevents:** two independently-built features (Smart Plug import view, Event logging) choosing different answers to "what happens to old data when the tag is deleted or reassigned" — one might cascade-delete, another might silently follow a retag.
- **Rule:** Room, Power Point, and Device are **soft-deleted** (`ArchivedAt`, never a hard delete) — historical foreign keys stay valid and the UI can offer reassignment. In addition, `SmartPlugReading` and `Event` snapshot the Room/PowerPoint/Device identity **by value** at write time (denormalized display fields), because a Power Point's live Room assignment can change later — a live FK-join would incorrectly rewrite history to reflect the new assignment. FR-9/FR-16's "stays attributed to the tag active at the time" is satisfied by the snapshot, not by the FK.

## AD-11 — Shared audit-correction mechanism

- **Binds:** Meter Reading edits, Tariff edits, and (AD-22) Smart Plug reading `KwhValue` boundary-row corrections (Cross-Cutting NFR: audit trail on corrections)
- **Prevents:** each editable entity growing its own bespoke "keep the old value" pattern.
- **Rule:** One `AuditCorrection` table (`EntityType`, `EntityId`, `FieldName`, `OldValue`, `NewValue`, `CorrectedAtUtc`) and one `IAuditCorrectionRecorder` service, called from both Meter Reading and Tariff update paths. No entity-specific "PreviousValue" column duplicated per table. **Out of scope by construction, not by oversight:** FR-23's full-dataset restore is a wholesale replace with no partial-merge mode (PRD FR-23 consequence) — it is not an "edit" of an existing row and does not go through `IAuditCorrectionRecorder`. Any future import path that *does* merge into existing data must route through this AD's mechanism; a wholesale restore never does.

## AD-12 — Meter Reading regression queue

- **Binds:** FR-25
- **Prevents:** a second regression arriving mid-classification from racing the first, or entry-order being mistaken for chronological order.
- **Rule:** At most one **open** `MeterRegressionPrompt` per Main Meter at a time. Prompts are ordered by the reading's timestamp, not its creation/entry order. An open prompt excludes its triggering Reading (and everything chronologically after it) from FR-3's baseline computation until resolved as *reset* or *rollover*.

## AD-13 — Single-artifact deployment: backend serves the SPA

- **Binds:** all (deployment)
- **Prevents:** self-host and cloud needing structurally different deployment topologies, which would violate the PRD's explicit "one deployment artifact" NFR.
- **Rule:** The `Api` project serves the built React/shadcn SPA's static assets directly (ASP.NET Core SPA-hosting pattern) from the same container as the API. **This deviates from, and supersedes, the PRD addendum's candidate shape** (Azure Static Web App + separate Container App) — that split has no self-host equivalent, and (reconfirmed 2026-08-09) costs a guaranteed extra $9/month on Azure for capability this project's traffic doesn't need. Addendum updated to match.

## AD-14 — Main Meter is the sole authoritative total

- **Binds:** Pattern Detective (FR-5, FR-9), Data Export/Import
- **Prevents:** rebuilding v1's core failure — a Residual/attribution figure that looks precise enough to trust and isn't. This is the brief's single named non-negotiable invariant; the spine must protect it structurally, not just by naming it.
- **Rule:** `MeterReading` is the only entity representing authoritative total consumption. This binds the **whole system, not just Domain/Application** — no domain code, application service, API response DTO, or frontend view sums `SmartPlugReading` or `Event` data into a figure that is compared against, reconciled with, or rendered alongside the Main Meter total as if checking it (e.g. no chart puts a summed-measured-total series on the same axis as Meter-derived pace). `SmartPlugReading` and `Event` data may only ever be surfaced as context/signal (FR-5, FR-9's "measured context, not a reconciled breakdown") — there is no `Residual` type, field, DTO property, or view anywhere in the system, backend or frontend.

## AD-15 — Generic by default: no hardcoded household-specific values

- **Binds:** all (Household & Access, Pattern Detective, Tariff Radar)
- **Prevents:** the product quietly becoming single-household-shaped — the brief's secondary-audience requirement (other self-hosters run it unforked) has real architectural teeth: a hardcoded default anywhere is a fork waiting to happen.
- **Rule:** Every household-specific value (Yearly Baseline presets, trending threshold default, currency, Locale) is a `Household`-scoped config row, never a literal in code. Presets (e.g. FR-2's 1p/2p/3p/4p kWh figures) are offered as suggested starting values in the UI, never silently applied as defaults a household didn't choose.

## AD-16 — Offline-safe, idempotent Meter Reading writes

- **Binds:** FR-1 (offline capture NFR)
- **Prevents:** a double-inserted reading when a flaky-signal sync retries after losing its acknowledgment, and — the opposite failure — naive dedup logic that incorrectly collapses a legitimate second same-day reading with a different timestamp (FR-1 explicitly requires both to be possible).
- **Rule:** Meter Reading creation carries a client-generated idempotency key (GUID) set at the moment of entry, before any network attempt. The frontend queues unsent readings locally (IndexedDB) while offline and flushes on reconnect. The API upserts by idempotency key: a retried request with the same key is a no-op against an already-recorded reading; a new key is always a new reading, even at an identical or near-identical timestamp.

## AD-17 — Session persistence via server-side cookie, not client-stored tokens

- **Binds:** Household & Access (FR-26–FR-28), UJ-1's "stays logged in on their phone"
- **Prevents:** two independently-built areas choosing different auth-persistence strategies (e.g. one storing a token in `localStorage`, another assuming a cookie) — and the XSS token-theft exposure that comes with client-side token storage. Also prevents the specific scale-to-zero failure where ASP.NET Core's Data Protection key ring regenerates on every cold start, silently invalidating every existing session cookie the moment the Container App scales back up — which would defeat this AD's entire purpose without ever throwing a visible error.
- **Rule:** Authentication uses ASP.NET Core's cookie authentication handler chained to the OIDC handler — the browser holds an httpOnly session cookie, not a token the SPA can read or store itself. Data Protection keys are persisted externally via `PersistKeysToDbContext` against the same `EnergyTrackerDbContext` (portable across both AD-2 providers, no extra infra) — never left to the in-memory default, which does not survive a scale-to-zero cold start. This is what makes "stays logged in on their phone" durable across both app restarts and Azure scale-to-zero cycles.
- **FR-33 extension (Logoff / Account Switching, 2026-09-17):** Federated logoff needs no bespoke detection logic — it's stock behavior of `Microsoft.AspNetCore.Authentication.OpenIdConnect`, consistent with this AD's original "boring, framework-provided" choice. Logoff calls `HttpContext.SignOutAsync` for **both** the cookie scheme and the OIDC scheme in the same request (not just the cookie); signing out of the OIDC scheme is what triggers the handler's RP-initiated-logout redirect. The handler already resolves `end_session_endpoint` from the provider's cached discovery document (`.well-known/openid-configuration`, the same `ConfigurationManager<OpenIdConnectConfiguration>` the login flow already fetches — no extra network round trip) and redirects there automatically; `SignedOutCallbackPath`/`SignedOutRedirectUri` are configured to land the member back on the login step afterward (FR-33's "never a broken or blank page" AC). If the provider's discovery document has no `end_session_endpoint` (some minimal self-hosted OIDC servers omit it), the handler simply skips the IdP redirect and completes the local sign-out only — this is the framework's natural degrade path, not a branch this codebase writes. To satisfy FR-33's requirement that the member is *warned*, not just silently left partially signed in, the app checks the already-resolved `OpenIdConnectConfiguration.EndSessionEndpoint` for null *before* starting the logout flow and conditionally shows the warning proactively, rather than trying to detect after the fact whether a redirect happened. AD-16's offline-queue drain is a **frontend-only** precondition — the browser resolves/flushes/surfaces the IndexedDB queue before it ever calls the backend logoff route; no backend change needed for that half of FR-33. **One correction to Story 1.12's AC wording:** this app's cookie auth is self-contained/stateless (Data Protection-encrypted claims, no server-side session-ID store) — `SignOutAsync` deleting the cookie *is* the complete, correct invalidation mechanism for that design; there is no separate server-side revocation list to also clear, and building one (to defend against, e.g., a copied/stolen cookie surviving logoff) would be new scope beyond FR-33, not something this story needs. Flagged back to John to soften "invalidated server-side, not just removed client-side" accordingly.

Rules:
  - **Azure:** `ProtectKeysWithAzureKeyVault` (alongside the unchanged `PersistKeysToDbContext`) using the Container App's existing system-assigned managed identity against a Key Vault key. Config surface `DataProtection:KeyVaultKeyId`, read once at the composition root like every other adapter selection. Packages: `Azure.Extensions.AspNetCore.DataProtection.Keys` and `Azure.Identity`, **both pinned explicitly** in `Directory.Packages.props` (`Azure.Identity` is only transitive via `Microsoft.Data.SqlClient` today — don't rely on that).
  - **Self-host:** the existing `DataProtection:CertificateBase64` certificate path stays as the non-Azure protector.

## AD-20 — Duplicate-safe Smart-Plug reading writes

- **Binds:** FR-5, FR-24 (Cross-Cutting NFR10)
- **Prevents:** a re-imported Smart Plug export silently duplicating already-stored readings when its covered date range overlaps a prior import — the expected normal case for both vendor formats (Eve Home exports are always cumulative full-history; Meross exports are manually date-ranged with no last-import-date visibility), not a rare mistake.
- **Rule:** `SmartPlugReading` carries a database-level uniqueness constraint on `(PowerPointId, IntervalStart)` — the actual correctness guarantee, independent of any parser-level optimization. `ISmartPlugParser` adapters may additionally skip/filter already-covered rows before persisting as a performance optimization (Eve Home's guaranteed newest-first ordering permits an early stop; Meross's unordered rows require filtering every row), but that optimization is not itself the duplicate-safety mechanism — the DB constraint is what protects paths the optimization can't reach (e.g. AwaitingPowerPointMapping readings persisted before a Power Point, and thus a watermark, is known).
- **[AMENDED 2026-10-10, codebase audit C9; revised after reviewer gate] The unmapped-reading key includes the device tag.** Audit finding: the partial index `(HouseholdId, IntervalStart) WHERE PowerPointId IS NULL` is per-Household, so two *different* unmapped plugs covering the same period overwrite each other's readings through AD-23's raw-SQL upsert (silent data loss or misattribution on later mapping). Rule: the partial unique index becomes `(HouseholdId, DeviceName, IntervalStart) WHERE PowerPointId IS NULL` — `SmartPlugReading.DeviceName` is the parsed device tag, the plug's real identity. Re-uploading the *same* plug's file still upserts in place (AD-20's duplicate safety preserved); different plugs never collide. Rejected alternatives: per-`SmartPlugImportId` uniqueness (re-uploads of the same plug would duplicate) and blocking a second unmapped import (a UX dead end for multi-plug households).
  - **Prerequisite — bound `DeviceName`:** it is `nvarchar(max)` on SQL Server and `text` on Postgres today, and `nvarchar(max)` cannot be an index key. Add `HasMaxLength(200)`. The migration first checks the longest stored value and fails loudly with a clear message if any exceeds 200 characters (never truncates silently). Both parsers reject a device tag longer than 200 characters with a stable import error, and the restore validator enforces the same bound.
  - **Deploy order (expand/contract, both providers via `scripts/add-migration.sh`):** **Deploy N** narrows the column, adds the new partial index, and in the same release switches the unmapped-path upsert's conflict target (Postgres `ON CONFLICT` / SQL Server `MERGE ON`) and the unmapped path's `DeduplicateByMatchKey` to `(DeviceName, IntervalStart)`. The old index stays in N, because the previous revision and a rollback still need it as their `ON CONFLICT` arbiter. During N, a second plug's overlapping unmapped rows fail loudly on the old index instead of silently overwriting: an accepted transitional state. **Deploy N+1**, shipped promptly after N, drops the old index.
  - **`UpdateMappingAsync` is unchanged:** mapping moves rows to a concrete Power Point, so its collision key stays `(PowerPointId, IntervalStart)`, the mapped index. Re-keying it would misclassify a different device's row as "no conflict" and surface a unique violation as a 500 on Map.
  - Dual-provider Testcontainers test: two plugs covering the same period, both unmapped, both keep their readings; mapping each afterwards attributes correctly.

## AD-22 — Watermark corruption detection extends the value into the watermark

- **Binds:** FR-4, FR-24; `ISmartPlugParser`'s watermark contract (AD-9) for **both** `EveHomeXlsxParser` and `MerossCsvParser`; `SmartPlugImportRepository`/`ProcessSmartPlugImport` — the orchestration layer that owns the comparison and the correction write, not the parser; AD-11's audit-correction mechanism.
- **Prevents:** a silent, undetected correction to already-imported history — Eve Home or Meross revising a `KwhValue` it already reported at a timestamp this system has already stored, with the existing timestamp-only watermark (AD-9/AD-20) having no way to notice.
- **Rule — parser layer (symmetric across both vendors, no port change):** `ISmartPlugParser.Parse`'s signature is unchanged (`DateTimeOffset? watermark`) — the parser never needs to know the stored `KwhValue`. Both adapters now *include* the exact boundary row (`IntervalStart == watermark`) in the returned result instead of excluding it: `EveHomeXlsxParser`'s forward-streaming early-stop condition changes from `IntervalStart <= watermark` to `IntervalStart < watermark` — it reads and emits the boundary row, then stops one row later than today. `MerossCsvParser`'s per-row filter changes identically, from `dayStart <= watermark` to `dayStart < watermark`, for the single row exactly at the watermark timestamp. This closes the vendor asymmetry — corruption detection is not silently Eve-only.
- **Rule — orchestration/repository layer owns the comparison and the write:** `FindLatestReadingIntervalStartByPowerPointAsync` is extended to return the latest stored reading's `Id` and `KwhValue` alongside its `IntervalStart` (an `(Id, IntervalStart, KwhValue)` triple, not `IntervalStart` alone) — the `Id` is required because `IAuditCorrectionRecorder.RecordAsync` takes the target row's `entityId`, which neither the parser nor a bare `(IntervalStart, KwhValue)` pair can supply. After `Parse` returns, `SmartPlugImportRepository`/`ProcessSmartPlugImport` locates the returned boundary row (if any) by matching its `IntervalStart` to the watermark's `IntervalStart`, then compares its `KwhValue` to the watermark's stored `KwhValue`:
  - **Equal** — an exact re-report, not a correction: drop the row from the batch (nothing to write).
  - **Different** — perform a narrow, explicit update of *only* the existing stored row's `KwhValue` column (matched by the watermark's `Id`, equivalently identifiable via `(PowerPointId, IntervalStart)` — never a whole-row overwrite), plus the existing `IAuditCorrectionRecorder` call (`entityType=SmartPlugReading`, `entityId=<the watermark row's Id>`, `fieldName=KwhValue`, `oldValue`, `newValue`) — this reuses AD-11's mechanism as-is; it does not introduce a bespoke correction column or a second audit path. Either way, this row is excluded from whatever AD-23 batch handles genuinely new rows — it is never re-inserted through that path.
- **AD-10 constraint (named, not implicit):** the correction update above touches `KwhValue` and *only* `KwhValue` — never `RoomName`, `PowerPointName`, or `DeviceName`. Those are AD-10's by-value snapshot fields; re-deriving and overwriting them here (e.g. from a Room renamed since the original import) would reproduce the exact "live join rewrites history" failure AD-10 exists to prevent.
- **DST-fold / duplicate-timestamp discipline:** if more than one row in the parsed result shares the exact watermark `IntervalStart` (the same DST-fold case `SmartPlugImportRepository`'s existing per-row-fallback comments and tests already document elsewhere in this codebase), the same discipline applies here: deterministic keep-first — the first-encountered row in parse order is treated as *the* boundary row for comparison purposes — with a log entry noting the ambiguity, never multiple correction attempts against the same stored row.
- **Explicitly out of scope:** this AD only catches a revision to an already-seen `(PowerPointId, IntervalStart)` on the same device/Power Point stream, for either vendor. It does **not** catch a different physical device continuing to report under the same Power Point name at new, not-yet-seen timestamps — the watermark and this comparison never fire for rows past it. That gap remains open (see Deferred).

## AD-23 — Bulk-write via EFCore.BulkExtensions replaces per-row-conflict-tolerant writes

- **Binds:** `SmartPlugImportRepository.AddAsync`'s writes for `SmartPlugReading` (FR-4, FR-5, FR-24), both vendor adapters, both the one-time full-history first import and the routine small incremental delta. **Deliberately does not bind `UpdateMappingAsync`** — see the named carve-out below.
- **Prevents:** a second, independently-built bulk-write mechanism growing alongside this one for the same insert-or-upsert-by-content problem; a future feature re-inventing conflict-tolerant writes instead of reusing this path; a row-count threshold silently forking write behavior into two paths that can drift.
- **Rule:** `AddAsync`'s existing conflict-handling machinery — the `AnyExistingReadingAtSameKeyAsync` pre-check, the plain `AddRangeAsync`/`SaveChangesAsync` fast path, and the catch-`DbUpdateException`-then-`AddWithPerRowConflictToleranceAsync` per-row fallback loop — is replaced by **two** write paths, chosen by the same condition `ProcessSmartPlugImport` already branches on (whether the batch's Power Point is known), using `EFCore.BulkExtensions.Core` + `EFCore.BulkExtensions.SqlServer` + `EFCore.BulkExtensions.PostgreSql` (10.0.1) referenced directly for the primary path — **never** the umbrella `EFCore.BulkExtensions` package, which unconditionally pulls in the Oracle and SQLite adapters this project doesn't need. This is applied uniformly regardless of batch size — no row-count threshold or branch between "small delta" and "full-history" cases within either path.
- **[AMENDED 2026-09-04, Story 3.9, post-Story-3.8-spike] Two real unique indexes, two different write mechanisms — not one library covering both, as originally specified:** AD-20's actual duplicate-safety guarantee for `SmartPlugReading` is **two** separate unique indexes — `IX_SmartPlugReadings_PowerPointId_IntervalStart` on `(PowerPointId, IntervalStart)`, and a second, hand-added partial index, `IX_SmartPlugReadings_HouseholdId_IntervalStart_WhenPowerPointIdNull`, on `(HouseholdId, IntervalStart) WHERE PowerPointId IS NULL` — because neither provider treats `NULL = NULL` as a match against the first index, so it never fires for `AwaitingPowerPointMapping` rows (`SmartPlugReadingConfiguration.cs`). Story 3.8's spike (real Azure SQL + real Postgres, not Testcontainers) proved `BulkInsertOrUpdateAsync`'s `UpdateByProperties` cannot safely target the second index on either provider — it builds its own helper unique-index/MERGE-match logic that isn't scoped to the partial index's `WHERE PowerPointId IS NULL` predicate, and throws (rather than silently corrupting a row, which is the better of two bad outcomes but still means the originally-specified single-mechanism design doesn't work):
  - **Known Power Point (matches the first index):** `BulkInsertOrUpdateAsync` with `UpdateByProperties = [PowerPointId, IntervalStart]` and **`PropertiesToExcludeOnUpdate = [nameof(SmartPlugReading.Id)]`** — not the blanket `PropertiesToExclude` originally specified here, corrected per Story 3.8 spike Finding #1: `SmartPlugReading.Id` is a client-generated `Guid` (`Guid.NewGuid()`), not a DB-generated/IDENTITY column, so `PropertiesToExclude` (which omits a column from both insert *and* update) throws a NOT NULL violation on a genuinely-new row; `PropertiesToExcludeOnUpdate` is insert-safe.
  - **Unmapped, `AwaitingPowerPointMapping` batch (matches the second, partial index):** not `BulkInsertOrUpdateAsync` at all — a hand-written, provider-native raw-SQL upsert (`ExecuteSqlRawAsync` with positional `{n}` placeholders, parameterized), with its own explicit `WHERE PowerPointId IS NULL` (and explicit `HouseholdId` scoping, AD-3) written directly into the SQL text per provider. This is the one narrow, named exception to AD-2's "never branched on elsewhere" — see AD-2's own `[AMENDED]` bullet for the full reasoning and its scope limit.

  `ProcessSmartPlugImport` already knows which case applies — it already branches on whether `matchedPowerPoint` is non-null — so choosing between the two write paths costs nothing structurally beyond what was already planned; only the *mechanism* behind the second path changed after the spike's real-infrastructure result, not the branch point itself.
- **[AMENDED 2026-09-04, Story 3.9] A migration this AD's own primary path actually needs, contradicting this story's original "no new migration" Dev Notes assumption:** getting the primary path's ambient transaction to actually work on Postgres surfaced a further empirical finding beyond Story 3.8's spike (whose own scenarios never combined an ambient transaction with `UpdateByProperties` at all — only its cancellation scenario used a transaction, and that scenario never set `UpdateByProperties`). `EFCore.BulkExtensions.PostgreSql`'s merge path needs the match-key columns backed by a genuine Postgres `pg_constraint` entry to skip its own internal `CREATE UNIQUE INDEX CONCURRENTLY` helper-index step — which cannot run inside any transaction block, Postgres's own hard restriction, not a library bug. A plain EF Core `HasIndex(...).IsUnique()` unique index does not satisfy that check. Fixed by migration `AddSmartPlugReadingPowerPointIntervalStartUniqueConstraint` (both provider projects, AD-2 convention — Postgres: `ALTER TABLE ... ADD CONSTRAINT ... UNIQUE USING INDEX` promotes the existing index in place, no rebuild; SQL Server: a documented no-op, since `MERGE` has no equivalent restriction). See AD-2's own `[AMENDED]` bullet for a second, smaller Postgres-only wrinkle this same fix uncovered (a schema-resolution bug in the library's own constraint lookup, worked around via `CustomDestinationTableName`).
- **[AMENDED 2026-09-04, Story 3.9] Within-batch match-key collisions must be de-duplicated before either write path runs — confirmed empirically, resolving Task 7's own previously-open risk:** when two rows in the *same* incoming batch share the same match key (a genuine DST-fold pair, not the watermark-boundary row AD-22 already excludes upstream), Postgres's `ON CONFLICT ... DO UPDATE` throws `"ON CONFLICT DO UPDATE command cannot affect row a second time"` — it neither silently keeps one deterministically nor double-applies both, contrary to what was an open question before this story ran the case for real. `SmartPlugImportRepository.AddAsync` de-duplicates by `(PowerPointId, IntervalStart)` immediately before branching into either write path, keeping the first-encountered row per key (same "earlier-processed reading always wins" discipline the deleted per-row-fallback machinery used, and AD-22's own DST-fold handling in `ProcessSmartPlugImport` already established) and logging a warning when a duplicate is actually dropped.
- **Why the primary path's `PropertiesToExcludeOnUpdate=[Id]` alone is safe here:** this call's "update" branch (as opposed to plain insert) is only reachable in the narrow race window AD-20's own text already names — a concurrent completion for the same, already-known Power Point re-importing overlapping rows. In that window, the "existing" row this call matches against belongs to the *same* Power Point/import context as the incoming row, so its `RoomName`/`PowerPointName`/`DeviceName` already hold identical values — the overwrite is harmless. (The `AwaitingPowerPointMapping` path's own equivalent race is instead handled by the raw-SQL upsert's own `WHERE`-scoped `UPDATE`, which likewise only ever touches a row that already shares the same by-value snapshot fields for the same reason.) This is a narrower, different path than AD-22's boundary-row correction, which never reaches either write path at all: AD-22 excludes its corrected row from the batch and writes it separately, touching only `KwhValue`. So this AD's update-branch exclusions are not what protects AD-10's snapshot fields against AD-22's correction — AD-22's own narrow update path is.
- **`UpdateMappingAsync` is an explicit, deliberate carve-out — not an oversight.** It keeps its own pre-check (`AnyMappingConflictAsync`) / `ExecuteUpdateAsync` fast path / conflict-tolerant fallback (originally `UpdateMappingPerRowWithConflictToleranceAsync`; see the 2026-09-18 amendment immediately below for its current, set-based form) mechanism, untouched by this AD. Reason: it operates on a fundamentally different, inherently small and bounded volume — one already-persisted import's rows, already validated, being re-tagged with a new Power Point/Room (a metadata re-tag), not a bulk insert-or-upsert-by-content decision over a fresh, potentially huge parsed batch. The throughput problem this AD exists to solve doesn't apply there, so it deliberately stays on its existing mechanism rather than being forced onto `BulkInsertOrUpdateAsync`.
- **[AMENDED 2026-09-18, bugfix/power-point-mapping-duplicate-timeout] The "small/bounded volume" assumption behind the carve-out above was invalidated in production, but its conclusion still holds.** A full-history Eve Home re-export collided against ~100% of an existing Power Point's year+ of prior data — a shape the carve-out's original reasoning didn't anticipate. The per-row fallback this carve-out named (`UpdateMappingPerRowWithConflictToleranceAsync`: one `SaveChangesAsync` per reading, plus an extra SELECT+conditional-`ExecuteDeleteAsync` per collision) ran for ~4 minutes against that shape and was killed by Azure Container Apps' ~240s ingress idle timeout (HTTP 499), even though the classification logic itself (Story 3.7) resolved correctly. Fix: `UpdateMappingAsync`'s conflict-tolerant fallback (renamed `UpdateMappingSetBasedWithConflictToleranceAsync`) is now internally set-based — one bulk, `AsNoTracking` fetch classifies every colliding row in memory (no-conflict / exact-duplicate / divergent, same three-way rule as before), then one `ExecuteUpdateAsync` attaches the no-conflict subset and one `ExecuteDeleteAsync` removes the exact-duplicate subset; divergent rows are logged straight from the in-memory classification, no per-row DB round trip. The "existing reading" lookup this classification runs against must exclude the current import's own `SmartPlugImportId` — the first draft of this rewrite omitted that filter, so a second mapping call for the same import (a double-click, or a retry racing an already-committed first call) would match its own just-mapped readings against themselves and delete them as self-duplicates; caught in this story's own review loop before merge, not a live incident. This does **not** reverse the carve-out's conclusion: the method still does not use `BulkInsertOrUpdateAsync`/EFCore.BulkExtensions — it was the *volume* assumption that was wrong, not the write-mechanism choice, since this is still a metadata re-tag over already-persisted, already-validated rows rather than a bulk insert-or-upsert-by-content decision over a fresh parsed batch.
- **Parent-row transactional atomicity:** `dbContext.SmartPlugImports.AddAsync(import, ...)` (the parent row) and the `BulkInsertOrUpdateAsync` reading-write must be wrapped in one explicit database transaction (`dbContext.Database.BeginTransactionAsync`/commit). `BulkInsertOrUpdateAsync` does not participate in `SaveChangesAsync`'s pipeline, so without an explicit ambient transaction the "no partial import observable" guarantee the old single-`SaveChangesAsync` call provided for free would silently disappear.
- **License flag:** `EFCore.BulkExtensions` is dual-licensed (cFOSS). The free Community License applies if *any* of three independent conditions hold: (1) company/individual under $1M USD annual gross revenue — this project's case, at AD-13's personal/household scale — (2) non-profit/registered-charity use, or (3) use within Free Open Source-licensed software; the commercial license is required only if none of the three apply. This is the first non-Microsoft-licensed dependency of this kind in the stack; worth re-checking if the project's nature or scale ever changes. If licensing terms ever become a blocker, `EFCore.BulkExtensions.MIT` (an actively-maintained MIT-licensed fork) is a drop-in fallback.
- **AD-21 interaction — re-verify `Microsoft.Data.SqlClient`'s resolved version:** `EFCore.BulkExtensions.SqlServer` 10.0.1 requires `Microsoft.Data.SqlClient >= 6.1.4`, which will force a transitive bump past AD-21's currently-verified `6.1.1` (AD-21's `[ADOPTED]` bullet is amended with a forward pointer here). - **Condition before wide rollout:** a technical spike must run against the existing Azure SQL Basic and Postgres databases, using dedicated, disposable spike-only tables — never the live `SmartPlugReading` schema — to verify write throughput, that cancellation/transactional rollback still satisfies the existing "no partial row survives cancellation" invariant, **and** that the parent-row/reading-write transactional atomicity above actually holds under a mid-write failure. Until that spike runs, this AD's write path is not to be treated as safe to ship broadly.

## AD-24 — Single-instance invariant (explicit, documented, observed)

- **Binds:** `MemoryHouseholdImportUploadRegistry`, `HouseholdRecomputeLock`, temp-file job payloads (Smart Plug import, restore), `InProcessChannelJobQueue`, AD-6's startup sweep for the in-process adapter, the upload-registry expiry sweep, the in-process rate limiter (AD-27); `infra/modules/container-app.bicep`'s `maxReplicas`; `docs/self-hosting.md`.
- **Prevents:** the process-local mechanisms above silently becoming incorrect the day someone (an operator, a self-hoster, a future Bicep change) raises the replica count. Today only a Bicep default enforces it, while `AzureStorageQueueJobQueue`'s existence and some comments suggest multi-replica is supported (codebase audit A1, 2026-10-10).
- **Rule:** The application runs as **one active instance**. This is a deliberate invariant at AD-13's personal-household scale, not an oversight. The shared-state alternative (blob uploads, DB-backed registry and locks, job leases, a distributed rate-limit store) is deferred (see Deferred) and is the required prerequisite before this invariant may ever be lifted. Concretely:
  - `docs/self-hosting.md` states the invariant and lists the components above. The Bicep `maxReplicas` parameter's `@description` points to this AD, and `maxReplicas` stays `1`.
  - **Observed, not hard-enforced:** each instance writes a short-lived DB heartbeat row keyed by instance id; the app logs a warning only when another instance's heartbeat has overlapped its own for longer than **15 minutes**. Container Apps runs the old and new revision side by side until the new one is ready, so short overlaps are normal on every deploy and must neither warn nor block. The app must **never** refuse to start on this check: a hard singleton lock would fail the health gate on every deploy.
  - **One instance does not mean a stable disk.** Temp files are local to the replica, which Container Apps replaces on scale-to-zero, deploy or crash. Under this AD, temp-file payloads are accepted: a missing file is a terminal job failure with a clear error (AD-6 amendment, 2026-10-10), never a retry. Moving uploads to blob storage is part of the deferred shared-state work.
  - Process-local mechanisms keep a one-line comment pointing to AD-24 instead of re-arguing the single-instance assumption locally.

## AD-25 — Restore and export never carry access grants

- **Binds:** FR-22 (export), FR-23 (restore); `RestoreHouseholdData`, `HouseholdRestoreWriter`, `ValidateHouseholdImport`, the export reader and DTOs; `docs/data-export-format.md`, `docs/data-import-restore.md`; the Settings restore-completion UI.
- **Prevents:** an uploaded file, which is untrusted input chosen by any member, deciding who can access a Household (codebase audit S1: grant arbitrary OIDC identities, lock out all members), and the export leaking co-members' IdP subject identifiers (audit S12: GDPR personal data and the raw material for S1).
- **Rule:**
  - **Restore never writes `HouseholdMember` rows.** Current members are neither deleted nor replaced, and `HouseholdMember` is removed from the restore's delete/insert ordering. The "Session continuity across a restore" section of `docs/data-import-restore.md` is rewritten: continuity is now unconditional.
  - **Export member shape:** each `householdMembers[]` entry is exactly `{ "id", "displayName" }`. The restore validator requires `id`, accepts `displayName` as optional, and accepts and ignores `externalIssuer`/`externalSubjectId`, so pre-change export files still restore.
  - **Versioning (Ralf's decision, 2026-10-10):** `formatVersion` stays `"v2"`. The restore target must run the **same or a newer release** than the source; an older release rejects a newer export through its own validator (an explicit validation failure, never a partial restore). Both docs state this.
  - **Move-to-new-hosting:** after a restore completes, the UI lists the backup's member display names ("people in this backup") next to the existing invite flow. It does not compare them with current members: display names are nullable, editable and not identities. Re-invitation is the only path to access; nothing about access is reconstructed from the file.
  - **Residual file-controlled data is data, not access:** the AI-consent flag, audit rows and entity ids still come from the file, and none of them grants or removes access.
  - Test: restoring a file whose member list omits the caller, or lists foreign identities, leaves the Household's membership unchanged.

## AD-26 — Member trust model: all members fully trusted; removal exists; invites are revocable

- **Binds:** Household & Access (FR-26–FR-28): `HouseholdMember`, `HouseholdInvite`, `AcceptHouseholdInvite`, the invite preview and accept endpoints, new member list/remove/leave endpoints; restore, export, Smart Plug cleanup, Household settings.
- **Prevents:** roles or per-action permission checks growing ad hoc in individual endpoints; a Household having no way to cut off a former member (codebase audit A2, S13); a removed member walking back in through a still-open invite link (S10); and cross-Household member manipulation through the first endpoints that take a client-supplied member id.
- **Rule:**
  - **Full, equal trust.** Every `HouseholdMember` has the same rights. There is no Owner or role concept, and endpoints must not invent one locally (an explicit v2 non-goal; Owner role in Deferred). Accepted consequence: any member can remove every other member. Recovery from that is operator-level only (documented in `docs/self-hosting.md`), and each removal is logged as a structured event (remover and removed member ids). No new audit table.
  - **Removal and leaving** are one transaction that deletes the membership, **expires every open invite of the Household**, and increments `Household.Version` (AD-4). The last-member check runs inside that transaction, so two concurrent removals cannot leave zero members (the loser gets 409). Removing or leaving as the last member is rejected. Removal takes effect on the removed member's next request, because membership is resolved per request (AD-17 amendment). The member then lands in FR-26's Household-creation flow. Jobs a removed member queued earlier still run: jobs belong to the Household, not to the member.
  - **Tenant safety for member endpoints.** `HouseholdMember` is AD-3-exempt (no global query filter), so every lookup by member id goes through one repository method that takes the current `HouseholdId` and returns not-found (HTTP 404) for any other Household's member. An architecture test guards that `HouseholdMember` is only queried by id through that method.
  - **Invite tokens (S10):** new tokens are 32 bytes from `RandomNumberGenerator`, base64url-encoded; only a SHA-256 hash is stored. Members can list and revoke the Household's open invites. Preview and accept are rate-limited (AD-27). Migration is expand/contract: add the hash column; new invites are hash-only; lookup tries the hash first and the legacy plaintext column second; a later deploy, at least 7 days on (the invite lifetime), drops the plaintext column.

## AD-27 — HTTP hardening baseline

- **Binds:** the `Api` request pipeline (`Program.cs`), `web/index.html`, the web API client modules, every route.
- **Prevents:** XSS escalation without a CSP, clickjacking of destructive actions (restore, invite, removal), HTTPS downgrade, unthrottled abuse of the login, invite and upload routes (codebase audit S3), and cross-site request forgery that leans on `SameSite=Lax` alone (S9).
- **Rule:**
  - **Security headers, production only** (not `Development`, because Vite dev mode injects inline scripts). One small hand-written middleware, registered **first** in the pipeline so it also covers error and static-file responses, sets:
    - `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`. `style-src` needs `'unsafe-inline'` because Radix injects `<style>` elements at runtime (`react-style-singleton`: Select, and the scroll lock used by Dialog, Sheet and DropdownMenu); scripts stay strict, with no hashes or nonces. Verify `img-src data:` against the built bundle at story time and drop it if unused.
    - `X-Content-Type-Options: nosniff` and `Referrer-Policy: same-origin`.
    - Plus `UseHsts()`. Container Apps ingress does not add HSTS. No third-party header package.
  - **No inline scripts in `web/index.html`.** The pre-paint theme script moves to `web/public/theme-init.js`, loaded with a plain (non-module, non-deferred) `<script src>` in `<head>` so it still runs before first paint.
  - **Rate limiting** uses ASP.NET Core's built-in `AddRateLimiter`, which is in-process and correct under AD-24. `UseRateLimiter` comes after `UseRouting` and `UseAuthentication`. Rejections return **429** with ProblemDetails (the framework default is 503). Partitions:
    - per OIDC identity (issuer + subject, not member id, so invitees are covered) for uploads, export, invite create/preview/accept, and member removal;
    - per client IP for `/login`.
  - **Forwarded headers stay as they are.** `X-Forwarded-Proto` trust from any source is what fixed Story 1.7's login bug (`Program.cs`), so it is not narrowed. On Azure the per-IP key is not spoofable: Container Apps ingress supplies the rightmost `X-Forwarded-For` entry, and `ForwardLimit` stays 1. One live probe with a forged `X-Forwarded-For` confirms this at story time. Self-host: `docs/self-hosting.md` requires exposing the app only through a reverse proxy, because a client reaching Kestrel directly could spoof its IP. `AllowedHosts` stays `*`: the deploy health gate probes the revision FQDN, and the IdP's exact `redirect_uri` match is the safeguard (audit S8's `AllowedHosts` part is accepted, not fixed).
  - **CSRF defence in depth (S9):**
    - Every `/api` mutation (POST, PUT, PATCH, DELETE, including the multipart uploads) requires an `X-Requested-With` header, which a cross-site form cannot send. An endpoint filter on the `/api` group enforces it and returns 400 ProblemDetails when it is missing.
    - The frontend sends it from one shared API client (audit R2's extraction lands in the same story).
    - `/logout` becomes POST. It is an auth-flow change, so the live Auth0/Chrome verification gate applies.
  - **Tests:** integration tests assert the headers and the CSRF filter outside Development (these test hosts set AD-17's `AllowUnprotectedKeys` opt-out), and assert that the headers are absent in Development.
