- (decision) Backend language/runtime: C# on .NET 10 (LTS, supported to Nov 2028). Verified current via Microsoft Learn.
- (decision) Design paradigm: Ports & Adapters (Hexagonal). Binds: whole system. Prevents: OIDC, AI backend, job queue, and persistence provider each growing a bespoke one-off swap mechanism instead of one consistent port/adapter shape. Driven directly by user's own framing of the job-queue requirement (one abstraction, pluggable implementations) plus PRD's repeated 'swappable via config, no code change' requirements (OIDC, AI backend).
- (decision) Async job processing: IBackgroundJobQueue port. Adapters: in-process System.Threading.Channels-backed adapter (default, zero extra containers/infra, satisfies self-host single-instance case) and Azure Storage Queue adapter (cloud path, enables future KEDA queue-depth scaling). A dedicated self-host broker container is deferred, not built now -- in-process adapter covers that case already.
- (decision) Deployment topology: single container/process serves both the HTTP API and background job processing (hosted BackgroundService), for both self-host and Azure Container Apps. Splitting the worker into a separately-scaled Container App (queue-depth KEDA rule) is Deferred until import volume justifies it.
- (decision) Frontend hosting: ASP.NET Core backend serves the built React/shadcn SPA's static assets directly from the same container (classic ASP.NET Core SPA-hosting pattern), rather than the addendum's separate Azure Static Web App. Reason: PRD NFR demands one deployment artifact for both self-hosted and cloud; a two-service split has no self-host equivalent. Deviates from PRD addendum's candidate shape -- flagged for addendum update.
- (decision) Auth: ASP.NET Core's built-in OpenIdConnect authentication handler, fully config-driven (authority/client id/secret via env vars) -- no vendor-specific SDK. Works against Entra ID, Auth0, Authentik, Keycloak etc. interchangeably.
- (decision) Data access: EF Core 10, chosen over Dapper for productivity/correctness across ~28 FRs and solo development; global query filters give data-layer tenant isolation (PRD NFR) largely for free.
- (decision) Database engine: dual-provider, configurable via settings/env var -- PostgreSQL (self-host default; ARM+x86 compatible, low footprint) and Azure SQL Basic DTU (Azure production; near-zero cost per user's explicit choice). Both via EF Core providers (Npgsql, Microsoft.EntityFrameworkCore.SqlServer) selected at the composition root.
- (constraint) Dual DB-provider support cost: EF Core migrations must be maintained as two separate migration histories (one per provider); domain/application code must avoid provider-specific SQL, functions, or column types (e.g. no raw jsonb operators, no rowversion/xmin-specific concurrency tokens) to keep both providers behaviorally identical. This is real ongoing engineering surface for a solo developer -- accepted explicitly by the user given the cost benefit (near-free Azure SQL Basic DTU) and self-host ARM compatibility (Postgres).
- (version) PostgreSQL 17.x pinned for self-host (mature, broad Docker/ARM support); Azure SQL Basic DTU for cloud. EF Core 10 + Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3 + Microsoft.EntityFrameworkCore.SqlServer 10.x. Verified current via NuGet/Microsoft Learn, 2026-08-09.
- (decision) Dual-provider EF Core shape (verified against Microsoft Learn 'Migrations with Multiple Providers'): ONE shared DbContext type (not per-provider subclasses), with migrations split into two separate assemblies/projects -- Infrastructure.Migrations.Postgres and Infrastructure.Migrations.SqlServer -- each wired via MigrationsAssembly(...). Provider chosen by a single config value at the composition root (mirrors OIDC/AI-backend/job-queue adapter-selection convention).
- (constraint) Dual-provider migration drift risk: schema changes require running 'dotnet ef migrations add' once per provider migrations project; nothing prevents doing it for only one and having the other silently drift. Mitigation: a single wrapper script (scripts/add-migration.sh) runs both invocations together so a migration can't be added to only one provider by habit.
- (reference) Source: https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/providers -- confirms one-DbContext/multi-migrations-assembly pattern and config-driven provider selection via Generic Host.
- (version) Azure SQL Database Basic DTU tier confirmed current (not deprecated): 5 DTU, 2GB storage, no stop/start capability (unlike Postgres Flexible Server Burstable which can stop). Verified via Microsoft Learn 2026-08-09.
- (decision) Status (FR-6/7) and Tariff Check Reminder due-ness (FR-15) are computed lazily at request time (dashboard/API read), never via a recurring background scheduler. Reason: Azure Container Apps scale-to-zero means no in-process timer/IHostedService survives between requests -- a naive cron approach would silently stop firing once idle. FR-18's proactive weekly recap (deferred, post-MVP) will need an externally-triggered scheduler (Container Apps scheduled Jobs or a KEDA cron scaler) when built, not an in-process timer.
- (decision) Historical tag integrity (FR-9, FR-16, FR-28): Room/PowerPoint/Device are soft-deleted (never hard-deleted), keeping historical FK references valid and reassignable. Smart Plug readings and Events additionally snapshot the Room/PowerPoint/Device identity by value at write time (denormalized), since a PowerPoint's live Room assignment can change later and must not retroactively rewrite historical views.
- (decision) Audit trail on corrections (Meter Reading, Tariff edits) implemented via one shared AuditCorrection table/service, not two divergent per-feature implementations.
- (decision) AI Wattage Plausibility (FR-17): single IAiPlausibilityClient port implemented as one OpenAI-compatible HTTP adapter, configured per household with a base URL + API key -- covers local LMStudio and any cloud provider identically without separate adapter classes. Disabled cleanly when unset (graceful degradation per Constraints).
- (decision) Meter Reading Regression (FR-25): at most one open MeterRegressionPrompt per Main Meter; ordering is by reading timestamp (chronological), not entry order; an open prompt blocks FR-3 baseline computation for readings after it until resolved.
