# Version-currency / reality-check review: 2026-10-10 spine amendments

- **Reviewer role:** Version-currency / reality-check (architecture-spine reviewer gate)
- **Date:** 2026-10-10
- **Scope:** `ARCHITECTURE-SPINE/invariants-rules.md`: the `[AMENDED 2026-10-10]` bullets in AD-6 (l.42–47), AD-17 (l.115–119) and AD-20 (l.146), plus the new AD-24..AD-27 (l.197–232). `ARCHITECTURE-SPINE/deferred.md`: the three new end entries (l.15–17).
- **Method:** Every technical claim was checked against current Microsoft Learn / NuGet / Vite docs, or against the repo (`Directory.Packages.props`, `obj/project.assets.json`, EF model snapshots, `Program.cs`, `infra/`, `web/`). No builds were run.

## Verdict

**PASS WITH REQUIRED FIXES.** The direction is sound and most API, package and platform claims check out. Fix these before stories are cut:

1. **AD-20 (WRONG/blocking):** on SQL Server, `DeviceName` is `nvarchar(max)`. An `nvarchar(max)` column can't be an index key column at all, so the 1,700-byte question doesn't come up. The spine's "confirm it fits" has to become "add `HasMaxLength(n)` and an ALTER COLUMN migration first".
2. **AD-27 (WRONG):** `default-src 'self'` with no `style-src` override blocks the `<style>` elements that the shipped Radix primitives inject (`Select`, plus `Dialog`/`Sheet`/`DropdownMenu` through `react-remove-scroll-bar`). The style source has to be decided now, because "widen later" is the expected outcome, not an edge case.
3. **AD-27 (premise partly WRONG):** the ACA Consumption plan without a VNet has no documented, stable ingress range to pin. ACA itself overwrites and appends the rightmost `X-Forwarded-For` value, and ASP.NET Core's default `ForwardLimit = 1` reads only that rightmost value. So on Azure the per-IP key is not spoofable through `X-Forwarded-For` as the code stands. The real spoof exposure is **self-host**, where clients reach Kestrel directly. The fallback rule should be keyed to that.
4. **AD-17 (imprecise):** *Key Vault Crypto User* works but grants more than needed. The least-privilege built-in role for wrap/unwrap is **Key Vault Crypto Service Encryption User**. `Azure.Identity` is transitive only through `Microsoft.Data.SqlClient` 6.1.4, so it should be pinned explicitly.
5. **AD-6 (inconsistency):** the lazy 30-minute Processing-staleness rule fires well before a crashed Azure message becomes visible again (60-minute visibility timeout). The spine never says what the redelivered message does when it finds a `Failed` job. The "2 hours for Queued" rationale also cites the visibility timeout, which doesn't apply to messages that were never dequeued.

## AD-6 amendment: job liveness (C7/C8)

| # | Claim | Status | Evidence |

| 6.1 | The default `BackgroundServiceExceptionBehavior` is `StopHost`, so an exception escaping `ExecuteAsync` takes the web app down | **CONFIRMED** | Default since .NET 6: https://learn.microsoft.com/dotnet/core/compatibility/core-libraries/6.0/hosting-exception-handling . Still the default in .NET 10. | 6.2 | `DequeueCount` counts deliveries and can drive a "fail after 5" rule | **CONFIRMED** | Get Messages REST: "When a message is retrieved for the first time, its `DequeueCount` property is set to 1 … subsequently retrieved again, the `DequeueCount` property is incremented." https://learn.microsoft.com/rest/api/storageservices/get-messages#remarks |
| 6.3 | "Receive one message per poll, so the visibility timeout bounds one job, not eight" | **CONFIRMED** | The visibility timeout is stamped on every message at receive time (`TimeNextVisible = receive time + visibilitytimeout`, same REST page). The current code receives `maxMessages: 8` with a 60-minute timeout (`AzureStorageQueueJobQueue.cs:83-84`) and processes them one after another, so messages 2–8 can become visible again mid-batch. |
| 6.4 | A 60-minute visibility timeout is valid | **CONFIRMED** | Range is 1 second to 7 days (Queue Storage receive options). Repo: `AzureStorageQueueJobQueue.cs:75`. |
| 6.5 | "Queued with `CreatedAtUtc` older than 2 hours (beyond the Azure queue's 60-minute visibility timeout plus one redelivery)" | **WRONG (rationale)** | A `Queued` job's message has never been dequeued, so the visibility timeout doesn't apply to it. Under the spine's own model, a job whose message was dequeued and then lost is `Processing`, not `Queued`. What actually bounds legitimate Queued age is backlog depth × per-job time. Under the new one-message-per-poll rule and NFR1's 15-minute Tier-3 budget, a multi-file upload of 9 or more files can legitimately stay `Queued` for more than 2 hours and would be wrongly failed. **Fix:** "`Queued` with `CreatedAtUtc` older than 2 hours. This bounds a lost enqueue, not a slow backlog; the threshold assumes fewer than ~8 Tier-3 jobs queued per Household at once. | 6.6 | The lazy staleness rule and the 5-dequeue limit work together | **UNVERIFIED / gap** | After a crash mid-job, the message reappears 60 minutes later. Any read in between (30 minutes or more after `StartedAtUtc`) has already marked the job `Failed`. Today `BackgroundJobProcessor` deliberately *reuses* an already-`Processing` job (comment at `AzureStorageQueueJobQueue.cs:68-72`), and the spine doesn't say what happens when the redelivered message finds a **terminal** job. **Fix (add to the Azure-consumer bullet):** "On dequeue, if the job row is already terminal (`Failed`/`Completed`), delete the message without processing." In practice this makes the 5-dequeue limit a backstop for jobs nobody reads, which is fine, but it should be said explicitly. |
| 6.7 | "Only `OperationCanceledException` with `stoppingToken.IsCancellationRequested` may bypass the `Failed` write" | **CONFIRMED** (sound pattern) | Matches the existing `catch … when (!stoppingToken.IsCancellationRequested)` idiom at `AzureStorageQueueJobQueue.cs:100`. |
| 6.8 | The in-process adapter fails all `Queued`/`Processing` rows at startup | **CONFIRMED (self-host)**, with a caveat | Correct for a single self-host container (recreate stops the old container first). The caveat is AD-24's own observation that ACA runs old and new revisions side by side. If `InProcessChannelJobQueue` is ever selected on Azure, the new revision's sweep would fail jobs the old revision is still running. Suggest adding: "The startup sweep is valid only where AD-24's overlap cannot occur. Azure always uses `AzureStorageQueueJobQueue`." |

| # | Claim | Status | Evidence |
|---|---|---|---|
| 20.1 | SQL Server nonclustered index key limit is 1,700 bytes | **CONFIRMED** | https://learn.microsoft.com/sql/sql-server/maximum-capacity-specifications-for-sql-server?view=sql-server-ver17 (900 for clustered, 1,700 for nonclustered). |
| 20.2 | "confirm `DeviceName`'s max length fits SQL Server's 1,700-byte nonclustered key limit" | **WRONG (premise)** | `SmartPlugReadingConfiguration.cs:28-29` configures only `.IsRequired()`, with no max length. Docs: "`nvarchar(max)` … can't be specified as key columns for an index" (https://learn.microsoft.com/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17#arguments). The index **cannot be created** on SQL Server as specified. **Fix:** "`SmartPlugReading.DeviceName` first gets `HasMaxLength(200)` (or a measured bound; 2 × n + 8 + 16 bytes for HouseholdId/IntervalStart must stay ≤ 1,700, so n ≤ ~830), with an ALTER COLUMN migration in both providers that fails fast if existing data is longer (pre-check query). The parsers (`MerossCsvParser`, `EveHomeXlsxParser`) and restore validation reject or truncate longer tags. Only then is the partial unique index widened." On Postgres, `text` is indexable but B-tree entries are capped at about 2.7 kB, so the same bound is good hygiene there too. |
| 20.3 | Expand/contract ordering ("add the new index first, drop the old one in a later deploy … before the upsert's `ON CONFLICT`/`MERGE` target switches") | **UNVERIFIED / contradictory as worded** | Postgres `INSERT … ON CONFLICT (cols) WHERE …` requires an arbiter unique index that matches the target exactly. A violation of a *different* unique index (the old, narrower one) raises an error instead of taking the conflict path. So (a) while the old index exists, the new code can't insert a second device's row for the same interval, whatever the target, and (b) dropping the old index while the old revision (AD-24 overlap) still targets it makes the old code fail with "no unique or exclusion constraint matching the ON CONFLICT specification". SQL Server `MERGE` has no arbiter requirement but hits (a) the same way. **Fix:** state the real sequence. Deploy 1 adds the new index (plus column length) while keeping the old target. Deploy 2 switches the upsert target and classification and drops the old index **in the same migration as the code switch**, accepting that the brief revision overlap can fail an unmapped import on the old revision (it's retryable). Alternatively, keep both indexes and both targets valid until the old revision is gone. The current sentence ("drop must follow before the … target switches") reads both ways. |

## Suggested spine text fixes (consolidated)

1. **AD-20 amendment**, replace "confirm `DeviceName`'s max length fits …" with: *"`DeviceName` is currently `nvarchar(max)`/`text` with no configured length. `nvarchar(max)` cannot be an index key column, so first add `HasMaxLength(200)` with a pre-checked ALTER COLUMN migration in both providers and enforce the bound in both parsers and in restore validation. Then widen the partial unique index."* Also restate the expand/contract order as in 20.3.
2. **AD-17 amendment**: change the role to *Key Vault Crypto Service Encryption User* (scoped to the key; RBAC-model vault; versionless key id if rotation is enabled). Pin `Azure.Identity` explicitly. Make revocation `IKeyManager.RevokeAllKeys(cutoverUtc)` run after the old revision is deactivated.
3. **AD-27**: decide `style-src` now (`'self' 'unsafe-inline'`, or allow a nonce for Radix). Rewrite the forwarded-headers bullet around `ForwardLimit = 1` plus ACA's rightmost-IP guarantee, with self-host as the spoofable case. Order the pipeline as `UseForwardedHeaders → … → UseRouting → UseAuthentication → UseRateLimiter`, and set `RejectionStatusCode = 429`.
4. **AD-6 amendment**: on dequeue of a message whose job is already terminal, delete it. Re-derive the 2-hour Queued threshold from backlog size rather than from the visibility timeout. Limit the startup sweep to adapters and environments where no revision overlap occurs.
5. **AD-24**: the heartbeat warning has a grace period or a revision-name check, so it doesn't fire on every deploy.
