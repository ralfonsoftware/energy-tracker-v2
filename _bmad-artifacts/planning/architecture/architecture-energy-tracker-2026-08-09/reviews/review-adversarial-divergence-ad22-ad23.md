# Adversarial Divergence Review — AD-22 & AD-23

**Method:** construct pairs of independently-built implementations, each obeying the AD's literal text, that would still land incompatible — or find a real hole/ambiguity/edge case the text doesn't cover. Grounded against the live code (`SmartPlugImportRepository.cs`, `EveHomeXlsxParser.cs`, `ISmartPlugParser.cs`, `ProcessSmartPlugImport.cs`, `IAuditCorrectionRecorder.cs`, `SmartPlugReadingConfiguration.cs`, and both `AddSmartPlugReadingUniqueIndex` migrations), not the AD's prose alone.

**Verdict:** Both ADs are unsafe to hand to two independent implementers as written. AD-22 assigns its correction-detection mechanism to a component (`EveHomeXlsxParser`) that structurally cannot execute it — no DB access, no `HouseholdId`, and no target-row `Id` to correct — which alone guarantees two builders will put the real logic in different places. AD-23's `UpdateByProperties=[PowerPointId, IntervalStart]` silently degrades to "always insert, never update" for every `AwaitingPowerPointMapping` row on both providers, because AD-20's actual null-safety net is a *second*, unnamed partial index that `BulkInsertOrUpdateAsync`'s single `UpdateByProperties` target cannot cover — reopening the exact duplicate-row hazard AD-20 was written to close, for exactly the code path AD-20's own text calls out as the case the DB constraint (not the parser) has to protect. Recommend both sections go back for a revision pass before being treated as implementation-ready.

---

## Findings, ranked by severity

### 1. [CRITICAL] AD-22's correction write cannot literally happen inside `EveHomeXlsxParser` — the Rule names an actor that lacks the inputs to do the job

AD-22's Rule: *"`EveHomeXlsxParser`'s forward-streaming read no longer skips the exact boundary row... it reads that row and compares its parsed `KwhValue` against the stored value. On a mismatch, the stored `SmartPlugReading.KwhValue` is updated... **and** the change is recorded via the existing `IAuditCorrectionRecorder`."*

Follow that literally against the real signatures:

- `IAuditCorrectionRecorder.RecordAsync(Guid householdId, string entityType, Guid entityId, ...)` needs (a) the household id and (b) the **stored row's own `Id`** as `entityId`.
- `ISmartPlugParser.Parse(Stream fileContent, string fileName, DateTimeOffset? watermark, CancellationToken)` never receives a `householdId` at all — `ProcessSmartPlugImport` only stamps `reading.HouseholdId = householdId` on the returned DTOs *after* `Parse` returns (line 93 of `ProcessSmartPlugImport.cs`).
- AD-22's own described extension to `FindLatestReadingIntervalStartByPowerPointAsync` returns `(IntervalStart, KwhValue)` — not the stored row's `Id`. Nothing else in the Rule text supplies it either.
- `ParseDataRow` assigns every parsed reading a **fresh** `Guid.NewGuid()` (line 205) — a parsed boundary row's `Id` is never the stored row's `Id`, so even with DB access the parser has no key to update by.
- `EveHomeXlsxParser` has no repository/`DbContext` dependency today, and giving it one to perform the actual `UPDATE` + audit call would mean a format-parsing adapter now executes conditional writes against the database — directly inverting AD-9's own stated purpose ("prevents vendor-specific parsing logic leaking into the import pipeline **or the domain layer**"): this is import-pipeline logic (deciding to persist a correction, invoking the shared audit mechanism) leaking *into* the vendor parser, not out of it.

So the Rule as literally written describes something that cannot execute where it says it executes. Two independently-built stories resolve this differently, and both are "AD-22-compliant" because the AD never actually specifies which layer owns the write:

- **Story A** takes "EveHomeXlsxParser... compares and updates" at face value, injects `IAuditCorrectionRecorder` and repository access into the parser, and threads `householdId` through a widened `Parse` signature. Vendor-parsing code now does DB writes and Application-layer audit calls — a real AD-1/AD-9 layering violation nobody flagged because AD-22's text told them to build it there.
- **Story B** (the only version that actually works) keeps `Parse` a pure transform, changes the early-stop from `<=` to `<` so the boundary row flows out as an ordinary parsed reading, and does the comparison + `IAuditCorrectionRecorder.RecordAsync` call in `ProcessSmartPlugImport` (which already has `householdId` in scope and would need one more repository lookup to resolve the stored row's `Id` — itself unaddressed, see below).

These two are not just stylistically different — one is layering-illegal, and only one of them can actually satisfy `IAuditCorrectionRecorder`'s required parameters. The AD's silence on *where* the write happens is a critical hole, not a stylistic ambiguity. **This confirms and substantially sharpens rubric-walker Finding 3** (which correctly flagged the `Parse` signature/`KwhValue` ambiguity but stopped short of showing the parser can't supply `HouseholdId` or a target `entityId` either — i.e., that "the parser does it" isn't just awkward, it's not implementable as stated).

A residual gap even under the correct resolution (Story B): AD-22 never says how the orchestrator finds the stored row's `Id` to pass as `entityId`/to update. `FindLatestReadingIntervalStartByPowerPointAsync` as extended returns `(IntervalStart, KwhValue)` only. A correct implementation needs either that method extended again to return `Id` too (a third, unstated field), or a fresh lookup by `(PowerPointId, IntervalStart)` — the AD specifies neither.

### 2. [CRITICAL] `BulkInsertOrUpdateAsync`'s `UpdateByProperties=[PowerPointId, IntervalStart]` cannot see the `AwaitingPowerPointMapping` (`PowerPointId == null`) rows as "existing" on either provider — silently reopening AD-20's own named hazard

This is the sharpest way to state the pre-flagged question ("does `BulkInsertOrUpdateAsync` correctly handle a batch containing `PowerPointId == null`?"): **no, and the reason is fully documented in this repo's own migrations.**

`SmartPlugReadingConfiguration.cs` (lines 63–76) and the `AddSmartPlugReadingUniqueIndex` migrations establish, in explicit, hard-won prose (Story 3.4 Dev Notes Open Question #3, "confirmed with Ralf during dev-story activation"), that AD-20's uniqueness guarantee for `SmartPlugReading` is actually **two separate indexes**:

1. `IX_SmartPlugReadings_PowerPointId_IntervalStart` — composite unique index on `(PowerPointId, IntervalStart)`. On **both** Postgres and SQL Server, this index never fires for `PowerPointId IS NULL` rows (Postgres never treats `NULL = NULL`; EF Core's SQL Server provider auto-filters a unique index over a nullable column to `WHERE [PowerPointId] IS NOT NULL` — verified empirically per the migration's own comment).
2. `IX_SmartPlugReadings_HouseholdId_IntervalStart_WhenPowerPointIdNull` — a **second, hand-written partial unique index** on `(HouseholdId, IntervalStart) WHERE PowerPointId IS NULL`, added specifically to close the gap index #1 leaves open for `AwaitingPowerPointMapping` rows.

AD-23's Rule sets `UpdateByProperties = [PowerPointId, IntervalStart]`, describing it as "matching AD-20's existing unique index" — singular, and it names the *wrong one* for the null-`PowerPointId` case. `EFCore.BulkExtensions`' `BulkInsertOrUpdateAsync` on Postgres compiles `UpdateByProperties` into an `ON CONFLICT (PowerPointId, IntervalStart) DO UPDATE ...` target; on SQL Server it compiles into a `MERGE ... ON (target.PowerPointId = source.PowerPointId AND target.IntervalStart = source.IntervalStart)`. Both target expressions evaluate `NULL = NULL` as unknown/no-match by standard SQL semantics — identical to why index #1 above needed index #2 as a workaround in the first place. Concretely, for a batch of `AwaitingPowerPointMapping` readings (`PowerPointId == null` for every row, per `ParseDataRow` line 208 and the `AwaitingPowerPointMapping` branch in `ProcessSmartPlugImport`):

- **Postgres:** the `ON CONFLICT (PowerPointId, IntervalStart)` target never matches a null-`PowerPointId` row as a conflict from index #1's perspective, so the library always takes the INSERT path for these rows — reintroducing duplicate-row risk on any repeated/overlapping unmapped import (the exact "AwaitingPowerPointMapping readings persisted before a Power Point... is known" case AD-20's own text calls out as needing DB-level protection, not parser-level). If the insert then collides with index #2 (a real `(HouseholdId, IntervalStart)` duplicate), Postgres raises a `23505` unique-violation that the `ON CONFLICT (PowerPointId, IntervalStart)` clause does **not** suppress (an `ON CONFLICT` clause only absorbs violations of the index/constraint it names) — an unhandled exception aborting the whole bulk call, for a collision case the old `AnyExistingReadingAtSameKeyAsync` pre-check (`powerPointId is null ? ... r.PowerPointId == null && r.HouseholdId == householdId ...`) used to detect and route around *before* AD-23 deleted that pre-check.
- **SQL Server:** the `MERGE ... ON (PowerPointId = PowerPointId AND ...)` clause never treats two null-`PowerPointId` rows as matched either, so `WHEN NOT MATCHED THEN INSERT` always fires for these rows — same silent-duplicate-then-possible-hard-failure shape, this time surfaced as a `2601`/`2627` violation against index #2 that the `MERGE` statement's `WHEN MATCHED`/`WHEN NOT MATCHED` branches never anticipated.

Either way, AD-23's blanket replacement removes the one thing (`AnyExistingReadingAtSameKeyAsync`'s manual null-branch, plus the per-row fallback's ability to catch and tolerate the resulting `DbUpdateException`) that made the null-`PowerPointId` path safe, and AD-23's text never even acknowledges that AD-20's uniqueness guarantee for this exact case lives in a *different* index than the one it names. Two implementers diverge concretely: one notices this (most likely by hitting the production failure) and adds a second `BulkInsertOrUpdateAsync` call keyed by `(HouseholdId, IntervalStart)` scoped to `PowerPointId == null` batches (mirroring the DB's own two-index split); another follows the Rule's literal single `UpdateByProperties` list and ships a regression for every self-hoster whose first-ever Smart Plug import lands in `AwaitingPowerPointMapping` and gets re-uploaded (a normal, documented flow — Story 3.7's `UpdateMappingAsync` dedup-by-value logic exists precisely because this happens in production at real scale). **This is a new finding, not previously flagged** — sharper and more concrete than "does it handle the null case," since it identifies the exact mechanism (two non-overlapping unique indexes, one unnamed by AD-23) and the exact failure mode per provider.

### 3. [HIGH] AD-22's boundary-row logic is written entirely in terms of Eve Home's early-stop; Meross's "filter every row" path is left with no equivalent, undefined correction behavior

AD-22's whole Rule paragraph is scoped to "`EveHomeXlsxParser`'s forward-streaming read." AD-9/`ISmartPlugParser`'s own doc comment establishes that Meross does the **opposite** kind of watermark handling: "filtering every row" rather than early-stopping, because Meross's export has no documented row-order guarantee. AD-22 never mentions `MerossCsvParser` once, and its "Explicitly out of scope" paragraph only carves out the *different-device-same-name* gap — it says nothing about whether Meross corrections are in-scope-but-unaddressed or genuinely out of scope.

A Meross file's boundary row (`IntervalStart == watermark`) is presumably dropped today by whatever filter predicate excludes already-seen rows (structurally the same `<=`/`<` choice as Eve's early-stop, just applied per-row instead of as a stop condition). AD-22 gives an implementer no instruction on whether to touch that filter at all:

- **Team A** reasons "AD-22's intent is vendor-agnostic — Eve revising a value is not structurally different from Meross revising one" and adds the identical `== watermark → compare → correct` branch to Meross's per-row filter.
- **Team B** reads the Rule's literal scoping to `EveHomeXlsxParser` and leaves `MerossCsvParser` untouched — a Meross device silently revising an already-imported value is never detected, forever, with no violation of AD-22's text.

Both are compliant. The result is corruption detection that works for one vendor and silently doesn't for the other, which is precisely the "undetected correction to already-imported history" failure AD-22 exists to prevent — just reintroduced for exactly one of the two vendors this AD binds (AD-22's own **Binds** line names `ISmartPlugParser`'s watermark contract generically, not just the Eve adapter). This is a real, previously-unflagged gap.

### 4. [HIGH] Multiple incoming rows landing on the exact watermark timestamp (DST fold) make the boundary comparison's cardinality and audit-trail behavior undefined

This repo already has hard-won, documented knowledge that `(PowerPointId, IntervalStart)` is not a safe 1:1 assumption on the *incoming file* side, even though the DB enforces it on the *stored* side: `SmartPlugImportRepository`'s per-row fallback comments explicitly call out "a same-timestamp collision most commonly means two readings landed on the same local wall-clock `IntervalStart` (e.g. a DST fall-back fold under AD-9's zero-offset local time) — the earlier-processed reading above always wins, this one is dropped." AD-22 never engages with this at all.

Concretely: because AD-20's unique index guarantees at most **one stored row** can exist at a given `(PowerPointId, IntervalStart)`, but a DST fall-back means the *source file* can legitimately contain two physically-ordered rows whose local-clock `IntervalStart` both equal the current watermark, AD-22's "reads that row and compares" (singular) is ambiguous the moment there are two "that row"s:

- Does the loop treat the **first** `IntervalStart == watermark` row it streams past as *the* boundary row, compare/correct, and then `break` immediately (silently never examining the second same-timestamp row at all — which may itself be the more chronologically-recent of the two folded instants, i.e. the "real" newest data)?
- Or does it keep comparing every row with `IntervalStart == watermark` it encounters before finally breaking on the first row with `IntervalStart < watermark`? If so, a second boundary-timestamp row would trigger a **second** `IAuditCorrectionRecorder.RecordAsync` call against the same `entityId`, with `oldValue` set to whatever the first comparison just wrote as `newValue` — producing a spurious, misleading "correction of a correction" audit entry for what is actually just DST-fold noise, not a real vendor revision.

Two teams building against AD-22's text pick different answers here (one implements "first match wins, break," the other implements "keep comparing every `==` match until a real `<`"), and the results differ in both the stored `KwhValue` and the audit trail's shape for a real, already-known edge case in this exact codebase. AD-22 should state explicitly that a match is bounded to at most one row per watermark, and which physical row wins ties — the same way AD-20's fallback already had to make that call and documented it.

### 5. [MEDIUM] AD-23 is silent on whether the `SmartPlugImport` parent-row insert stays atomic with the `SmartPlugReading` bulk write, and the "Condition before wide rollout" spike doesn't obviously cover the gap

Today's `AddAsync` explicitly buys one guarantee with one `SaveChangesAsync` call: *"a partially persisted import (row without its readings) is never observable by a later read... in the overwhelmingly common case"* (comment at line 36-39). AD-23's Rule replaces the reading-side writes (`AddRangeAsync`/`SaveChangesAsync`) with `BulkInsertOrUpdateAsync`, but says nothing about `dbContext.SmartPlugImports.AddAsync(import, ...)` — the parent row. `BulkInsertOrUpdateAsync` is not part of the same `ChangeTracker`/`SaveChangesAsync` pipeline; by default it opens and commits its own transaction unless the caller explicitly supplies one via `BulkConfig.TransactionPerBulkOperation = false`/`SetOutputIdentity` plumbing.

AD-23's text never says whether the import-row insert and the bulk reading-write are wrapped in one explicit ambient transaction going forward. Two implementers diverge on exactly the property the original code's comment called out as important:

- **Team A** wraps `SmartPlugImports.AddAsync`+`SaveChangesAsync` and the `BulkInsertOrUpdateAsync` call inside one explicit `IDbContextTransaction`, preserving the original atomicity guarantee.
- **Team B** calls `SaveChangesAsync` for the import row, then `BulkInsertOrUpdateAsync` for the readings, sequentially with no shared transaction — silently reintroducing the "import row visible with zero readings if the process dies in between" anomaly the original single-`SaveChangesAsync` design existed to prevent, and quietly violating AD-23's own "Condition before wide rollout" bullet's "no partial row survives cancellation" bar for the cross-table case specifically.

The spike the AD does mandate is scoped to "dedicated, disposable spike-only tables" (singular framing, matching `SmartPlugReading`'s shape) — nothing in that bullet says the spike must also model the two-table `SmartPlugImport`+`SmartPlugReading` atomicity relationship, so Team B's regression could pass the mandated spike and still ship. This is a real, previously-unflagged gap in what "the spike" is required to prove.

### 6. [LOW, confirmed as low] `AwaitingPowerPointMapping` first import (watermark `== null`) is well-defined in the current code, but AD-22's text never states it explicitly

Tracing `ProcessSmartPlugImport.ExecuteAsync`: `watermark` is computed only `if (matchedPowerPoint is not null)` (line 50-55); when there's no match at all, or a match with zero prior readings, `watermark` stays `null`, and `EveHomeXlsxParser.Parse`'s existing guard (`if (watermark is not null && ...)`) means the boundary-comparison branch AD-22 adds simply never engages — the file parses in full, exactly as before this AD. This is unambiguous **in the code as it stands today**. The gap is purely textual: AD-22's Rule never states "this comparison only applies when a watermark exists; a null watermark is unconditionally a full, uncorrected parse" as an explicit invariant. Given Finding 1 above (the parser can't actually own this logic as literally written), a team rebuilding the feature from AD-22's prose alone — rather than from today's code — could plausibly re-derive different null-handling by accident while relocating the comparison to the orchestration layer. Kept at low severity only because the current code's behavior is sound; the ask is to make the AD text carry the invariant explicitly so a future rewrite can't silently drop it.

## Disposition of the three pre-flagged rubric-walker items

- **(a) AD-23 names only `AddAsync`; `UpdateMappingAsync` untouched** — independently confirmed on re-reading `SmartPlugImportRepository.cs` lines 202-375: `UpdateMappingAsync` has its own pre-check (`AnyMappingConflictAsync`)/fast-path (`ExecuteUpdateAsync`)/per-row-fallback (`UpdateMappingPerRowWithConflictToleranceAsync`, itself carrying Story 3.7's exact-duplicate delete logic) shape, structurally parallel to `AddAsync` and never named by AD-23's Rule. Agree this is a real gap as rubric-walker Finding 1 states; no refinement needed beyond noting that `UpdateMappingPerRowWithConflictToleranceAsync`'s duplicate-vs-divergent-data comparison (by `DeviceName`/`KwhValue`/`IntervalEnd`) is exactly the kind of per-row semantic AD-23's blanket upsert has no equivalent for, making a naive migration of this path even more lossy than a first read suggests.
- **(b) `PropertiesToExclude=[Id]` overwrites AD-10's snapshot fields** — independently confirmed: `SmartPlugReading`'s columns visible in `ParseDataRow`/`ProcessSmartPlugImport` include `RoomName`/`PowerPointName`/`DeviceName`/`SmartPlugImportId`/`HouseholdId` alongside `KwhValue`, none of which AD-23 excludes. Worth adding one concrete trigger scenario beyond the general risk rubric-walker already describes: `ProcessSmartPlugImport` re-resolves `matchedRoomName` from the **current** Room name on every run (`taggingScaffoldRepository.FindRoomAsync`, line 52-53) — so a boundary-row correction under AD-22, re-imported after a Room rename, would concretely overwrite that one historical row's `RoomName` snapshot with the *new* Room name via AD-23's blanket upsert, which is precisely the "live join incorrectly rewrites history" failure AD-10's text names as the thing it prevents. Also flag `SmartPlugImportId`: an upsert-driven overwrite would silently reattribute which import "owns" a corrected reading, which feeds `ListReadingsByImportIdAsync` and gap-detection queries keyed on that same id.
- **(c) `ISmartPlugParser.Parse`'s signature can't carry the stored `KwhValue`** — confirmed and superseded by Finding 1 above: the signature gap is real, but it's the smaller half of the problem. Even a widened signature doesn't give the parser `HouseholdId` or the stored row's `Id`, both required by `IAuditCorrectionRecorder.RecordAsync`, and the parser has no DB access to perform the actual `UPDATE` in the first place — so "the port contract changes" isn't just one open question, it's necessarily true that the correction write moves to a different layer than the one AD-22's prose names, and the AD needs to say so.
