# Requirements Inventory

## Functional Requirements

**4.1 Pattern Detective**

- FR-1: Meter Reading Entry — a Household member enters a Meter Reading (kWh value + timestamp, today pre-selected/editable) and saves with one confirmation tap. Testable: sub-1-minute save-to-confirmation on the default path; multiple readings per day accepted with differing timestamps; earlier/backfilled timestamps accepted, not rejected.
- FR-2: Yearly Baseline Configuration — a Household member sets/edits the Household's Yearly Baseline (kWh/year) during onboarding and from settings. Testable: household-size presets (1p≈1500, 2p≈2500, 3p≈3500, 4p≈4250 kWh) offered as suggestions, never silently applied; changing the baseline never retroactively rewrites past Status history.
- FR-3: Gap-Tolerant Rolling Baseline Computation — compute expected consumption pace from the Meter Reading sequence regardless of interval length. Testable: multi-day gaps don't break/reset computation; pace compares to baseline like-for-like (pace-to-date vs baseline-to-date); unusually long gaps are flagged low-confidence rather than shown with normal certainty.
- FR-4: Smart Plug File Import — upload Eve Home `.xlsx` / Meross `.csv` exports; system parses and associates data with the tagged Power Point. Testable: async processing with a completion notification (never blocks the UI); import tagged to a not-yet-existing Power Point prompts creation/mapping; Eve Home timestamps kept as local time, never UTC-converted; Meross device identity comes from the filename pattern, not in-file metadata.
- FR-5: Baseline Sharpening from Smart Plug Signal — imported Smart Plug data refines Status as an additional signal. Testable: zero-Smart-Plug-coverage households still get a fully functional Status from readings alone; Smart Plug data is never summed against or reconciled to the Main Meter total.
- FR-6: Status Computation — compute a single Status (within range / below baseline / trending) from pace vs Yearly Baseline and the household's threshold. Testable: "trending" fires when pace exceeds baseline pace by more than the configurable threshold (default ~100 kWh); recomputes on every new Reading or completed import, never on a fixed schedule alone; Status is undefined (not defaulted) with fewer than two Readings or no Yearly Baseline; an exact tie resolves to "within range."
- FR-7: Dashboard Status Display — the main dashboard shows the current Status as the primary, glanceable element. Testable: visible without scrolling or drilling in on first load; no chart required to read it; first-ever load with no computable Status shows an onboarding prompt, never blank space or a default value. Out of scope: ambient/push notification delivery of Status (deferred).
- FR-8: Trend History View — view historical Status/pace trend over time. Testable: shows trend, not just a point-in-time value; gaps in the Reading history render as a visible break, never interpolated (distinct from FR-24's Smart-Plug-import interpolation treatment).
- FR-9: Per-Plug Measured Data View — view measured Smart Plug data organized by Room → Power Point → Device. Testable: explicitly presented as measured context, never a reconciled attribution breakdown of the Main Meter total; retagging a Power Point/Device after import leaves previously-imported data attributed to the tag active at import time.
- FR-24: Smart-Plug Import Gap Handling — detect gaps within an import's covered date range and handle them without treating them as zero consumption. Testable: a missing date is a Gap, a 0 kWh reading is a valid data point (not a Gap); gap-fill values used to sharpen the baseline are bounded (e.g. capped at the preceding week's average) and visibly flagged as interpolated; a gap at the very start of a household's first-ever import is left unfilled and flagged as missing; an import that's entirely gaps is flagged for review, not wholesale-interpolated.
- FR-25: Meter Reading Regression Detection — a Reading lower than its chronological predecessor is flagged instead of feeding a negative rate into FR-3, and classified as *reset* or *rollover*. Testable: confirming *reset* starts a new baseline sequence forward without discarding prior history; confirming *rollover* computes the interval as (meter's known digit capacity − previous reading) + new reading; "immediately preceding" is timestamp order, not entry order; an unconfirmed regression excludes that Reading from baseline computation and never silently expires/defaults; a second regression arriving while one is open queues behind it.

**4.2 Tariff Savings Radar**

- FR-10: Tariff Configuration — maintain the Household's current Tariff: base fee, price/kWh, currency, contract start date, Contract Period. Testable: tariff history retained (each entry covers until the next entry's start date, never overwritten); price fields lock once the contract start date has passed, requiring an explicit override step to edit; flat base-fee-plus-price/kWh only (tiered/time-of-use out of scope); currency is a required per-entry field, never hardcoded to EUR.
- FR-11: Candidate Tariff Comparison Entry — enter a candidate tariff (price/kWh, base fee, optional switching-bonus terms) to compare against the current Tariff. Testable: comparison entries are scratch/exploratory and never alter the Household's actual current Tariff until an explicit switch.
- FR-12: Bonus-Decay Normalized Savings Projection — project annual savings of the candidate vs the current Tariff, applying Bonus-Decay Normalization. Testable: uses actual household consumption pace from Pattern Detective, never a generic/assumed usage figure; a comparison requested before a usable pace exists (fewer than two Readings) shows the same onboarding empty state as FR-6/FR-7, not a zero/undefined projection.
- FR-13: Two-Way Attractiveness Signal — show a green/red signal twice: once with the Switching Bonus included, once normalized out. Testable: both signals shown together, never toggled; an exact breakeven (zero projected savings) resolves to red/not-worth-switching — ties favor staying put.
- FR-14: Shared Bonus-Decay Math with Pattern Detective — Tariff Savings Radar and Pattern Detective's pace threshold use the same underlying normalization logic. Testable: a formula change affects both features identically, no separate/divergent implementations.
- FR-15: Tariff Check Reminder — *(sequenced after FR-10–FR-14 are stable, not day-one)* proactive prompt to revisit Tariff Radar, gated to no earlier than 3 months before the current Contract Period ends, then recurring at a customizable cadence. Testable: no reminder fires while more than 3 months remain in the Contract Period; default recurring cadence is 3 months, editable per household; no reminder fires if no Tariff is configured yet; the gate opens and stays open on the recurring cadence whether the tariff then ends outright or auto-continues on a rolling basis (no explicit contract end date required); editing the contract start date/Contract Period recomputes the gate and cadence going forward.

**4.3 Context Capture**

- FR-16: Event Logging — log an Event via short text/tap-first entry with an optional tag to a Room, Power Point, or Device. Testable: comparable effort to a Meter Reading entry, deliberately low-friction, not a form; backfillable to a past date/time; a deleted tagged item leaves the Event's historical tag as inert text rather than a broken reference. Out of scope: recurring/pattern events — each Event is a single dated occurrence.
- FR-17: Wattage Plausibility Correlation — give a logged Event a rough plausibility correlation against the consumption deviation (bump or dip) Pattern Detective observed around that time. Testable: shown as rough/approximate, never false precision or verified attribution; direction (bump vs dip) is inferred from the Event, not assumed to always be a bump; an Event with no corresponding deviation is shown without a correlation, never flagged as wrong; two Events in the same window as one deviation both receive the correlation (many-to-one, not first-match-wins); the AI backend (local LMStudio vs cloud API) is a Household-level config choice, always visible and under household control; the feature is optional and gracefully degradable — the rest of the product functions fully with it disabled.
- FR-18: Proactive Weekly Recap — *(optional, ships after FR-16/17 are stable)* when Pattern Detective flags a spike or trending Status, proactively prompt "anything unusual this week?" and thread the reply onto the flagged spike as an Event. Testable: opt-in, off by default per household; fires only against an actual detected spike/trending Status, not a fixed weekly schedule; a reply becomes a normal Event, shown/correlated exactly like a self-initiated entry; a given episode prompts once, not on every recomputation cycle; suppressed if the household already logged a covering Event before the prompt would fire; a confirmed FR-25 meter reset is not itself treated as a spike for prompting.

**4.4 Extensible Platform** (all Could-have)

- FR-19: Custom Event/Plausibility Rules — define custom rules for how logged Events correlate to Wattage Plausibility, beyond built-in logic. Testable: this is the seam voice input plugs into later — dictation becomes just another input modality producing an Event.
- FR-20: Generic Data-Source Column Mapping — *(low confidence, see Open Question 1)* map a new Smart Plug export format's columns to the system's schema without a code change. Testable: scoped to tabular/mappable formats only; formats requiring bespoke parsing remain a code-level addition. Feasibility must be evaluated before committing engineering time; may be dropped entirely.
- FR-21: Tunable Threshold/Spike Settings — adjust threshold/spike-detection settings beyond FR-6's single trending-threshold number (trend-view sensitivity, per-plug highlighting) via the product's UI/settings, never by editing deployment config files.

**4.5 Data Export/Import** (Must-have)

- FR-22: Full Data Export — export all of a Household's data (Meter Readings, Tariff history, Events, Smart Plug data, settings) in a documented format for disaster-recovery backup.
- FR-23: Full Data Import — import a previously exported v2 dataset to restore an instance or move it to new hosting. Testable: import validates against the documented v2 export format and rejects/reports malformed data rather than partially applying it; v2-to-v2 restore/migration only, no v1 data conversion; importing into a Household that already has data is blocked by default, requiring an explicit "replace all data" confirmation — no partial-merge mode.

**4.6 Household & Access**

- FR-26: Household Provisioning — the first person to access a fresh deployment can create the Household and becomes its first member, authenticated via the configured OIDC provider. Testable: a fresh deployment with no Household routes any authenticated visitor into Household creation rather than a broken/empty dashboard; creation requires no second party, invite code, or manual database step.
- FR-27: Household Member Invitation — an existing member can invite additional members to the same Household. Testable: all members have equal, full access — no separate admin/owner role.
- FR-28: Room / Power Point / Device Management — create, edit, and delete Rooms, Power Points, and Devices used across Pattern Detective (FR-4, FR-9) and Context Capture (FR-16). Testable: deleting a Power Point or Device that already has tagged historical data orphans/leaves that data reassignable rather than cascade-deleting it.

## NonFunctional Requirements

**Cross-Cutting (PRD §Cross-Cutting NFRs)**

- NFR1: Performance tiers — Tier 1 (reading entry FR-1, dashboard load FR-7) responds in ≤2s. Tier 2 (in-app operations with visible processing) completes in ≤30s with a UI progress hint. Tier 3 (Smart Plug imports, scheduled jobs) is fully asynchronous with a completion notification.
- NFR2: Hosting cost-efficiency — deployable comfortably on modest self-hosted hardware (e.g. a low-power NAS/single-board-computer) *and* on low-tier, scale-to-zero cloud tiers — the same deployment artifact serves both, no separate "cloud edition."
- NFR3: Auth — every route sits behind authentication; the OIDC provider is swappable via configuration only (no code change); no unauthenticated endpoints except the OIDC callback itself.
- NFR4: Tenant isolation — all data is isolated per Household, enforced at the data-access layer, not just the UI.
- NFR5: i18n/locale — no hardcoded locale-specific strings or formats anywhere; all data stored locale-neutral (ISO 8601 timestamps with explicit offset, decimal-point numbers); scheduled/background jobs run in UTC regardless of display Locale. Launch Locales are `de-DE` and `en-US`; additional Locales are a translation/formatting-table addition, not a code change.
- NFR6: Currency handling — monetary values are always fixed-decimal, never floating-point; currency is a Household-level configurable field (FR-10), not hardcoded to EUR — Tariff Savings Radar and its projections display in the Household's configured currency.
- NFR7: Offline capture — Meter Reading entry (FR-1) queues locally and syncs when connectivity returns; the core reading habit must not depend on live connectivity at the point of entry.
- NFR8: Audit trail on corrections — editing a Meter Reading or Tariff entry preserves the original value as a visible correction note rather than a silent overwrite.
- NFR9: Recomputation policy — edits to configuration inputs (Yearly Baseline, trending threshold, Bonus-Decay Normalization formula) affect calculations going forward only; historical computed values are never silently rewritten by a later settings change, unless an FR states an explicit exception.
- NFR10: Data integrity under concurrency — concurrent writes to the same Household's data never silently lose an update; the exact conflict-resolution UX is an architecture-phase decision guided by this no-silent-data-loss guarantee.
- NFR11: Documentation as onboarding path — setup and configuration docs are written so "found this on GitHub" is a real onboarding path — a Self-Hoster can go from clone to a running instance using written docs alone, no direct support channel required (load-bearing for SM-5 external adoption).

**Constraints & Guardrails (PRD §Constraints and Guardrails)**

- NFR12: Privacy — self-hosted by default, no third-party account required to view your own data; no telemetry/analytics phone-home by default.
- NFR13: Data ownership — a Household's data is always exportable in a documented format (FR-22); no vendor lock-in path where data can only be read back through the product itself.
- NFR14: Cost — the product must not require a paid third-party service to run a basic self-hosted instance; optional integrations (e.g. AI-assisted Wattage Plausibility) degrade gracefully rather than becoming a hard dependency.
- NFR15: Product discipline ("says less, on purpose") — the dashboard Status (FR-7) is the headline the product is judged by; drill-down views (FR-8, FR-9) existing is fine, but UX and implementation must never make checking the drill-down a precondition for trusting the Status (ties to counter-metric SM-C2).

## Additional Requirements

*(from ARCHITECTURE-SPINE.md and SOLUTION-OVERVIEW.md)*

- **No third-party starter template.** The architecture defines a custom Structural Seed (layered .NET solution — `Domain` / `Application` / `Infrastructure` / `Infrastructure.Migrations.Postgres` / `Infrastructure.Migrations.SqlServer` / `Api` — plus a `web/` React+Vite+shadcn frontend, `scripts/`, and dual Docker Compose files) rather than scaffolding from an off-the-shelf template. This structural seed must be established as Epic 1 Story 1, before any feature work.
- **AD-1 — Ports & Adapters dependency direction:** Domain has zero external package references beyond the BCL; Application defines port interfaces only and never references Infrastructure/Api; all framework/vendor packages live in Infrastructure/Api.
- **AD-2 — Dual database-provider persistence:** one shared `EnergyTrackerDbContext`; two migrations-only projects (`Infrastructure.Migrations.Postgres`, `Infrastructure.Migrations.SqlServer`); provider chosen once via a single `Database:Provider` config value; portable schema/LINQ subset only (no provider-specific features); every migration added to both projects atomically via `scripts/add-migration.sh`.
- **AD-3 — Data-layer tenant isolation:** every Household-scoped entity carries `HouseholdId`; enforced via a single DbContext-level global query filter sourced from `ICurrentHouseholdAccessor`; `Find()`, `FromSqlRaw`, and `.IgnoreQueryFilters()` are never used against a Household-scoped entity, including in background job processing.
- **AD-4 — Optimistic concurrency:** a plain `int Version` column (never a provider-specific `rowversion`/`xmin`) on Meter Reading, Tariff, and Household settings; a conflicting write throws and maps to HTTP 409; client reloads and retries.
- **AD-5 — Shared Bonus-Decay Normalization module:** lives in exactly one place, `Domain.Calculations.BonusDecayNormalizer`, called by both Pattern Detective and Tariff Savings Radar; neither feature reimplements or locally adjusts the formula.
- **AD-6 — Async job processing shape:** one `IBackgroundJobQueue` port, generic over a `JobEnvelope<TPayload>` envelope; two adapters (`InProcessChannelJobQueue` self-host default, `AzureStorageQueueJobQueue` cloud); API and worker are one process/container in both environments; client polls `GET /api/jobs/{id}`, never WebSocket/SSE.
- **AD-7 — Live compute + immutable snapshot history:** current Status (FR-6/FR-7) and Tariff Check Reminder due-ness (FR-15) are pure synchronous computations evaluated on every read, never precomputed on a schedule; every Status (re)computation also writes an immutable `StatusSnapshot` row via exactly one `IStatusRecomputeService`; Trend History (FR-8) reads only persisted snapshots, never a live recompute — protects the no-retroactive-rewrite guarantee (NFR9).
- **AD-8 — AI Wattage Plausibility adapter:** one `IAiPlausibilityClient` port, one adapter (`OpenAiCompatibleClient`) speaking the OpenAI-compatible HTTP shape (covers both local LMStudio and cloud providers via base-URL/API-key config); resolves to a no-op when unset, and the rest of the product never branches on whether AI is enabled.
- **AD-9 — Smart-plug import parser port:** one `ISmartPlugParser` port, one adapter per vendor format (`EveHomeXlsxParser`, `MerossCsvParser`); Eve Home timestamps parsed as local time, never UTC-converted; Meross device identity from the documented filename pattern, not file-body metadata; FR-20's generic column mapping is explicitly not built against this port yet.
- **AD-10 — Historical tag integrity:** Room, Power Point, and Device are soft-deleted (`ArchivedAt`, never hard-deleted); `SmartPlugReading` and `Event` snapshot the Room/PowerPoint/Device identity by value at write time (denormalized display fields), not via a live FK-join, so a later retag never rewrites history.
- **AD-11 — Shared audit-correction mechanism:** one `AuditCorrection` table and one `IAuditCorrectionRecorder` service, called from both Meter Reading and Tariff update paths; FR-23's full-dataset restore is a wholesale replace and explicitly does not go through this mechanism.
- **AD-12 — Meter Reading regression queue:** at most one open `MeterRegressionPrompt` per Main Meter at a time; prompts ordered by the reading's timestamp, not entry order; an open prompt excludes its triggering Reading (and everything chronologically after it) from baseline computation until resolved.
- **AD-13 — Single-artifact deployment:** the `Api` project serves the built React SPA's static assets directly from the same container (ASP.NET Core SPA-hosting pattern) — no separate frontend hosting service in either self-host or cloud.
- **AD-14 — Main Meter is the sole authoritative total:** `MeterReading` is the only entity representing authoritative total consumption; no domain code, application service, API response DTO, or frontend view may sum `SmartPlugReading` or `Event` data into a figure compared against or rendered alongside the Main Meter total; there is no `Residual` type, field, DTO property, or view anywhere in the system.
- **AD-15 — Generic by default:** every household-specific value (Yearly Baseline presets, trending threshold default, currency, Locale) is a `Household`-scoped config row, never a literal in code; presets are offered as suggested starting values, never silently applied.
- **AD-16 — Offline-safe, idempotent Meter Reading writes:** Meter Reading creation carries a client-generated idempotency key (GUID) set before any network attempt; the frontend queues unsent readings in IndexedDB while offline and flushes on reconnect; the API upserts by idempotency key.
- **AD-17 — Session persistence via server-side cookie:** ASP.NET Core cookie authentication chained to the OIDC handler — the browser holds an httpOnly session cookie, never a token the SPA reads or stores; Data Protection keys are persisted externally via `PersistKeysToDbContext` so sessions survive Azure scale-to-zero cold starts.
- **AD-18 — i18n:** `Household.Locale` is the single field driving both number/date display formatting and UI language; underlying data stays locale-neutral in storage regardless of `Locale`; frontend translations live in additive resource files (i18next-style); backend-rendered strings use .NET's `IStringLocalizer`/`.resx`; a new Locale is a resource-file addition, never a code change.
- **AD-19 — Operational baseline:** the `Api` exposes a `/health` liveness-only endpoint (no DB/dependency check); structured logging (Serilog or equivalent) to stdout/stderr only; all secrets supplied via environment variables/Container Apps secrets/a self-host `.env` file, never committed or baked into the image.
- **Consistency Conventions:** PascalCase singular C# entities/DTOs; kebab-case plural API routes (`/api/meter-readings`); `I{Capability}` ports in `Application/Ports`, `{Vendor}{Capability}` adapters in `Infrastructure/Adapters`; every swappable capability selected by exactly one config value read once at the composition root; all timestamps `DateTimeOffset` ISO 8601 with explicit offset; all money `decimal`; API errors as RFC 7807 `ProblemDetails`; the Dashboard Status endpoint returns only the current Status value and one headline/supporting sentence — drill-down data is always a separate endpoint, never merged into the Status response.
- **Stack:** .NET 10 / ASP.NET Core 10 Minimal APIs / EF Core 10; Npgsql (Postgres 17 self-host) + Microsoft.EntityFrameworkCore.SqlServer (Azure SQL Basic DTU cloud); React 19 + Vite 8 + shadcn/ui + Tailwind CSS v4; i18next (or equivalent); IndexedDB offline queue + service worker for Meter Reading creation; Docker/Docker Compose (self-host reference deployment); Azure Container Apps + Azure Storage Queue (cloud).
- **Deferred by architecture (informs sequencing, not MVP build scope):** FR-20 generic Smart-Plug column mapping (feasibility spike first); FR-19 custom event/plausibility rules engine; FR-21 broader tunable thresholds beyond FR-6; FR-18 proactive weekly recap (needs an externally-triggered scheduler and a decided notification channel — PRD Open Question 2); splitting the worker into its own independently-scaled process; a bundled local OIDC provider for dev/test; multi-Main-Meter UI/logic (data model allows it, UI/logic doesn't yet).

## UX Design Requirements

*(from DESIGN.md and EXPERIENCE.md — the bmad-ux spine pair)*

- UX-DR1: Implement the full design token set (brand-accent; status semantic triad — within-range/below-baseline/trending — with dedicated AA-verified badge-text tokens distinct from the raw triad hex; the 4th attractiveness-signal color pair with its own dedicated supporting-text and figure-text tokens; text/surface glass tokens; focus-ring token) with light and dark values as equal citizens, neither derived from the other.
- UX-DR2: Build the Status card component (the product's hero surface, FR-7): rear/front glass panel stack, specular-sweep entrance animation, status dot + uppercase badge (using the dedicated badge-text tokens, never the raw triad hex), headline sentence, supporting sentence with tabular-nums figures. Exactly 3 visual states (within range / below baseline / trending) plus the distinct onboarding empty-state layout — never a 4th "unknown" status color.
- UX-DR3: Build the Log Reading sheet component: presented as a sheet over the Dashboard (never its own route), today's date/time pre-selected and editable, single tabular-nums kWh field, single "Save reading" pill action, top-rounded/flush-bottom shape, offline queue-and-sync behavior (NFR7).
- UX-DR4: Build the Meter Regression prompt component (FR-25): modal Dialog with neutral/informational glass treatment (explicitly not destructive/error styling), *reset*/*rollover* as two plain-labeled shadcn buttons, supersedes rather than stacks on an open Log Reading sheet.
- UX-DR5: Build the Tariff Check prompt card component (FR-15): quiet-weight, near-transparent glass-less surface, shown only when a check is actually due, neutral "nothing due right now" microcopy otherwise (never a fabricated recommendation), deliberately lower visual weight than the Status card at all times.
- UX-DR6: Build the Trend chart component (FR-8): Moderate-density as the only shipped default (no user-facing density toggle), status-triad line coloring for in-range vs trending segments only (never a 4th chart-specific color), a labeled gap-band treatment for Reading-history gaps (never an interpolated line) reused for Smart-Plug-import gap flagging (FR-24).
- UX-DR7: Build the Tariff comparison card component (FR-10–FR-13): current-vs-candidate summary panels plus the two-way attractiveness signal rows (bonus-included / bonus-normalized) always shown together, never toggled, using the dedicated attractiveness-signal color tokens and their AA-verified supporting-text/figure-text variants.
- UX-DR8: Build the primary action button (Log Reading trigger): pill shape, gradient fill, press state compresses to ~0.965 scale with shadow pull-in — never a color flash.
- UX-DR9: Build the nav chrome: bottom tab bar (mobile) carrying Dashboard / Trend History / Tariff Radar / Settings only, brand-accent-tinted active state, no badge/counter treatment; less-frequent surfaces (Onboarding, Smart Plug Import, Log Event) reached via Settings or contextual entry points rather than their own tab.
- UX-DR10: Enforce the two-separate-green-systems discipline system-wide: brand-accent (chrome/interactive only) is never reused for a Status/trend meaning and vice versa; the attractiveness-signal pair is never reused for Status meaning or chrome; red/`destructive` is reserved exclusively for genuine system errors, never for "trending" or any Status/pace signal.
- UX-DR11: Implement the dark-mode-first "liquid glass" elevation system (rear/front panel stack, backdrop blur+saturate, specular sweep) with the documented Light-mode degradation path (frosted-white translucency + soft green-tinted drop shadows instead of glow) — both modes rendered and verified, not one derived from the other.
- UX-DR12: Implement the Information Architecture's 8 surfaces (Dashboard, Log Reading, Trend History, Tariff Radar, Log Event, Settings, Onboarding/Household Setup, Smart Plug Import) with their specified reach points and purposes.
- UX-DR13: Enforce one-level-deep modal/sheet stacking system-wide: a sheet never opens on top of another sheet; the Meter Regression prompt supersedes (never stacks on) an open Log Reading sheet.
- UX-DR14: Implement the full State Patterns table's explicit empty/edge-state treatments (onboarding-empty Status, mid-life undefined Status, pre-pace tariff comparison, no-tariff-check-due, import-in-progress, the three import-gap variants, unresolved-regression, unusually-long-gap, offline-at-entry, cold-load skeleton, no-deviation Event, correction-preserved edit, locked-tariff-field edit, import-validation-failure) — each with its specified treatment, never a generic/blank fallback.
- UX-DR15: Implement the Interaction Primitives motion contract (status card entrance/settle, ~2.2s specular sweep, primary-action press compression, sheet slide/backdrop-blur-ramp) entirely gated behind `@media (prefers-reduced-motion: no-preference)`, with every animated element having a fully settled, instantly legible base/fallback state — a real CSS media-query gate, not a "slow it down" compromise.
- UX-DR16: Meet WCAG 2.2 AA across the responsive surface: color-blind-safe status triad (always paired with a text badge and plain-language headline, never a bare colored dot); 44×44pt-equivalent tap targets; focus order follows reading order; focus-trap and return-focus on the Log Reading sheet and Meter Regression prompt; role/label announcement on sheet/modal open; Status recompute announced via `aria-live="polite"`.
- UX-DR17: Implement the microcopy voice/tone discipline as reusable copy (plain-language, specific, no exclamation marks/streak/gamification language, no false-precision AI phrasing, no fabricated recommendations) across the Status headline/body, Tariff Check card, Wattage Plausibility correlation text, Trend History gap labels, and empty states, per the Voice and Tone Do/Don't table.
- UX-DR18: Implement the Meter Reading Regression Classification micro-flow exactly per its 7-step walkthrough (timestamp-order comparison, modal supersession, *reset*-vs-*rollover* computation paths, queuing behind an unresolved prompt).
- UX-DR19: Implement the mobile-first / secondary-tablet-width responsive layout model: single-column phone layout throughout; Trend History widens to a tablet/browser frame but stays single-column-of-cards internally (no dense multi-column grid).
