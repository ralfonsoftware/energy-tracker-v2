topic: Batch the Story 3.10 manual job-history 'delete everything' cleanup so it stops timing out (HTTP 500) on Azure SQL Basic tier
updated: 2026-09-12T19:25
---

- (event) Root cause investigation (systematic-debugging, Phase 1-3) confirmed live in production 2026-09-12: DELETE /api/smart-plug-import-jobs?deleteAll=true returns HTTP 500. Container App logs show SqlException/Win32Exception(258, WAIT_TIMEOUT) at exactly ~120s (Program.cs's configured CommandTimeout). Azure Monitor SQL metrics show DTU ~99% and Log IO ~95-99% during precisely the two failed request windows, ~0% otherwise. deleteAll=false (30-day cutoff) succeeds in <100ms in the same window. User (Ralf) confirmed he triggered 'clean up everything'.
- (decision) Root cause: DeleteJobsAsync(cutoffUtc: null) (CleanUpSmartPlugImportJobs use case, story 3.10) selects every BackgroundJob/SmartPlugImport row for the household with no age/state bound, then shared helper DeleteEligibleAsync (SmartPlugImportRepository.cs:749-773) deletes/cascades all of them in one unbatched explicit transaction (SmartPlugImportGaps delete -> SmartPlugImports delete, which cascades a SetNull update across every linked SmartPlugReading -> BackgroundJobs delete). On a household with enough accumulated history, that single transaction's log-write volume exceeds Azure SQL Basic-tier (5 DTU) throughput within the 120s CommandTimeout.
- (note) Same failure class as a prior documented incident: Program.cs:148-156 records a 2026-09-05 incident (large bulk import saturating Basic-tier DTU/log throughput) and explicitly states a further CommandTimeout bump is not the durable fix for an operation whose cost is unbounded by design.
- (assumption) No data corruption occurred: the delete is wrapped in one explicit transaction (dbContext.Database.BeginTransactionAsync), so the client-side timeout/disconnect rolled it back cleanly — confirmed by the pattern (repeated identical failures, no partial-state symptoms reported) though not by direct row-count inspection (firewall blocked ad hoc DB access from this session).
- (decision) Fix direction chosen with Ralf: batch DeleteEligibleAsync's deletes into bounded-size chunks so no single DB command's log-write volume scales with total accumulated household history, instead of raising the timeout further or moving to an async job queue.
- (capability) CAP-1: Batched bulk delete. Intent: DeleteEligibleAsync processes jobIds/importIds in bounded-size chunks, each chunk executed as its own ExecuteDeleteAsync call(s), so a single command's log-write volume is bounded regardless of how many rows are eligible overall. Success: a DeleteJobsAsync(cutoffUtc: null) call against a household with a very large eligible set (order of magnitude beyond what caused the production timeout) completes without hitting CommandTimeout, verified against both providers.
- (capability) CAP-2: Atomicity preserved. Intent: the overall delete-everything-eligible operation remains all-or-nothing from the caller's perspective — a failure partway through must not leave some chunks committed and others not, matching the guarantee the 2026-09-11 code-review fix (explicit transaction) established. Success: a simulated failure/cancellation mid-way through a multi-chunk delete leaves the database in its original pre-delete state (verified via an integration test that forces a failure after at least one chunk has executed).
- (capability) CAP-3: No regression for existing callers. Intent: SweepExpiredAsync (automatic, terminal-states-only sweep) and the manual 30-day-cutoff DeleteJobsAsync path keep behaving exactly as today — same eligibility results, same FK-dependency delete order — after DeleteEligibleAsync is batched. Success: existing SmartPlugImportRepositoryTests and CleanUpSmartPlugImportJobsTests for both paths still pass unchanged, plus a new small-eligible-set case (fewer rows than one batch) proves batching is a no-op at small scale.
- (constraint) Dual-provider (AD-2): the batching implementation must work correctly and identically on both Npgsql/Postgres and Microsoft.Data.SqlClient/SqlServer — no provider-specific batching primitive.
- (constraint) Must not change DeleteJobsAsync's or SweepExpiredAsync's public eligibility semantics (which rows qualify) — only how DeleteEligibleAsync executes the deletes for whatever set they hand it.
- (constraint) Chunk size must be chosen to keep a single command's log-write volume safely within Basic-tier (5 DTU) throughput inside the existing 120s CommandTimeout — this is a capacity constraint, not an arbitrary code-style choice; document the reasoning at the constant's definition site the way Program.cs:140-159 already documents its own timeout/batch-size reasoning.
- (non-goal) Not in scope: moving 'delete everything' to the existing async background job queue (AD-6) — considered and deliberately deferred in favor of the smaller, targeted batching fix.
- (non-goal) Not in scope: an Azure SQL tier upgrade — batching is the chosen mitigation; a tier upgrade remains a possible future lever but isn't part of this fix.
- (non-goal) Not in scope: changing SweepExpiredAsync's or DeleteJobsAsync's eligibility query logic, or the frontend cleanup dialog/UX from story 3.10.
- (question) Exact chunk size (e.g. 500 vs 1000 IDs per batch) is left to the implementer to settle empirically/by reasoning during implementation, bounded by SQL Server's ~2100 parameter limit (same constraint Program.cs:144-146 already documents for MaxBatchSize) and by keeping per-chunk log volume well under what saturated Basic tier in the observed incident.
- (question) Whether each chunk should share the existing outer transaction or use its own per-chunk transaction is an implementation decision — sharing one outer transaction preserves the strongest atomicity guarantee (CAP-2) but keeps holding one long-running transaction's log growth; per-chunk transactions bound that further but weaken all-or-nothing semantics and need an explicit call on which is acceptable. Flagged for the implementer/reviewer to resolve and document, not pre-decided here.

- (event) Round 1 fix (batch DeleteEligibleAsync by import COUNT, PR #47) deployed 2026-09-12 to production. User re-ran 'clean up everything' and got the same HTTP 500/SqlException(WAIT_TIMEOUT at 120s CommandTimeout). - (event) Fresh evidence: only ONE chunk of 60 ran before timing out, because total eligible rows for this household (60 BackgroundJobs, 51 paired SmartPlugImports) is well under the existing DeleteBatchSize=200 threshold — import-count-based chunking never actually split anything for this household. Azure Monitor shows the same DTU/Log-IO ~99% saturation signature as round 1.
- (event) Root cause confirmed via a temporary, since-removed read-only Azure SQL firewall rule + direct COUNT queries (user approved the temporary access, rule added and removed within the same session): of the household's 51 SmartPlugImports, 5 individually carry 57171/66238/112005/114077/122158 SmartPlugReading rows each; total readings across all 51 imports = 487380. 'Clean up everything' tries to SetNull-cascade all 487380 rows in one single DELETE FROM SmartPlugImports command since the whole eligible set fits in one chunk of 200.
- (decision) This is the exact residual risk round-1's own review (Blind Hunter) flagged and the team deliberately deferred (deferred-work.md: 'chunking by import count bounds typical/average cascade... does not bound a single pathologically large import's own cascade') — now confirmed as the live, actually-occurring cause, not theoretical.
- (decision) New fix direction (confirmed with Ralf): chunk the importIds loop by CUMULATIVE SmartPlugReading count per import, not import count. Measure each eligible import's reading count via one GROUP BY query (missing/zero for imports with no readings), then greedily pack imports into chunks bounded by cumulative reading count. Keep the existing DeleteBatchSize=200 import-count cap too as a secondary/outer bound (parameter-list sanity for many-small-imports batches) — the new row-volume bound and the existing count bound both apply, whichever is hit first ends a chunk.
- (capability) CAP-4: Row-volume-aware import chunking. Intent: the importIds loop chunks by both cumulative SmartPlugReading count and import count (whichever bound is hit first), so a small number of eligible imports with large individual reading counts no longer bypass batching by fitting under the count-based threshold alone. Success: DeleteJobsAsync(cutoffUtc: null) against a household shaped like the reported incident (order of 50-60 imports, several individually carrying 50k-120k+ readings, ~487k total) completes without hitting CommandTimeout, verified against SqlServer (the actual production provider in both incidents) and Postgres.
- (constraint) The jobIds loop (bounding BackgroundJobs' own direct delete row/log volume — no downstream cascade) is unaffected and keeps its existing DeleteBatchSize=200 import-count-based chunking unchanged; only the importIds loop's chunking strategy changes.
- (constraint) Measuring reading counts costs one extra GROUP BY query per DeleteJobsAsync/SweepExpiredAsync call — acceptable since this is a manual, low-frequency, already-slow-by-nature cleanup operation, not a hot path.
- (non-goal) Not in scope (still): a single individual import whose OWN reading count alone exceeds the row-volume threshold cannot be split further (an import is the atomic unit for the SmartPlugImportGaps+SmartPlugImports delete pair) — named explicitly as a still-not-fully-solved edge case, though the observed incident data (largest single import: 122158 rows) shows this is not what caused either incident; the incident was caused by the SUM across several large imports in one uncapped batch, which row-volume-bounded packing directly fixes.
- (non-goal) Not in scope: changing SweepExpiredAsync's or DeleteJobsAsync's eligibility query logic, the frontend cleanup dialog/UX, or moving to the async job queue — same non-goals as round 1, unchanged.
- (question) Exact row-volume threshold per chunk is left to the implementer, informed by this incident's own numbers (487380 total readings across 51 imports saturated Basic-tier for ~2 minutes in one command) — should be set well under that scale, and documented with the same reasoning discipline as DeleteBatchSize's own comment.

- (event) Round 2 fix (chunk by reading volume, CAP-4, PR #48) deployed 2026-09-12. Same household ran 'clean up everything' again: this time every individual DB command succeeded (no CommandTimeout, confirmed via chunked measurement/importIdBatch parameter names in logs and no SqlException) but two chunk-delete commands took 117.6s and 64.5s respectively, and the whole synchronous HTTP request ran 240.2s total before the connection was aborted (HTTP 499, 'client closed request' — not 500). Azure Monitor confirmed DTU/Log IO sustained ~99% for the full ~4-minute window. Root cause: this household's total accumulated data now genuinely takes longer to fully process than the ~240s ceiling something in the request path (most likely Azure Container Apps' fixed ingress idle timeout) allows for one synchronous HTTP response — a wall-clock ceiling, not a per-command timeout. This is exactly the residual risk both round-1 and round-2 specs explicitly named as an accepted, deliberately-deferred non-goal ('no upper bound on total chunk count per call... relaxing atomicity is an explicit non-goal here'; 'moving delete-everything to the async job queue... deliberately deferred') — now confirmed as the live, actually-occurring failure mode, not theoretical.
- (decision) Renegotiated with Ralf: the round-1 non-goal 'moving delete-everything to the async job queue (AD-6) — considered and deliberately deferred' is now superseded. Two rounds of synchronous-request chunk-tuning (CAP-1 import-count, CAP-4 reading-volume) correctly bound every individual DB command but cannot bound total wall-clock time for a household whose accumulated data genuinely exceeds the platform's synchronous-HTTP ceiling — no chunk-size tuning fixes a wall-clock ceiling. Moving to the existing async background-job pattern (AD-6, already used for ProcessSmartPlugImport) sidesteps the ceiling entirely: the client polls GET /api/jobs/{id} instead of waiting on one long synchronous response.
- (capability) CAP-5: Async cleanup execution. Intent: 'clean up everything'/'older than 30 days' runs as a background job (new JobTypes.CleanUpSmartPlugImportJobs, reusing IBackgroundJobQueue/JobEnvelope<T>/BackgroundJobProcessor's existing dispatch and BackgroundJob status machinery) instead of executing synchronously inside the DELETE request — the endpoint enqueues and returns 202+jobId immediately, matching the existing POST /smart-plug-imports upload pattern; the client polls GET /api/jobs/{id} for completion the same way the existing Smart Plug import upload flow already does. Success: a household whose total cleanup work exceeds the ~240s synchronous HTTP ceiling (reproducing the confirmed 2026-09-12 16:42 incident's data shape) still completes 'clean up everything' successfully end-to-end via polling, with no HTTP request held open longer than the existing POST-and-poll upload flow's own request duration.
- (constraint) DeleteJobsAsync/DeleteEligibleAsync's own chunking (CAP-1/CAP-4) is unchanged and still required — moving to async removes the HTTP-timeout ceiling but does not remove the value of bounding individual DB command duration; both layers apply together.
- (constraint) New job type's BackgroundJob rows must not appear in the existing Smart Plug import job history list or become eligible for cleanup by DeleteJobsAsync's own eligibility query themselves — both already filter strictly on JobType == JobTypes.ProcessSmartPlugImport, so a distinct JobTypes.CleanUpSmartPlugImportJobs constant naturally satisfies this with no additional filtering logic needed.
- (constraint) Frontend cannot reuse the existing use-smart-plug-import-job.ts polling hook as-is — its state machine branches on import-specific importStatus/gaps semantics that don't apply to a cleanup job; a new, simpler polling hook is needed (queued/processing/completed/failed only, no import sub-status).
- (non-goal) Not in scope: changing DeleteJobsAsync/DeleteEligibleAsync's chunking algorithm or thresholds (CAP-1/CAP-4 stand as already fixed and verified) — this capability changes only how/when that already-correct logic is invoked (async instead of sync), not the logic itself.
- (non-goal) Not in scope: a general-purpose async-job UI framework — reuse the existing GET /api/jobs/{id} polling infrastructure and status shape as-is; only the minimum new plumbing (job type, payload, dispatcher case, one new frontend hook) is in scope.
- (question) Whether the existing cleanup confirmation dialog's UX (job-history-list.tsx) needs a redesign for a polling/progress experience, or can reuse a minimal 'processing...' state matching the existing upload flow's polling UI, is left to the implementer/UX judgment during implementation — no dedicated UX pass is presumed necessary given the existing upload flow's pattern already covers this shape of interaction.
