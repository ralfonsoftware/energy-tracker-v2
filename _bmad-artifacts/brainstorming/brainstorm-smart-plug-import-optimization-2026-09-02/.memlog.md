- (technique) started Question Storming
- (question) Why does it take so long for just a few additional days of new data?
- (question) Why isn't the import smart about detecting which data is already known/unchanged?

- (question) Why does the import not remember the last timestamp and value, to detect what's actually new?
- (insight) Storing (timestamp, value) pairs as the watermark -- not just a timestamp -- makes silent corrections to already-imported rows discoverable (value differs at a known timestamp)
- (question) Why not read just the first rows/header to extract the recorded Eve device name and match it against known Power Points before processing everything for nothing?

- (insight) Power Point mapping itself is treated as the guard against name collisions/renames -- ambiguous or unknown matches fall back to manual choice rather than needing separate collision-detection logic
- (question) How do we write many rows in the fewest round-trips, as fast as possible?
- (question) How do we discover a partial/interrupted import so we know a batch didn't leave data half-written?
- (question) How do we handle gaps/pauses in a data period -- both ones present in the imported file and ones already sitting in the database?
- (insight) DTU throttling on Azure SQL Basic is expected to just slow the import down, not crash it mid-batch -- so 'partial write' risk is more about process interruption (timeout, restart, crash) than throttling itself
- (question) Where does the time actually go -- file parsing, DB work, or Power Point association -- and is that distribution even known/measured today?

- (technique) started Morphological Analysis (facilitator-chosen 3rd technique)
- (idea) PARAMETER: delta-detection option -- interval/gap-based check: if a time period sits between two already-known periods with no gap, infer it's already imported without checking each row individually
- (idea) PARAMETER: delta-detection option -- parse the file in reverse (most-recent to oldest), stop at the first already-known entry, drastically cutting rows touched; user-configurable as 'smart import' (early stop) vs 'full import' (parse everything, e.g. to catch corrections)
- (idea) PARAMETER: mapping option -- match against filename pattern history rather than (or in addition to) in-file device name: filenames are stable except for an embedded export-date segment, so stripping the date and matching the remaining pattern against previously-confirmed imports gives a reliable, cheap same-room/same-device signal
- (idea) PARAMETER: bulk-write option -- non-EF-Core bulk library (e.g. EFCore.BulkExtensions) for fast batched writes
- (idea) PARAMETER: bulk-write option -- go provider-specific/native (e.g. Postgres COPY, SQL Server native bulk mechanisms) to squeeze maximum throughput per engine, rather than staying in the portable relational subset
- (insight) TENSION to resolve later: provider-native bulk-write options sit in tension with AD-2's 'one shared DbContext, portable subset only' rule -- would need to be isolated behind the existing config-driven adapter-selection pattern (like DB provider itself) rather than branching inline, if pursued
- (idea) CONFIGURATION A: reverse-parse-with-early-stop (delta) + in-file device name matching (mapping) + bulk-library writes (EFCore.BulkExtensions-style, EF-adjacent) -- the 'fast, mostly-in-existing-stack' combination
- (idea) CONFIGURATION B: gap-inference (delta) + filename-pattern-history matching (mapping) + provider-native SQL bulk writes (bulk-write) -- the 'aggressive, historically-informed, higher-risk/higher-throughput' combination
