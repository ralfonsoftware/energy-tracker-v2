# Project Context for AI Agents

_This file contains critical rules and patterns that AI agents must follow when implementing code in this project. Focus on unobvious details that agents might otherwise miss._

---

## Technology Stack & Versions

**Backend:** .NET 10 (LTS to Nov 2028), ASP.NET Core 10 Minimal APIs, EF Core 10.
**Frontend:** React 19.2, Vite 8.2, TypeScript ~6.0, Tailwind CSS v4, shadcn/ui + Radix.

**Key dependencies:**
- Persistence: Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3 (Postgres 17 self-host) / Microsoft.EntityFrameworkCore.SqlServer 10.0.12 (Azure SQL Basic DTU) — dual-provider, config-selected.
- Auth: Microsoft.AspNetCore.Authentication.OpenIdConnect 10.0.12 + cookie auth, Microsoft.AspNetCore.DataProtection.EntityFrameworkCore 10.0.12, Azure.Extensions.AspNetCore.DataProtection.Keys 1.6.4 + Azure.Identity 1.21.0 (both pinned explicitly in `Directory.Packages.props` and referenced by the Api project; Key Vault protector for the Data Protection key ring, AD-17; `Azure.Identity` also arrives transitively via `Microsoft.Data.SqlClient`).
- Observability: Serilog.AspNetCore 10.0.0, OpenTelemetry.* 1.19.x (`OpenTelemetry.Instrumentation.EntityFrameworkCore` is pinned to `1.19.1-beta.1` deliberately — no stable release exists upstream).
- .NET testing: xunit.v3.mtp-v2 3.2.2, Shouldly 4.3.0, NSubstitute 6.2.0, Testcontainers.PostgreSql/MsSql 4.15.0, Microsoft.AspNetCore.Mvc.Testing 10.0.12.
- Frontend: i18next 26.x + react-i18next 17.x, class-variance-authority, tailwind-merge, lucide-react.
- Frontend testing: Vitest 4.1, @testing-library/react 16.3, @playwright/test 1.62, oxlint 1.75 (not ESLint).

**Version constraints:**
- SDK pinned via `global.json` to `10.0.100`, `rollForward: latestFeature`.
- All NuGet versions are centrally managed in `Directory.Packages.props` (`ManagePackageVersionsCentrally=true`) — never add `Version=` to a `<PackageReference>` in a `.csproj`; bump the version in `Directory.Packages.props` instead.
- EF Core packages (EFCore, EFCore.Design, EFCore.Relational, EFCore.SqlServer) are pinned to the identical `10.0.12` line to avoid transitive version conflicts — bump together, never individually (the `dotnet-ef` tool in `.config/dotnet-tools.json`, `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore`, `OpenIdConnect`, `Mvc.Testing` and `Microsoft.Extensions.Logging.Abstractions` ride the same patch). OpenTelemetry packages move together on one 1.x line as well.
- `xunit.v3.mtp-v2` runs on Microsoft.Testing.Platform (`global.json` `test.runner`), not the classic VSTest runner — test invocation differs from xUnit v2 projects.

## Critical Implementation Rules

### Language-Specific Rules

**C# (nullable/implicit usings enabled across all projects):**
- File-scoped namespaces, primary constructors for DI (e.g. `public class CreateDevice(ITaggingScaffoldRepository repository)`), one use-case class per file — no feature-folder nesting under `Application/` (flat: `CreateDevice.cs`, `ArchiveRoom.cs`, etc.).
- Use cases are named as imperative verbs (`CreateHousehold`, `RenameDevice`, `AcceptHouseholdInvite`) with a single `ExecuteAsync(...)` method — not a generic `Handler`/CQRS mediator pattern.
- Validation throws typed domain exceptions (`TaggingScaffoldValidationException`, `HouseholdValidationException`, `*NotFoundException`, `*ArchivedException`) rather than returning result objects or throwing generic `ArgumentException`.
- `Nullable` and `ImplicitUsings` are `enable` — don't add explicit `using System;` etc., and treat nullable warnings as real (no `!`-suppressing without reason).
- Ports live in `Application/Ports` named `I{Capability}`; adapters live in `Infrastructure/Adapters` named `{Vendor}{Capability}` — never place an interface and its implementation in the same project.
- **AD-1 (Ports & Adapters direction):** Domain has zero external package refs beyond the BCL. Application defines interfaces only — never references `Infrastructure` or `Api`. All framework/vendor packages live in `Infrastructure`/`Api`. Enforced by `tests/EnergyTracker.Architecture.Tests` (`DomainHasNoExternalDependenciesTests.cs`) — a violation fails the test suite, not just a convention.

**TypeScript/Frontend:**
- `verbatimModuleSyntax: true` — type-only imports must use `import type { Foo }`, not a plain `import { Foo }` that gets erased.
- `noUnusedLocals` + `noUnusedParameters` + `erasableSyntaxOnly` are on — unused bindings and non-erasable TS syntax (e.g. enums, parameter properties) fail the build (`tsc -b`).
- Path alias `@/*` → `web/src/*` — use `@/components/...` imports, not relative `../../` chains, for anything outside the same folder.
- Linting is **oxlint**, not ESLint — don't propose `.eslintrc` config or ESLint-specific rule names.
- `allowImportingTsExtensions` + `noEmit` — this is a bundler-mode (Vite) TS setup; don't assume CommonJS/`tsc`-emit conventions.

### Framework-Specific Rules

**ASP.NET Core / EF Core (backend) — these are architecture-spine invariants, not preferences:**
- **Config-driven adapter selection:** every swappable capability (DB provider, job queue, AI backend, OIDC) is selected by exactly **one** config value read once at the composition root (`Program.cs`). No feature code branches on environment or provider elsewhere.
- **Tenant isolation (AD-3):** every Household-scoped entity carries `HouseholdId`; `EnergyTrackerDbContext.OnModelCreating` applies a global query filter from `ICurrentHouseholdAccessor`. Never write per-handler/per-repository household filtering, and never use `DbSet<T>.Find()`, `FromSqlRaw`, or `.IgnoreQueryFilters()` against a Household-scoped entity — that's the specific bypass this rule exists to close.
- **Household is resolved once per request, asynchronously (Story 11.12, audit C2):** `HouseholdMembershipMiddleware` (`UseHouseholdMembership()`, registered in `Program.cs` after `UseExceptionHandler`, `UseAuthentication`, `UseAuthorization` and `UseRateLimiter` and before the first endpoint) looks the caller up through `HouseholdMembershipResolver` (`SingleOrDefaultAsync` on `IDbContextFactory<HouseholdMembershipDbContext>.CreateDbContextAsync`, issuer from `HouseholdClaimTypes.ValidatedIssuer`) for an authenticated request under `/api` only, and stores a `ResolvedHouseholdMembership` in `HttpContext.Items` (a principal with no row is stored as "none" too). `CurrentHouseholdAccessor` only reads it (constructor: `IHttpContextAccessor` and `JobHouseholdContext`, nothing else; lazy, because Data Protection builds it inside `UseAuthentication`): no synchronous lookup, no cross-request cache, nothing in the cookie or the claims (AD-17/AD-26: a removed member's next request resolves nothing). Without an `HttpContext` it takes the job path (`JobHouseholdContext`, unchanged). An authenticated principal with no cached value makes it throw an `InvalidOperationException` naming `UseHouseholdMembership` (never a silent fallback or "no Household"), so a new authenticated route **outside `/api`** that needs the Household must be covered by the middleware first. Membership changes inside a request are not visible until the next one (create, accept and remove do not read the accessor after the write). `HouseholdMembershipIsResolvedOncePerRequestTests` guards the accessor, the one place that opens the membership context, the claims and the registration order; `HouseholdMembershipIsResolvedPerRequestTests` counts lookups on a real host (its factory decorator throws on a synchronous `CreateDbContext()`).
- **Dual-provider persistence (AD-2):** one shared `EnergyTrackerDbContext`, never a per-provider subclass. Only the portable relational subset (`string`, `int`, `decimal`, `DateTimeOffset`, `bool`, `byte[]`, standard LINQ) — no Postgres `jsonb`/`ILike`, no SQL Server `rowversion`, no provider-specific column mapping. A migration is added to **both** provider projects in the same commit via `scripts/add-migration.sh <Name>`, never to one alone.
- **Optimistic concurrency (AD-4):** concurrency-sensitive entities (Meter Reading, Tariff, Household settings) carry a plain `int Version` EF concurrency token — never a provider-specific mechanism (`rowversion`/`xmin`). Conflicts throw `DbUpdateConcurrencyException` → HTTP 409 with current server state; never last-write-wins or silent merge.
- **Compute-at-request-time vs. persisted history (AD-7):** current Status/Reminder are pure synchronous computations on every read — never precomputed by a background schedule (`IHostedService`/`Timer` doesn't survive scale-to-zero). Every time Status is recomputed, it's also written to an immutable `StatusSnapshot` row via the **one** `IStatusRecomputeService` — don't build a second snapshot writer. History reads (Trend History) always read persisted `StatusSnapshot`, never a live recompute.
- **Async jobs (AD-6):** one `IBackgroundJobQueue` port, payload is always a plain JSON-serializable record (`JobEnvelope<TPayload>`) — never a delegate/closure-based executor. Clients learn a job finished by **polling** `GET /api/jobs/{id}`, never WebSocket/SSE. Every `BackgroundJob` status change goes through `IBackgroundJobLifecycle` (one conditional update, `StartedAtUtc` ownership token; stale/interrupted jobs fail as `job-interrupted`) — never assign `Status` anywhere else; `BackgroundJobStatusHasOneWriterTests` enforces it.
- **Main Meter is sole authoritative total (AD-14):** no domain code, service, DTO, or frontend view may sum `SmartPlugReading`/`Event` data into a figure compared against or rendered alongside the Main Meter total. No `Residual` type/field/DTO/view anywhere.
- **No hardcoded household-specific values (AD-15):** every household-specific value (baselines, thresholds, currency, locale) is a `Household`-scoped config row, never a literal in code.
- **Idempotent Meter Reading writes (AD-16):** creation carries a client-generated idempotency key (GUID) set before any network attempt; the API upserts by that key.
- **Auth (AD-17):** cookie auth chained to OIDC — the SPA never reads or stores a token itself. Data Protection keys persist via `PersistKeysToDbContext`, never the in-memory default (doesn't survive scale-to-zero). The key ring must be encrypted at rest: Azure Key Vault (`DataProtection:KeyVaultKeyId`, Container App managed identity) on Azure, a certificate (`DataProtection:CertificateBase64`) or an explicit opt-out (`DataProtection:AllowUnprotectedKeys=true`) elsewhere, chosen once by `DataProtectionKeyProtection` at the composition root. **Fail closed:** outside Development with none of the three the app refuses to start; any new test host that runs outside Development sets the opt-out. Key Vault wins over a certificate; Development with nothing configured stays unprotected and warns. **Session lifetime (Story 11.8, S13):** an explicit 14-day sliding window plus a 90-day absolute cap (`SessionLifetime.cs`): an issued-at stamp is written into the ticket's `AuthenticationProperties.Items` at sign-in (`OnSigningIn`, not on renewal; never `IssuedUtc`, which restarts on renewal) and `OnValidatePrincipal` rejects and signs out a cookie with no stamp, an unreadable stamp or a stamp 90 days old. A cookie without a stamp is rejected on purpose (no grandfathering), so deploying this signs everyone out once. The clock is `TimeProvider` from DI.
- **Member trust and invites (AD-26, Story 11.9, audit A2/S10):** every member has full, equal trust; there are no roles and no endpoint may invent an Owner or admin check. Removing a member and leaving are one route (`DELETE /api/household-members/{id}`, the id is the caller's own when leaving) and one `SaveChanges` in `HouseholdRepository.RemoveMemberAsync`: it deletes the membership, expires every open invite and bumps `Household.Version`, which is the race guard (the last-member count is only the friendly error). `HouseholdMember` and `HouseholdInvite` are AD-3 query-filter exceptions, so every by-id access carries an explicit `HouseholdId`: the one by-id member lookup is `FindMemberInHouseholdAsync`, and `HouseholdMemberLookupsAreHouseholdScopedTests` fails for a new file that queries either set, a bypass (`Find`, `IgnoreQueryFilters`, `FromSql`) or a by-id access without `HouseholdId`. Revoking an invite sets `ExpiresAtUtc` to now (no column). Invite tokens are 32 random bytes as base64url and only their SHA-256 hash is stored (`TokenHash`); `InviteToken` is the only place that generates or hashes a token, lookup tries the hash first and the legacy plaintext `Token` column second (dropped in a later release, see `deferred-work.md`). The open-invite list never returns a token or hash, and no exception message, log line or response may carry a presented token. A removed member's cookie stays valid but resolves no Household on the next request (AD-17 amendment), so they land in household creation; their already-open tab keeps its stale `ready` state, and `HouseholdMemberEndpointsTests` sweeps every `/api` route as a removed member and fails if any answers 2xx (add new routes with the usual no-Household 403 check). The two `DELETE` routes carry `RateLimitPolicies.MemberRemoval`.
- **HTTP hardening (AD-27, Story 11.7):** outside Development a hand-written middleware (`SecurityHeaders.cs`, registered **first**) sets the CSP (`script-src 'self'`, `style-src 'self' 'unsafe-inline'` for Radix, `form-action 'self'`, `frame-ancestors 'none'`, `img-src 'self'`), `nosniff` and `Referrer-Policy: same-origin` in `Response.OnStarting` (set before `next()` they are lost on a 500, because `UseExceptionHandler` resets the response); `UseHsts()` follows `UseForwardedHeaders`. `web/index.html` carries no inline script (guarded by `IndexHtmlHasNoInlineScriptTests`); the pre-paint theme script is `web/public/theme-init.js`. **CSRF (Story 11.8, S9):** every POST/PUT/PATCH/DELETE under `/api` needs an `X-Requested-With` header, enforced by one endpoint filter on the `/api` group (`RequestedWithFilter.cs`, `RequireRequestedWith()`; presence only, the SPA sends `fetch`); `POST /logout` carries the filter explicitly. The filter adds a marker (`RequestedWithRequiredMetadata`) and `RequestedWithRoutesTests` fails for any mutation route without it, so a new route cannot ship unprotected. Endpoint filters run after parameter binding, so a body that fails to bind answers the binding's 400 first. Rate limiting is the built-in in-process limiter (`HttpRateLimiting.cs`, `UseRateLimiter` after `UseAuthorization`): policies are per route via `RequireRateLimiting`, identity-keyed (issuer + subject) except `/login` (client IP); the limits are the table in Story 11.7, and `RateLimitedRoutesTests` fails when a new upload/export/invite route is not classified. Forwarded headers stay untouched (Story 1.7); a deploy's health gate probes `/health` only, so a CSP regression is caught only by a local Production rehearsal in Chrome and the live check, never by the pipeline.
- **Uploads are streamed and bounded (Story 11.10, audit S4):** never read an upload into one string or array. `POST /api/household-import` copies the file to a temp file and validates it from that `FileStream` with `HouseholdImportJsonReader` (`Utf8JsonReader`, two passes; buffer capped at 4 MiB, 200 failures, 100 member names of 200 characters), and `RestoreHouseholdData` deserializes from the stream; `HouseholdImportIsStreamedTests` fails on `ReadToEnd`, `ReadAllText`, `ReadAllBytes`, `JsonDocument.Parse(`, a whole-export `Deserialize` or `new StreamReader(` in those files. The temp file is deleted on every path that does not end in a successful `Register` (one `try/finally` in `ReceiveUploadAsync`). The registry holds at most one pending upload per Household (replacement at `Register` of the new validated one, atomic under one lock, never touching a consumed token's file) and `Consume` deletes the file of an expired or wrong-Household entry. An XLSX package is opened in exactly one place, `EveHomeXlsxParser.OpenDocument`: a decompressed-size pre-scan (64,000,000 bytes in total across all entries, real bytes counted, cancellable, entries .NET cannot inflate and directory entries skipped), `OpenSettings.MaxCharactersInPart` as the backstop, a 400,000-row cap in `Parse`, and rows read cell by cell with a 100-cell cap (a row is never loaded whole); the limits throw `SpreadsheetTooLargeException`, which `BackgroundJobProcessor` maps by type to `spreadsheet-too-large` (translated in both locales). The restore job still materializes the whole object graph; see `docs/data-import-restore.md`.
- **Config correctness (Story 11.11, audit S7/C11/C1):** `ConnectionStrings:Default` is required outside Development: unset, empty or whitespace stops the host with a message naming `ConnectionStrings:Default`/`ConnectionStrings__Default` (never a configured value), and only Development falls back to the local `change-me` string (the check runs before the Data Protection one; `ConnectionStringStartupTests` pins it, and any new test host outside Development sets the setting). `/login` answers a 503 `application/problem+json` "Sign-in is not configured" when OIDC is unset (the rate limiter still applies on both branches). The AI backend is configured **only** through `Ai:Endpoint`, `Ai:ApiKey`, `Ai:Model` and `Ai:BackendLabel`, read once in `AiPlausibilityBackendConfiguration` (no `AiPlausibility:*` fallback): blank endpoint is the no-op client, a set endpoint that is not an absolute http(s) URL fails startup, the startup log names the adapter and never the key, and `AiConfigurationKeysAreOneSetTests` fails when the code, `appsettings.json`, `.env.example`, `docker-compose.yml`, `scripts/run-api.sh` and the Bicep env block stop naming the same four keys.
- **One active instance (AD-24, Story 11.13, audit A1):** the app is correct only with exactly one instance; `maxReplicas` stays `1` in `container-app.bicep`, `main.bicep` and `main.bicepparam`, and raising it is an architecture decision, not a config change. Seven process-local mechanisms are bound by it (upload registry, per-Household recompute lock, temp-file job payloads, in-process Channel queue, AD-6's startup sweep, the upload-registry expiry sweep, the in-process rate limiter); each keeps a one-line `AD-24` comment instead of re-arguing it, and `docs/self-hosting.md` ("Run exactly one instance") lists them. A new `ConcurrentDictionary<`, `SemaphoreSlim`, `Channel.Create`, `IMemoryCache`, `AddRateLimiter` or `Path.GetTempPath` in `src` fails `SingleInstanceInvariantIsDocumentedTests` until it is listed, commented and documented. `InstanceHeartbeatService` observes the invariant: it writes its own `AppInstances` row every minute and logs one warning per other instance that has overlapped it for more than 15 minutes; it never blocks startup, never touches `/health`, never lets an exception escape `ExecuteAsync`, and nothing reads the table except that log line (AD-7). `AppInstances` is an AD-3 exemption (no `HouseholdId`, no query filter, not exported or restored), like `HouseholdMember`, `HouseholdInvite` and `DataProtectionKeys`.
- **Restore re-keys, and one active restore or cleanup per Household is a database index (Story 11.14, audit C10, AD-6):** `RestoreHouseholdData` gives every restored entity a new `Guid` id and every meter reading a new `IdempotencyKey` (`HouseholdRestoreRekey`, pure, in Application, built from the deserialized file) and rewrites every reference, including the two without a foreign key (`Event.TaggedEntityId` by `TaggedEntityType`, `AuditCorrection.EntityId` by `EntityType`); a reference that resolves to nothing in the file is kept as it is. Ids in a backup are file-local names, never stable identifiers, so nothing may persist one across a restore. The filtered unique index `UX_BackgroundJobs_ActiveExclusive` on `BackgroundJobs (HouseholdId, JobType)` covers `JobTypes.ExclusivePerHousehold` (`RestoreHouseholdData`, `CleanUpSmartPlugImportJobs`) while `Status` is `Queued` or `Processing`; it is raw SQL in the two `AddActiveJobGuard` migrations only and must never become a `HasFilter` in the shared model (AD-2). `BackgroundJobEnqueueRecorder` turns a rejected insert into `ActiveJobAlreadyExistsException` (probe for the active row, no provider error codes), which restore-confirm answers `409` and cleanup answers `202` with the existing job id; the early checks stay as the fast path. `ActiveJobGuardIsDeclaredTests` fails for a changed index, a filter or unique index in `BackgroundJobConfiguration`, a second thrower, or a new `BackgroundJobStatus` nobody classified as active or terminal; `HouseholdRestoreRekeyTests` and the C10 cases in `HouseholdRestoreWriterTests` cover the re-key.
- **Time is injected, and the recompute lock evicts (Story 11.17, audit C5/C6):** Application and Infrastructure code (and the one Api endpoint that needs it) read the clock only through an injected `TimeProvider` (`timeProvider.GetUtcNow()`, registered once as `TimeProvider.System` in `Program.cs`); `NoDirectClockReadsTests` fails on `DateTimeOffset.UtcNow`/`Now`, `DateTime.UtcNow`/`Now`/`Today` or `TimeProvider.System` anywhere in `src` outside `Program.cs` (comments stripped, `Migrations` excluded). Domain never reads a clock: a calculation takes `now` as a parameter (`SmartPlugGapDetector.DetectGaps`). Keep the number and order of clock reads per operation as they were (`now` is a data point, `BackgroundJobLifecycle`'s token is truncated to whole milliseconds, `InProcessChannelJobProcessingService` captures its start once at construction). Tests use `tests/Shared/ManualTimeProvider.cs` (`Advance`, `Set`; linked into the Application, Infrastructure and Api test projects), never a `FakeTimeProvider` package and never `Task.Delay` to make time pass. `HouseholdRecomputeLock` reference-counts its per-Household entries (holders plus waiters, one `lock`, never held across an `await`) and removes an idle entry; the timeout and cancellation paths return their reference, so the dictionary is bounded by Households in use, not Households ever seen (AD-24 still applies: the lock is process-local).
- **Trending threshold is annual (Story 11.15, audit C12, FR-6):** `Household.TrendingThresholdKwh` is kWh per year; `PatternDetectiveCalculator.ResolveStatus` takes the annual value plus the pace window's `Elapsed` and scales it with `BonusDecayNormalizer.NormalizeToDate`, so a first-year household reaches *Trending* at the same relative overshoot as after a year; the scaling is `TrendingThreshold.ScaleToDate` (the normalizer's proration, floored at one meter step, 1 kWh, and never above the annual figure, so a day or two of readings cannot be decided by rounding noise; `WindowedDeviationCalculator` calls it too); *below baseline* is still any shortfall and a tie is *within range*. `CurrentStatusResult.TrendingThresholdToDateKwh` and the detail response's `trendingThresholdToDateKwh` carry the figure that decided the Status; snapshots are never rewritten (AD-7).
- **Single deployment artifact (AD-13):** the `Api` project serves the built SPA from `wwwroot/` — don't introduce a separate static-hosting deployment path.
- **Operational baseline (AD-19):** `/health` is liveness-only (no DB check). Logging is structured (Serilog) to stdout/stderr only, no environment branching in logging code. Secrets only via env vars/Container Apps secrets/`.env` — never committed or baked into the image.

**React (frontend):**
- **i18n (AD-18):** `Household.Locale` is the single field driving both number/date formatting and UI language; translations are additive i18next catalogs in `web/src/locales/{locale}` — adding a locale is a resource-file addition, never a code change.
- **Offline queue (AD-16/stack):** Meter Reading creation only (not edits) queues locally via IndexedDB and flushes on reconnect — don't extend this offline pattern to other writes without a matching architecture decision. **A reading the server permanently refuses is kept, never deleted (Story 11.16, audit C4):** `flushQueue` marks a 4xx answer (except 401, 403, 408 and 429, which are transient like 5xx and a network failure) on the entry itself (`QueuedMeterReading.rejection`: status, the server's `detail`, a timestamp; no store or `DB_VERSION` change), skips marked entries from then on, and the Dashboard shows them in one quiet card under the Status card (`RejectedReadingsCard`, fed by `useRejectedReadings`, which re-reads on `QUEUE_CHANGED_EVENT`, dispatched after every committed write) until the member corrects and resends (`resendRejectedReading`: same `idempotencyKey`, it has no parameter for the key) or discards it. Entry and `rejection` are one read-modify-write in one transaction and a missing key is never created. `listPending()` returns every entry on purpose (logoff and leave count them, `removeForHousehold` deletes them); use `listNeedsAttention(householdId)` for the rejected ones.
- **Visual reordering must not reorder focus (WCAG 2.4.3):** `wide:order-*`, `flex-row` pairs and grids may only rearrange content so that Tab order still equals reading order. `web/e2e/tab-order.spec.ts` enforces this per surface. There are no exceptions: NavChrome's two placements (`top` first in `<main>`, `bottom` last) are mounted separately precisely so no CSS `order` is needed, and the spec guards it. Add any new reordered surface to that spec.
- **Breakpoint and column width have guarded copies:** `--breakpoint-wide` (index.css) is the breakpoint's source; `web/src/layout-constants.drift.test.ts` fails and names stale copies of the px-valued breakpoint (hook `WIDE_QUERY`, `min-width: Npx` stubs and assertions, e2e 600-699 literals) and of the column (`wide:max-w-[Cpx]` wrappers vs `app-shell.spec.ts` column assertions). To change the breakpoint, edit `--breakpoint-wide` first and let the test list the other copies; the column has no single source, so change all copies together. Other forms (rem, `max-width`, `min-[…]:` variants) are not scanned.
- **All HTTP goes through `web/src/lib/api-client.ts` (Story 11.8, AD-27):** `apiFetch` adds `credentials: 'include'` and the `X-Requested-With` header the API requires on every mutation; `ApiError` and `toApiError` live only there, with no re-exports and no per-feature copies. `FrontendUsesTheSharedApiClientTests` fails on a bare `fetch(`, a second `ApiError`/`toApiError` or `credentials: 'include'` anywhere else under `web/src`. `apiFetch` returns the raw `Response` and never throws on a non-2xx status; call sites branch on `status` themselves.
- Components follow the existing `web/src/components/{feature}` grouping (e.g. `household-invite`, `household-creation`, `tagging-scaffold`) plus a shared `components/ui` for shadcn primitives — new feature UI gets its own folder, not dumped into `components/ui`.

### Testing Rules

**.NET tests:**
- Test class per subject, named `{SubjectClass}Tests` (`CreateDeviceTests` for `CreateDevice`), one file per class, mirrored 1:1 into `{Layer}.Tests` (e.g. `EnergyTracker.Application` → `EnergyTracker.Application.Tests`).
- Test methods use `Snake_case_with_underscores` describing behavior (`Creates_and_persists_an_active_device_on_the_power_point`) — not `MethodName_Scenario_ExpectedResult` or camelCase.
- Assertions use **Shouldly** (`.ShouldBe(...)`, `Should.ThrowAsync<T>(...)`) — never raw xUnit `Assert.*`.
- Mocking uses **NSubstitute** (`Substitute.For<IPort>()`, `.Returns(...)`, `.Received(1)...`) against Application ports — never a hand-rolled fake/stub class.
- Async tests pass `TestContext.Current.CancellationToken` (xUnit v3 MTP convention) — not `CancellationToken.None` or `default`.
- Integration-level tests (migrations, DB-touching) use **Testcontainers** (real Postgres/SqlServer containers, not an in-memory EF provider) — AD-2's dual-provider portability can only be verified against real engines.
- **Database tests share one server per provider (spec-ci-pipeline-runtime-speedup).** A new Infrastructure or Api test class takes `PostgresTestDatabase` / `SqlServerTestDatabase` (`tests/Shared/SharedDatabaseServers.cs`, linked into both test projects, one shared Postgres/SQL Server container per test assembly); `IAsyncLifetime` on the class creates and drops one empty database on it, and the class still migrates itself. Never `new PostgreSqlBuilder(...)`/`new MsSqlBuilder(...)`, which starts a container per test method and was 9 of the 13 minutes of a deploy. The one exception is a test that creates a server-wide login (`...MinimalSqlServerPermissionsTests`). `TestsShareDatabaseServersTests` enforces it.
- `EnergyTracker.Architecture.Tests` encodes spine invariants as executable tests — when adding a new AD-style invariant, consider whether it belongs here as a guard test, not just as prose.

**Frontend tests:**
- Unit/component tests are colocated next to source (`color-scheme.test.ts` next to `color-scheme.ts`) — not a parallel `__tests__/` tree.
- Vitest + Testing Library (`@testing-library/react`), `jsdom` environment, globals on.
- E2E tests live in `web/e2e/*.spec.ts` via Playwright (`test:e2e`) — separate from the Vitest unit-test path (`test`/`test:watch`).

### Code Quality & Style Rules

**Naming:**
- Entities/DTOs: PascalCase C#, singular (`MeterReading`, never `MeterReadings`).
- API routes: kebab-case plural nouns (`/api/meter-readings`).
- Ports: `I{Capability}` in `Application/Ports`; adapters: `{Vendor}{Capability}` in `Infrastructure/Adapters`.

**Data & format rules (apply everywhere, not just at entity boundaries):**
- All timestamps are `DateTimeOffset`, ISO 8601 with explicit offset on the wire — never bare `DateTime`.
- All money is `decimal`, never `double`/`float`. Currency is an ISO 4217 code stored per Tariff entry.
- Background/scheduled work runs in UTC regardless of display Locale — locale only affects display, never storage.

**Errors:**
- API errors are RFC 7807 `ProblemDetails` — no ad hoc error shapes or bare status codes with a string body.
- Concurrency conflicts return HTTP 409 with the current server state (AD-4), not a generic 400/500.

**C# documentation:**
- Public use-case classes get a single-line `/// <summary>...</summary>` stating what they do and which acceptance criteria they satisfy (e.g. `Creates a Device on a Power Point in the caller's own Household (AC #1, #4).`) — not multi-line XML doc blocks or `<param>`/`<returns>` tags for straightforward cases.

**shadcn/ui config (`web/components.json`):**
- Style `radix-nova`, base color `neutral`, icon library `lucide`, no `tailwind.config` file (Tailwind v4 CSS-first config lives in `src/index.css`) — don't scaffold a `tailwind.config.js`/`.ts`.
- Aliases: `@/components`, `@/components/ui`, `@/lib`, `@/lib/utils`, `@/hooks` — prefer `npx shadcn add` over hand-writing primitives that already exist as shadcn components.

**oxlint (`web/.oxlintrc.json`):**
- `react/rules-of-hooks` and `no-unused-vars` are `error` (build-breaking); `react/only-export-components` is `warn` with `allowConstantExport: true`.

### Development Workflow Rules

**Git/commits:**
- Commit messages use a Conventional-Commits-style prefix (`feat:`, `fix:`, `doc:`) followed by a concise imperative summary.
- Branch naming: `feature/{short-description}` (e.g. `feature/otel-integration`).
- Commits/PRs frequently reference the AD number or story number they implement — carry that traceability forward when a change maps to a spine decision or story file.

**CI (`pr-review.yml`):**
- Runs on every PR against `main`: builds/tests/lints the .NET solution and web frontend; runs infra `what-if` only when `infra/**` changed and the PR isn't from a fork. Never deploys — deploys only happen from `app-deploy.yml`/`infra-deploy.yml` on push to `main`.
- **`app-deploy.yml` is four jobs (spec-ci-pipeline-runtime-speedup):** `frontend-tests`, `backend-tests` and `image-build` run in parallel and `deploy` needs all three. Only `deploy` logs in to Azure (job-level `id-token: write`, none at workflow level), migrates, pushes and rolls out; `image-build` builds with `push: false` and exports the Actions layer cache (`scope=app-image`) that `deploy`'s "Build and push image" reads via `cache-from`. `AppDeployWorkflowJobsGuardTests` pins the `needs` list and keeps Azure, secrets and `push: true` out of the other three; the preflight and restore-point guards read the steps of `deploy`. "Ensure ACR pull credential and target port" skips its two writes when the live app already has system identity for the registry and target port 8080.
- **Two Azure identities (Story 11.5, audit S11):** `pr-review.yml`'s `validate-infra` logs in as the read-only `energy-tracker-pr-reader-uami` (Reader plus the custom `Energy Tracker PR What-If` role, because Reader alone is denied the what-if call) (`AZURE_PR_CLIENT_ID`, `pull_request` credential, what-if with `--validation-level ProviderNoRbac`); the Owner-scoped deploy identity (`AZURE_CLIENT_ID`) is reachable only from `main`. Never give the PR identity a write or key-listing right; rights and probes are in `infra/README.md` ("Workflow identities and their permissions").
- **Preflight:** each Azure-authenticated workflow runs `Preflight: identity permissions` (`scripts/ci/azure-preflight.sh <mode>`) before any step that changes something; `WorkflowPreflightGuardTests` enforces the order.
- **Actions are pinned to a commit SHA with a `# vX.Y.Z` comment** (`WorkflowActionsArePinnedToCommitShaTests`). Dependabot GitHub Actions PRs are never auto-merged: read the SHA diff, merge by hand. CodeQL (`codeql.yml`) and the image scan (`container-scan.yml`) are separate workflows with no secrets and are not required checks.
- **Image (Story 11.11, audit S5):** the runtime stage runs as `USER $APP_UID` (the aspnet image's non-root `app`, 1654; the files stay root-owned, the process writes only `/tmp`), and the build stage copies `global.json` and `Directory.Build.props` before `dotnet restore`, so the NuGet-audit gate and the SDK pin apply to the shipped image. `DockerImageMatchesTheVerifiedBuildTests` guards both and fails on a later `USER root`/`USER 0`.
- **Registry retention (spec-acr-image-retention):** `acr-retention.yml` (Sundays 01:00 UTC, or by hand with a `dry_run` input) keeps the 7 newest `energy-tracker` images in the Basic ACR with `acr purge` as an ACR Task (the built-in retention policy is Premium-only). It runs as the deploy identity from `main` after the `retention` preflight, in its own concurrency group (not `infra-app-deploy`, whose single pending slot a purge could take from a queued deploy), refuses to run when the running image is not among the 7 newest tags, and sweeps orphaned manifests only when older than an hour. Never `continue-on-error` it, never add a `push`/`pull_request` trigger, never `--include-locked`; `AcrRetentionWorkflowGuardTests` enforces this. A rollback target must be one of the last 7 images.
- **Node:** CI's `node-version` must match the Dockerfile's frontend stage (`node:26-alpine`); change both together. The vitest config turns off Node's built-in `localStorage` (`--no-experimental-webstorage`) because it shadows jsdom's.
- `npm audit --omit=dev --audit-level=moderate` gates `build-test-lint` like the NuGet Audit gate below.
- The `build-test-lint` job has **no `name:` override** — GitHub branch protection matches required status checks by job id, not display name.
- Workflow-level `concurrency` cancels in-progress runs on new pushes to the same PR.
- **NuGet Audit gate (`Directory.Build.props`):** `NuGetAuditMode=all` + `NuGetAuditLevel=moderate` + `NU1902`–`NU1904` in `WarningsAsErrors` — a moderate-or-worse advisory on a direct **or transitive** package fails `dotnet restore` (the `build-test-lint` job's first step), not just warns. Don't suppress an NU190x code to unblock a PR — bump/replace the offending package (see `spec-nuget-audit-ci-gate.md`, `spec-ssh-net-cve-fix.md`).

**`_bmad-artifacts/implementation/deferred-work.md` convention:**
- **Append new sections at the end of the file, in chronological order (oldest first, newest last).** Never insert at the top. This matches what the `bmad-code-review` skill does, and the Epic 8 retro found that mixed insertion order (newest-first sections interleaved with appended ones) was a main reason the file became hard to read (519 lines, ~58 sections). Each section keeps the heading `## Deferred from: code review of <story-or-spec> (<YYYY-MM-DD>)`. Traces to the Epic 8 retro (2026-10-02, Action #5).
- **Every entry starts with a status marker:** `[open]`, `[resolved: <story-or-spec>]`, or `[accepted: <reason, plus revisit trigger if any>]` (`[promoted: needs story]` while a promoted item has no story yet). New entries are written `[open]`. When an entry is resolved or accepted, move it out of `deferred-work.md` (resolved: delete; accepted: move to `deferred-work-accepted.md`) instead of leaving it. Review the open items, and the themed index at the top of the file, at each epic retro. Traces to the Epic 8 retro (2026-10-02, Action #7); the 2026-10-02 triage (`spec-deferred-work-triage.md`) established the two-file split.

**Migrations:**
- Always add migrations via `scripts/add-migration.sh <Name>` — never `dotnet ef migrations add` directly against one provider project (AD-2).
- **Expand/contract:** a migration must be safe for the **previous** application image to run against. `app-deploy.yml` migrates before deploying, and its health-check rollback redeploys the previous image against the already-migrated schema; a failed multi-migration run can also stop partway. Destructive changes (drop/rename column or table, narrowing `AlterColumn`, new NOT NULL without default) ship in a **later** deploy than the code that stops using the old shape.
- Rollback is a point-in-time restore, not `Down()`: every deploy writes a "Pre-migration restore point" block to the Actions run summary; the procedure is `infra/README.md` → "Rolling back a bad migration".

**Local dev scripts (`scripts/`):** `run-api.sh`, `migrate.sh`, `add-migration.sh` — prefer these over raw `dotnet run`/`dotnet ef` invocations; they encode required env vars and provider wiring documented in `docs/local-development.md`.

### Critical Don't-Miss Rules

**Process gates (hard, no exceptions):**
- **No fix to already-shipped code merges without a linked spec/story doc, regardless of size or urgency.** Write at least a minimal `spec-*.md` (or story stub) before or as part of the fix — never skip it because the fix is trivial or there's incident pressure, since that's exactly the condition under which it's been skipped before. Hard gate at PR merge, no exceptions. Traces to the 2026-09-11 Epic 4 retro (PR #40/#41 shipped production-surfaced integration fixes with zero spec/story trail); recurred at smaller scale afterward (`1b1960c`, `ee178cc`, `b40902a` — CI/test-flakiness fixes merged straight to `main` with no linked spec).
- **A story touching OIDC claims, auth flows, or any other browser-dependent behavior cannot move review→done without live Auth0/Chrome verification actually performed.** If Chrome isn't available, the story stays blocked in review — never mark the live-verification task complete on the strength of a unit/component test alone. Raise a "not connected" Claude-in-Chrome extension immediately and pause for the user to start/connect it, then resume — don't silently defer the check and let code review catch the gap after the fact (Epic 6 Retro Action Item #1 sharpened this to a dev-story-time gate after Story 6.2's Task 7 got checked off without an actual live run for AC #5, caught only in review). Traces to the 2026-09-11 Epic 4 retro (3.5/3.6/4.1/4.2 all deferred live verification with no follow-up; the one time it was checked, 3.6, it found a real live-broken bug — `ClaimTypes.Name` never populates against this app's Auth0 config — that automated tests couldn't catch). Held without exception since: 6.1/6.2/6.3, 7.1, and 7.2 each performed a genuine live Auth0/Chrome session before reaching `done`.
- **Live-resize verification procedure (breakpoint/layout checks, e.g. the 660px `wide:` breakpoint).** In the Claude-in-Chrome sandbox, `resize_window` on an already-navigated tab does **not** change the real `window.innerWidth` (Stories 8.1/8.2/8.6/8.7), and some sessions clamp the window to a hard floor (8.3: exactly 660px, which coincides with this app's breakpoint). Follow this order — don't rediscover it:
  1. Close prior tabs, then `tabs_create_mcp` a **fresh** tab (tabs in a group share one window/viewport, so a stale tab skews the measurement).
  2. `resize_window` that new tab to the target width **before its first `navigate`**, then navigate to the app. Resizing after navigation, or re-navigating after a second resize, has no effect.
  3. **Confirm the width, don't assume it:** read `window.innerWidth` via `javascript_tool` and require it to equal the target. Measure with `getBoundingClientRect()`/`getComputedStyle()` rather than eyeballing a screenshot. **For checks that need real key presses (Tab order, focus, shortcuts):** take a `screenshot` first — key presses only reach the page after a screenshot call has focused it, and a plain `Tab` right after `navigate` registers no stops (Story 10.3). Then press the keys and read `document.activeElement` after each one.
  4. Cover both sides of each breakpoint with one tab per width (e.g. 500px, 659px, 660px, 1000px). If a 659px request reads back 660px, that is the clamp floor — it is **not** a 659px check. The usual cause is a stale tab still open in the same window (it clamps every tab's width to 659/660, whatever the target): close all other tabs in the window, create a fresh tab and redo the resize-then-navigate order. If it still reads back 659/660, retry in a fresh tab group or ask the user. Readings of exactly 659 or 660 for *other* targets (e.g. 500 or 1000) mean the same stale-tab clamp — don't record them as passes.
  5. An in-tab resize across the breakpoint without reload (live `matchMedia` `change` swap) can't be driven by automation — **ask the user to resize the real window** and record what they observe. Don't skip it.
  6. **Not acceptable substitutes** for the live-check task: a Playwright `setViewportSize()` spec (keep it as the regression guard, but it doesn't satisfy the gate), a same-origin iframe (media-query `change` events don't fire; 8.12), or a check that silently landed on a different width. A substitute stays blocked in review unless the user explicitly accepts it in review and the acceptance is recorded in the story (8.12: Ralf accepted iframe evidence on 2026-09-30).
  Traces to the Epic 8 retro (2026-10-02, Action #4): the live-verification step was substituted or partial in 6 of 12 stories (8.1, 8.2, 8.3, 8.6, 8.10, 8.12), each caught only in review.
- **Amend ACs at decision time.** When an Ask First or review decision changes, adds or removes an Acceptance Criterion, edit the AC in the story file in the same session and mark it `AMENDED <date, decision>` (who decided, one clause on what changed). Keep the old text visible as `~~struck through~~` right after the new text; a new AC gets `AMENDED <date, decision> (added)`. A header HTML comment or Dev Notes remark alone does not count, because the ACs are what dev-story, review and the Acceptance Auditor read. If the change also revises another story's AC or an AD, mark that source too (a one-line `AMENDED` note on the old text pointing at the new story). Create-story changes that only add implied requirements stay labelled "implied requirement", not `AMENDED`. Traces to the Epic 10 retro (2026-10-10, Action #1): Ask First and review decisions had changed ACs without leaving a trail in the AC text.

**Anti-patterns to avoid (each traces to a real architecture decision — see `_bmad-artifacts/planning/architecture/architecture-energy-tracker-2026-08-09/ARCHITECTURE-SPINE/invariants-rules.md`):**
- **Don't reimplement Bonus-Decay Normalization (AD-5):** the pace/savings formula shared by Pattern Detective and Tariff Savings Radar lives in exactly one place, `Domain.Calculations.BonusDecayNormalizer` — never a locally-adjusted copy in a feature.
- **Don't hard-branch on AI availability (AD-8):** `IAiPlausibilityClient` resolves to a no-op when unconfigured — features must not check "is AI enabled" and take a different code path; the correlation field is simply absent from the response.
- **Don't parse smart-plug files outside `ISmartPlugParser` (AD-9):** one port, one adapter per vendor (`EveHomeXlsxParser`, `MerossCsvParser`). Eve Home timestamps are parsed as **local time, never UTC-converted** — deliberate, documented behavior, not a bug to fix. Meross device identity comes from the filename pattern, not file-body metadata.
- **Don't hard-delete or live-FK-join Room/PowerPoint/Device (AD-10):** they're soft-deleted (`ArchivedAt`). `SmartPlugReading`/`Event` snapshot the Room/PowerPoint/Device identity **by value** at write time — a live FK join would incorrectly rewrite history when a Power Point's Room assignment changes later.
- **Don't build a bespoke "keep the old value" column per entity (AD-11):** all correction audit trails go through the single `AuditCorrection` table + `IAuditCorrectionRecorder`. Carve-out: FR-23's full-dataset restore is a wholesale replace, not an edit, and does not go through this mechanism.
- **Don't allow two open regression prompts per Main Meter (AD-12):** at most one open `MeterRegressionPrompt` at a time, ordered by reading timestamp (not entry order).

**Edge cases agents should handle:**
- An open `MeterRegressionPrompt` excludes its triggering reading (and everything chronologically after it) from baseline computation until resolved.
- Job envelopes must be plain JSON-serializable records — a delegate/closure payload works against `InProcessChannelJobQueue` but silently fails to serialize on `AzureStorageQueueJobQueue`.
- **Multi-field edits:** capture every "old" field value into a local *before* calling the repository's write/update method, not just the first field touched. EF Core's identity map can return the same tracked entity instance across a `FindByIdAsync`-then-`UpdateAsync` call pair, so reading a field's "old" value after the write already reflects the new value (silently records `OldValue == NewValue` in an `AuditCorrection` row). Only a real-`DbContext` test (not an NSubstitute-mocked one) can catch this — found in Story 5.1's `EditTariff`.
- **"Lock field X unless condition Y" gates:** explicitly test whether the gate can be bypassed by editing a *different* field in the same or a sequential request, not just the field the lock is nominally about. Found in Story 5.1: pairing a `ContractStartDate` change with a price-field edit in one request let the override gate evaluate against the stale pre-edit date.

**Security:**
- Every route requires authentication except the OIDC callback — don't add an unauthenticated endpoint without an explicit, reviewed reason.
- Never store an auth token client-side (`localStorage`/`sessionStorage`/JS-readable cookie) — enforced by `FrontendDoesNotStoreAuthTokensTests`. The sole, allowlisted exception is the per-device theme preference (`'light'`/`'dark'`, FR-35) in `web/src/lib/color-scheme.ts` (+ its test); `web/public/theme-init.js` (the pre-paint copy, Story 11.7) isn't scanned (guard covers only `.ts`/`.tsx` under `web/src`), and `color-scheme.test.ts` runs it to keep it in sync. Session state lives only in the httpOnly cookie.
- Logout is a `fetch` `POST /logout` (with the CSRF header) that clears the cookie and answers `200 { redirectUrl }`; the SPA navigates to that URL. A form POST answered with a 302 to the identity provider would be blocked by the CSP's `form-action 'self'`, so the CSP is not widened. The OIDC sign-out event (`FederatedLogout.cs`) must keep protecting `State`, or the provider's confirmation lands on a blank page.
- Secrets (DB connection string, OIDC client secret, AI API key) come only from env vars/Container Apps secrets/`.env` — never committed, never baked into the image.
- Never log, print or paste Data Protection key XML (`DataProtectionKeys.Xml`); check key rows with counts only. Outside Development or the explicit opt-out no row may contain `<masterKey` (revoked pre-cutover rows excepted until deleted). Key Vault role: Key Vault Crypto Service Encryption User on the key only, never the vault (guarded by `DataProtectionKeyVaultInfraTests`).

**Performance/operational gotchas:**
- `/health` must stay liveness-only (no DB/dependency check) — adding one risks a restart loop when Postgres/Azure SQL is briefly slow, since Container Apps' probe would fail and cycle the container.
- OTel logging (`Otel:Exporter=AzureMonitor`) deliberately does not forward logs to Application Insights in Azure — only traces + metrics — because Application Insights shares the same Log Analytics workspace/quota that stdout logging already streams into; a second log path would double-ingest against the shared daily cap.
- Check `docs/local-vs-azure-deltas.md` before touching auth, ingress, the database provider, or the deploy pipeline — local dev/self-host and Azure structurally diverge (TLS termination, ACR/managed-identity credential timing, region provisioning, blank-env-var handling) in ways that only surface on a live Azure deployment.
