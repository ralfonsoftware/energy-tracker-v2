# Story 5.1: Tariff Configuration

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Household member,
I want to maintain my Household's current Tariff,
so that the app always knows my real electricity contract terms.

## Scope Reality Check — Read This First

This is the **first story in Epic 5** and the **first backend/frontend code for Tariff anything** — there is no existing `Tariff` entity, repository, use case, endpoint, or frontend surface today. `nav-chrome.tsx` already renders a **disabled placeholder** tab for "Tariff Radar" (`<div role="button" aria-disabled="true">`, see its own comment: *"only Tariff Radar doesn't have a surface yet (Epic 5)"*) — this story is what turns that into a real, clickable destination.

**Do not build Stories 5.2/5.3/5.4's features here.** Epic 5's header binds AD-5 (`BonusDecayNormalizer`) and AD-7 (request-time Reminder computation) to the whole epic, but neither belongs to this story:
- AD-5 (Bonus-Decay Normalization) is Story 5.2's candidate-comparison math. This story has no candidate tariff, no savings projection, no Pattern Detective pace lookup.
- AD-7's Reminder due-ness computation is Story 5.4. This story does not add a Tariff Check prompt, cadence, or reminder gate.

This story is scoped to exactly FR-10: enter/maintain the Household's current Tariff, retain history, lock past-dated price fields behind an explicit override, flat-rate-only modeling, required non-EUR-hardcoded currency, audit-trailed corrections, and 409-on-concurrent-edit.

The `key-tariff-radar.html` mockup ([mockups/key-tariff-radar.html](../planning/ux-designs/ux-energy-tracker-2026-08-08/mockups/key-tariff-radar.html)) only shows a **read-only** "Your current tariff" summary (field-rows: Base fee, Price per kWh, Contract started) as part of the *comparison card* — that's Story 5.2/5.3's UI, reused here only as a rendering reference for the summary rows. **No mockup exists for the actual Tariff Configuration entry/edit form** (the create form, the history list, the locked-field override step). Follow the nearest already-shipped analogous pattern instead of inventing new visual language — see Dev Notes' "Closest existing analogs" below. This mirrors `edit-meter-reading-dialog.tsx`'s own documented precedent for the exact same situation ("no mockup exists for this story (added post-UX-freeze)").

## Acceptance Criteria

(Sourced from `_bmad-artifacts/planning/epics/epic-5-tariff-savings-radar.md`, Story 5.1 block, lines 10-44.)

1. **Given** the Tariff Configuration surface, **when** I enter base fee, price/kWh, currency, contract start date, and Contract Period, **then** the entry is saved as the Household's current Tariff (FR-10).
2. **Given** an existing Tariff entry, with a new Tariff entry later added, **when** the new entry's start date arrives, **then** history is retained — each entry covers until the next one's start date, never overwritten (FR-10).
3. **Given** a Tariff entry whose contract start date has passed, **when** I try to edit its price fields, **then** they are locked, requiring an explicit override step rather than a silent overwrite (FR-10).
4. **Given** Tariff Configuration, **when** modeled, **then** it supports only a flat base-fee-plus-price/kWh structure — tiered/time-of-use billing is out of scope (FR-10).
5. **Given** a Tariff entry, **when** saved, **then** currency is a required field, never hardcoded to EUR, and displays as a fixed-decimal value, never floating-point (FR-10, NFR6).
6. **Given** an existing Tariff entry, **when** I edit its value, **then** the original value is preserved and shown as a visible correction note, never silently overwritten, via the shared `AuditCorrection` mechanism (NFR8, AD-11).
7. **Given** two Household members editing the same Tariff entry concurrently, **when** both submit, **then** the second writer receives a 409 conflict rather than silently overwriting the first (AD-4, NFR10).

## Dev Notes

- **Currency: its own column per Tariff entry, not a reuse of `Household.Currency`.** There's a real tension in the source docs worth naming explicitly so it isn't rediscovered mid-implementation: `cross-cutting-nfrs.md`'s NFR6 bullet says "*Currency is a Household-level configurable field (FR-10)*," which reads like it means reuse the existing `Household.Currency` (already implemented, set at household creation, exposed via `/api/session` and `/api/households/{id}`). But `consistency-conventions.md`'s Data & Formats row is unambiguous and more specific: **"Currency: ISO 4217 code stored per Tariff entry."** The ERD in `structural-seed.md` also models `Tariff` as its own entity under `Household ||--o{ Tariff : "history of"` with no shared-currency annotation. Epic 5's own AC #1/#5 list "currency" as one of the fields entered *per Tariff entry*, alongside base fee/price/kWh/dates — not a household-wide setting. **Go with `consistency-conventions.md`: `Tariff.Currency` is its own required column.** `Household.Currency` is unrelated and untouched by this story.
- **`ContractStartDate` is `DateTimeOffset`, not `DateOnly`.** It's conceptually a date-only value, which makes `DateOnly` tempting — but AD-2's portable relational subset (the only types allowed so Postgres/SQL Server store identically) is `string`/`int`/`decimal`/`DateTimeOffset`/`bool`/`byte[]`/standard LINQ. `DateOnly` isn't on that list and nothing in this codebase uses it. Follow `MeterReading.ReadingTimestamp`'s precedent instead.
- **Price/kWh precision is `(18, 4)`, deliberately different from every other decimal column in this codebase.** Every existing `decimal` column (`MeterReading.KwhValue`, `Household.YearlyBaselineKwh`, `Household.TrendingThresholdKwh`, `StatusSnapshot`'s two decimals) uses `HasPrecision(18, 2)`. `Tariff.PricePerKwh` is the one exception — copy-pasting `(18, 2)` here would truncate the 4-decimal-place tariff pricing the mockup itself displays (`€0.3200`).
- **Closest existing analogs to build from — read these completely before writing new code, don't reinvent:**
  - `EditMeterReading.cs` + `MeterReadingRepository.UpdateKwhValueAsync` (`src/EnergyTracker.Infrastructure/Adapters/MeterReadingRepository.cs:153`) — the exact AD-4 + AD-11 combination (`OriginalValue` set before save, `Version++`, catch `DbUpdateConcurrencyException`, wrap the value-update + one audit-correction write in `IUnitOfWork.ExecuteInTransactionAsync`, no-op-skip discipline) that `EditTariff` needs to replicate.
  - `MeterReadingEndpoints.cs` — endpoint shape, exception-to-status-code mapping, the `TryGetHouseholdId` copy-per-file convention, and the 409-is-message-only-body precedent.
  - `yearly-baseline-form.tsx` + `edit-meter-reading-dialog.tsx` — the only two existing frontend examples of "load current value, submit, handle a 409 by refetching and requiring resubmission against the fresh Version, never auto-retry." Both are directly reusable shape templates for `tariff-configuration-form.tsx`/`edit-tariff-dialog.tsx`.
  - `GetMeterReadingHistory.cs` — the paginated-list-plus-batched-correction-lookup shape `GetTariffHistory.cs` should copy.
  - `AuditCorrectionRecorder.cs` + `AuditCorrection.cs` — already carries a comment anticipating this exact story: *"a future Tariff-editing story is expected to reuse this unmodified."* Reuse the table and `RecordAsync` unmodified; only `GetLatestForEntitiesAsync`'s multi-field limitation (Task 4) might need an additive extension.
- **No mockup exists for the Configuration form itself** — see "Scope Reality Check" above. Don't wait on or request new UX mockups for this story; build against the closest shipped analogs instead, same call `edit-meter-reading-dialog.tsx` made for its own no-mockup situation.
- **Recent commit pattern (story 3.10, `2386600`/`08e5f36`):** this codebase's most recent code-review round added an explicit transaction around a multi-step delete specifically because a "this story's operation materially widened a pre-existing untransacted gap's blast radius" — the general lesson for this story is the same discipline already designed into Task 3: every multi-write path (repository update + N audit-correction writes) must be one `IUnitOfWork.ExecuteInTransactionAsync` call, never sequential unwrapped writes.
- **What this story explicitly does NOT touch:** `Domain.Calculations.BonusDecayNormalizer` (doesn't exist yet — Story 5.2 creates it), any Reminder/cadence logic, any candidate-tariff or comparison concept, `IStatusRecomputeService` (Tariff edits don't affect Status/pace).

## Review Findings

- [x] [Review][Patch] No uniqueness/overlap guard for two Tariff entries sharing the same `ContractStartDate` — `CreateTariff.ExecuteAsync` must reject a new entry whose `ContractStartDate` matches an existing entry for the household (400/`TariffValidationException`). Decision: reject outright (user-selected). [src/EnergyTracker.Application/CreateTariff.cs]
- [x] [Review][Patch] Server-side locked-price-field override (AC #3, resolved as server-enforced) can be bypassed by pairing a `ContractStartDate` change with a price-field change in the same or a follow-up edit — `EditTariff.ExecuteAsync` computes `isLocked` from `tariff.ContractStartDate` (the pre-edit value) even when `changedContractStartDate` is true in the same request, and a `ContractStartDate`-only edit is never itself gated by the override check. Two exploit paths: (1) one request that simultaneously moves the date into the past and edits price, evaluated against the still-future old date; (2) two sequential requests — first move the date to the future (ungated, not a price field), then edit price freely since it now reads as unlocked. Recommended fix: require `overrideConfirmed` whenever `changedContractStartDate` is true and either the old or the new `ContractStartDate` is `<= now`, in addition to the existing price-field gate. [src/EnergyTracker.Application/EditTariff.cs:89-94]
- [x] [Review][Patch] Tariff amounts in the history list drop trailing zeros, contradicting AC #5's "displays as a fixed-decimal value, never floating-point" — `Intl.NumberFormat(locale, { maximumFractionDigits: 4 })` has no `minimumFractionDigits`, so `12.50` renders as `12.5` and `0.3200` as `0.32` (locked in by the colocated test asserting `'12.5 EUR'`). [web/src/components/tariff/tariff-history-list.tsx:58]
- [x] [Review][Patch] `EditTariffDialog` never exposes editing/correcting `ContractStartDate`, even though the resolved Open Question #2 explicitly puts multi-field edits (including this field, one of Tariff's five independently-correctable fields) in scope, and the backend/port/i18n support for it is fully built. A Tariff entry's start date can never be corrected through the UI today. [web/src/components/tariff/edit-tariff-dialog.tsx]
- [x] [Review][Patch] Correction notes shown in the history list aren't parsed/locale-formatted despite `TariffFieldCorrectionResponse`'s own doc comment promising "the frontend parses/formats per field type and the household's own Locale (AD-18)" — `formatCorrection` interpolates the raw invariant-culture string directly, so a `ContractStartDate` correction shows a raw ISO-8601 timestamp (e.g. `2026-01-15T00:00:00.0000000+00:00`) and decimal corrections ignore the household's locale decimal separator. - [x] [Review][Patch] `ContractStartDate` has no validation on Create or Edit, unlike every other field in this story — a raw request omitting it from the JSON body binds to `default(DateTimeOffset)` (0001-01-01) and is accepted as a valid, immediately-"current" Tariff entry with no bound check.
