# Story 1.12: Logoff / Account Switching

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Household member,
I want a dedicated, always-reachable logoff control that fully signs me out — including at the identity provider,
so that I can switch accounts on a shared device without the OIDC provider silently re-authenticating whoever was logged in before.

*(added 2026-09-17, new FR-33 — epic 1 was previously "done"; this is a late addition, not a gap in earlier work.)*

## Acceptance Criteria

1. **Given** an authenticated Household member on any screen of the app, **when** they look for a way to log off, **then** the control is reachable directly, not buried behind multiple navigation steps — logoff is a routine action on shared/multi-account devices, not a rare edge case (FR-33).
2. **Given** a Household member triggers logoff, **when** the configured OIDC provider supports RP-initiated logout (`end_session_endpoint`), **then** the app clears its own server-side session cookie *and* redirects through the provider's `end_session_endpoint`, ending the provider's session too, before returning the member to the login step — a subsequent login is not silently completed by a still-active provider session (FR-33, AD-17).
3. **Given** a Household member triggers logoff, **when** the configured OIDC provider does not advertise/support RP-initiated logout, **then** the app falls back to clearing only its own local session cookie, and the member is shown a clear warning that they may still be signed in at the identity provider (FR-33).
4. **Given** unsynced Meter Readings queued locally in IndexedDB (AD-16's offline queue) at the moment logoff is triggered, **when** logoff proceeds, **then** the app either flushes them to the server first (if connectivity allows) or explicitly surfaces them to the member before completing logoff — they are never silently discarded or carried over to attribute against whichever Household the next logged-in account belongs to (FR-33).
5. **Given** the session cookie itself, **when** logoff completes, **then** no token or session artifact readable by the SPA is ever exposed in the process — the browser only ever held the httpOnly session cookie, cleared via the framework's `SignOutAsync` (not a bespoke client-side-only delete). This app's cookie auth is self-contained/stateless (Data Protection-encrypted claims, no server-side session-ID store) — `SignOutAsync` deleting the cookie *is* the complete, correct invalidation mechanism; there is no separate server-side revocation list to build (confirmed with Winston, AD-17 architecture consult, 2026-09-17).
6. **Given** a member who has just logged off, **when** the redirect completes, **then** they land on the login step ready to authenticate again (as the same or a different account), never a broken or blank page.

## Dev Notes

- **Most of the hard backend plumbing for this story already exists**, built as part of Story 1.5's original OIDC setup — this is not a greenfield auth story. `AuthEndpoints.cs`'s `/logout` already does the two-scheme `Results.SignOut` with `oidcConfigured` branching; `Program.cs` already wires cookie + OIDC auth, `OnRedirectToIdentityProviderForSignOut` (sets `ClientId` on the end-session request, required for Auth0 to resolve which app is signing out without `id_token_hint`), `PersistKeysToDbContext`, and the `ForwardedHeadersOptions` fix from Story 1.7. **Do not rebuild any of this.** This story's real net-new surface is: (1) a frontend signal for whether federated logout is available, (2) the frontend control itself (doesn't exist anywhere yet — checked, no logoff/logout UI in any component), (3) the offline-queue pre-logoff check, and (4) closing the loop on AC #6's landing behavior.
- **AD-17's FR-33 extension** (`_bmad-artifacts/planning/architecture/architecture-energy-tracker-2026-08-09/ARCHITECTURE-SPINE/invariants-rules.md`, "AD-17" section) is the authoritative architecture decision for this story and directly resolves several ACs as "no backend change needed" — read it in full before starting Task 1/2, it pre-answers most of the "how should this work" questions, including the corrected AC #5 wording (originally drafted by John as "invalidated server-side," corrected by Winston to reflect this app has no server-side revocation store — `SignOutAsync` deleting the cookie is already complete and correct).

- **Auth0 discovery/logout-consent research (done during story creation, not previously documented anywhere in this repo):** Auth0 implements OpenID Connect RP-Initiated Logout 1.0 and does expose `end_session_endpoint` in `/.well-known/openid-configuration` when the tenant/app is configured for it — so AC #2's happy path is realistically testable against the real dev tenant (Task 7). Auth0 shows a logout-consent interstitial when neither `id_token_hint` nor `logout_hint` accompanies the end-session request, which is exactly this app's situation given `SaveTokens = false`. This is expected framework/provider interaction, not a defect — see Task 7 for how to treat it during live verification. - **AD-19's known local-vs-Azure deltas** (`docs/local-vs-azure-deltas.md`) doesn't have a dedicated section for logout specifically, but D1 (forwarded headers/HTTPS termination, the same class of bug Story 1.7 fixed for `/login`'s `redirect_uri`) applies equally to whatever URL the OIDC handler builds for `post_logout_redirect_uri` on the end-session request — if the live Azure verification (post-deploy, not this session) shows a scheme mismatch there, it's the same root cause as Story 1.7, already fixed generically at the `ForwardedHeadersOptions` level, not a new bug to chase.
- **Consistency Conventions still apply, unchanged:** `Oidc:*` config is still read exactly once at the composition root (`Program.cs`) — this story adds no new config reads or environment branching. No new `ProblemDetails` shape needed — `/api/session`'s existing plain `Results.Ok(...)` pattern is sufficient for the new boolean field.
