## Story

As a household member,
I want state-changing requests to come only from the app itself, and sessions to expire eventually,
so that a hostile site can't act as me, and a stolen cookie doesn't live forever (audit S9, S13).

## Acceptance Criteria

1. **Given** any `/api` POST, PUT, PATCH or DELETE (including multipart uploads) without an `X-Requested-With` header, **when** it arrives, **then** it is rejected with 400 ProblemDetails by one endpoint filter on the `/api` group (AD-27).
2. **Given** the frontend, **when** this story is done, **then** one shared `web/src/lib/api-client.ts` (credentials, the CSRF header, `ApiError`/`toApiError`) replaces the ~10 per-feature copies (audit R2, web side).
3. **Given** logout, **when** the member signs out, **then** it is a POST. FR-33 behaviour is preserved, including draining the offline queue first and the end-session warning.
4. **Given** the cookie handler, **when** a session is issued, **then** the 14-day sliding expiration is explicit, and a 90-day absolute cap based on an issued-at value in the ticket rejects older sessions (AD-17).
5. **Implied (the epic says "it is a POST" but not how the browser follows it; Story 11.7's deferred note makes this a hard requirement):** logout is a `fetch` POST made through the shared client, not a `<form method="post">`. The production CSP has `form-action 'self'` and Chrome enforces it on the redirect that follows a form submission, so a form POST that is answered with a 302 to the Auth0 end-session URL can be blocked. `POST /logout` therefore answers **200 `application/json` `{ "redirectUrl": "<string>" }`** and the SPA sets `window.location` to that URL. The CSP is **not** widened. The URL is the one the OIDC handler builds (end-session endpoint, `client_id`, `post_logout_redirect_uri`, protected `state`), or `/` when there is nothing to redirect to (OIDC unconfigured, or a provider with no `end_session_endpoint`). The auth cookie is cleared on the same response.
6. **Implied (a logout that any other site can trigger is the part of S9 that was actually exploitable):** `POST /logout` requires the same `X-Requested-With` header and answers the same 400 ProblemDetails without it. `GET /logout` is removed: it no longer signs anyone out. `/logout` stays outside `/api`, unauthenticated and unthrottled (it must work when the cookie has already expired, and with OIDC unconfigured).
7. **Implied (AC #1 is untestable without a guard, and a new mutation route must not ship unprotected):** a guard test asserts, on the real endpoint data source, that every POST/PUT/PATCH/DELETE route under `/api`, plus `POST /logout`, carries the filter's marker metadata. Behaviour tests prove a header-less request is rejected for a JSON POST, a no-body DELETE, a no-body POST and a multipart upload, with the handler not having run.
8. **Implied (AC #2 is a refactor with no behaviour change, so it needs a guard to stay true):** an architecture test fails when any non-test file under `web/src` other than `lib/api-client.ts` calls `fetch(`, declares `class ApiError` or `toApiError`, or spells `credentials: 'include'`. Every existing call site moves to the shared client with its behaviour (status branching, `AbortSignal` use, multipart bodies, the offline queue's timeout and 401/403 handling) unchanged.
9. **AMENDED 2026-10-17, Ralf's decision at create-story review (Q2): unstamped cookies are rejected, not grandfathered.** A cookie that carries no issued-at stamp, including every cookie issued before this ships, is rejected and signed out, so each member signs in once after the deploy. A stamp that cannot be parsed is rejected as well (fail closed). The cap is checked on every request that presents the cookie, including `/api` calls made after the sliding renewal. Accepted consequence: while an old and a new revision overlap during a deploy or a rollback, a sign-in handled by the old revision yields an unstamped cookie that the new revision rejects, so a member may be sent through `/login` again until the overlap ends (Ralf is the only user).
   ~~**Implied (the cap needs rules for cookies that already exist and for the rollout):** a cookie issued before this ships has no issued-at stamp. It is **not** rejected: it is stamped "now" on its next request and kept (its 90 days start at the first request after deploy), so a rolling deploy or a rollback to the previous image never causes a sign-in loop. A stamp that cannot be parsed is rejected (fail closed). The cap is checked on every request that presents the cookie, including `/api` calls made after the sliding renewal.~~
10. **Implied (a failed logout must never look like a successful one):** if the POST fails (offline, 5xx, non-JSON), the dialog stays open with an inline error in de-DE and en-US, the member can retry or cancel, and the member is not navigated anywhere. The buttons that start the POST are disabled while it is in flight.
11. **Implied (docs that would otherwise go stale):** `_bmad-artifacts/project-context.md` ("Auth (AD-17)", "HTTP hardening (AD-27)", a new frontend rule for the shared client, the "Security" bullets, Last Updated), the AD-27 CSRF bullet in `ARCHITECTURE-SPINE/invariants-rules.md` (logout is a fetch POST returning the end-session URL, and why), `docs/self-hosting.md` (a 90-day maximum session; any script that calls the API must send `X-Requested-With`), `docs/local-development.md` (only the `/logout` sentence if it still says GET), and `deferred-work.md` (resolve the 11.7 entry for this story, add the new ones).

### What this fixes and why it is safe to change

- **S9 (Low, verified):** CSRF defence is `SameSite=Lax` alone, and `GET /logout` signs the user out and bounces them through the identity provider, so any page can log a member out with an `<img src="/logout">`. After this story a cross-site request cannot carry the custom header (no CORS is configured, so there is no preflight approval), and logout is a POST that also needs it.
- **S13 (Low, verified):** the cookie uses the framework's 14-day sliding default with no absolute limit, so a stolen cookie that keeps being used never dies. After this story: explicit 14-day sliding plus a 90-day absolute cap stamped into the ticket.
- **R2, web side:** `ApiError`, `toApiError` and `fetch(..., { credentials: 'include' })` are repeated in ~20 files today (the audit said ~10). One module makes the CSRF header a one-place change and makes 11.9's new calls correct by default.

### Technical details the dev must get right

- **`Results.SignOut` is gone from `/logout`.** It makes the handler write the 302. Use `HttpContext.SignOutAsync` twice and return your own `Results.Ok`. Order matters: sign the cookie scheme out first so its `Set-Cookie` is on the response before anything else touches it.
- **State protection (3.3b) is the easy thing to forget** and the failure is silent in unit tests that only check the URL: the provider redirects back to `/signout-callback-oidc?state=...`; with no `state`, the handler returns `true` without a redirect and the member sees an empty page. The 1.5(a) test must unprotect the state; the live check (8.2c, R2c) must land on the sign-in step.
- **`HandleResponse()` and `HttpContext.Items`:** the event runs inside `SignOutAsync` on the same request, so `Items` is the simplest hand-off; use one constant key. Do not write the response body from inside the event, the endpoint owns the response (a second write would throw).
- **Do not log the URL.** It carries `state` and `client_id`; log nothing from it.
- **Safe navigation target (6.1):** the server value is trusted but the client still checks it: `new URL(value, window.location.origin)` and require `protocol` to be `http:` or `https:`; a leading `//` is protocol-relative and resolves to another origin, so a value starting with `//` becomes `/`. For same-origin results prefer `pathname + search + hash` so the test can assert `/`.
- **`apiFetch` and `Headers`:** `new Headers(init.headers)` accepts a plain object, a tuple array or a `Headers`. In jsdom/Vitest the global `fetch` is stubbed, so assertions read `fetchMock.mock.calls[0][1].headers` as a `Headers` instance (`.get('X-Requested-With')`), not as a plain object; update the three tests that assumed plain objects.
- **Clock in tests:** `SessionLifetime` takes `TimeProvider` from `RequestServices`. `Substitute.For<TimeProvider>()` with `GetUtcNow().Returns(...)` works for the unit tests (the class's `GetUtcNow` is virtual); stamps built relative to real `UtcNow` (89 and 91 days) are equally fine and need no substitute for the wiring test. No new package (`Microsoft.Extensions.TimeProvider.Testing` is **not** added).
- **Unstamped-cookie rule (AC #9, amended) in code:** missing stamp -> reject and sign out; no lazy stamping, no `ShouldRenew`. Do not use `Properties.IssuedUtc` as a fallback stamp (it restarts on every sliding renewal, so it would quietly grandfather old sessions).
- **Filter metadata:** `RouteHandlerBuilder.AddEndpointFilter<T>()` has no discoverable footprint on the built endpoint, which is why the marker metadata exists. Add the marker in the same extension method that adds the filter, so the two cannot drift.
- **Antiforgery is a different thing.** Minimal APIs that bind `IFormFile` need antiforgery handling in .NET 8+; whatever the upload routes already do about that (`DisableAntiforgery` or equivalent) is unchanged. Do not add `UseAntiforgery`.

- Read from the `dotnet/aspnetcore` `main` branch source on 2026-10-17, **not** from the 10.0.12 package; confirm each point with the tests above rather than trusting it. `OpenIdConnectHandler.SignOutAsync`: forwards to `Options.ForwardSignOut` if set; builds an `OpenIdConnectMessage` with `IssuerAddress = _configuration?.EndSessionEndpoint ?? ""` and `PostLogoutRedirectUri` = `SignedOutCallbackPath` made absolute; defaults `properties.RedirectUri` to `SignedOutRedirectUri` or the current URL; reads `id_token` from the sign-out scheme for `IdTokenHint`; awaits `Events.RedirectToIdentityProviderForSignOut`; **if the event handled the response it returns before protecting state or redirecting**; then `message.State = Options.StateDataFormat.Protect(properties)` (after copying a non-empty `message.State` into `properties.Items[".userstate"]`); throws if `IssuerAddress` is empty; for `RedirectGet` calls `Response.Redirect(message.CreateLogoutRequestUrl())`. `HandleSignOutCallbackAsync`: unprotects `state` only when present and redirects only when the resulting properties carry a `RedirectUri`, otherwise returns without a redirect.
- Cookie authentication: `CookieAuthenticationEvents.OnSigningIn` runs for `SignInAsync`, `OnValidatePrincipal` runs on every authenticate of the cookie scheme, `RejectPrincipal()` plus `SignOutAsync` is the documented way to invalidate; `ShouldRenew = true` re-issues the cookie; `AuthenticationProperties.Items` round-trips through the ticket. The cookie `Events.OnRedirectToLogin` default treats `X-Requested-With: XMLHttpRequest` as an Ajax request; this app overrides that handler for `/api` and the header value used here is `fetch`, so that framework special case is not triggered.
- Endpoint filters (minimal APIs, .NET 7+): `RouteGroupBuilder.AddEndpointFilter<T>()` applies to every endpoint in the group; filters run after parameter binding, before the handler.
- Fetch semantics: a cross-origin redirect to a non-CORS endpoint is invisible to the page (`redirect: 'manual'` yields an opaque redirect), and CSP `form-action` also restricts redirect targets after a form submission in Chrome; both are why logout is JSON, not a 302.

## Questions for Ralf (defaults above apply unless you overrule; none block starting Task 1)

1. **Q1 Header value and scope.** The check is "header present"; the SPA sends `X-Requested-With: fetch`. `POST /logout` needs it too (it is outside `/api`, so I add the same filter to it explicitly), which the epic text does not say. Default: as written.
2. **Q2 Cookies that exist at deploy.** They have no issued-at stamp. **Decided 2026-10-17 (Ralf): reject unstamped cookies and force one sign-in.** This gives the strictest cap, at the price of a possible short sign-in bounce while an old and a new revision overlap during a deploy or rollback. Recorded in AC #9 (amended). The lazy-stamp alternative (stamp "now", keep the session) was not chosen.
3. **Q3 Logout mechanism.** Default: `fetch` POST that returns `{ redirectUrl }`, CSP unchanged. The alternative is a real `<form method="post">` plus widening `form-action` to the identity provider's host: simpler client, but the CSP then depends on the configured authority and a form cannot send the CSRF header.
4. **Q4 Old `GET /logout`.** Default: removed with no shim; an old tab with a cached bundle that still navigates there lands on the SPA instead of signing out, and reloading fixes it. Say so if you want a temporary redirect.
5. **Q5 Window and cap numbers.** 14 days sliding and 90 days absolute are the epic's numbers. Keep?
