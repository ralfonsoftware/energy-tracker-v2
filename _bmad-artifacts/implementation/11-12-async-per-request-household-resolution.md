## Story

As a household member,
I want API requests not to block a thread on a database lookup,
so that the app stays responsive under bursts on Azure SQL Basic (audit C2).

## Acceptance Criteria

1. **Given** an authenticated API request, **when** it is processed, **then** membership is resolved once, asynchronously, in middleware, and cached in `HttpContext.Items`. `CurrentHouseholdAccessor` only reads the cached value. The job path (`JobHouseholdContext`) is unchanged.
2. **Given** AD-17's rule that membership is resolved per request, **when** this story is done, **then** nothing caches membership across requests or in the cookie. A removed member is still cut off on their next request (test).
3. **Implied (the AC says "once" and "only reads"; both must be provable and not only true on the day):** (a) for one authenticated `/api` request that touches many filtered entities (e.g. `GET /api/status`), exactly **one** membership lookup runs, through `CreateDbContextAsync`; (b) **no** synchronous membership lookup exists anywhere: the accessor has no database dependency at all (its constructor takes `IHttpContextAccessor` and `JobHouseholdContext` and nothing else), contains no `SingleOrDefault`/`ToList`/`.Result`/`.Wait()`/`GetAwaiter().GetResult()`, and a host test whose `IDbContextFactory<HouseholdMembershipDbContext>` throws from the **sync** `CreateDbContext()` passes the whole request flow; (c) two requests by the same principal run two lookups, never one (no cross-request cache); (d) an unauthenticated `/api` request (401), `/health`, `/login`, `/logout`, a static asset and an SPA route run **zero** lookups, even with a signed-in cookie (the lookup is not free, and static assets must never pay it).
4. **Implied (where the middleware sits is part of the contract):** it is registered in `Program.cs` **after** `UseAuthentication`, `UseAuthorization` and `UseRateLimiter` and before the endpoints, and after `UseExceptionHandler`. After authorization so a 401 costs nothing; after the rate limiter so a throttled request (429) costs nothing (AD-27, Story 11.7 put the limiter after authorization for the same reason); after the exception handler so a database failure during the lookup answers the usual RFC 7807 500, not a bare one. It acts only on paths under `/api` for a request whose `User.Identity.IsAuthenticated` is true.
5. **Implied (what the accessor does when nothing is cached; decided here, see Q1):** (a) `HttpContext` is null (a background job scope, the startup sweep, a raw test scope) -> the job path, exactly as today: `HouseholdId` is `JobHouseholdContext.HouseholdId`, `HouseholdMemberId` is null; (b) a cached value is present -> it is returned as is, including a cached "no Household" (null, null); (c) no cached value, and the principal lacks the subject claim or the validated-issuer claim (anonymous, or a claim-less principal) -> (null, null) with no database access, as today; (d) no cached value, and the principal **has both** claims -> `InvalidOperationException` whose message names `UseHouseholdMembership` and the cause ("the middleware did not run for this request") and carries **no** claim value. This never silently falls back to a synchronous lookup and never turns a wiring bug into "everyone looks household-less".
6. **Implied (the resolved shape and the lookup must stay exactly what they are, so tenant isolation does not move):** the lookup is the same query as today (`HouseholdMembers` by `ExternalIssuer == issuer && ExternalSubjectId == subject`, projected to member id and `HouseholdId` through an anonymous type, not a ValueTuple: Npgsql cannot read a server-side tuple projection), now `SingleOrDefaultAsync` with `HttpContext.RequestAborted`, on a context from `CreateDbContextAsync` that is disposed with `await using`. A principal with no `HouseholdMember` row resolves to (null, null) and is cached as such, so the rest of the request does not look it up again. The issuer comes from `HouseholdClaimTypes.ValidatedIssuer` and the subject from `ClaimTypes.NameIdentifier`, as today (never ambient `Claim.Issuer`).
7. **Implied (membership changes inside a request are not visible until the next one; confirm it changes nothing today):** `POST /api/households`, `POST /api/household-invites/{token}/accept` and `DELETE /api/household-members/{id}` change membership. None of them reads the accessor after the write today (create and accept use only exempt entities and the principal's claims; remove reads the accessor first). After this story the value is fixed at the start of the request, so a read after the write would see the old state. A test per route proves the response is unchanged and that the **next** request sees the new state (a creator's second request has a Household; an accepted invitee's second request has the inviter's Household; a removed member's second request has none).
8. **Implied (drift guard in this repo's style: prose rules die, executable ones do not):** `tests/EnergyTracker.Architecture.Tests/HouseholdMembershipIsResolvedOncePerRequestTests.cs` (text scan with comments stripped, each scanned file must still exist and still contain what it is scanned for): fails when `CurrentHouseholdAccessor.cs` mentions a DbContext/factory/`HouseholdMembers`, a synchronous or blocking call, `IMemoryCache`/`IDistributedCache`/`ConcurrentDictionary` or a `static` field; when any file under `src` other than the resolver calls `CreateDbContext`/`CreateDbContextAsync` on a `HouseholdMembershipDbContext` factory; when any file under `src` adds a household or member claim to a principal or cookie ticket (a `new Claim(` whose type is not `HouseholdClaimTypes.ValidatedIssuer`, outside the OIDC `OnTokenValidated` handler in `Program.cs`); when `Program.cs` does not register `UseHouseholdMembership()` after `UseExceptionHandler`, `UseAuthentication`, `UseAuthorization` and `UseRateLimiter` and before the first `app.Map…`. `HouseholdMemberLookupsAreHouseholdScopedTests`' allow-list entry for `CurrentHouseholdAccessor.cs` moves to the resolver file (Task 4.3).
9. **Implied (docs and comments that would otherwise go stale):** the doc comments of `CurrentHouseholdAccessor`, `ICurrentHouseholdAccessor` (the HTTP path is "resolved per request by `HouseholdMembershipMiddleware`"), `HouseholdMembershipDbContext` (now used by the resolver, not the accessor; the circular-DI reasoning still holds for keeping it a separate context), the comments at `Program.cs:183-185` and `EnergyTrackerDbContext.cs:11-15` (the latter already names a factory type that does not exist), `docs/data-import-restore.md` lines 218-223 and 255 (they describe the accessor's lookup), and `_bmad-artifacts/project-context.md` (Task 6).

## Dev Notes

### What this fixes and why it is safe to change

- **C2 (Medium, verified).** `CurrentHouseholdAccessor.Resolve()` runs `SingleOrDefault()` on a context from `CreateDbContext()` the first time `HouseholdId` or `HouseholdMemberId` is read in a scope. The first read is almost always inside EF's query-filter evaluation (`EnergyTrackerDbContext.CurrentHouseholdId`, a property read per query) or at the top of an endpoint's `TryGetHouseholdId`. Either way it blocks the request thread for one round trip on every API call. The audit's fix is the one the epic names: resolve once in async middleware, cache in `HttpContext.Items`, and let the accessor only read.
- **Why `Items` is safe under AD-17/AD-26.** `Items` lives exactly as long as the `HttpContext`, i.e. one request. A removed member's cookie stays valid but their next request runs the middleware again, finds no `HouseholdMember` row and caches (null, null) for that request only: the existing behaviour, now in one place. Nothing is written to the cookie or the `ClaimsPrincipal`; the middleware stores a value in `Items`, it does not add claims.
- **Why one lookup also fixes nested scopes.** `IHttpContextAccessor.HttpContext` is shared by every DI scope inside the request, so a scope created mid-request reads the same `Items` value. Today each such scope would run its own lookup.

### Design decisions already made (do not re-litigate; Ralf can override at review; none changes an epic AC)

- **Q1 an authenticated principal with no cached value throws.** The alternatives are (a) a silent synchronous fallback, which reintroduces C2 invisibly the day someone adds a route outside `/api`, and (b) returning null, which turns a wiring bug into every user looking household-less and 403ing, or, worse, into the Create-a-Household screen for a member who has one. A loud, message-named 500 on the first request of the developer who adds such a route is the cheaper failure. The throw carries no claim value (the subject is an identifier).
- **Q2 the middleware is path-scoped to `/api`, not endpoint-metadata-scoped.** Metadata (a marker on routes that need a Household) would be more precise but is one more thing for a new route to forget; `/api` already means "authenticated, needs the Household" for every route (`/api/session`, `POST /api/households` and the invite routes, which do not read it, pay one indexed lookup; accepted). Revisit only if a non-`/api` authenticated route appears.
- **Q3 the resolver is a separate injectable class, not logic in the middleware.** The query needs a dual-provider test against real Postgres and SQL Server (AD-2); a middleware cannot be tested that way without a host. The middleware stays a few lines.
- **Q4 the cached value is a small record in `Items` behind one helper**, not three loose `Items` keys and not a scoped service: the epic says `HttpContext.Items`, and a scoped holder would not be shared by a scope created mid-request.
- **Q5 the live gate applies** (Part R) although the epic does not list 11.12 under the Auth0 live gate; if Ralf prefers not to treat it as a gate, the story can close on the automated evidence.

### Technical details the dev must get right

- **Async all the way:** `await using var dbContext = await factory.CreateDbContextAsync(cancellationToken);` then `SingleOrDefaultAsync(cancellationToken)`. Pass `HttpContext.RequestAborted`. No `.Result`, no `.GetAwaiter().GetResult()`.
- **Projection:** keep `Select(m => new { MemberId = (Guid?)m.Id, HouseholdId = (Guid?)m.HouseholdId })` and convert to the record client-side. A ValueTuple projection throws `NotSupportedException` on Npgsql (existing comment).
