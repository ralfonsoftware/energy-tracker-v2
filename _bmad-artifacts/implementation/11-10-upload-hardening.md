## Story

As the operator,
I want uploads to use bounded memory and disk,
so that one large or malicious file can't take down the container (audit S4).

## Acceptance Criteria

1. **Given** `POST /api/household-import`, **when** a file is uploaded, **then** it is streamed to disk and validated with `Utf8JsonReader` over a `FileStream`, never read into a single string. Peak memory for a 32 MB export is measured before and after, and recorded.
2. **Given** a Household with a pending validated upload, **when** it uploads again, **then** the previous pending upload and its file are removed, so there is at most one pending upload per Household.
3. **Given** `Consume` in the upload registry, **when** an entry is expired or belongs to another Household, **then** its file is deleted on every path.
4. **Given** an XLSX Smart Plug file, **when** it is parsed, **then** `OpenSettings.MaxCharactersInPart` and a row-count cap apply, and a zip-bomb fixture is rejected with a stable import error.
5. **Implied (the temp file must never outlive a failed request; today the file is only written after validation, so streaming it first creates this leak):** the upload endpoint deletes its temp file on **every** path that does not end in a successful `Register`: a validation failure (400), the too-large check, any exception, and a cancelled request (client abort). A test proves each.
6. **Implied (the wire contract and the validator's behaviour are an oracle, not a rewrite licence):** the response of `POST /api/household-import` is unchanged (200 `{ token, summary }`, 400 `failures[]`, 400 too-large, 403 no Household), and the validator returns the **same failures with the same text in the same order** as today for every input the 24 existing `ValidateHouseholdImportTests` cover. Order stays the validator's fixed field order (`exportedAtUtc`, `household`, `householdMembers`, `mainMeter`, `meterReadings`, `meterRegressionPrompts`, `tariffs`, `events`, `rooms`, `powerPoints`, `devices`, `smartPlugReadings`, `statusSnapshots`, `auditCorrections`), never file order. Streaming must not change these behaviours, each with its own test: (a) malformed JSON anywhere in the file, even at the end, yields the single failure `The file is not valid JSON: …` and none of the partial structural failures collected before it; (b) `formatVersion` is checked first and alone even when the property is the **last** one in the file; (c) a reference to an array that appears **later** in the file (`smartPlugReadings` before `powerPoints`, `meterRegressionPrompts` before `meterReadings`) still resolves; (d) a leading UTF-8 BOM is accepted (today's `StreamReader` strips it; `Utf8JsonReader` throws on it, so skip it explicitly), and so does the restore job's read (Task 3.3); (e) the legacy identity fields on `householdMembers[]` are still accepted and ignored (AD-25); (f) a structurally valid file that `System.Text.Json` still cannot deserialize into the export DTOs is a reported failure at validation time (`The file passed structural validation but could not be parsed: …`), never a surprise in the restore job: keep that safety net per item (Task 2.3).
7. **Implied (bounded memory has to be true for hostile files, not only for the 32 MB export; each of these is a way to rebuild the S4 hole one level down, so each is a requirement):** (a) the reader's buffer never grows beyond **4 MiB**; a single token or array element that does not fit fails validation with a stable failure (`a single value in the file is larger than 4 MiB`), it never grows the buffer (a 250 MB file that is one giant string must cost 4 MiB, not 250 MB); (b) the `failures` list keeps the first **200** failures in the canonical order, then one final entry `… and N more failures not shown.` (N exact); (c) the summary retains at most **100** member display names, each truncated to **200** characters (the count `householdMembers` stays exact); (d) the per-array duplicate-id sets and the reference-id sets are the one place memory still grows with the file, by item **count** (about 32 bytes per id), not by file size. That residual is accepted, recorded in Completion Notes with the measured worst case, and added to `deferred-work.md` (Task 7.2).
8. **Implied (the restore job re-reads the same file; leaving a `ReadAllTextAsync` there would keep the 2x-UTF-16 string the epic forbids for this file):** `RestoreHouseholdData` deserializes from a `FileStream` (`JsonSerializer.DeserializeAsync<HouseholdExportResult>`), not from a string. The object graph still materializes (the restore writer takes the whole `HouseholdRestoreData`), so this halves the transient peak but does not bound it; say so in Completion Notes and `docs/data-import-restore.md`. A fully streaming restore is out of scope.
9. **Implied (what "removed" means for the registry, so the one-pending rule cannot destroy a running restore):** (a) replacement happens in `Register` of the **new, already validated** upload, so an invalid or aborted re-upload leaves the previous pending upload intact; (b) only entries still held by the registry are replaced: a token that was already consumed (its file now belongs to a queued or running restore job) is not in the registry and its file is never touched; (c) the swap is atomic: two concurrent registers for the same Household end with exactly one entry and exactly one file left on disk (the loser's and the replaced files are deleted); (d) other Households' entries are never touched; (e) the 30-minute TTL, the expiry sweep on `Register`, and `Consume`'s "null for unknown, expired and wrong-Household alike" contract are unchanged. A wrong-Household `Consume` still removes the entry (it does today, via `TryRemove` first); the change is that its file is now deleted too, exactly as AC #3 says.
10. **Implied (AC #4 names two settings; a bomb is only "rejected with a stable import error" if the failure is recognizable, and `MaxCharactersInPart` alone cannot do that, see Dev Notes "XLSX evidence"):** (a) `EveHomeXlsxParser` opens every package through one private helper (used by both `ReadDeviceTag` and `Parse`) that sets `OpenSettings.MaxCharactersInPart = 64,000,000` and first runs a **decompressed-size pre-scan**: it counts the real decompressed bytes of each package entry through a bounded counting sink (never trusting the declared size) and throws `SpreadsheetTooLargeException` when the entries together exceed the same 64,000,000 limit. **AMENDED 2026-10-21, Ralf (code review decision):** the limit is on the total of the real decompressed bytes of all entries, not per entry, because a per-entry limit lets a small upload hold hundreds of near-limit entries; ~~when any entry exceeds the same 64,000,000 limit~~; (b) `Parse` throws the same exception once it has read more than **400,000** rows (all `Row` elements, so empty rows count; `ReadDeviceTag` reads two rows and needs no cap); (c) `SpreadsheetTooLargeException` maps by type to the new stable code `spreadsheet-too-large` in `BackgroundJobProcessor` (the Story 11.4 `DeviceTagTooLong` pattern), the SPA translates it in both locales (`jobError.spreadsheetTooLarge`, generic copy without numbers so the limits can change without a copy change), and its English message is logged but never reaches `ErrorMessage`; (d) shared strings are resolved through a list built once per `Parse`, not `SharedStringTable.ElementAt(i)` per cell (that is O(i) per lookup, so a capped 400,000-row file whose cells point into a large table would still be a CPU bomb); (e) `MaxCharactersInPart` stays set as the backstop. If it ever trips without the pre-scan having tripped, the `XmlException` is an ordinary generic job failure (null `ErrorMessage`), and a test pins that. (f) **AMENDED 2026-10-21, Ralf (code review decision) (added):** a worksheet row is read cell by cell through the forward-only reader, never loaded whole, and a row of more than 100 cells (`MaxCellsPerRow`; a real row has two) throws `SpreadsheetTooLargeException`, so a hostile row of millions of cells inside the character limit cannot be built as one DOM element; the pre-scan is cancellable.
11. **Implied (a guard the next change cannot silently undo, in this repo's style):** `tests/EnergyTracker.Architecture.Tests/HouseholdImportIsStreamedTests.cs` (text scan with comments stripped, non-vacuous) fails when `HouseholdImportEndpoints.cs`, `ValidateHouseholdImport.cs` or `RestoreHouseholdData.cs` contain `ReadToEnd`, `ReadAllText`, `ReadAllBytes`, `JsonDocument.Parse(` on a string, `JsonSerializer.Deserialize<HouseholdExportResult>(` on a string or `new StreamReader(`, and fails when `EveHomeXlsxParser.cs` contains `SpreadsheetDocument.Open(` outside the one helper or no longer mentions `MaxCharactersInPart`. It also asserts each scanned file still exists and still contains the identifier it is expected to (`Utf8JsonReader`, `OpenSettings`), so a rename cannot empty it.
12. **Implied (docs that would otherwise go stale):** `docs/data-import-restore.md` ("Where the uploaded file lives", "Upload size limit": one pending upload per Household, files deleted on every path, streamed validation and its limits, the measured before/after), `_bmad-artifacts/project-context.md` (one bullet: uploads are streamed, the 4 MiB / 200 / 100 bounds, the XLSX caps, `SpreadsheetTooLargeException`), `deferred-work.md` (Task 7.2), the sprint status.

## Dev Notes

### What this fixes and why it is safe to change

- **S4 (Medium, verified), four findings in one place.** (1) `POST /api/household-import` reads the file into one `string` (`ReadToEndAsync`), parses it into a `JsonDocument`, deserializes it again into the whole object graph, and writes the string back to disk; the restore job later `File.ReadAllTextAsync`s it and deserializes again. The audit estimates 5-10x the file size per upload at peak; the container is 0.5 vCPU / 1 GiB. (2) Validated uploads wait 30 minutes and nothing limits how many a Household has pending. (3) `Consume` removes the entry first and leaks the file on an expired or wrong-Household token. (4) The XLSX 20 MB cap is on the compressed size, `SpreadsheetDocument.Open` has no limit, and the whole `SharedStringTable` is loaded as a DOM.
- The risk is concentrated in **the validator rewrite** (it is the largest single file of validation rules in the Application layer and has an exact-text contract), **the registry's concurrency**, and **the XLSX limits tripping on a legitimate file**. That is why the existing 24 validator tests are the oracle, why Task 1.2(j) proves bounded buffering deterministically, why Task 1.5(c) pins the real sample files, and why Task 9 and Part R exist (the deploy health gate probes `/health` only).

### Design decisions already made (do not re-litigate; Ralf can override at review)

- **The cap stays 250 MB** (Q1). The audit suggested lowering it or making it configurable; the epic's ACs do not, and with streaming the cap bounds disk and time, not memory.
- **Replacement at `Register` of the new validated upload**, not at the start of a new upload (AC #9a), so a bad re-upload cannot destroy a good pending one.
- **Per-element `JsonDocument` inside a `Utf8JsonReader` loop**, reusing the existing rules, instead of rewriting 600 lines of rules as token-level code. It satisfies AC #1 literally ("validated with `Utf8JsonReader` over a `FileStream`") and keeps the failure text identical by construction.
- **Two passes over the temp file**, because references can point at arrays later in the file and `formatVersion` can be last (AC #6b, c). It costs a second sequential read of a file that is already on local disk.
- **Bounds on what is *retained*, not extra rejections** (AC #7b, c): no previously valid file becomes invalid except one with a single value over 4 MiB, which no export produces.
- **Pre-scan plus `MaxCharactersInPart`** (AC #10): the pre-scan is the deterministic, memory-safe rejection that can be mapped to a stable code; `MaxCharactersInPart` is the setting the AC names and the backstop.
- **Generic `spreadsheet-too-large` copy without numbers**, so the constants can change without touching two locale files.

### XLSX evidence (measured 2026-10-21 by create-story, DocumentFormat.OpenXml 3.5.1, .NET 10.0.402, scratch project outside the repo; the dev re-verifies in Task 1.5)

- `OpenSettings.MaxCharactersInPart` is honoured by `OpenXmlReader` and by the DOM load of `SharedStringTablePart.SharedStringTable`. On a 5,000,000 limit the real 16.8 million character sample sheet fails mid-read with `System.Xml.XmlException: The input document has exceeded a limit set by MaxCharactersInDocument.`; on 100,000,000 it reads all 121,644 rows. An early exit after two rows (what `ReadDeviceTag` does) never trips it. A synthetic 845 million character sheet (66 MB zipped) trips the 100,000,000 limit after 2.7 s with about 3 MB of managed memory.
- **The exception is a plain `XmlException` whose text is a localized resource string and is the same type a corrupt file throws**, so mapping "limit hit" to a stable code by catching it would be a guess. That is why AC #10 adds the pre-scan.
- **The shared-strings DOM is the real memory hazard**: a 200 million character `sharedStrings.xml` (a 1.5 MB zip) loaded with no limit allocated about 560 MB, and with a 100 million limit still about 320 MB before the exception (about 2.8 bytes per character, UTF-16 plus nodes). A `MaxCharactersInPart` setting alone would still let a hostile file allocate hundreds of MB on a 1 GiB container; the pre-scan rejects it before OpenXml loads anything.
- Real data: the sample Eve files are 7.8 to 16.8 million characters of sheet XML (the largest is 121,644 rows, 1.3 MB zipped); `sharedStrings.xml` is about 320 bytes.

### Technical details the dev must get right

- **`Utf8JsonReader` over a stream is the classic buffer-refill pattern** (carry `JsonReaderState`, pass `isFinalBlock`, copy `bytes[reader.BytesConsumed..]` to the front, read more). The two traps are `Skip()` on a big value (needs the whole value in the buffer) and a token larger than the buffer (a string token cannot be split): both end in the 4 MiB failure, never in growth. Rent with `ArrayPool<byte>.Shared` and return it in a `finally`; clear it if you worry about content lingering (it is the member's own data, in memory for a request).
- **`JsonDocument.ParseValue(ref reader)`** needs the element complete in the buffer; it is what `TrySkip()` on a reader copy guards. Dispose each element's `JsonDocument` (`using`) so its pooled arrays return.
- **BOM:** skip `EF BB BF` once at the start. UTF-16 files (which the old `StreamReader` would have decoded) are no longer supported; that is a deliberate, harmless narrowing (exports are UTF-8) and shows as the not-valid-JSON failure.
- **Failure text parity** includes `JsonException.Message` for malformed JSON: it now comes from `Utf8JsonReader` instead of `JsonDocument.Parse`; both carry the same line/byte position wording. Check what the existing malformed-JSON test asserts and keep it passing; do not assert more of the message than it does today.
- **Seekability:** two passes need `Stream.CanSeek`. The endpoint passes a `FileStream`; reject a non-seekable stream with an `ArgumentException`, never copy it into memory.
- **Registry concurrency:** `ConcurrentDictionary` alone cannot express "remove the Household's old entry and add the new one atomically"; a plain `lock` over both dictionaries is fine at this scale (one process, a handful of Households, AD-24). Delete files **outside** the lock.
- **Do not delete a file the registry no longer owns** (AC #9b): after `Consume` succeeds, the registry has handed ownership to the confirm endpoint and then the job.
- **Temp-file seam:** keep it tiny. It exists so tests can count one host's files; it is not a feature.
- **`ZipArchive` pre-scan:** open in `ZipArchiveMode.Read` over the same seekable stream, `leaveOpen: true`; enumerate entries; for each, open and copy into a sink that counts bytes and throws `SpreadsheetTooLargeException` when the running count for that entry passes the limit; then `Position = 0`. A `InvalidDataException` from a corrupt zip stays what it is today (a generic parse failure). Do not trust `ZipArchiveEntry.Length`.
- **Row cap and watermark:** the cap counts rows *read*, so an incremental import that early-stops at the watermark reads few rows and is never near the cap; a first import of a very long history is the case it protects.
- No new packages (`DocumentFormat.OpenXml` 3.5.1 is already pinned in `Directory.Packages.props`). No `TimeProvider` (Story 11.17 migrates `DateTimeOffset.UtcNow` everywhere at once).

### Completion Notes List

- **What was built.** `POST /api/household-import` streams the upload to a temp file and validates it from a `FileStream` with `HouseholdImportJsonReader` (buffer 64 KiB, doubling to a hard 4 MiB cap, BOM skipped, tokens crossed one at a time, one array element materialized at a time) in two passes over the file: pass 1 proves it is well-formed and collects `formatVersion`, `mainMeter.id` and the meter reading, room and power point id sets; pass 2 runs the unchanged `Validate*`/`Require*` rules per element into per-field failure buckets emitted in the validator's fixed order (200 kept, exact remainder). `HouseholdImportValidationResult` now carries a small `HouseholdImportInventory` (counts, at most 100 names of 200 characters) instead of the object graph; the summary response is unchanged. `RestoreHouseholdData` deserializes from the file stream. The registry keeps at most one pending upload per Household (one lock over a token index and a Household index, replacement at `Register` of the new validated upload, deletes outside the lock, a consumed token's file never touched) and `Consume` now deletes the file of an expired or wrong-Household entry. `ReceiveUploadAsync` owns one `try/finally` that deletes the temp file on every exit that is not a successful `Register`. `EveHomeXlsxParser` opens every package through `OpenDocument`: a decompressed-size pre-scan (real bytes counted, 64,000,000 per entry), `OpenSettings.MaxCharactersInPart` as the backstop, a 400,000-row cap in `Parse`, shared strings read once into a list; the limits throw `SpreadsheetTooLargeException`, mapped by type to `spreadsheet-too-large` and translated in both locales.
