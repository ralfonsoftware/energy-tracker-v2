## Story

As a household member,
I want restoring another household's export, on the same instance, to either work or fail with a clear message,
so that duplicating or migrating a household isn't a generic failure (audit C10).

## Acceptance Criteria

1. **AMENDED 2026-10-25, Ralf chose re-key at Task 0.3 (Ask First):** **Given** a restore file whose entity ids or meter-reading idempotency keys already exist in another Household, **when** it is restored, **then** the entities are re-keyed with foreign keys remapped inside the file, so the restore succeeds. ~~**Given** a restore file whose entity ids or meter-reading idempotency keys already exist in another Household, **when** it is validated, **then** the outcome is clear: either the entities are re-keyed with foreign keys remapped inside the file, or the file is rejected up front with a specific message. *Ask First: re-key or reject.*~~
2. **Given** two concurrent restore-confirms with different tokens, **when** both run, **then** at most one restore job is active per Household, enforced by a database guard (e.g. a filtered unique index on active restore and cleanup jobs), not by check-then-enqueue alone.
3. **Implied (what "re-keyed with foreign keys remapped inside the file" has to mean; the AC is not met by regenerating the primary keys alone):** `RestoreHouseholdData` gives **every** restored entity a new `Guid` `Id` and regenerates every `MeterReading.IdempotencyKey`, so a restore can no longer collide with any row of any Household (nothing is detected, nothing is probed: new random ids cannot collide, Q1). Every reference inside the file follows its target to the new id: `PowerPoint.RoomId`, `Device.PowerPointId`, `MeterReading.MainMeterId`, `MeterRegressionPrompt.MainMeterId`/`MeterReadingId`/`PreviousMeterReadingId`, `SmartPlugReading.PowerPointId` (optional: null stays null), and the two **polymorphic** references that have no foreign key and are easy to miss: `Event.TaggedEntityId` (resolved by `TaggedEntityType` `"Room"`, `"PowerPoint"` or `"Device"`) and `AuditCorrection.EntityId` (resolved by `EntityType`: `"MeterReading"` and `"Tariff"` are the two written today, `"Room"`, `"PowerPoint"` and `"Device"` are mapped too if present). A polymorphic reference that resolves to nothing in the file (an unknown type, or an id the file does not contain) is **kept as it is**, never dropped and never failed: it is a history pointer, not a foreign key (document this in `data-import-restore.md`). `Household.Id`, the Household settings patch, `HouseholdMember` (AD-25) and everything the restore never touched stay exactly as they were. Re-keying happens in one place, a pure class in Application (see Task 2), after the file is deserialized and before `IHouseholdRestoreWriter` is called; the writer, the validator and the file format are not changed.
4. **Implied (restoring a household's own export into itself must keep working, and it now changes ids; say so and prove it):** the existing round trip (`Full_validate_then_confirm_flow_restores_the_Households_own_exported_data`, the "own backup" case) still completes, and afterwards the Household holds exactly the exported rows (same counts per category, same field values, same internal graph: every reference resolves, every polymorphic reference points at a row that exists) under **new** ids. A second restore of the same file gives the same result with different ids again (retry is safe, `docs/data-import-restore.md` "Retrying is safe" stays true). A new test restores **household A's export into household B while A still exists** (the C10 case, the one that failed before) through the real writer on both providers, and A's rows are untouched.
5. **Implied (the guard has to be a real constraint, portable across both providers, and it must not need the application-level check to be correct):** one filtered unique index on `BackgroundJobs` over `(HouseholdId, JobType)` with the filter `JobType IN ('RestoreHouseholdData', 'CleanUpSmartPlugImportJobs') AND Status IN (Queued, Processing)` (the integers, `3` and `0`). It is created by **one expand-only migration per provider**, created through `scripts/add-migration.sh AddActiveJobGuard` and then hand-edited, as **raw SQL in each provider's migration only**, with **no `HasFilter` in the model and no change to the model snapshot** (the Story 3.4/11.4 precedent in `SmartPlugReadingConfiguration.cs`: a filter is dialect SQL text and the configuration class is shared by both providers, AD-2). Other job types (`ProcessSmartPlugImport`, `CorrelateEvent`) are not constrained: several Smart Plug files queue per Household by design. A terminal row (`Completed`, `Failed`) is outside the index, so a finished or stale-failed job frees the slot (`FailStaleAsync`, the startup sweep and `TryComplete`/`TryFail` need no change). The set of guarded job types lives in one place, `JobTypes.ExclusivePerHousehold` (Application), and both migrations and the guard test (AC #11) agree with it.
6. **Implied (the migration must be creatable on a database that already holds duplicates, and the previous image must keep working against it):** before `CREATE UNIQUE INDEX`, each provider's migration fails the **surplus** active rows of a guarded type: for every `(HouseholdId, JobType)` with more than one `Queued`/`Processing` row it keeps the newest (`CreatedAtUtc`, then `Id`) and sets the others to `Failed` with `ErrorMessage = 'job-interrupted'` and `CompletedAtUtc` set (a stable code both locales already translate; history is kept, nothing is deleted; a non-null `CompletedAtUtc` because the cleanup sweeps read it). No duplicates is the expected production state (the old check-then-enqueue made them a narrow race), so the statement normally updates zero rows; it exists so that an index build failure never fails a deploy (Q3). Expand/contract holds: the index only adds a constraint, and the previous image's check-then-enqueue can at worst turn a lost race into an unhandled 500 instead of a 409 (accepted for the rollback window; stated in a one-line comment in each migration, as `app-deploy.yml`'s health-check rollback redeploys the previous image against the migrated schema).
7. **Implied (the two endpoints that enqueue a guarded job must turn a lost race into the answer they already give for the early check, never a 500):** `BackgroundJobEnqueueRecorder.RecordAsync` (the one place the `Queued` row is inserted, shared by both queue adapters; the row is written **before** the queue send, so a rejected insert sends nothing) catches `DbUpdateException` for a guarded job type, probes whether an active row of that `(HouseholdId, JobType)` now exists (a plain portable query with an explicit `HouseholdId` predicate in a fresh scope, **no provider error-code sniffing**, no `IgnoreQueryFilters`), and throws a new `ActiveJobAlreadyExistsException(jobType, activeJobId)` (Application, one type per file) when one does; any other `DbUpdateException`, and any exception for an unguarded type, propagates unchanged. (a) `POST /api/household-import/{token}/confirm` catches it around `EnqueueAsync`, deletes the consumed upload's temp file (the same cleanup as the early-check path) and answers the same `409` ProblemDetails ("A restore is already in progress for this Household..."). (b) `DELETE /api/smart-plug-import-jobs` catches it and answers `202` with the **existing active job's id** (the same idempotent contract as its early check). The early checks (`FailStaleAsync` + `ListByJobTypeAsync`) stay: they are the friendly fast path and the place stale rows are failed first; the index is the arbiter.
8. **Implied (the guard must be provable without relying on timing, and the two requests of AC #2 must be real):** (a) a repository/recorder test per provider against **migrated** databases (not `EnsureCreated`, which would not create the raw index) proves the index: a second active restore row for one Household is rejected as `ActiveJobAlreadyExistsException` carrying the first job's id; a different Household, a different guarded type, an unguarded type, and the same type after the first job reached `Completed` or `Failed` are all accepted; `FailStaleAsync`, `TryFailNonTerminalAsync` and the startup sweep free the slot; (b) an Api test sends **two confirms with different tokens in parallel** with the early check made blind (a decorator over `IBackgroundJobRepository` whose `ListByJobTypeAsync` returns an empty list for the restore type), so both reach the enqueue: exactly one answers `202` and one `409`, exactly one active row exists afterwards, and the loser's temp file is gone; the same shape for two parallel cleanups (both `202`, same job id, one row). Mutation-checked in Task 7.
9. **Implied (executable drift guard in this repo's style, prose rules die):** `tests/EnergyTracker.Architecture.Tests/ActiveJobGuardIsDeclaredTests.cs` (text scan, comments handled as in `BackgroundJobStatusHasOneWriterTests`, non-vacuous, each scanned file must exist and each assertion must have found its anchor): (a) both provider migrations that create the index contain `CREATE UNIQUE INDEX`, every entry of `JobTypes.ExclusivePerHousehold` and the integers of `BackgroundJobStatus.Queued` and `Processing` (read from the enum, not hard-coded in the test); (b) the set of `BackgroundJobStatus` members other than `Completed` and `Failed` is exactly `{Queued, Processing}`, so a **new** status fails the test until someone decides whether it is "active" for the index; (c) `BackgroundJobConfiguration.cs` contains **no** `HasFilter` and no index over `JobType` with a unique flag (the declared-only-in-migrations rule, with the failure message pointing at `SmartPlugReadingConfiguration.cs`); (d) only `BackgroundJobEnqueueRecorder` throws `ActiveJobAlreadyExistsException`. The failure messages name AD-6, AD-2 and this story.
10. **Implied (a restore that assigns new ids must not leave the running app showing stale ones, and the docs must stop saying ids are reused):** (a) `docs/data-import-restore.md` is corrected where it says ids come from the file: "Write target: always the current session's Household" (the paragraph that says internal references are "reused byte-for-byte", about lines 214-221) and "What gets replaced, and how" (the sentence "reusing each row's original `Id` from the file"), plus a new short section "Ids and meter-reading idempotency keys are reassigned on every restore" (what is regenerated, which references follow, the polymorphic rule of AC #3, that this is what makes duplicating or migrating a household work on one instance, that ids in a backup are file-local names and not stable identifiers, and that bookmarked links to an entity id from before a restore stop resolving); the "Confirm" bullet of "The two-phase flow" and the "If a restore is interrupted" paragraph say the one-active-restore rule is a database constraint; (b) `docs/data-export-format.md` states in one sentence under its id fields that ids identify rows **within the file** and that a restore assigns new ones; (c) the dev reads `web/src/components/data-import/data-import-panel.tsx` and `use-household-import-job.ts` and the screens that hold entity ids in state or in a route, and records in Completion Notes what the SPA does after a completed restore (refetch on mount, a reload, or nothing) and what a member sees when they open a screen that still holds an old id; **a fix is in scope only if a confirmed, reproducible stale-id failure exists** (Task 6.2), otherwise the finding is documented and no frontend file changes.
11. **Implied (AD-6 and project-context must say what now exists):** `ARCHITECTURE-SPINE/invariants-rules.md` AD-6 gets one `[IMPLEMENTED 2026-10-25, Story 11.14]` line (the filtered unique index, the guarded types, `ActiveJobAlreadyExistsException`, the early check kept as the fast path) and the restore sentence of the document that says entities keep their ids, if one exists (the dev greps `ARCHITECTURE-SPINE` for the reuse claim and corrects it with a one-line `AMENDED 2026-10-25, Story 11.14` note, not a rewrite of the Rule); `_bmad-artifacts/project-context.md` gets one bullet under "Framework-Specific Rules" (the two rules: restore re-keys everything, and the one-active-restore-or-cleanup index is raw SQL in migrations only; both guard tests; the `ExclusivePerHousehold` list) and a bumped "Last Updated"; "Async jobs (AD-6)" keeps its text.

## Dev Notes

### What this fixes and why it is safe to change

- **C10 (Low, verified).** `RestoreHouseholdData.ToRestoreData` copies `Id` and every reference from the file, and `MeterReading.IdempotencyKey` has a global unique index (`MeterReadingConfiguration.cs:50-51`). Restoring household A's export into household B on one instance while A exists fails on the first `AddRangeAsync` chunk after the delete phase, inside the transaction: it rolls back cleanly, the member sees a generic "restore failed", and nothing says why. The second half of C10 is that "one restore per Household" is only an application check (`ListByJobTypeAsync` then `EnqueueAsync`, `HouseholdImportEndpoints.cs:106-141`): two confirms with two tokens can both pass it before either row exists.
- **Why re-keying is safe.** Nothing outside the file's own graph points at restored ids: `SmartPlugImportId` is always null on restored readings, `BackgroundJob` rows and `HouseholdMember` rows are not restored (AD-25, and they carry no restored ids), every FK between restored categories is inside the file, and the two references without a foreign key (`Event.TaggedEntityId`, `AuditCorrection.EntityId`) are exactly the ones AC #3 names. The restore is already "a wholesale replace, not an edit" (`docs/data-import-restore.md`), so new ids do not change what a member sees: same names, values and history.
- **Why the guard is safe.** The index only forbids what the application already forbids (a second active restore or cleanup per Household). Terminal rows are outside it, and every code path that ends a job already goes through `IBackgroundJobLifecycle` (AD-6), so the slot is always freed by the existing transitions. Nothing reads or writes the index directly. The only new failure mode is the one AC #7 handles: a lost race, which now answers like the early check instead of a 500.

### Q1: re-key or reject (the Ask First, with the facts that decide it)

**Recommendation: re-key.** The epic leaves the choice to Ralf; the code makes it lopsided:

- **Reject "up front" needs a cross-Household existence probe, which AD-3 forbids.** To say "this id already exists in another Household" the code must query other Households' rows: `IgnoreQueryFilters()`, a raw query, or a second unfiltered context. AD-3's rule is that none of these is ever used against a Household-scoped entity, and the one place that does bypass the filter on purpose, `HouseholdExportReader`, is guarded by `HouseholdExportReaderDoesNotBypassTenantIsolationTests` to carry an explicit **`HouseholdId == current`** predicate; a collision probe is by definition the opposite (`!=`). So "reject" is not just more code, it needs an AD-3 amendment.
- **Reject "at restore time" cannot say why.** Catching the primary-key or unique violation after the delete phase would be portable only by inspecting provider error text, and the same violation also fires for file problems the validator does not check (duplicate Room names, duplicate `(PowerPointId, IntervalStart)`), so the specific message would sometimes be wrong. It also fails the AC's "up front".
- **Re-key has no detection step at all.** New random ids cannot collide, so it works on the first try and the user story's "duplicating or migrating a household" simply works. Cost: ids change on every restore (including a household restoring its own backup), which breaks only bookmarked entity links and an open tab's in-memory ids; the offline queue holds no restored ids (it queues new readings with their own idempotency keys).
- **Alternatives considered and left out:** *re-key only when the file's `household.id` differs from the current one* (a cheap proxy; it is wrong exactly in the cases that matter, a doctored or copied file, and it keeps two code paths); *re-key only on collision* (needs the probe above).

### If Ralf chooses reject instead

The active-job guard (Task 3) is unchanged. Task 2 is dropped and replaced by: an AD-3 amendment, written and approved first, that allows one narrow collision probe (a port `IHouseholdImportCollisionProbe` in Application, an adapter in Infrastructure that reads only `Id` columns of the twelve categories and the idempotency keys, filtered `HouseholdId != current`, chunked like the restore's deletes, and a guard test that it never returns or logs a row's content); the probe runs in `ReceiveUploadAsync` after validation and before `Register` (so the file is rejected up front, with the temp file deleted by the existing `finally`), and answers `409` ProblemDetails with a stable `errorCode` (`restore.id_collision`) and a message that names the **category and count** of colliding ids, never an id; `ValidateHouseholdImport` stays pure. Tasks 1.1-1.3 and 7.1 become probe tests; `docs/data-import-restore.md` gains a "Restoring another household's backup on the same instance is refused" section instead of AC #10a's new section, and the stale "reused byte-for-byte" text stays true. One new frontend string pair (de-DE, en-US) is needed for the `409` detail.

### Design decisions already made (do not re-litigate; Ralf can override at review; none changes an epic AC except Q1, which is the epic's own Ask First)

- **Q1 re-key everything, always** (see above). Pending Task 0.3.
- **Q2 a filtered unique index on `(HouseholdId, JobType)` for the two guarded types, not one index across both** (restore and cleanup are allowed to be active together; the epic says "active restore and cleanup jobs", not "one of either"), and not on every job type (several Smart Plug imports queue per Household).
- **Q3 the migration fails surplus duplicates instead of failing loudly.** A unique-index build error would fail the deploy and force a point-in-time restore for a phantom job row; failing the surplus rows with `job-interrupted` keeps history and is what `FailStaleAsync` would eventually do to such rows anyway. (Story 11.4's migration chose to fail loudly because truncating a name would destroy data; nothing is destroyed here.)
- **Q4 detect the conflict by probing after the failed insert, not by parsing the database error.** Portable across Npgsql and SqlClient, no error-number tables, and the probe also returns the id the cleanup endpoint needs.
- **Q5 the early checks stay.** They fail stale rows first and give the friendly answer without a failed insert; removing them would make every busy-household answer depend on an exception.
- **Q6 `IdempotencyKey` is re-keyed too.** Keeping it would keep the global unique index as a collision source; the only loser is a retry of an already-uploaded reading that crosses a restore, which cannot exist in practice (the client queue retries within seconds).
- **Q7 `AuditCorrection.EntityId` that resolves to nothing is kept.** It has no foreign key and is read by `(EntityType, EntityId)` for rows that exist; dropping or failing on an unresolved one would lose history for no benefit.

### Technical details the dev must get right

- **The two polymorphic references are the easy bug.** `Event.TaggedEntityId` and `AuditCorrection.EntityId` have no foreign key, so no database error and no validator check will tell you they were left pointing at old ids: only the Task 1.1 tests and the C10 round trip (Task 1.3, which then reads the restored events and corrections back and checks each id resolves) catch it. `TaggedEntityType` is `"Room"`/`"PowerPoint"`/`"Device"` (capitalised, `CreateEvent`), `EntityType` is `"MeterReading"`/`"Tariff"`; compare case-insensitively to be safe.
- **Maps over a streamed-in graph, not a second graph.** `HouseholdExportResult` is already fully materialized; build the maps once, then produce entities. Do not copy the `SmartPlugReadings` list twice (it can hold hundreds of thousands of rows; restore peak RSS is already the next memory risk, `deferred-work.md`).
- **Id source.** `Guid.NewGuid()` like the rest of the codebase (`Guid.CreateVersion7` would change index locality on SQL Server and is not part of this story); inject `Func<Guid>` only so the pure tests are deterministic. Register nothing new in DI unless the use case constructor needs it: keep `RestoreHouseholdData(IHouseholdRestoreWriter)` as is and let it own a `new HouseholdRestoreRekey()` field, or add a defaulted parameter; do not break `Program.cs`'s `AddScoped<RestoreHouseholdData>()` or the existing `Sut()` in `RestoreHouseholdDataTests`.
- **Migration SQL.** Postgres: `UPDATE "BackgroundJobs" ... WHERE "Status" IN (0, 3) AND "JobType" IN (...) AND EXISTS (SELECT 1 FROM "BackgroundJobs" n WHERE n."HouseholdId" = "BackgroundJobs"."HouseholdId" AND n."JobType" = "BackgroundJobs"."JobType" AND n."Status" IN (0, 3) AND (n."CreatedAtUtc" > "BackgroundJobs"."CreatedAtUtc" OR (n."CreatedAtUtc" = "BackgroundJobs"."CreatedAtUtc" AND n."Id" > "BackgroundJobs"."Id")))`; SQL Server needs an alias on the updated table (`UPDATE j SET ... FROM [BackgroundJobs] j WHERE ...`). `Status = 2`, `ErrorMessage = 'job-interrupted'`, `CompletedAtUtc` the provider's current instant. Do not use the literal `2`/`0`/`3` without a comment naming `BackgroundJobStatus`.
