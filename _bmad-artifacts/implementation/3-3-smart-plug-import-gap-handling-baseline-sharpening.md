# Story 3.3: Smart-Plug Import Gap Handling & Baseline Sharpening

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Household member,
I want my Smart Plug data to sharpen my Status without ever being treated as more certain than it is,
so that gaps in coverage don't quietly corrupt my baseline.

## Acceptance Criteria

1. **Given** a Household with zero Smart Plug coverage, **when** Status is computed, **then** it still gets a fully functional Status from Meter Readings alone (FR-5).
2. **Given** imported Smart Plug data, **when** Status is computed, **then** the data sharpens the Status as an additional signal — it is never summed against or reconciled to the Main Meter total (FR-5, AD-14).
3. **Given** a Smart Plug import completes, **when** processing finishes, **then** Status recomputes immediately via the same `IStatusRecomputeService` used for new Meter Readings (Story 2.4), writing a fresh `StatusSnapshot` row — never left to a fixed schedule (FR-6, AD-7).
4. **Given** an import's covered date range, **when** a date within it has no interval data, **then** it's treated as a Gap; a 0 kWh reading is treated as a valid data point, never as a Gap (FR-24).
5. **Given** a Gap used to sharpen the baseline, **when** its value is filled, **then** it's bounded (e.g. capped at the preceding week's average) and visibly flagged as interpolated, never presented as measured data (FR-24).
6. **Given** a Gap at the very start of a household's first-ever import, with no preceding week to average, **when** detected, **then** it's left unfilled and flagged as missing, not interpolated from nothing (FR-24).
7. **Given** an import file whose data is entirely Gaps, **when** processed, **then** it's flagged for review rather than wholesale-interpolated (FR-24).
8. **Given** the gap-flagged visual treatment, **when** rendered, **then** it reuses the same gap-band / status-trending color vocabulary as Trend History gaps rather than inventing a new one (UX-DR6).

## Dev Notes

### This is the hardest story in Epic 3 — read the whole Dev Notes before starting

Stories 3.1/3.2 built the upload/parse/mapping pipeline; this story is the first to touch **Status** (Epic 2's core deliverable) from Smart Plug data, and the epic/PRD deliberately leave the *mechanism* of "sharpening" underspecified (`FR-5`'s own text: "refines Pattern Detective's baseline/Status as an additional signal" — no further detail anywhere in the PRD, epics, architecture spine, or UX docs; confirmed via full-text search of all planning artifacts). Task 4's design (low-confidence-flag softening only, never touching the pace/baseline figures) is this story's own proposal for satisfying AC #2 within AD-14's hard boundary — it is the recommended default, not a directly-stated requirement. **See "Open Questions for Ralf" below; confirm this mechanism before/during dev-story activation, exactly the same "propose → confirm" pattern Story 2.4 used for `LowConfidenceGapDays`'s 45-day default.**

### Architecture constraints (binding, not optional)

- **AD-14 — the single most important constraint in this story, and it has a literal, automated guard.** `tests/EnergyTracker.Architecture.Tests/PatternDetectiveDoesNotReferenceSmartPlugOrEventDataTests.cs` scans `GetCurrentStatus.cs`, `StatusRecomputeService.cs`, `PatternDetectiveCalculator.cs`, `BonusDecayNormalizer.cs`, `Status.cs`, `StatusSnapshot.cs`, `IStatusRecomputeService.cs`, `StatusSnapshotConfiguration.cs`, `StatusEndpoints.cs` for the literal word `SmartPlugReading` (and `Event`) and fails the build if found — even inside a non-comment line that merely mentions it. Task 4's `ISmartPlugCoverageSignal` port design exists specifically to satisfy AC #2 ("sharpens... as an additional signal") **without** any of those nine files ever containing the word `SmartPlugReading` — the port's name, its DTOs, and its implementation file are all outside the guard's file list and may reference `SmartPlugReading` freely. Do not "fix" a failing guard test by editing the test itself; that defeats its entire purpose (it was written in Story 2.4 explicitly so a *future* story — this one — couldn't quietly wire Smart Plug data into Pattern Detective's core math).
- **AD-7 — two completion paths, two hooks, both new to this story.** Both gap detection (Task 2/3) and Status recompute (Task 3) must fire from **both** `ProcessSmartPlugImport`'s direct-match completion and `MapSmartPlugImportToPowerPoint`'s mapping completion. Story 3.2's own Dev Notes explicitly flagged the Status-recompute half of this for 3.3's author; this story additionally introduces gap detection as a *second* thing that must not be wired to only one path. The `CompleteSmartPlugImportProcessing` helper (Task 3) exists to prevent the logic being written twice and drifting.
- **AD-9 — gap detection stays vendor-agnostic.** `SmartPlugGapDetector` (Task 2) operates purely on `SmartPlugReading.IntervalStart`/`IntervalEnd` dates, which are already normalized by each vendor's `ISmartPlugParser` adapter (Eve Home ~10-minute point samples, `IntervalStart == IntervalEnd`; Meross one full-day interval per row, Story 3.1's `MerossCsvParser.cs:57-58`). No vendor-specific logic belongs in the gap detector.
- **AD-10 — gap detection needs a resolved Power Point, so it cannot run before matching.** Exactly like the AD-10 by-value snapshot Story 3.2 built, gap detection (which needs "prior readings for this Power Point" to compute a trailing average) can only run once a Power Point is known — i.e. at one of the two completion paths, never during `AwaitingPowerPointMapping`'s parked state (Task 3).
- **AD-2 — the new `SmartPlugImportGap` table needs a migration via `scripts/add-migration.sh`**, both provider projects, one commit (Task 1). `EstimatedTotalKwh` uses `HasPrecision(18, 6)` — match `SmartPlugReading.KwhValue`'s scale (`SmartPlugReadingConfiguration.cs:19-20`'s documented reasoning: Eve Home's Wh/1000 figures need more than 2 decimal places), not `MeterReading`'s scale-2.

### Existing code to reuse, not reinvent

- `IStatusRecomputeService`/`StatusRecomputeService` (Story 2.4) — call unchanged, exactly as `CreateMeterReading.ExecuteAsync` already does for the Meter-Reading-create path (`src/EnergyTracker.Application/CreateMeterReading.cs:78`). Do not build a second snapshot writer.
- `GetCurrentStatus.ExecuteAsync` (Story 2.4) — already computes `IsLowConfidence` from the Meter-Reading-only gap (`src/EnergyTracker.Application/GetCurrentStatus.cs:52-55`); Task 4 extends this exact method, doesn't duplicate its logic elsewhere.
- `ISmartPlugImportRepository`/`SmartPlugImportRepository` (Story 3.1/3.2) — extend with the new read/write methods Task 3 needs (`ListReadingsByPowerPointAsync`, `AddGapsAsync`/equivalent, `ListGapsByImportIdAsync`); follow the existing single-`SaveChangesAsync`-per-operation, no-partially-observable-state discipline every existing method in that file already follows.
- `SmartPlugImportValidationException` (`ProcessSmartPlugImport.cs`, bottom of file) — this story **modifies** its one existing throw site (`readings.Count == 0`) rather than adding a parallel check; see Task 3.
- `PatternDetectiveCalculator`/`BonusDecayNormalizer` (Story 2.4) — **do not touch**. Task 4's entire design goal is that these two files, and the pace/baseline math they implement, are completely unaffected by this story.

### Open Questions for Ralf — confirm before/during dev-story activation

*(Same pattern as Story 2.4's `LowConfidenceGapDays` default and Story 3.2's Room-picker addition: proposed here with a concrete recommended default, but genuinely undetermined by the PRD/epics/architecture — confirm before or during dev-story activation, then move this section's answers into Completion Notes, same as Story 2.4/3.2 did.)*

1. **What exactly does "sharpens the Status as an additional signal" mean, mechanically?** No PRD/epic/architecture/UX doc specifies this beyond the qualitative wording (confirmed via full-text search). **Recommended default (Task 4):** Smart Plug interval data can only *soften* the existing `IsLowConfidence` flag (never touches `PaceToDateKwh`/`BaselineToDateKwh`/the Trending resolution) when it corroborates an otherwise-long Meter-Reading gap. Alternative designs considered and rejected: (a) summing Smart Plug kWh into the pace figure — directly forbidden by AD-14; (b) surfacing Smart Plug data only as inert UI context with zero effect on Status — technically satisfies AC #1 but makes AC #2's "sharpens... as an additional signal" wording meaningless, since nothing about Status would actually change.
2. **Gap-fill "preceding week" data source when the gap sits at a file's own start edge.** AC #6's wording ties "no preceding week to average" to "a household's first-ever import," while the mockup's own copy (`key-smart-plug-import.html:484`) scopes it to "no prior **Office Desk** [Power-Point] history" — a Power-Point-level, not household-level, framing. **Recommended default (Task 2):** resolve at Power-Point granularity — a gap is fillable whenever *any* of the 7 preceding calendar days has data anywhere (this import's own earlier rows, or a prior persisted import for the same Power Point), regardless of whether it's technically the household's very first import ever. This is simpler to test, matches the mockup's literal copy, and degrades correctly to "household's first-ever import" as a special case (no Power Point has any prior data yet either).
3. **AC #7's "covered date range" for a file that parses to zero rows.** Recommended default (Task 3): reuse `ProcessSmartPlugImport`'s pre-existing `readings.Count == 0` check as AC #7's trigger — see Task 3 for the reasoning. If Ralf intends a genuinely different scenario (e.g. a file with real rows whose dates somehow all still count as gaps against some external "expected" range), that would need an actual range signal this story doesn't currently have access to (neither vendor format carries a declared date-range separate from its own rows) and should be scoped as a follow-up, not built speculatively here.

### Known non-goals (avoid scope creep)

- **No UI for browsing/re-reviewing a `FlaggedForReview` import's raw data.** The mockup's State 5 "Review file details" button (`key-smart-plug-import.html:536`) has no corresponding drill-down screen designed anywhere — render the button as a visual affordance only (or omit it) rather than building a new detail view; not required by any AC.
- **No retroactive gap re-detection when new data arrives for a Power Point.** A gap detected and persisted at import-completion time is not re-evaluated by a later, unrelated import — each `SmartPlugImportGap` is scoped to the `SmartPlugImportId` that produced it, immutable after creation (same "insert-only, never rewritten" discipline as `StatusSnapshot`, AD-7/NFR9's precedent, even though this isn't itself an AD-7 concept).

- **Design refinement discovered during implementation of `SmartPlugGapDetector` (Task 2), beyond the story's literal text — flagging transparently, same as prior stories' "propose → confirm" pattern applied retroactively:** a literal reading of Task 2 step 3 ("if at least one of the 7 preceding days has data → Estimated; if none → Missing") makes `Missing` mathematically unreachable. A detected gap's immediately-preceding calendar day is *always* present in the data by construction — that's what makes it the gap's boundary in the first place — so "at least one of 7 preceding days has data" is always true for any gap a presence-based sweep can find. Implemented instead: `Estimated` requires a **genuine full preceding week** to have elapsed since this Power Point's earliest-ever known reading (across prior imports, or this file's own first date if none); fewer than 7 calendar days of real history behind the gap is treated as "no preceding week to average" (`Missing`), regardless of how sparse that short stretch is. This is reachable, unit-tested (`SmartPlugGapDetectorTests`), and satisfies AC #6's literal wording ("no preceding week to average") more faithfully than the mathematically-dead alternative. The actual numeric fill for `Estimated` still averages only whichever of the literal 7 trailing days have data, per AC #5.
- **AC #6/mockup-vs-buildable discrepancy, documented rather than silently resolved:** the mockup's State 4 narrates a gap literally *preceding* a first-ever import's earliest real reading (e.g., "Aug 1–3 missing, Aug 4–9 measured"). Neither vendor parser carries a declared file date-range separate from its own rows (same limitation Dev Notes already flagged for AC #7's Open Question #3), so a leading gap with literally zero rows anywhere in the file is structurally undetectable — the covered range can only start at the first date that actually has a row. The implemented behavior (above) reaches the same *practical* outcome AC #6 needs (an early, thin-history gap gets `Missing`, not a spurious `Estimated`) without depending on unavailable file-range metadata.
