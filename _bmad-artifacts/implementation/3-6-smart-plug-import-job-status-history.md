# Story 3.6: Smart Plug Import Job Status & History

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Household member,
I want to see the status of every Smart Plug import my household has ever run — not just the one I'm watching finish — in six clearly distinct states,
so that I can find and resolve one that needs my attention without having to remember who uploaded what.

## Context (why this is needed)

Story 3.1 built per-file upload + polling (`GET /api/jobs/{id}`), and Story 3.5 built a client-side, this-action-only multi-file queue on top of it — both are ephemeral: reload the page, or have another member start an import, and that state is gone. FR-32 (added 2026-08-26, epic-3) adds a **durable, household-wide** list on the same screen: every job any member has ever queued, in exactly six never-folded-together states, with a 30-day lazy retention sweep for the three terminal ones. AD-6 was extended the same day to name the exact backend shape this needs (`BackgroundJobStatus.Queued`, enqueue-time row creation, read-triggered sweep) — this story is where that extension gets built.

## Acceptance Criteria

1. **Given** any Household member, **when** they open the Smart Plug Import screen, **then** they see every import job queued by any member of their Household, not only their own (FR-32, AD-3 tenant isolation still scopes this to one Household, never cross-Household).
2. **Given** a job's lifecycle, **when** rendered in the list, **then** it shows exactly one of six states — Waiting, Processing, Success, Error, Needs Mapping, Flagged for Review — never folded into one another or a generic pending/done (FR-32, UX-DR21).
3. **Given** a job enqueued but not yet dequeued (e.g. a cold start, or a later file in a multi-file queue), **when** the list is read, **then** it shows as Waiting — backed by a new `BackgroundJobStatus.Queued` value and a `BackgroundJob` row created at enqueue time, not only once dequeued (AD-6 extension).
4. **Given** a job in Needs Mapping (Story 3.2's create-or-map condition), **when** a Household member selects that row, **then** it opens directly into that import's create-or-map-Power-Point prompt — the household never has to relocate the original upload to resolve it (FR-32).
5. **Given** a job in Flagged for Review (Story 3.3's entirely-Gaps condition), **when** rendered, **then** it is visually and semantically distinct from Error — the file parsed without failure, it simply had nothing usable (FR-32, UX-DR21).
6. **Given** a job that reached Success, Error, or Flagged for Review, **when** 30 days have elapsed since its completion, **then** its job/audit record is removed the next time the list is read — a lazy, read-triggered sweep piggybacked on the list query, never an `IHostedService`/`Timer`-based schedule (AD-7) — and the `SmartPlugReading` data that job already wrote is never touched (AD-6 extension, AD-20).
7. **Given** Waiting, Processing, or Needs Mapping jobs, **when** 30 days elapse, **then** they are never auto-removed — only completed/resolved/failed states are subject to cleanup (FR-32).
8. **Given** a Household with no Smart Plug import activity in the last 30 days, **when** the screen is opened, **then** it shows an empty state, not an error or blank space (FR-32, UX-DR21).

## Dev Notes

### The two hazards most likely to cause a broken or incomplete implementation

1. **`SmartPlugReading.SmartPlugImportId`'s FK is `Restrict` today (Task 3).** Attempting Task 4's sweep against the current schema will throw a foreign-key-violation on the first `SmartPlugImport` delete that has any readings attached (i.e. every real Success import) — this is not a theoretical edge case, it will fail every single sweep. Fix the FK's delete behavior (`SetNull`) and the column's nullability *before* writing the sweep, not after.
2. **`BackgroundJob.Status`/`SmartPlugImportStatus` are both stored as plain ints (no `HasConversion`).** `Queued` must be appended to the end of `BackgroundJobStatus`, never inserted before `Processing` — inserting it first silently reinterprets every already-persisted `Processing`/`Completed`/`Failed` row as the wrong status the moment this migration runs. Story 3.3 already established this exact append-only discipline for `SmartPlugImportStatus.FlaggedForReview`; follow the same rule here.

### Architecture constraints (binding, not optional)

- **AD-6 extension (this story's primary spec):** `invariants-rules.md:39` is the authoritative source for the `Queued` status + enqueue-time row creation + lazy read-triggered sweep shape — re-read it if any task above is ambiguous.
- **AD-3 (tenant isolation):** the new list endpoint and `QueuedByHouseholdMemberId` FK follow the same Household-scoping discipline as every other entity in this codebase — no `IgnoreQueryFilters()`/`FromSqlRaw`/`.Find()` against `BackgroundJob`/`SmartPlugImport`/`HouseholdMember`.
- **AD-7 (no scheduled background sweep):** the retention sweep is piggybacked on `ListSmartPlugImportJobs`'s own query path — never an `IHostedService`/`Timer`. Do not add one.
- **AD-20 (Smart Plug data is never deleted by this mechanism):** the sweep deletes only `BackgroundJob`/`SmartPlugImport`/`SmartPlugImportGap` audit rows — `SmartPlugReading` rows are never deleted, only detached (`SmartPlugImportId → NULL`) via Task 3's `SetNull` FK.
- **AD-2 (dual-provider):** the one migration covering Tasks 1-3 goes through `scripts/add-migration.sh` to both `Infrastructure.Migrations.Postgres` and `Infrastructure.Migrations.SqlServer` projects, verified via Testcontainers on both — this migration is schema-only (enum append needs no data migration; the nullable-column change and new FK are portable EF operations), unlike Story 3.4/3.7's raw-SQL cleanup migrations.

### Existing code to reuse, not reinvent

- `PowerPointMappingDialog` (Story 3.2) and `GapCard` (Story 3.3) — both reused completely unmodified for Needs Mapping and Flagged for Review row interactions. Do not fork or duplicate either component.
- `nav-chrome-active-bg`/`-active-foreground` tokens (Story 3.5's entry-icon precedent) for Processing/Needs Mapping badge chrome; `status-trending`/`-badge-bg`/`-badge-text` tokens (`GapCard.tsx`) for Flagged for Review — no new color tokens needed anywhere in this story.
- `BackgroundJobProcessor`'s existing scope-per-operation (`IServiceScopeFactory`) pattern — the new enqueue-time recorder (Task 1) and any DB access from the two singleton queue adapters should mirror it exactly, not invent a second convention.
- `ExecuteDeleteAsync`/`ExecuteUpdateAsync` set-based idiom — already established in `SmartPlugImportRepository.UpdateMappingAsync` and Story 3.7's duplicate-cleanup fix, for exactly the same reason (this table can hold hundreds of thousands of rows; load-then-mutate-then-save does not scale here).

### Known non-goals (avoid scope creep)

- **No UI anywhere else in the app to view/edit a household member's display name** — Task 2 only captures it at membership-creation time (household creation / invite acceptance) for this story's own "Queued by" line. A Settings-page member list/rename feature is not in scope.
- **No live push/WebSocket updates to the job history list** — AD-6 forbids it outright; the list's own periodic re-fetch (Task 5) is the only "freshness" mechanism, same polling-based discipline as every other async surface in this codebase.
- **No retroactive backfill of `QueuedByHouseholdMemberId`/`OriginalFileName`/`DisplayName` for jobs/members that already exist in production** — all three are nullable specifically so pre-existing rows degrade gracefully (a pre-Story-3.6 `BackgroundJob` row, if one somehow still exists past its own age, would show a generic "queued by a household member" and an empty filename — acceptable, not worth a data migration for).
- **No change to the per-session upload-queue UI (`use-smart-plug-import-job.ts`, the existing `SmartPlugImportQueueItem`)** — Story 3.5's ephemeral, this-action-only queue stays exactly as-is; this story adds a second, separate, durable list below it, per EXPERIENCE.md's explicit "sits on the same screen, below the upload area" framing.
