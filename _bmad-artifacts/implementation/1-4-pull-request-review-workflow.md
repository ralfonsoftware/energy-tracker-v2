# Story 1.4: Pull Request Review Workflow

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a contributor,
I want a GitHub Actions workflow that runs on every pull request,
so that build failures, test failures, or infrastructure drift are caught before merge, without deploying anything.

## Acceptance Criteria

1. **Given** a pull request opened or updated against `main`, **when** the workflow runs, **then** it restores/builds the .NET solution and `web/` frontend, runs the full test suite, and reports pass/fail as a PR status check.
2. **Given** the same PR, **when** linting is configured for the frontend/backend, **then** lint failures are also reported as a status check.
3. **Given** the PR workflow needs to validate infrastructure changes, **when** `infra/**` Bicep files changed in the PR, **then** it authenticates via OIDC federated-credential login scoped to the `pull_request` subject — distinct from the `main`-branch credential used for real deploys — and runs a read-only `what-if`/validate operation only, never an actual deployment.
4. **Given** a PR opened from a fork, **when** the workflow runs, **then** no Azure login step executes with deploy-capable permissions, since the federated credential's trust policy does not cover fork-originated runs — avoiding a credential-leak/privilege-escalation path.
5. **Given** the workflow's checks, **when** all pass, **then** the PR is unblocked for merge per branch protection; when any check fails, the PR is blocked.

## Tasks / Subtasks

- [ ] Task 1: Author the CI build/test/lint job (AC #1, #2)
  - [ ] New workflow file `.github/workflows/pr-review.yml`, trigger: `pull_request: { branches: [main] }` (no `paths:` filter at the workflow level — AC #1 requires build/test to run for **every** PR against `main` regardless of which files changed; contrast with `infra-deploy.yml`'s `infra/**` filter, which doesn't apply here since this workflow's build/test job isn't infra-specific)
  - [ ] `permissions: { contents: read }` at the workflow level for this job — no `id-token: write` here (that's scoped to the `validate-infra` job only, Task 2, keeping the least-privilege boundary explicit per-job)
  - [ ] Concurrency: `group: pr-review-${{ github.event.pull_request.number }}`, `cancel-in-progress: true` — set once at the **workflow level** (top-level `concurrency:` key, sibling of `on:`/`permissions:`), not per-job. This workflow has two jobs (`build-test-lint` here, `validate-infra` in Task 2); a workflow-level `concurrency:` block applies the same cancel-on-resupersede behavior to both, so a rapid sequence of pushes to the same PR doesn't leave stale `what-if` runs piling up in `validate-infra` while only `build-test-lint` gets canceled. `app-deploy.yml`/`infra-deploy.yml` only ever had one job each, so there's no existing precedent to copy for this two-job case — don't default to a job-level block by analogy with those files. This is **deliberately the opposite** of `app-deploy.yml`/`infra-deploy.yml`'s `cancel-in-progress: false`: those must never race concurrent deploys against the same live resource, while a PR check has no such shared-mutable-state risk, and canceling a superseded run on `synchronize` (new push to the PR) saves CI minutes instead of running two checks for a commit nobody cares about anymore.
  - [ ] Job `build-test-lint`, `runs-on: ubuntu-latest`, `timeout-minutes: 30` (same budget as `app-deploy.yml`'s job, for the same reason — bound a hung step)
  - [ ] `actions/checkout@v7` (default shallow clone — this job never diffs against `base`, unlike Task 2's job)
  - [ ] `actions/setup-dotnet@v6` with `global-json-file: global.json` (picks up SDK `10.0.100`/`rollForward: latestFeature` — do not hardcode a `dotnet-version`, exactly as `app-deploy.yml` already does)
  - [ ] `dotnet restore EnergyTracker.sln`, then `dotnet build EnergyTracker.sln --no-restore --configuration Release` — **Release**, not the default Debug, to match what `app-deploy.yml` gates and what `Dockerfile` actually publishes (this exact Debug/Release mismatch was a Story 1.3 review finding — don't reintroduce it here)
  - [ ] `dotnet test EnergyTracker.sln --no-restore --configuration Release` — runs all three test projects (`Api.Tests`, `Infrastructure.Tests`, `Architecture.Tests`) via the `Microsoft.Testing.Platform` runner (`global.json`). `Infrastructure.Tests` uses Testcontainers, which drives Docker directly — `ubuntu-latest` ships Docker pre-installed, so no `services:` block is needed, exactly as `app-deploy.yml` already established. A non-zero exit here must fail the job (AC #1) — do not add `continue-on-error:` or `if: always()` anywhere in this sequence.
  - [ ] `actions/setup-node@v7` with `node-version: '22'` — matches `Dockerfile`'s `node:22-alpine` build stage exactly, same reasoning `app-deploy.yml` documents (don't follow `web/package.json`'s `@types/node ^24`, that's a type-checking version only)
  - [ ] `npm --prefix web ci` (reproducible, matches `Dockerfile`'s frontend stage — never `npm install`), `npm --prefix web run build`, `npm --prefix web run test` (Vitest, single run via `vitest run`)
  - [ ] Lint step (AC #2): `npm --prefix web run lint` (this repo's frontend lint is `oxlint`, already configured in `web/package.json`'s `lint` script — add it as its own step so a lint failure is individually visible in the PR checks UI, not buried inside the build step). **No backend/.NET linting is currently configured anywhere in this repo** (no `.editorconfig`, no `EnableNETAnalyzers`/`AnalysisLevel`/`TreatWarningsAsErrors` in any `.csproj`/`Directory.Build.props` — verified by search at story-creation time). AC #2's condition ("when linting is configured...") is therefore **not yet true for the backend** — do not invent a backend lint gate (e.g. `dotnet format --verify-no-changes`) as part of this story; that would silently expand scope beyond what's configured today. If backend analyzers get configured in a later story, this workflow's frontend-lint step is the pattern to extend, not something to redesign.
  - [ ] Playwright `test:e2e` is **not** included in this gate, for the same reasoning `app-deploy.yml`/Story 1.3 already established and documented (epic AC only names "the test suite" without specifying e2e; browser-install + server-spinup cost/flakiness isn't justified here). Keep this consistent rather than re-litigating it — note the decision in Completion Notes rather than silently omitting it.

- [ ] Task 2: Author the conditional, fork-safe infra validation job (AC #3, #4)
  - [ ] Same workflow file, second job: `validate-infra`, `runs-on: ubuntu-latest`, `timeout-minutes: 15`, independent of `build-test-lint` (no `needs:` — both should start immediately in parallel; infra validation failing should not block seeing .NET/frontend results and vice versa, and neither result depends on the other)
  - [ ] `permissions: { id-token: write, contents: read }` on this job only — `build-test-lint` must **not** carry `id-token: write` (least-privilege boundary, and matches AC #4's spirit of not handing OIDC capability to a job that never needs it)
  - [ ] `actions/checkout@v7` with **`fetch-depth: 0`** (full history) — this job (unlike `build-test-lint`) needs to diff the PR's changed files against `base`, and a PR's auto-generated merge-commit ref (`refs/pull/N/merge`, what `pull_request` events check out by default) has its parent commits unavailable in a depth-1 shallow clone, so a bare `git diff HEAD^1 HEAD` would fail with "unknown revision" on a shallow checkout
  - [ ] Step "Check for infra changes" (`id: changes`): `git diff --name-only ${{ github.event.pull_request.base.sha }} ${{ github.event.pull_request.head.sha }} | grep -q '^infra/' && echo "infra_changed=true" >> "$GITHUB_OUTPUT" || echo "infra_changed=false" >> "$GITHUB_OUTPUT"` — a plain `git diff`/`grep`, no new third-party action (`dorny/paths-filter` etc. would work too, but this repo has so far used only first-party/`docker`/`azure` actions; keep that pattern rather than introducing a new dependency for one boolean check)
  - [ ] Step "Check if PR is from a fork" (`id: origin`): `echo "is_fork=${{ github.event.pull_request.head.repo.full_name != github.repository }}" >> "$GITHUB_OUTPUT"` — this is the explicit guard AC #4 requires. Do not rely solely on GitHub's built-in behavior of withholding secrets/OIDC tokens from fork-triggered `pull_request` runs (real, but an *implicit* safety net — if relied on alone, a fork PR that touches `infra/**` would hit `azure/login` and fail with an opaque credential error instead of a clear, intentional skip). Making the fork check an explicit, named condition is what makes AC #4 verifiable by reading the workflow, not just true by accident of platform behavior.
  - [ ] All remaining steps in this job gated on **both** `steps.changes.outputs.infra_changed == 'true'` **and** `steps.origin.outputs.is_fork == 'false'` via `if:`
  - [ ] Azure login (OIDC): `azure/login@v3` with `client-id: ${{ secrets.AZURE_CLIENT_ID }}`, `tenant-id: ${{ secrets.AZURE_TENANT_ID }}`, `subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}` — **reuse the same three repository secrets** `app-deploy.yml`/`infra-deploy.yml` already use (same managed identity). This relies on the existing identity's **second federated credential**, already provisioned for the `pull_request` subject (see Task 3) — no second identity, and no new credential to create. The AC's "distinct... credential" refers to the federated-credential trust entry (subject `pull_request` vs. `main`-branch), not a distinct Azure identity/secret set.
  - [ ] Resolve the resource group's what-if target the same way `infra-deploy.yml` does: `${{ vars.AZURE_RESOURCE_GROUP_NAME }}` (repo variable, not a secret — do not hardcode or reintroduce a second name)
  - [ ] Run **only** `az deployment group what-if` (never `az deployment group create`) against `infra/main.bicep` / `infra/main.bicepparam`, mirroring `infra-deploy.yml`'s existing `What-if (manual runs only)` step verbatim in mechanism — including passing `DATABASE_ADMIN_PASSWORD` from `secrets.DATABASE_ADMIN_PASSWORD` as an env var (the `@secure()` bicepparam parameter needs it to resolve even for a dry-run; `what-if` does not persist or expose this value)
  - [ ] Add a clearly-worded step (no `if:` restriction, always runs) that echoes a one-line notice when infra changed but validation was skipped because the PR is from a fork (`steps.changes.outputs.infra_changed == 'true' && steps.origin.outputs.is_fork == 'true'`) — e.g. `::warning::infra/** changed in this fork PR; what-if validation was skipped (fork PRs never get Azure credentials) — a maintainer should check out the branch locally and run 'az deployment group what-if' before merging.` This keeps AC #4's silent-skip invisible-to-reviewers risk from becoming its own gap — the job still reports success (no false-red block on a legitimate contribution), but the PR page isn't silently missing information a reviewer needs.

- [ ] Task 3: Verify the existing `pull_request` federated credential (prerequisite for Task 2 to function; not itself expressible in Bicep/workflow YAML)
  - [ ] **No credential needs to be created by this story.** The user-assigned managed identity `infra-deploy.yml`/`app-deploy.yml` already authenticate as — `energy-tracker-devops-uami` — already has **two** federated credentials configured: one trusting the `main`-branch push subject (pre-existing, documented in `infra/README.md`'s "One-time identity bootstrap" section) and one trusting the `pull_request` subject (already provisioned ahead of this story, outside of it). Task 2's `azure/login@v3` step in `validate-infra` can rely on the `pull_request`-subject credential already being in place — do not re-run `az identity federated-credential create` for it.
  - [ ] Confirm the existing `pull_request` credential's subject matches GitHub's documented OIDC subject-claim format for the `pull_request` event, `repo:ralfonsoftware/energy-tracker-v2:pull_request` — verify with `az identity federated-credential list --identity-name energy-tracker-devops-uami --resource-group <bootstrap-resource-group>` if live Azure CLI access is available; if not available, state in Completion Notes that the subject was taken on the user's word rather than independently verified, and that Task 2 should be watched for an `AADSTS70021`-shaped failure on first real PR run if the subject turns out to differ.
  - [ ] No new GitHub repository secrets are needed — `AZURE_CLIENT_ID`/`AZURE_TENANT_ID`/`AZURE_SUBSCRIPTION_ID` are identical across all three workflows (same identity, now three federated-credential trust entries total: `main`-branch push [shared by `infra-deploy.yml` and `app-deploy.yml`] and `pull_request` [this story])
  - [ ] Update `infra/README.md`'s "One-time identity bootstrap (already done — reference only)" section to note the identity now carries **two** federated credentials rather than one — add a reference-only entry for the `pull_request`-subject credential alongside the existing `main`-branch one, in the same style (a documentation record of what already exists, not a re-run instruction)

- [ ] Task 4: Branch protection (manual GitHub repo-settings step, not expressible in workflow YAML or Bicep) (AC #5)
  - [ ] Document (in `infra/README.md` or a comparable ops doc) that `main` needs GitHub branch protection with required status checks matching this workflow's two job names (`build-test-lint`, `validate-infra`) enabled via Settings → Branches → Branch protection rules, or `gh api repos/ralfonsoftware/energy-tracker-v2/branches/main/protection` — this is what actually makes AC #5's "blocks merge on failure" true; the workflow YAML itself only produces pass/fail status checks, it cannot make GitHub *require* them
  - [ ] Note: `validate-infra` reports success even when its steps are skipped (no infra changes, or fork-origin skip per Task 2) — a required status check on a job with conditional steps still reports an overall pass when the job itself doesn't fail, so making it a required check does not block non-infra PRs. Confirm this understanding is correct by reading GitHub's docs on required status checks with conditional jobs, or note it as unverified if not confirmed live.
  - [ ] If enabling branch protection is done via `gh api`/`gh ruleset`, note the exact command run in Completion Notes; if done manually via the Settings UI (no CLI trace), say so explicitly rather than fabricating a command that wasn't actually run

## Dev Notes

- **This story adds no new Azure resources and changes no Bicep templates, and no new federated credential either.** The `pull_request`-subject federated credential on the existing identity (`energy-tracker-devops-uami`) was already provisioned ahead of this story — Task 3 is a verification/documentation step, not a creation step. This story's only artifacts are one new GitHub Actions workflow file and a documentation update to `infra/README.md`. Cost impact: zero (NFR2/NFR14) — `what-if` is a read-only ARM API call with no billable resource created.
- **Two workflows already establish the patterns this story must reuse, not reinvent:** `.github/workflows/app-deploy.yml` (build/test steps for .NET + web — copy the restore/build/test/setup-node/npm sequence nearly verbatim, Release configuration and all) and `.github/workflows/infra-deploy.yml` (the OIDC login shape, the `what-if` step's exact `az deployment group what-if` invocation and its `DATABASE_ADMIN_PASSWORD` env-var handling, and the `vars.AZURE_RESOURCE_GROUP_NAME` repo-variable convention). Read both files in full before writing `pr-review.yml` — this story is assembling already-proven pieces into a new trigger shape, not designing new CI mechanics from scratch.
- **Concurrency semantics deliberately differ from the other two workflows** — see Task 1's `cancel-in-progress: true` note. Don't copy `app-deploy.yml`/`infra-deploy.yml`'s `cancel-in-progress: false` by reflex; the rationale (avoid racing a shared live resource) doesn't apply to a PR check, and canceling superseded runs is the better default here.
- **The fork-safety mechanism (AC #4) has two layers, and Task 2 implements the outer one explicitly rather than relying on the inner one alone:**
  1. GitHub's platform-level behavior: `pull_request`-triggered workflow runs from a forked repository do not receive repository secrets or an OIDC token, regardless of `permissions: id-token: write` in the workflow file. This is real and is the actual security backstop.
  2. This story's explicit `is_fork` check (Task 2) makes that backstop *visible and intentional* in the workflow's own logic, so a reviewer can confirm AC #4 by reading the YAML rather than trusting undocumented platform behavior — and so a fork PR that touches `infra/**` gets a clear skip notice instead of an opaque `azure/login` failure.
- **Subject claim for the existing `pull_request` federated credential is expected to be `repo:ralfonsoftware/energy-tracker-v2:pull_request`** (constant string per GitHub's OIDC subject-claim format for the `pull_request` event — same value whether the PR originates from a branch in this repo or, hypothetically, a fork; the fork exclusion comes from GitHub withholding the token entirely for fork runs, not from the subject claim differing). This credential was already provisioned ahead of this story on `energy-tracker-devops-uami`; Task 3 confirms rather than assumes this subject. Verify this subject format against GitHub's current OIDC docs at implementation time rather than trusting it blindly — federated-credential subject formats have historically been an easy-to-get-subtly-wrong detail.
- **No backend lint gate exists yet, and this story does not create one** — see Task 1's lint step notes. Don't let AC #2's phrasing ("when linting is configured for the frontend/backend") be misread as "make sure both are configured"; it's a conditional describing what to gate *if* configured, and only the frontend currently is.
- **`fetch-depth: 0` is scoped to the `validate-infra` job only** (Task 2) — `build-test-lint` doesn't need full history and should stay on the default shallow checkout for speed; don't apply `fetch-depth: 0` to both jobs out of consistency-for-its-own-sake.
- **Two jobs, not one**, so GitHub's branch-protection required-status-checks can gate on `build-test-lint` and `validate-infra` independently (Task 4) — a hypothetical single combined job would make it impossible to distinguish "the app is broken" from "the infra plan is invalid" from the PR checks list alone.
- **This workflow must never run `az deployment group create`** — that's `infra-deploy.yml`'s exclusive job, gated to `push` on `main` only. Re-read AC #3's "read-only what-if/validate operation only, never an actual deployment" as a hard constraint, not a suggestion — accidentally wiring `create` into a PR-triggered workflow would let an unmerged PR branch modify live Azure infrastructure, which is exactly the class of mistake OIDC-subject-scoping (AC #3) and this AC together exist to prevent.
- **Task 4 is the piece of this story that cannot be verified by reading/running code alone** — it needs live GitHub repo-admin access. Task 3 no longer has this constraint: the `pull_request` federated credential already exists, so Task 3 is a lightweight verification (confirm the subject claim, update documentation) rather than a live-Azure-CLI-dependent creation step. Follow the same honesty discipline Story 1.3's Dev Notes established: state plainly in Completion Notes which ACs were verified live vs. only structurally, rather than implying full verification that didn't happen.
- **Constraints that still apply, unchanged**: AD-19 (secrets via env vars/repo secrets only, never committed or baked into anything — this story introduces zero new secret values and zero new trust relationships, since the `pull_request` federated credential already exists), NFR2/NFR14 (no new billable resources).
