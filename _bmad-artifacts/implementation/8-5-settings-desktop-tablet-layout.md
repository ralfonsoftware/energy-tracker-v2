# Story 8.5: Settings Desktop/Tablet Layout

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Household member,
I want Settings at ≥660px organized into clearly labeled sections, with "Invite a member" in a place that makes sense,
so that I don't have to guess why an unheaded button sits below the room list.

## Acceptance Criteria

1. **Given** the Settings page is displayed at ≥660px, **when** the page loads, **then** content is organized into labeled sections: "Yearly Baseline", "AI Plausibility Check", "Household", "Rooms, Power Points & Devices", "Data" (UX-DR25). **And** "Invite a member" renders as a regular row inside the "Household" section, not as a standalone unheaded button below the room list.
2. **Given** the household-size presets in the "Yearly Baseline" section, **when** rendered at ≥660px, **then** they use the already-established compact `hh-preset` sizing instead of the currently oversized boxes.
3. **Given** the Room tree in the "Rooms, Power Points & Devices" section, **when** a level (Room or Power Point) is expanded, **then** parent levels show a chevron + item-count summary (e.g. "Living Room — 5 Power Points") instead of equally-weighted bordered buttons at every depth (UX-DR26). **And** "Add Power Point"/"Add Device" renders as a text link at the end of the expanded level, not a persistently-rendered filled pill.

## Dev Notes

- **This is a UI-only story with no new domain capability, no backend change, and no new architecture decision** — Epic 8's own framing, same as Stories 8.1-8.4. UX-DR19 (660px column), UX-DR25 (labeled sections), and UX-DR26 (tree chevron+count) are the drivers.

- **Why Task 1 exists even though Story 8.5's own AC bullets never restate the 660px column constraint (unlike 8.2/8.3/8.4, which each end with an explicit "…constrained to the 660px column" AC):** Epic 8's own top-level framing paragraph is explicit that UX-DR19's amendment "applies to every screen (Dashboard, Trend History, Tariff Radar, **Settings**), not only Trend History as originally scoped" — Settings is named by name. Leaving Settings as the one screen in this epic without the column constraint, on the very last story of the sequence, would be an inconsistent, jarring gap the epic's own text doesn't intend. Treat this as in-scope, not invented scope creep.

- **Why every AC #3 (tree) and AC #1 (sections) change is width-gated, even though the epic's own AC block for the tree doesn't restate a "≥660px" qualifier the way the sections/preset AC blocks do:** `_bmad-artifacts/planning/ux-designs/ux-energy-tracker-2026-08-08/EXPERIENCE.md` line 36 is the authoritative source here and is explicit: **"Settings restructuring (≥660px):"** governs the entire paragraph — sections, "Invite a member" placement, and the tree chevron+count/text-link changes all together. This resolves what would otherwise be a real ambiguity (the epic AC's per-bullet phrasing is looser than EXPERIENCE.md's own qualifier) in favor of the more specific, more recently-authoritative source, and keeps this story consistent with every sibling Epic 8 story's "no regression below 660px" discipline. Do not remove the filled "Add Power Point"/"Add Device" buttons or hide the section labels below 660px.

- **Why the section-label replaces each card's own heading (Yearly Baseline, AI Plausibility Check, Rooms/Power Points & Devices) instead of sitting alongside it:** `critique-desktop-breakpoint-2026-09-23.html`'s own confirmed "after" markup (lines 764-780) shows each `form-card`'s internal heading is *gone* in the restructured version — the `<div class="section-label">Jahresbasiswert</div>` is immediately followed by `<div class="form-card">` whose first child is the description paragraph, not a duplicate `<h4>Jahresbasiswert</h4>` (contrast with the same section's "before" markup, line 723, which *does* have that `<h4>`). Adding a new small-caps `SectionLabel` **without** hiding the existing `<h2>` would produce two stacked headings saying almost the same thing at ≥660px — not what the confirmed mockup shows. Hiding the original `<h2>` via `wide:hidden` and swapping in an `<h2>`-rendering `SectionLabel` preserves exactly one heading level at every width, with zero risk to other consumers (`YearlyBaselineForm`/`AiPlausibilityForm`/`TaggingScaffoldManager` are each used in exactly one place, confirmed via a full-codebase grep — this file's own References section cites the grep).

- **Household/Data section boundary — resolved conflict between three sources that don't agree with each other:**
  - `requirements-inventory.md`'s UX-DR25 text and `EXPERIENCE.md` line 36 both describe only **4** sections, with "Household" containing "Invite a member… alongside data export/import" (implying Data lives inside Household).
  - The epic's own Story 8.5 AC block (epic-8-desktop-tablet-layout-correction.md, the literal acceptance criteria this story is graded against) lists **5** sections, with "Data" named as its own separate entry — while still citing UX-DR25 as its source, despite UX-DR25's own text disagreeing.
  - `critique-desktop-breakpoint-2026-09-23.html`'s actual rendered mockup markup settles it: Section 5's "after" state shows "Haushalt" containing only an "Invite a member" row (no data row inside it — the "Daten exportieren & importieren →" row shown there is one specific mockup iteration, not consistent with Section 7's separate treatment); Section 7's "after" state shows a **fully separate, later "Daten" section-label** with the actual `DataExportPanel`/`DataImportPanel`-equivalent card content rendered inline on the same page (not linked to elsewhere) — matching this codebase's actual single-page `SettingsPage` architecture (there is no routing infrastructure for a nested data sub-page, and building one would be a large, unrequested architectural change).

"Data" = its own section, wrapping the existing `DataExportPanel`/`DataImportPanel` unchanged.
