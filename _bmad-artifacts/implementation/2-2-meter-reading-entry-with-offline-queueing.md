# Story 2.2: Meter Reading Entry with Offline Queueing

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Household member,
I want to log a Meter Reading with today's date/time pre-selected in under a minute, even without connectivity,
so that I can capture my meter's number as part of my routine without breaking the habit.

## Acceptance Criteria

1. **Given** the Log Reading sheet **When** it opens **Then** today's date/time is pre-selected and editable, I enter a single kWh number, and save with one confirmation tap (FR-1)
2. **Given** the default path with no edits **When** I save **Then** confirmation lands in under a minute, responding within the ≤2s Tier 1 target (FR-1, NFR1)
3. **Given** I already logged a reading today **When** I log a second reading later the same day with a different timestamp **Then** it's accepted as a distinct entry — never rejected as a duplicate or silently overwritten (FR-1)
4. **Given** I enter a reading with an earlier timestamp than my most recent one **When** I save it **Then** it's accepted as a backfill, not rejected (FR-1)
5. **Given** no network connectivity at the meter **When** I save a reading **Then** it queues locally (IndexedDB) and syncs automatically when connectivity returns (NFR7)
6. **Given** a queued offline reading whose sync retries after losing its acknowledgment **When** the retry lands **Then** the API's idempotency-key upsert treats it as a no-op against the already-recorded reading — never a duplicate insert (AD-16)
7. **Given** a genuinely new reading entered while an earlier sync is still pending **When** both eventually sync **Then** both are recorded as distinct readings — the idempotency mechanism never collapses a legitimate second entry (AD-16)
8. **Given** the Log Reading sheet **When** presented **Then** it renders as a sheet over the Dashboard, never its own route, with top-rounded/flush-bottom shape and a tabular-nums kWh field (UX-DR3)
9. **Given** the Log Reading sheet **When** it opens **Then** it traps focus while open and returns focus to the triggering control on close, is announced on open (role + label) for screen readers, and its Save action meets the 44×44pt-equivalent tap-target minimum (UX-DR16)

## Dev Notes

- **This story is backend-greenfield.** No `MeterReading`, `MainMeter`, idempotency-key, or offline-queue code exists anywhere in the repo today — there is nothing to extend, only the `Room`/`PowerPoint`/`Device` AD-3 pattern and `Household`'s AD-4 pattern to model structurally after (see Task 1/2 for the exact files to mirror).
- **`MainMeter` is a new entity this story must create, not just `MeterReading`.** The architecture ERD (`structural-seed.md`) models `Household ||--o{ MainMeter : has` and `MainMeter ||--o{ MeterReading : has` as two separate entities; no prior story created `MainMeter`. Skipping straight to `MeterReading` rows keyed only on `HouseholdId` would miss this and break Story 2.3's AD-12 ("at most one open regression prompt per Main Meter").
- **AD-4 vs. AD-16 — don't conflate them.** AD-4's `int Version` concurrency token is for **edits** (Story 4.3's correction flow) and is deliberately *not* added to `MeterReading` in this story (see Task 1). This story's only concurrency concern is AD-16's idempotency-key upsert on **creation**, which is a different mechanism (unique-index + catch-and-refetch, not `OriginalValue`/`DbUpdateConcurrencyException`).
- **No prior UX mock exists for this exact sheet treatment** — `EXPERIENCE.md` marks Log Reading among the "spine-only, no rendered mock" surfaces, though `DESIGN/components.md` and the State Patterns/Interaction Primitives tables give enough concrete detail (radius, press-scale, motion) to implement without inventing values. The `{colors.focus-ring}` token referenced by `dos-and-donts.md` for `:focus-visible` styling is not actually defined yet in the live token set (only a one-off hardcoded value exists in a motion demo file) — if focus-visible styling needs it, either add the token to `web/src/index.css` or fall back to the existing default outline rather than inventing a color.
- **The offline/queued visual state is genuinely undesigned**, not just underspecified — there's no badge/icon/color token for it anywhere in the UX docs. Task 5 directs plain neutral text over inventing a new status color, consistent with the product's "never a 4th status color" discipline (UX-DR1/UX-DR2), but this is a reasonable interpretation, not a documented spec — flag it if a real design pass happens later.
- **Dashboard sequencing:** the real Dashboard/Status card is Story 2.5's scope. This story adds only a placeholder trigger to the existing Story-1.1 placeholder view in `App.tsx` — do not block on or attempt to build the Status card here. **And the reverse boundary matters too:** Story 2.5's own AC text explicitly names "the primary 'Log Reading' action button (pill shape, gradient fill) that opens the Log Reading sheet from Story 2.2" (UX-DR8) as its own deliverable — so this story must *not* build that polished button, only a plain trigger sufficient to open/test the sheet. Getting this backwards means either duplicated UI or Story 2.5 having to tear out this story's work.
- **Deliberately no Service Worker**, despite `structural-seed.md`'s `web/` line mentioning one alongside the IndexedDB queue. A Service Worker + the Background Sync API would be the more resilient design (syncs even if the tab is fully closed while offline), but Background Sync API support is inconsistent across mobile browsers — notably iOS Safari, which matters for a "logging from the basement on your phone" flow — and isn't required by any AC here (AC #5 just says "syncs automatically when connectivity returns," which a `window.online` listener plus an app-mount flush satisfies for the case that matters: the app being open when connectivity returns, or being reopened after it already has). Revisit only if a later story's requirements actually need closed-tab background sync.
