# Story 2.3: Meter Reading Regression Detection & Classification

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Household member,
I want a Meter Reading lower than the previous one to be flagged and classified rather than silently breaking my baseline,
so that a meter swap or digit rollover doesn't corrupt my Status.

## Acceptance Criteria

1. **Given** a new Meter Reading lower than the Reading immediately preceding it by timestamp (not entry order) **When** it's saved **Then** a classification prompt opens asking to confirm *reset* or *rollover*, and no negative consumption rate is computed (FR-25)
2. **Given** the classification prompt **When** I confirm *reset* **Then** a new baseline-computation sequence starts going forward without discarding prior Reading history (FR-25)
3. **Given** the classification prompt **When** I confirm *rollover* **Then** the interval's consumption is computed as (meter's known digit capacity − previous Reading) + new Reading (FR-25)
4. **Given** a backfilled Reading **When** compared for regression **Then** "immediately preceding" is determined by timestamp order, never entry order (FR-25)
5. **Given** an unconfirmed regression prompt **When** any later reading or Status computation runs **Then** the flagged Reading is excluded from baseline computation until resolved, and the prompt never silently expires or defaults to either classification (FR-25)
6. **Given** a second lower-than-previous Reading arrives while an earlier regression prompt is still open **When** it's detected **Then** it queues behind the first rather than opening a second, conflicting prompt — at most one open `MeterRegressionPrompt` exists per Main Meter (FR-25, AD-12)
7. **Given** the regression prompt triggers while a Log Reading sheet happens to be open **When** it opens **Then** it supersedes the Log Reading sheet rather than stacking on top of it (UX-DR13)
8. **Given** the regression prompt UI **When** rendered **Then** it uses the neutral/informational glass treatment, never destructive/error styling — this is a normal classification step, not a system error (UX-DR4, UX-DR18)
9. **Given** the regression prompt **When** it opens **Then** it traps focus while open and returns focus to the triggering control on close, and is announced on open (role + label) for screen readers (UX-DR16)

## Scope Boundary — What This Story Does NOT Do

**No live baseline/pace computation exists yet.** Story 2.4 (Gap-Tolerant Rolling Baseline & Status Computation) is what actually turns Meter Readings into a consumption pace/Status. AC #2 and #3's "a new baseline-computation sequence starts" / "the interval's consumption is computed as..." describe the *eventual* effect once 2.4 exists — there is no Status endpoint, no pace calculation, and nothing to display a computed kWh figure to yet. This story's job is to **detect the regression, classify it, and persist everything 2.4 will need** (the classification itself, and — for rollover — the digit capacity used) so 2.4's baseline math can consume it correctly. Do not build a consumption-computation feature here; verify AC #2/#3 via persisted state (`MeterRegressionPrompt.Classification`, `.DigitCapacityKwh`), not a displayed/returned kWh figure.

**Two design decisions this story makes that aren't explicitly spelled out anywhere in the PRD/architecture/UX docs** (flagged again at the end as open questions for confirmation, but a concrete default is needed to implement):

1. **Where the meter's "known digit capacity" comes from.** No prior story, PRD FR, or architecture doc defines a field for this. Per AD-15 (no hardcoded household-specific values), this story adds a nullable `MainMeter.DigitCapacityKwh` column. The classification prompt's *rollover* action captures it inline the first time (a lightweight numeric input alongside the rollover confirmation — not a separate settings flow), then persists it onto `MainMeter` so future rollovers on the same meter pre-fill it and stay a one-tap confirmation, matching the UX spec's "household resolves them one at a time, in one tap" framing.
2. **AD-11's audit-correction mechanism does not exist in the codebase yet** (no `AuditCorrection` table, no `IAuditCorrectionRecorder` — grep confirms nothing has built it as of Story 2.2). A prior architecture review (`reviews/review-adversarial-divergence.md`, finding #8) flagged that it's undefined whether resolving a `MeterRegressionPrompt` should route through AD-11. Since the mechanism doesn't exist, this story **does not** attempt to wire one — resolving a prompt is not treated as an "edit" for AD-11 purposes. Revisit if/when a later story (4.3's correction flow is the likely candidate) builds `AuditCorrection`.

## Dev Notes

- **This story extends `CreateMeterReading`, not just adding new files** — Story 2.2's own Dev Notes explicitly scoped regression detection out and flagged it as "Story 2.3's entire job... do not add a comparison-against-previous-reading check, even defensively." That means Task 2 is a real modification to an existing, tested, reviewed use case (constructor signature changes from one dependency to two) — re-run and update `CreateMeterReadingTests.cs`'s existing cases for the new constructor shape, don't just add new test methods alongside stale ones that no longer compile.
- **"Open" is computed, not stored.** No `IsOpen`/`Status` column on `MeterRegressionPrompt` — "the open one" is always the earliest-by-`ReadingTimestamp` unresolved prompt for a Household (equivalently, its one Main Meter — v2 is single-Main-Meter-per-Household, `deferred.md`). This is deliberate: a persisted queue-position/open-flag is a second piece of state that has to be kept in sync with resolution order and reading timestamps, which is exactly the kind of drift AD-12 exists to prevent. Don't add one.
- **Digit capacity is genuinely undefined upstream** — see "Scope Boundary" above for the full reasoning; this is flagged again as an open question at the end of this document. The `MainMeter.DigitCapacityKwh` field, and capturing it inline on first rollover, is this story's own design decision to make FR-25's rollover math implementable at all, not something copied from an existing spec. If Ralf's answer to the end-of-document question changes the intended UX (e.g., a dedicated Settings field instead), this task list's Task 6 dialog behavior is the part to revisit — the backend shape (nullable `MainMeter` column, captured-once-then-reused) still holds either way.
- **Race-safety is not optional here, same lesson as Story 2.2.** `CreateMeterReading`'s existing `AddAsync` can return a *different* persisted `MeterReading` than the one constructed locally (idempotency-key race, existing behavior) — Task 2 must detect against that returned instance, and the new `MeterRegressionPromptRepository.AddAsync` needs its own catch-detach-requery on the `MeterReadingId` unique index for the same reason `MeterReadingRepository` needed one for `IdempotencyKey`/`HouseholdId`. Skipping this reproduces Story 2.2's review-found race class in a new place.
- **AD-11 does not apply here** — see Scope Boundary decision #2. Do not add an `AuditCorrection` row or invent a recorder call; the mechanism doesn't exist in this codebase yet.
- **No glass-panel tokens are wired yet** (`{colors.surface-glass}`, backdrop-blur, etc.) — confirmed by grep against `web/src/index.css`; only the base shadcn delta (background/foreground/primary/ring/font) from the Epic-1 retro action item is wired. This is the same gap Story 2.2 hit for the Log Reading sheet. Use plain shadcn `Dialog` defaults for the regression prompt — this already satisfies "neutral, not destructive" (no `destructive` variant anywhere in this component), it just isn't the literal glass-panel treatment `DESIGN/components.md` describes. Flag if a real design/token pass happens later, same as 2.2 did.
- **This is the first enum in the codebase.** Do not register a global `JsonStringEnumConverter` in `Program.cs` for it — map `MeterRegressionClassification` to/from a plain `string` explicitly in the endpoint DTOs, matching how every other endpoint here hand-maps between Domain types and response records (e.g. `MeterReadingEndpoints.ToResponse`).
- **Dashboard/global wiring, not a Story-2.5 boundary issue this time.** Unlike the Log Reading trigger button (Story 2.2 → Story 2.5 handoff), the regression prompt dialog is not a Dashboard-specific surface — FR-25 can trigger from *any* reading entry, and EXPERIENCE.md's component table says it's "triggered inline, wherever a Reading is entered." Render it at the `App.tsx` level (sibling to the current dashboard placeholder), not nested inside dashboard-specific markup, so it isn't accidentally scoped to a view that Story 2.5 later restructures.

## Open Questions for Ralf (raised during story creation, not blocking — see Scope Boundary for the defaults this story ships with)

1. **Digit capacity source.** This story adds it as a `MainMeter`-scoped value captured inline the first time a rollover is confirmed (no dedicated Settings UI). Is that the right long-term home for it, or should a Settings field for "meter digit capacity" be added as its own small story later (e.g. for a household that wants to set it proactively, before ever hitting a rollover)?
2. **AD-11 vs. regression resolution.** Confirmed the mechanism doesn't exist yet, so this story doesn't wire it — but should resolving a `MeterRegressionPrompt` (especially *rollover*, which effectively reinterprets a reading's meaning) count as an "edit" once Story 4.3 builds `AuditCorrection`? Worth a one-line decision in AD-11 or AD-12 at that point (per `review-adversarial-divergence.md` finding #8) so it isn't re-litigated then.
3. **Out-of-order resolve → 409.** This story blocks resolving a queued (non-open) prompt directly via the API with a 409, even though the UI never exposes that path in normal use. Reasonable defensive default, or should the API instead silently reorder / allow it? (No AC requires either; 409 was chosen as the safer default.)
