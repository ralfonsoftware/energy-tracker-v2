## Story

As a household member,
I want the keys that sign my session cookie to be encrypted at rest,
so that someone with database read access can't forge my session (audit S2).

## Acceptance Criteria

1. **Given** a new `infra/modules/key-vault.bicep` (RBAC permission model, one key), **when** it is deployed, **then** the Container App's system-assigned identity holds **Key Vault Crypto Service Encryption User** on that key only, and `DataProtection__KeyVaultKeyId` is set (AD-17, 2026-10-10).
2. **Given** the composition root, **when** `DataProtection:KeyVaultKeyId` is set, **then** `ProtectKeysWithAzureKeyVault` is used alongside `PersistKeysToDbContext`. `Azure.Extensions.AspNetCore.DataProtection.Keys` and `Azure.Identity` are pinned explicitly in `Directory.Packages.props`.
3. **Given** a non-Development environment with neither Key Vault nor a certificate configured, **when** the app starts, **then** it refuses to start unless `DataProtection:AllowUnprotectedKeys=true` is set, and the selected protector or opt-out is logged.
4. **Given** existing self-host installs, **when** this ships, **then** `docs/self-hosting.md` has a Data Protection section (certificate, or a deliberate opt-out), `.env.example`/`docker-compose.yml` carry the setting commented out, and the release note flags the breaking change.
5. **Given** the cutover, **when** the pre-cutover revision is deactivated, **then** Ralf runs the `infra/README.md` runbook step that revokes old keys (`RevokeAllKeys`), and a live Auth0/Chrome check confirms a fresh sign-in works and the new key in `DataProtectionKeys` is encrypted.
6. **Implied (not in the epic text; AC #5 has no runnable step without it):** the runbook step in AC #5 is backed by a small, opt-in startup action. When `DataProtection:RevokeKeysCreatedBeforeUtc` (ISO 8601, with offset) is set, the app calls `IKeyManager.RevokeAllKeys` for that cutoff **only if** at least one non-revoked key created before the cutoff exists, so a restart with the setting left in place is a no-op (no extra revocation row per restart). Absent or blank, nothing happens. Invalid value: startup fails with a clear message. The default and the alternative are in Questions (Q1).
7. **Implied (not in the epic text; the fail-closed rule has edge cases):** precedence and validation, decided here so the dev does not invent them: (a) Key Vault wins when both `KeyVaultKeyId` and `CertificateBase64` are set, and a warning says the certificate is ignored; (b) `AllowUnprotectedKeys` is honoured only when its value is exactly `true` (case-insensitive); blank, `false` or anything else still fails closed; (c) `AllowUnprotectedKeys=true` together with a configured protector is ignored (the protector is used) and logged; (d) in `Development` with nothing configured the app keeps starting unprotected, logs that fact at warning level, and needs no opt-out; (e) `KeyVaultKeyId` must be an absolute `https` URI, else startup throws with a message that names the setting.
8. **Implied (not in the epic text; "must stay true" guards):** executable guards in `EnergyTracker.Architecture.Tests` or `EnergyTracker.Api.Tests` for: the selection matrix (AC #2, #3, #7), key rows being encrypted at rest (certificate path, real Postgres), the revocation behaviour (AC #6), and the infra shape (RBAC vault, role scoped to the key, env var wired, no access policies, packages pinned). See Tasks.
9. **Implied (not in the epic text; docs that would otherwise go stale):** `_bmad-artifacts/project-context.md` ("Auth (AD-17)", "Security", Technology Stack), `docs/local-development.md` (a full `docker compose up` now runs as Production and needs the certificate or the opt-out), `docs/local-vs-azure-deltas.md` (Key Vault protector exists only in Azure; local and self-host use a certificate or the opt-out), and `infra/README.md` ("What gets deployed", runbook, identity table) describe the new state.

## Dev Notes

### What this fixes and why it is safe to change

- **S2 (Medium, verified):** `Program.cs` encrypts the key ring only when `DataProtection:CertificateBase64` is set. `infra/modules/container-app.bicep` sets no `DataProtection__*` variable, so **production runs in the plaintext mode**: the `DataProtectionKeys` table holds the master key of the cookie data-protection key ring in the clear, next to the household data. Anyone with database read access, or a backup, can forge a session cookie for any member. The design is fail-open: leaving an optional setting out silently selects the weaker mode.
- The fix has three layers: (1) Azure encrypts the ring with a Key Vault key through the Container App's managed identity (no secret to leak); (2) self-host keeps the certificate path; (3) outside Development the app refuses to start when neither is present unless the operator opts out explicitly. The opt-out makes the weak mode a conscious choice instead of a default.
- Existing sessions: until the revoke, the old plaintext key stays valid and nothing changes for members. The revoke signs every member out once (14-day sliding cookie, no data loss). No data migration, no EF migration, no schema change.

### Rollout order (this is the part that breaks things if done wrong)

1. **PR A (infra) first.** It creates the vault, the key, the role assignment and sets `DataProtection__KeyVaultKeyId` on the Container App. The currently running app image ignores that variable, so nothing changes in production. `infra-deploy.yml` deploys it (it re-applies the currently running image, Story 1.6).
2. **PR B (app) second.** Its merge triggers `app-deploy.yml`. The new image reads `KeyVaultKeyId`, selects the Key Vault protector and starts. It does not call Key Vault yet: the existing key is a plaintext key that still decrypts, and a new key is only created at rotation or after the revoke. So a role that has not propagated cannot break the deploy or the health check (`/health` is liveness-only).
3. **Why not one PR:** a merge touching `src/**` and `infra/**` starts `app-deploy.yml` and `infra-deploy.yml` together (shared concurrency group, order not guaranteed). If the app deploy ran first, the new image would start in Production with neither Key Vault nor opt-out configured, **refuse to start** (that is the point of fail closed), fail the health check and be rolled back to the previous image; `infra-deploy.yml` would then re-apply that older image. Recoverable by re-running `app-deploy.yml`, but a red run on purpose is the wrong way to ship a security story. Story 11.4's N/N+1 split is the precedent.
4. **Cutover (R2) last**, after the pre-cutover revision is deactivated. Order inside R2: revoke, then watch the first Key Vault call, then R3.
5. **Failure mode to know:** if the first Key Vault call fails after the revoke (role not propagated, wrong scope), every request that needs a key fails until it is fixed. Sessions were already invalidated by the revoke, so fixing and restarting the revision costs nothing extra. This is why R1 verifies the role first.

### Technical details the dev must get right

- **How the Key Vault protector works** (Azure SDK source, `AzureKeyVaultXmlEncryptor`): it generates a random AES key per key-ring element, encrypts the XML with it, and wraps the AES key with the vault key (`RSA-OAEP`). The encrypted element stores `kid` = the resolved key's own id (taken from the resolved key object, so with a version). Decryption resolves that stored `kid` and unwraps. Consequences: (1) one wrap per key creation, one unwrap per key-ring load, tiny operation volume; (2) a **versionless** `DataProtection:KeyVaultKeyId` resolves to the latest version for new keys while old keys carry their own version, so a later vault key rotation does not break old rings. The SDK source was read for this story; the versionless behaviour of the resolver itself was not run end to end, so confirm it live in R2/R3 (the `kid` in a new row should name a version).
- **Required rights:** "Key Vault Crypto Service Encryption User" (`e147488a-f6f5-4113-8e2d-b22465e65bf6`) grants `keys/read`, `keys/wrap/action`, `keys/unwrap/action` data actions. That is what the encryptor needs (resolve = read key metadata, wrap, unwrap). Nothing else, and nothing at vault scope.
- **Role scope on a key:** a role assignment can be scoped to the key resource (`Microsoft.KeyVault/vaults/keys`). Use `scope: key` in Bicep with the `existing` key reference.
- **Credential:** `DefaultAzureCredential` on Container Apps uses the managed-identity endpoint injected by the platform. The first token fetch happens lazily at first use, not at startup.
- **Key ring cache:** the ring is cached in-process for up to about 24 hours (project-context/AD-17). A single replica (AD-24) makes that harmless; it is also why the revoke runs after the old revision is gone.
- **`RevokeAllKeys(revocationDate, reason)`** writes a revocation record into the key repository (a new `DataProtectionKeys` row) that revokes keys created on or before that date; it does not delete key rows. A key created after the cutoff is unaffected. A host that finds no usable default key creates a new one immediately (activation now, because the ring is empty), which is what the first request after the revoke does. In the tests, take the cutoff **after** host 1 created its key and **before** host 2 starts.
- **Do not exercise Key Vault from tests.** No live vault in CI (no Azure secrets in the PR path, by design). The Key Vault branch is tested by selection and by the encryptor type only; real proof is R2/R3.
- **WebApplicationFactory and fail-closed:** the factory's default environment is Development. For a Production host use `WithWebHostBuilder(b => b.UseEnvironment("Production"))`. `Program` is a top-level-statements class made visible to tests already (`Program` is used by the existing factories).
- **Case and format of config:** .NET configuration keys are case-insensitive and `__` maps to `:`; `DataProtection__KeyVaultKeyId` and `DataProtection:KeyVaultKeyId` are the same key. Bicep uses the double-underscore form (matches the existing `OIDC__*` style).
- **Dependencies:** `Azure.Extensions.AspNetCore.DataProtection.Keys` 1.6.4 depends on `Azure.Core` 1.61.0, `Azure.Security.KeyVault.Keys` 4.10.0 and `Microsoft.AspNetCore.DataProtection` (framework-provided). Today `Azure.Core` resolves to 1.60.0 and `Azure.Identity` to 1.17.1 (both transitive). The NuGet Audit gate (moderate, as errors) applies to the new transitive set: if an advisory appears, bump or replace, never suppress.
- **Cost:** a Standard vault with one software-protected RSA key and a handful of operations per month is negligible next to the Azure SQL Basic tier (NFR2/NFR14 cost discipline); check the Azure pricing page for Key Vault at implementation time and record the line in Completion Notes rather than trusting a remembered number.

### Release note draft (AC #4; Ralf publishes it, task R4)

> **Breaking change for self-hosted installs: Data Protection keys must now be protected.** Energy Tracker stores the keys that sign your session cookie in its database. Until now, without a certificate they were stored unencrypted, so anyone who could read the database or a backup could forge a login. Both options and the exact commands are in `docs/self-hosting.md`. Installs that already use a certificate need no change. After switching to a certificate, existing members sign in once more. No data is lost.
