## Story

As a household with several smart plugs,
I want two unmapped plug files covering the same period to keep their own readings,
so that no consumption data is silently overwritten before I map the plugs (audit C9).

## Acceptance Criteria

1. **Given** `SmartPlugReading.DeviceName` (today `nvarchar(max)`/`text`), **when** this story's first migration runs, **then** the column becomes `HasMaxLength(200)`. The migration first checks the stored maximum and fails loudly instead of truncating. Both parsers reject a device tag longer than 200 characters with a stable import error, and the restore validator enforces the same bound.
2. **Given** deploy N, **when** it ships, **then** the partial unique index `(HouseholdId, DeviceName, IntervalStart) WHERE PowerPointId IS NULL` exists, and the unmapped-path upsert (`ON CONFLICT`/`MERGE ON`) and its `DeduplicateByMatchKey` use that key. The old index is still present.
3. **Given** deploy N+1 (a second PR in this story, shipped promptly after N), **when** it ships, **then** the old `(HouseholdId, IntervalStart) WHERE PowerPointId IS NULL` index is dropped. The story is done only after N+1.
4. **Given** `UpdateMappingAsync`, **when** a plug is mapped, **then** its collision key is still `(PowerPointId, IntervalStart)`, unchanged.
5. **Given** two different plugs' files covering the same period, both unmapped (dual-provider Testcontainers), **when** both are imported and later mapped, **then** each keeps and is attributed its own readings, and re-uploading the same plug's file still updates in place.
6. **Implied (not in the epic text; reads AC #1's "stable import error" under AD-6):** the over-length rejection is the stable failure code `device-tag-too-long` (a new entry in `JobFailureCodes`, set by exception **type** in `BackgroundJobProcessor`, never from message text), translated in en-US and de-DE and recognised by `web/src/lib/job-error.ts`. AD-6 (amended 2026-10-10) says job failure reasons are stable codes, not English text, and the household's primary locale is German; a verbatim English `SmartPlugImportValidationException` sentence would break that rule. The import still ends `Failed` and its job-history row still appears (the generic catch in `ProcessSmartPlugImport` persists it).
7. **Implied (not in the epic text; documentation that would otherwise go stale):** `docs/data-export-format.md` (`deviceName` is at most 200 characters), the AD-2 / AD-20 / AD-23 passages in `invariants-rules.md` that still name the old `(HouseholdId, IntervalStart)` key, and the comments in `SmartPlugReadingConfiguration.cs` and `SmartPlugImportRepository.cs` describe the new key. The old key text is struck through or replaced, not left beside the new one.

## Dev Notes

### What this fixes and why it is safe to change

- **C9 (Medium, verified in code):** readings for an import whose device tag matches no Power Point are upserted with the conflict key `(HouseholdId, IntervalStart) WHERE PowerPointId IS NULL`, and on conflict the upsert **overwrites** `SmartPlugImportId`, `DeviceName`, `KwhValue` and the rest. Upload plug A (unknown tag), then plug B (a different unknown tag) covering the same period, without mapping A in between: B's rows replace A's for every shared `IntervalStart`. Mapping A later attributes only the non-overlapping rows; the overwritten consumption is gone or attributed to B. No test covered it.
- **The fix is the key, not a guard.** AD-20 (amended 2026-10-10) chose `(HouseholdId, DeviceName, IntervalStart)` because the device tag is the plug's real identity. Rejected alternatives, do not re-open: per-`SmartPlugImportId` uniqueness (a re-upload of the same plug would duplicate its rows) and blocking a second unmapped import (a dead end for multi-plug households).
- No API shape, no export format change, no frontend flow change. The only user-visible new thing is one failure sentence (`device-tag-too-long`).
- **Dual-provider and raw SQL are in scope here by necessity:** the unmapped upsert is the one place AD-2 allows provider branching (`dbContext.Database.IsNpgsql()` / `IsSqlServer()` inside `UpsertAwaitingMappingReadingsAsync`). Do not add a third branch point; change the two statements in place.

### Design decisions already made (do not re-litigate)

- **Key = `(HouseholdId, DeviceName, IntervalStart) WHERE PowerPointId IS NULL`; `DeviceName` ≤ 200** (AD-20, amended 2026-10-10 after the reviewer gate).
- **Two deploys, expand then contract.** N: narrow the column, add the new index, switch the code, keep the old index. N+1: drop the old index. Between them a second plug's overlapping unmapped rows fail loudly on the old index; this is the accepted transitional state (sprint change proposal §3 risks), never a silent overwrite.
- **Deploy N is a justified exception to Story 10.1's expand/contract rule** (Retro 10 note, in the epic text): narrowing `AlterColumn` is destructive-class and normally ships in a later deploy than the code that stops using the old shape, but SQL Server cannot index `nvarchar(max)`, and N creates the index, so the narrowing cannot wait. Safeguards are listed in Task A5.4; record the exception in the migration comments (done in A5.4) **and** in this story's Completion Notes. Do not add `project-context.md` text for it (a one-off exception, not a rule change).
- **Bound enforced at four layers:** parsers (stable error), restore validator (collected failure), the migration pre-check (fails the deploy loudly), the column itself. A 201st character can no longer reach the database through a supported path, and the pre-check turns an unsupported path (manual SQL, an old restore) into a failed deploy with a readable message, not a truncation.
- **Length unit = .NET `string.Length` (UTF-16 code units) > 200 is rejected.** SQL Server's `nvarchar(200)` is 200 UTF-16 units; Postgres `varchar(200)` counts characters (code points, never more than code units). The .NET rule is therefore the strictest and guarantees a fit on both. A tag of 101 emoji (202 units) is rejected; that is intended.
- **Stable error = failure code, by exception type** (AC #6), in the 11.2/11.3 pattern. Not `SmartPlugImportValidationException`. Confirmed by Ralf on 2026-10-11 (code plus en-US and de-DE translation).
- **`DeviceName` leaves the `DO UPDATE SET` / `WHEN MATCHED` list** (A6): it is part of the key, and on SQL Server's case-insensitive collation an assignment could silently rewrite the stored snapshot.
- **No `DeviceName` normalisation** (trim/lower-case/Unicode-normalise) in this story; the tag is the plug's identity exactly as parsed. Eve already trims; Meross does not.

### Technical details the dev must get right

- **New index statements** (raw SQL in the migration, both providers; same style as the 2026-08-22 migration):
  - Postgres: `CREATE UNIQUE INDEX "IX_SmartPlugReadings_Household_Device_IntervalStart_Unmapped" ON "SmartPlugReadings" ("HouseholdId", "DeviceName", "IntervalStart") WHERE "PowerPointId" IS NULL;`
  - SQL Server: `CREATE UNIQUE NONCLUSTERED INDEX [IX_SmartPlugReadings_Household_Device_IntervalStart_Unmapped] ON [SmartPlugReadings] ([HouseholdId], [DeviceName], [IntervalStart]) WHERE [PowerPointId] IS NULL;`
  - Creation can never fail on existing data: the new key is strictly looser than the old unique key.
  - SQL Server key size: 16 + 400 + 10 bytes ≈ 426, under the 1,700-byte nonclustered limit.
- **Postgres identifiers are limited to 63 bytes and longer names are silently truncated.** The old index name is 67 characters, so Postgres stores it as its first 63. Any statement that spells the full 67-character name (the original migration's `Down()`, N+1's `DROP INDEX IF EXISTS`) is truncated the same way and still matches, which is why it works; a **new** name over 63 characters would silently collide with a prefix-sharing name and make tests that look indexes up by name lie. The new name above is 60 characters. Tests look indexes up by definition (columns + predicate), not by name.
- **Postgres arbiter inference.** `ON CONFLICT (cols) WHERE pred` only treats a conflict on a unique index whose columns and predicate match as the arbiter. During N both unmapped indexes exist: a *same-plug* re-upload conflicts on both and takes the `DO UPDATE` path through the new arbiter; a *different-plug* overlap conflicts only on the old index, which is not the arbiter, so Postgres raises `23505` (loud). On SQL Server the `MERGE ON` (now including `DeviceName`) finds no match for a different plug, `WHEN NOT MATCHED` inserts, and the old filtered unique index raises error 2601 (loud). The `AddAsync` catch block already detaches the change tracker and the transaction rolls back, and the job ends `Failed` with the generic message.
- **SQL Server is case- and trailing-space-insensitive for this key** (default collation `SQL_Latin1_General_CP1_CI_AS` on Azure SQL and the MsSql container; no collation is configured anywhere in the repo). Two plugs whose tags differ only by case or trailing spaces would still collide on SQL Server (the later import overwrites the earlier one's values), while Postgres treats them as distinct. Power Point matching in `ProcessSmartPlugImport` is ordinal, so such tags are two different plugs for matching but one for this key. Accepted: far narrower than C9, a per-column collation cannot be put on an index, and normalising the tag is out of scope. Do not write a test that pins this difference as intended behaviour. Ralf accepted it on 2026-10-11; it is recorded in `deferred-work-accepted.md`.
- **EF/migration mechanics.** `HasMaxLength(200)` changes the model snapshot, so `add-migration.sh` produces an `AlterColumn` with `oldType: "nvarchar(max)"` (SQL Server) / `"text"` (Postgres). Postgres: `ALTER COLUMN … TYPE character varying(200)` scans (and rewrites) the table under an exclusive lock; SQL Server: the column change rewrites the data. Postgres would also refuse a too-long value on its own, but only with a generic message, hence the explicit pre-check first. The raw `CREATE INDEX` statements are not in the model, so the snapshot only changes for `DeviceName`. EF applies a migration's `Up()` in one transaction on both providers here (no `suppressTransaction` is used in this repo), so the pre-check failing leaves nothing changed.
- **N+1 is an empty-model migration.** Generating it with `add-migration.sh` yields an `Up()`/`Down()` with no operations plus an unchanged snapshot; that is expected. Do not invent a model change to make EF generate something.
- **Old image during the deploy window.** After N's migration and before the new revision is healthy, the previous image keeps serving. It still has valid arbiters (old index kept) and writes tags that were already ≤ the new limit in practice; a tag over 200 from the old image would fail loudly at the database (never truncate). That window is minutes.
