## Story

As a household member in my first year,
I want *Trending* to warn me as early in the year as it would after a full year,
so that a surprise invoice doesn't build up unnoticed (audit C12, FR-6 clarified 2026-10-10).

## Acceptance Criteria

1. **Given** `PatternDetectiveCalculator.ResolveStatus`, **when** Status is computed, **then** the difference to date is compared against `TrendingThresholdKwh` scaled to the same elapsed period via `BonusDecayNormalizer.NormalizeToDate` (AD-5), which matches `WindowedDeviationCalculator`. *Below baseline* stays any shortfall, and a tie still resolves to *within range*. **AMENDED 2026-10-25, Ralf (code review decision 1c):** the scaled threshold is never below one meter step, 1 kWh, and never above the configured annual figure (`TrendingThreshold.ScaleToDate`, used by `ResolveStatus`, the detail figure and `WindowedDeviationCalculator`), so rounding noise over a day or two cannot decide *Trending*; ~~no floor (Q7)~~.
2. **Given** existing `StatusSnapshot` rows, **when** this ships, **then** they are not rewritten (forward-only; AD-7 and the PRD recomputation policy).
3. **Given** FR-30's detail view and the threshold setting, **when** they are shown, **then** the detail view shows both the configured (per-year) and the scaled threshold, and the setting is labelled "per year" in both locales. The release note says that households in their first year will see *Trending* earlier.
4. **Implied (AC #1 says "scaled to the same elapsed period"; the code has to say which period, and the two calculators have to provably agree):** the elapsed period is the one `GetCurrentStatus` already uses for `BaselineToDateKwh`, `PaceToDateResult.Elapsed` (first to last included reading inside the trailing 365 days, gaps absorbed, voided Reset pairs left out). `ResolveStatus` takes the **annual** threshold plus that `TimeSpan` and calls `BonusDecayNormalizer.NormalizeToDate(annualThreshold, bonusTermsKwh: 0m, elapsed)` itself, the same call `WindowedDeviationCalculator.ComputeDeviation` makes, so the scaling cannot be forgotten at a call site (the C12 bug class). No second copy of the proration formula anywhere (AD-5). Because the pace window is capped at 365 days, a household with a full year of readings gets a factor of about 1: its Status does not change. Only households with less than a year of readings see *Trending* earlier.
5. **Implied (the detail view must show the number that actually decided the Status, not a second computation that can drift):** `CurrentStatusResult` gains `TrendingThresholdToDateKwh` (the scaled value, computed once in `GetCurrentStatus` with the same `NormalizeToDate` arguments as `ResolveStatus` uses) next to the existing `TrendingThresholdKwh` (still the configured, annual value). `GET /api/status/detail` gains the additive field `trendingThresholdToDateKwh`; `trendingThresholdKwh` keeps its name and meaning (so a stale open tab or the previous image keeps working: expand/contract for an API field). `GET /api/status` is not touched (drill-down data never merges into the headline response). A test proves the two figures cannot disagree: with the difference equal to the displayed scaled threshold the Status is *within range*, one hundredth above it is *trending*.
6. **Implied (the "setting is labelled per year" part of AC #3 has to land somewhere real):** there is **no UI that edits `TrendingThresholdKwh`** today (no settings field, no endpoint writes it: `deferred-work.md` Story 2.4 entry, FR-21's editing UI has not shipped; confirmed by a grep of `web/src` and `src/EnergyTracker.Api`). So the only place the setting is labelled is the detail view's configured-threshold row: its label becomes "Trending threshold (per year)" / "Schwellenwert für Anstieg (pro Jahr)", and a second row, labelled "Threshold for this period" / "Schwellenwert für diesen Zeitraum", shows the scaled value. Both rows are in `en-US` and `de-DE` (the `translation-consistency` test keeps the key sets equal). When FR-21's settings editor is built it must carry the same "per year" wording: this is recorded on the existing `[open]` entry in `deferred-work.md` (Task 6.2), not built here. The scaled value is shown with up to one decimal (a threshold for a few days is a few kWh, and a whole-number format would show "0 kWh"); the configured value stays a whole number as today.
7. **Implied (the semantics are written where the next reader will look; the audit asked for it by name):** `Household.TrendingThresholdKwh` carries a short comment saying it is an annual overshoot in kWh per year, compared after scaling to the elapsed period (FR-6), and `ResolveStatus`'s comment is rewritten (the old one says "pace - baseline == threshold" and "Anything below baseline-to-date", which stays true but now needs the scaled meaning). `docs/data-export-format.md`'s `trendingThresholdKwh` row gets a description ("annual overshoot, kWh per year"); the export and restore code and the `formatVersion` do not change (the value's meaning did not change in storage, only in use).
8. **Implied (forward-only has to be checkable, not just promised):** the diff contains no migration, no change to `StatusSnapshot.cs`, `StatusSnapshotConfiguration.cs` or `StatusRecomputeService.cs`, and no data statement; `GetStatusHistory` keeps reading persisted snapshots only. Nothing recomputes history on deploy: the live `GET /api/status` uses the new rule at once, the `StatusSnapshot` table only gets a new row at the next Meter Reading or completed Smart Plug import (AD-7), so a first-year household's Trend History can show a step (for example *within range* to *trending*) at the first recompute after the deploy. That is the intended forward-only behaviour and is said in the release note, not "fixed".
9. **Implied (tests that pin the old behaviour must be found and changed on purpose):** the `ResolveStatus_applies_the_strictly_greater_than_threshold_rule` theory in `PatternDetectiveCalculatorTests` (4 cases, signature changes), the `CompareTariffTests.StatusAtElapsedDays` record construction (a new required record parameter) and the three status-detail DTO fixtures in the frontend (`status-api.test.ts`, `status-detail-dialog.test.tsx`, `dashboard-page.test.tsx` lines ~412 and ~486) are edited in the marked places only. Every other existing test passes **unedited**; in particular the two `GetCurrentStatusTests` threshold cases (`..._within_the_trending_threshold_...WithinRange` at difference 0 and `..._more_than_the_threshold_resolves_to_Trending` at difference 175) and the `StatusEndpointsTests` status cases keep their expectations (none sits between the scaled and the unscaled threshold; if one does, record it in Debug Log References and say why the new expectation is right).

### What this fixes and why it is safe to change

- **The bug (audit C12).** `GetCurrentStatus` computes `baselineToDateKwh = NormalizeToDate(yearlyBaseline, 0, elapsed)` (the baseline for the span the readings cover) but hands `household.TrendingThresholdKwh` to `ResolveStatus` as is. The decision (Ralf with John, 2026-10-10) is that the threshold is annual and Status scales it.

A first-year household gets a lower bar, i.e. earlier *Trending*: exactly the intended change, and the release note says so. No storage, no migration, no job, no restore/export format change.

### Technical details the dev must get right

- **Exact ties need exact spans.** `NormalizeToDate` converts `elapsed.TotalDays` (a `double`) to `decimal`. Whole-day spans and `TimeSpan.FromDays(182.5)` convert exactly; spans built from `DateTimeOffset.UtcNow` subtractions in two statements can be off by a tick. Unit tests that assert an exact tie therefore build timestamps from a fixed `DateTimeOffset` plus `AddDays(n)` (integer `n`), and the Api test avoids exact ties entirely (Postgres keeps microseconds).
- **Which elapsed.** It is `paceResult.Value.Elapsed` (sum of the walked pairs' spans), not "last minus first reading" and not "time since the Household was created". They are equal unless a Reset pair was voided; use the same value the baseline uses so threshold and baseline always cover the same period.
- **Numeric scale.** 100 kWh x 73 / 365 = 20 exactly; for 100.5 days the figure has many decimals. Do not round in the domain or the Application layer; the only rounding is the display format in the dialog. Do not compare the scaled threshold to a rounded difference anywhere.
- **Stale tab safety.** A browser tab loaded before the deploy talks to the new API fine (additive field), but a tab loaded **after** the deploy talking to a still-running previous revision (rollback) gets a detail response without `trendingThresholdToDateKwh`. The dialog should not print "NaN kWh": render the scaled row only when `typeof detail.trendingThresholdToDateKwh === 'number'` (a one-line guard, with a one-line comment about rollback), and add a test case with the field absent that expects no scaled row and no crash. TypeScript's type says `number`, so build the fixture with a cast.
- **Locale strings.** Keys live under `dashboard.statusDetail`; i18next interpolation uses `{{name}}`; the German file uses typographic em dashes and real umlauts as the existing strings do. Do not hardcode "per year" in the component. No existing test looks up the old label text (`git grep -n "Trending threshold" -- web/src web/e2e` finds only a comment), so the label change breaks no assertion; if one appears by the time you start, update it as a marked edit, not by loosening it.
- **AD-14 scan.** See Task 1.4: no `Event` / `SmartPlugReading` words in non-comment lines of the three scanned files.
- **Convention checks:** file-scoped namespaces, `/// <summary>` already present on `GetCurrentStatus`, comments of one to three lines of *why*, test names `Snake_case_with_underscores`, Shouldly (`ShouldBe(expected, tolerance)` for decimals), NSubstitute for ports, `TestContext.Current.CancellationToken` in async tests, `import type` for type-only imports in TypeScript, `@/` alias imports, oxlint (not ESLint).
