## Story

As a household member who logs readings offline,
I want to be told when a queued reading was rejected,
So that I don't silently lose a reading I entered (audit C4).

## Acceptance Criteria

1. **Given** `flushQueue` receives a permanent 4xx for a queued reading, **when** it handles the response, **then** the reading stays in IndexedDB in a "needs attention" state instead of being deleted.
2. **Given** readings needing attention, **when** the member opens the app, **then** they see them with the server's reason, and can correct and resend them or discard them explicitly. *Ask First (Sally, if needed): where this surfaces.* (Resolved at create-story to a default, confirmed by Ralf through the mock of Task 3; see AC #6.)
3. **Given** AD-16, **when** a corrected reading is resent, **then** it keeps its idempotency key, unless the correction changes its identity.
4. **Implied (the "needs attention" state has to be a real, durable state, and nothing else may keep treating the entry as a normal queued one):** `QueuedMeterReading` (web/src/lib/offline-queue.ts) gains one optional field, `rejection?: { status: number; detail: string | null; rejectedAtUtc: string }`. An entry with `rejection` is *needs attention*; an entry without it is *pending* (every entry written before this story is pending, so no migration of existing data). The object store, its key path (`idempotencyKey`) and `DB_VERSION` (1) do **not** change: IndexedDB stores whole objects, and adding a field needs no `onupgradeneeded`. Consequences the dev must apply, because they are easy to miss:
   - `flushQueue` **skips** needs-attention entries (it must not re-POST an entry the server already refused, on every reconnect, forever).
   - `listPending()` keeps returning **every** entry of the store (pending and needs-attention). Its callers want exactly that: `checkPendingReadingsBeforeLogoff` counts what is still on the device, and `removeForHousehold` (Story 11.9, leaving a Household) must delete the rejected entries too. Do **not** change `listPending` to filter; add `listNeedsAttention(householdId)` and `isNeedsAttention(reading)` next to it. (A rename of `listPending` is left out; see "Considered and left out".)
   - Marking an entry rejected is a read-modify-write that **does nothing when the entry no longer exists** (it was discarded, or `removeForHousehold` ran, while the POST was in flight); it must never resurrect a deleted entry.
5. **Implied (what "permanent 4xx" means once a wrong answer is no longer harmless):** today `isPermanentRejection` is "any 4xx except 401 and 403". With deletion that already lost data for 408 and 429; with this story it would also put a reading in *needs attention* for a rate-limit or a timeout, which the member can do nothing about and which a plain retry fixes. 408 (Request Timeout) and 429 (Too Many Requests) are **transient**: the entry stays pending, exactly like 5xx, 401, 403 and a network failure. The meter-reading route has no rate-limit policy today (`HttpRateLimiting.cs`), but a proxy in front of the app can still answer 429. Every other 4xx (400 from `MeterReadingValidationException` or a body that fails to bind, 404, 405, 413, 415, 422, ...) is permanent.
6. **Implied (the Ask First, resolved to a default; Ralf confirms or changes it in Task 3's mock):** the list surfaces on the **Dashboard** (the landing view, so "when the member opens the app" is met), as one card directly **under the Status card** and above the Tariff Check card; it renders **nothing** when the signed-in Household has no needs-attention entry. It is not on Settings (not seen on open), not inside the collapsed *Meter Readings* history card on Trend History (server data, collapsed by default, a different page), and there is no badge on the nav chrome. The Status card stays the first and highest-weight element (Story 2.5 AC). Each row shows the kWh value and the reading's date and time in the Household's locale, the reason (AC #7), and two actions: *Correct and resend* and *Discard*. Rows are ordered by `readingTimestamp`, oldest first. The card follows the app's tone: calm, no alarm (DESIGN/colors.md reserves red for genuine system errors and critical messages; whether a lost reading counts as one is exactly the colour question the mock settles).
7. **Implied ("with the server's reason"):** the reason is `rejection.detail`, the RFC 7807 `detail` string the API returned (for example `Reading timestamp '2026-11-02T10:00:00+00:00' is too far in the future.`), shown **verbatim**. When the response had no usable `detail` (a body that failed to bind answers a bare 400), a translated fallback names the status ("The server didn't accept this reading (error 400)."). The server's `detail` is English prose (the meter-reading endpoints return no `errorCode`, unlike `EventEndpoints`), so a `de-DE` household sees English there; the surrounding labels are translated. That is a known, accepted limitation of this story; adding `errorCode`s to `CreateMeterReading` and translating them is recorded as an `[open]` item (Task 8.2), not built here.
8. **Implied (correct and resend; AC #3 made precise):** *Correct and resend* opens a dialog with the reading's kWh (the shared `UnitInput`, unit inside the field) and its date and time (`datetime-local`), pre-filled from the entry, and the reason visible above the fields. On submit the app calls one new function, `resendRejectedReading(householdId, idempotencyKey, { kwhValue, readingTimestamp })` (in `meter-reading-sync.ts`). **It has no parameter for the key**: it reads the stored entry, writes the corrected values back **under the same `idempotencyKey`**, clears `rejection` (the entry is an ordinary pending one again), and POSTs it through the same `post()` as `flushQueue`. The key is the entry's identity (AD-16: "a new key is always a new reading"); the two editable fields are payload, so **no correction in this story changes identity**, which resolves the epic's "unless" clause (Q2). Outcomes: `200` → the entry is removed and `onSynced` fires (a resent reading can open a regression prompt and changes Status, like any flushed reading); a permanent 4xx → the entry goes back to needs attention with the **new** `rejection` and the dialog stays open showing the new reason; AMENDED 2026-10-28, code-review decision (Ralf, option b): a network failure or timeout (the request never got an answer) → the entry **stays pending** (it syncs on reconnect like any queued reading), the dialog closes and the card's live region says the existing `meterReading.savedOffline` text; an HTTP answer that is transient (5xx, 401, 403, 408, 429) → the entry **stays pending** with the corrected values, the dialog **stays open** and shows a translated "couldn't reach the server / try again" message (the member can retry or cancel; a cancelled dialog leaves the entry pending, to sync on the next flush). ~~anything transient (network failure or timeout, 5xx, 401, 403, 408, 429) → the entry **stays pending** (it syncs on reconnect like any queued reading), the dialog closes and the card's live region says the existing `meterReading.savedOffline` text.~~ A second submit while one is in flight is impossible (button disabled, `submitting`).
9. **Implied (discard is explicit and not a mis-tap):** *Discard* does not delete on the first press. It swaps the row's actions for an inline confirmation ("Discard this reading? It can't be recovered." with *Discard* and *Keep*); only the second *Discard* removes the entry. A discarded entry is gone from IndexedDB (`remove`) and the row disappears. No undo.
10. **Implied (the list must follow the queue without a page reload):** a background flush on reconnect (`registerOfflineSync`) can reject an entry while the Dashboard is open. `offline-queue.ts` dispatches one `window` event (`QUEUE_CHANGED_EVENT`) after every mutation (`enqueue`, `remove`, mark-rejected, resubmit); a small hook, `useRejectedReadings(householdId)` (new, `web/src/hooks/`), reads `listNeedsAttention` on mount, on household change and on that event, ignores a result that arrives after unmount or after a newer read, and **swallows an unreadable store** (private browsing or blocked storage: the card renders nothing and the app works as before). The hook is the only reader; the card does not poll.
11. **Implied (leaving and logging off must count what is on the device, including rejected entries):** `checkPendingReadingsBeforeLogoff` keeps counting every entry of the Household (`pendingCount`, rejected ones included, so the *leave Household* dialog's "couldn't be synced... will be deleted from this device" warning and `removeForHousehold` stay correct) and additionally returns `attentionCount` (how many of them are needs-attention). The logoff dialog's *Unsynced readings* step (`settings.logoff.queueWarning*`) shows one extra sentence when `attentionCount > 0` ("n of them were rejected by the server and are waiting for you on the dashboard"), in both locales and with plural forms. The leave dialog's copy is unchanged (it already says "couldn't be synced").
12. **Implied (accessibility and i18n, the project's standing bar):** every string is in `en-US` and `de-DE` (the `translation-consistency` test keeps the key sets equal), with plural forms where a count appears. Row actions have accessible names that identify the reading (value and timestamp, like `meterReadingHistory.editTriggerFor`). The card's list region is `aria-live="polite"` so a row that appears after a background flush is announced. The dialog is a Radix `Dialog` (focus trap, Escape) like `EditMeterReadingDialog`. The dashboard's Tab order equals reading order (no CSS `order`; `web/e2e/tab-order.spec.ts` is not changed because no reordering is introduced).
13. **Implied (`flushQueue` has no test of its own today, and the behaviour being changed is exactly its 4xx branch):** there is no `meter-reading-sync.test.ts`; the only coverage of `flushQueue` is incidental through `logoff.test.ts`. This story adds that file and pins every branch (AC #1, #4, #5, #8), red first. The existing tests pass **unedited** except the marked edits of Task 6.
14. **Implied (docs and project memory, the Story 11.1-11.15 practice):** `_bmad-artifacts/project-context.md` rewrites the existing *Offline queue (AD-16/stack)* bullet (it says "Meter Reading creation only"; it now also says rejected entries are kept, how they are marked, and the 408/429 rule) and bumps "Last Updated"; `ARCHITECTURE-SPINE/invariants-rules.md` AD-16 gets one `[IMPLEMENTED <date>, Story 11.16]` line; `deferred-work.md` gets the `[open]` items of Task 8.2. The release-note text is drafted in this file (Task 8.4) and goes in the PR body; **Ralf** publishes it.

## Dev Notes

### What this fixes and why it is safe to change

- `flushQueue` treats a reading the server will never accept (a validation 400) as garbage and deletes it, logging only to the console. The reading was typed by a person, possibly in a basement with no signal, and may be the only record of that meter value. The fix keeps the entry, says why it was refused, and lets the member decide. Nothing server-side changes: the API already answers `400` with a problem `detail` for every validation failure, and AD-16 already makes a resend with the same key harmless.
- Why a rejected entry is realistic at all: the form blocks values `<= 0` (`min="0.01"`), but not a timestamp more than 5 minutes ahead of the server clock (`CreateMeterReading.MaxFutureClockSkew`; a wrong device clock or a mistyped date), not a value of `10^15` or more (`MeterReadingValidation.MaxKwhValue`), and not a body the binder refuses. Online, such a request fails visibly in the sheet (`attemptSend` throws `ApiError`, the sheet shows `detail`); only the **offline-then-flush** path loses it silently. That is why the bug is rated Low and why the UI must stay proportionate (one quiet card, shown only when needed).
- The server never persisted a reading whose answer was a 4xx (`CreateMeterReading` validates before `AddAsync`; the idempotency fast path runs first and returns the existing row, so a key that exists never yields a 4xx). Therefore resending corrected values under the same key always inserts a fresh row, and a corrected resend can never silently come back as "no-op with the old values". If that ever stops being true (a validation that runs after the insert), AC #3 has to be revisited: that is the "unless the correction changes its identity" case, and it does not exist today.

### Design decisions already made (do not re-litigate; Ralf can override at review; none changes an epic AC)

- **Q1 State lives on the entry** (`rejection` field), not in a second object store. One store, one key, no `DB_VERSION` bump, no migration of existing data, and `removeForHousehold` keeps working untouched.
- **Q2 "Unless the correction changes its identity" = never, in this story.** Identity is the idempotency key; kWh and timestamp are payload (AD-16). The resend function has no key parameter, so the code cannot change identity by accident. If Ralf wants "a much later timestamp means a different reading", that is a new key via discard-and-log-again, not a hidden rewrite.
- **Q3 408 and 429 are transient** (AC #5), a deliberate extension of the epic's "permanent 4xx": without it the new state would hold readings that need no human.
- **Q4 Server `detail` verbatim, English** (AC #7): the audit asks for "the server's reason"; translating it needs backend `errorCode`s, recorded as `[open]`.
- **Q5 Placement: Dashboard card under the Status card** (AC #6), pending the mock; no nav badge, no Settings entry.
- **Q6 Two-step discard inline** (AC #9), not a modal: it keeps the one-level-deep modal rule (UX-DR13) free for the resend dialog.

### Technical details the dev must get right

- **One IndexedDB transaction per read-modify-write.** `get` and `put` inside the same `readwrite` transaction; awaiting a Promise between them (an `await openDatabase()` is fine *before* the transaction, an `await` of anything *inside* is not) lets the transaction auto-commit and the `put` throws `TransactionInactiveError`. `fake-indexeddb` enforces this too, so the tests catch it.
- **Dispatch the change event on `transaction.oncomplete`,** and only when something actually changed (missing key: no event). The hook reads the store again on the event; an early event would read stale data.
- **`toApiError(response)` already returns `detail: null` for a non-JSON body.** Do not re-parse the response; call it once per rejected response. `ApiError.detail` can also be an empty string: treat `''` as `null` when building `rejection`.
- **`datetime-local` round trip:** stored `readingTimestamp` is a UTC ISO string; the field needs the *local* `YYYY-MM-DDTHH:mm` form (`toDateTimeLocalValue(new Date(iso))`), and the way back is `new Date(value).toISOString()`. Seconds and milliseconds of the original are lost on a corrected resend, as for a new reading; that is fine.
- **Number input:** `Number(kwhValue)` like the sheet; `UnitInput` has `min="0.01"`, `step="0.01"`. A browser-valid value can still be rejected by the server (the point of the story).
- **Do not hold the `flushing` guard in `resendRejectedReading`.** It is a user action on one entry; the guard exists to stop two background flushes. A race with a flush on the same key is safe by AD-16 (test 2.2 (g)).
- **Lint:** `react-hooks/exhaustive-deps` is a real warning source in this repo (Story 11.18 will fix the existing one); do not add another. The new hook's effects list their dependencies.
- **Styling tokens:** Tailwind v4, tokens from `index.css`; `bg-surface-quiet border-surface-quiet-border` (QuietCard) or `GlassCard`; text `text-muted-foreground`, `text-destructive` only if the mock says so. No new colour literal outside the documented tokens.
