## Follow-up: OIDC callback URL scheme mismatch (2026-08-13)

- source_spec: none
  summary: Login against Auth0 fails with "Callback URL mismatch" — the app generates `redirect_uri=http://.../signin-oidc` (note `http`, not `https`), but Auth0 only has `https://.../signin-oidc` whitelisted. Auth0's own error payload confirms `authorized: ["https://...signin-oidc"]` vs `attempt: "http://...signin-oidc"`.
  evidence: Likely root cause identified but not yet fixed: `src/EnergyTracker.Api/Program.cs:174-177` configures `app.UseForwardedHeaders(...)` for `XForwardedFor | XForwardedProto` — needed because Container Apps terminates TLS at its ingress and forwards plain HTTP to the container (the adjacent comment already explains exactly this). However, `ForwardedHeadersOptions.KnownNetworks`/`KnownProxies` are left at their ASP.NET Core defaults (loopback-only) instead of being cleared — per the framework's documented behavior, `ForwardedHeadersMiddleware` only honors `X-Forwarded-*` headers when the immediate connecting proxy IP matches a `KnownProxies` entry or falls inside a `KnownNetworks` CIDR; Container Apps' internal ingress IP won't match either, so the header is silently ignored and `Request.Scheme` stays `http`. The comment at line 172-173 asserts trusting the header "without a KnownProxies allowlist is safe" but the code never actually clears the lists to make that trust take effect. Likely fix: add `options.KnownNetworks.Clear(); options.KnownProxies.Clear();` inside the `ForwardedHeadersOptions` initializer — not applied here since this was found during unrelated login-fix verification, not scoped/tested as its own change.
