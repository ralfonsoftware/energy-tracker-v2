# Story 2.2b: Design System Foundation

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a developer,
I want the DESIGN.md-described glass-panel component layer wired into the codebase as shared, reusable pieces,
so that every screen built from here on — starting with Story 2.3's regression prompt — renders against the real design system instead of deferring it again.

## Why This Story Exists (not a PRD/epic story)

Not FR-backed, no epic file entry — cross-cutting infra, inserted via `_bmad-artifacts/planning/sprint-change-proposal-2026-08-16.md`. Same category as Epic 1's retro action items *"Wire DESIGN.md's real design tokens..."* and *"Sweep existing Epic 1 UI... to use the real design tokens"* — both closed at base-token scope only (`--primary`/`--background`/`--foreground`, confirmed via grep against `web/src/index.css`). This story is the deferred continuation of exactly those two items, now covering the component-level tokens and shared pieces they explicitly scoped out. Story 2.2's and Story 2.3's own Dev Notes both flag the same gap ("No glass-panel tokens are wired yet... flag if a real design/token pass happens later") — this is that pass.

## Acceptance Criteria

1. **Given** DESIGN.md's confirmed dark/light values **When** `web/src/index.css` is inspected **Then** it defines, as Tailwind v4 `@theme inline` entries for both `:root` and `.dark`: the glass surface pair (`surface-glass`, `surface-panel-back`), the status triad (`status-within-range`/`status-below-baseline`/`status-trending`) with their AA-verified badge-text pairs, the `rounded-sm/md/lg/full` radius scale, and the `card-padding`/`card-gap`/`mobile-margin` spacing values — copied verbatim from `DESIGN/*.md` and the mockups' own CSS, no new color/spacing decisions made
2. **Given** the `Button` component **When** a `variant="glass-primary"` is used **Then** it renders the pill-shaped gradient fill (dark `#6FE3C4→#2FB397`, light `#227A61→#145A47`) with the `active:scale-[0.965]` press-compression already established in `log-reading-sheet.tsx`'s local `SAVE_BUTTON_CLASSNAME`, and that local constant is deleted in favor of the shared variant
3. **Given** a bare-kWh numeric field **When** rendered via the new unit-input pattern **Then** "kWh" renders as a suffix inside the same bordered box as the number, never as a separate label beside it (matches `key-settings.html`/`key-log-reading-flow.html`)
4. **Given** the Yearly Baseline form **When** its preset row renders **Then** it shows one compact row of 4 icon buttons (not text pills), each with an `aria-label` stating the full preset sentence (reusing the existing `yearlyBaseline.preset1-4` i18n strings), and tapping one fills the kWh field without submitting — Story 2.1's AC #1 ("never silently applied as a default") holds unchanged
5. **Given** Settings' Room/Power Point/Device tree **When** rendered **Then** it uses the glass tree-card surface and `lucide-react` icon actions (rename/delete) in place of the plain `<details>`/full-width-text-`Button` treatment, with **no functional change** to Add/Rename/Delete/Delete-confirm behavior
6. **Given** a Delete confirmation (Room/Power Point/Device) **When** rendered **Then** it uses a neutral/amber "archive" treatment, never `variant="destructive"` — AD-10: this is a reversible archive, not data loss (the mocks deliberately avoid red here; the current code's `variant="destructive"` is the one real behavioral fix in this story, not just restyling)
7. **Given** Household Creation, Household Invite, and the Log Reading sheet **When** rendered **Then** each uses the Task 1-4 shared primitives, matching `key-onboarding.html` Frame 1, `key-household-invite.html`'s existing link-generate functionality, and `key-log-reading-flow.html`'s Log Reading sheet frame respectively — with **no change to any component's existing props, state shape, or public API** (Story 2.3 depends on `log-reading-sheet.tsx`'s current `{ trigger: ReactNode }` contract and internal `open` state — see Scope Boundary)
8. **Given** all 6 retrofitted screens' existing test suites **When** run **Then** they pass — only selectors/queries affected by markup changes are updated; no test is deleted or weakened to make a failure disappear
9. **Given** the new shared pieces (unit-input, household-size preset row, `Button`'s `glass-primary` variant) **When** unit-tested **Then** each has Vitest + Testing Library coverage for its stated behavior

## Scope Boundary — What This Story Does NOT Do

**No new features, no functional changes except the Delete-not-destructive fix (AC #6).** This is a presentation-layer retrofit of screens that already work. Every item below was checked against the actual current code (not assumed from the mocks) before being ruled out:

1. **`StatusBadge` and the bottom-tab nav chrome are deferred to Story 2.5.** Neither has a consumer today: `App.tsx` has no router (`view` is a local `useState<'dashboard' | 'settings'>`, per Story 1.5's explicit "no react-router yet" precedent — grep confirms), and the Dashboard is still Story 1.1's placeholder (`<h1>{t('app.title')}</h1>` + a plain `<Button>`). Building either now would be speculative — Story 2.5 needs a real Status to badge and a real multi-surface shell to hang tabs on, neither of which exists yet.
2. **Household Invite's retrofit is a visual restyle of the existing inline-panel + link-generate flow only.** `invite-generate-panel.tsx` today has no Sheet/Dialog overlay, no email-invite field, no member list. `key-household-invite.html`'s Frame 1 (email field) and Frame 2 (member list + pending badge) describe functionality Story 1.8 never built — don't add them here. Restyle what exists (generate button → link row → copy button → expiry note) with the new surface/button primitives.
3. **Household Creation's retrofit matches `key-onboarding.html` Frame 1 only.** Frame 2 (a 2-step wizard, progress dots, Yearly Baseline folded into onboarding) doesn't correspond to anything in this codebase — Yearly Baseline is Settings-only (Story 2.1), reached after household creation, not during it. Don't build a wizard or progress-dots component.
4. **Room/Power Point/Device retrofit does not add a "Move to…" action.** That's Story 2.6, not yet built (`sprint-status.yaml`: `backlog`). The device-row icon actions are Rename + Delete only (2 icons, not the mock's 3).
5. **`log-reading-sheet.tsx`'s prop contract and `open`-state management are untouched.** Story 2.3's Task 6 (already written) converts this component from internally-managed `open` state to controlled `open`/`onOpenChange`/`onSaved` props — that is 2.3's job, immediately after this story. Touch only the JSX inside `SheetContent`/the `Input`/the `Button` — restyle in place, don't restructure state.
6. **Dashboard (2.5), Trend History/Tariff Radar/Smart Plug Import (Epics 3-5) are out of scope.** Shared pieces land here only where a real consumer exists in one of the 6 retrofitted files, or is the very next story (2.3's regression modal, via the shared Dialog glass classnames from Task 4).
7. **No new shadcn primitive is hand-rolled where the CLI already provides one.** `Card` and `Badge`* don't exist yet in `web/src/components/ui/` — scaffold via `npx shadcn add card badge`, then layer the DESIGN.md delta on top (same pattern `Button`/`Dialog`/`Sheet`/`Input`/`Label`/`Select` already follow — DESIGN.md's own Brand & Style section: *"specifies only the brand/material-layer delta on top of shadcn's defaults... Everything not named here inherits shadcn's defaults unchanged"*). *`Badge` is scaffolded for forward use (its glass/status variants land in Task 3 for completeness against the token set) even though `StatusBadge`-the-composed-component is deferred per item 1 above — the raw shadcn `Badge` primitive existing is harmless and saves a step for 2.5; do not build a `StatusBadge` wrapper component this story.

## Dev Notes

- **This is a presentation-layer-only story.** No API, Domain, or Infrastructure file changes anywhere in this story — grep the task list above to confirm before starting any task; if a task seems to need a backend change, that's a signal the task has drifted out of scope.
- **Read every file before editing it.** All 6 retrofit targets were read in full during story creation (see References) — their current behavior (loading/error states, 409-conflict handling, offline-queue integration, dialog state machine) must be preserved exactly. This story changes *how it looks*, never *what it does*, except the one named exception (AC #6, Delete→amber).
- **`log-reading-sheet.tsx` is a shared dependency with Story 2.3.** That story's Task 6 is already written against this file and expects the current `{ trigger: ReactNode }` prop shape and internal `open` state — see Scope Boundary #5. If this story's retrofit and 2.3 land out of order or need rebasing, the JSX-only nature of this story's change (no prop/state changes) is what keeps that safe.
- **`lucide-react` is already a dependency** (`^1.31.0`, used today in `dialog.tsx`/`sheet.tsx`/`select.tsx` for `XIcon`/`ChevronDownIcon`/etc.) — use it for every icon this story needs (`Pencil`, `Trash2`, `ChevronRight`, person icon for the preset row — check `lucide-react`'s export name, likely `User` or `UserRound`). Do not hand-copy the inline `<svg><path .../></svg>` markup from the static HTML mockups — those exist as standalone offline files with no bundler and can't import a package; the real app can and should use the installed icon library.
- **Tailwind v4 CSS-first config** (`web/src/index.css`, no `tailwind.config.js` — confirmed absent) is where Task 1's tokens go, inside an `@theme inline` block per the existing pattern already in this file (lines 7-49). Don't scaffold a config file.
- **shadcn config**: `web/components.json` — style `radix-nova`, base color `neutral`, icon library `lucide` (confirmed). `npx shadcn add card badge` follows the project's existing scaffolding convention exactly (same as how `dialog`/`sheet`/`select` were originally added).
- **Testing**: Vitest + Testing Library, `jsdom`, globals on, colocated test files (`*.test.tsx` next to source, not a parallel `__tests__/` tree) — existing convention, no change.
- **oxlint** (not ESLint) enforces `react/rules-of-hooks` and `no-unused-vars` as build-breaking — deleting `SAVE_BUTTON_CLASSNAME` and the inline `PRESETS` array from their old locations (Tasks 2, 4) must be followed through completely, not left as unused dead code.
