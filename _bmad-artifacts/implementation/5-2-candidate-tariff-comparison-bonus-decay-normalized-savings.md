# Story 5.2: Candidate Tariff Comparison & Bonus-Decay Normalized Savings

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Household member,
I want to enter a candidate tariff and see an honest, bonus-normalized savings projection against my current one,
so that I can judge whether switching would actually save money.

## Scope Reality Check — Read This First

This is the **second story in Epic 5**, building directly on Story 5.1's `Tariff` entity/CRUD (done). Epic 5's header binds AD-5 (`BonusDecayNormalizer`), AD-7 (request-time computation), UX-DR5/7/10/12 to the **whole epic**, but most of that belongs to later stories:

- **This story owns:** FR-11 (candidate entry, scratch/exploratory), FR-12 (bonus-decay normalized annual savings projection using actual Pattern Detective pace), FR-14 (reusing the shared `Domain.Calculations.BonusDecayNormalizer` — never a local reimplementation), and NFR6 (fixed-decimal currency display).
- **Do NOT build Story 5.3's Two-Way Attractiveness Signal here.** FR-13's "green/red signal shown twice — once with the Switching Bonus included, once normalized out" — the dedicated `--attractiveness-worth-it`/`--attractiveness-not-worth-it` color pair, the "Worth switching"/"Not worth it" verdict badges, the *naive* (bonus-included, undecayed) savings figure — all of that is Story 5.3's UX-DR7/UX-DR10-gated work. This story computes and shows exactly **one** number: the honest, bonus-normalized annual savings projection, in plain text/typography (reuse `GlassCard`, no color-coded verdict).
- **Do NOT build Story 5.4's Tariff Check Reminder here.** AD-7's Reminder due-ness computation, the 3-month gate, cadence — none of that belongs to this story. The `tariff-check-card` banner already visible at the top of `key-tariff-radar.html`'s mockup frames is Story 5.4's (and partly 5.1's nav-entry) responsibility, not this one's.
- **No new persisted entity.** A candidate tariff is FR-11's "scratch/exploratory" — it is never written to the database. The comparison is a pure, stateless, request-time computation (same "compute live" spirit AD-7 established for Status, though AD-7 itself doesn't bind this story — noted only because it's the same design instinct).

## Acceptance Criteria

(Sourced from `_bmad-artifacts/planning/epics/epic-5-tariff-savings-radar.md`, Story 5.2 block, lines 46-72.)

1. **Given** a candidate tariff (price/kWh, base fee, optional switching-bonus terms), **when** I enter it, **then** it's scratch/exploratory — it never alters my Household's actual current Tariff until I explicitly switch (FR-11).
2. **Given** a valid candidate entry, **when** the projection is computed, **then** it uses my actual household consumption pace from Pattern Detective, never a generic/assumed usage figure (FR-12).
3. **Given** fewer than two Meter Readings exist (no usable pace yet), **when** I request a comparison, **then** it shows the same onboarding empty state as the Dashboard Status, not a zero or undefined projection (FR-12).
4. **Given** the projection's Bonus-Decay Normalization, **when** computed, **then** it calls the single shared `Domain.Calculations.BonusDecayNormalizer` also used by Pattern Detective's pace threshold — never a locally reimplemented or adjusted formula (FR-14, AD-5).
5. **Given** the normalization formula changes, **when** redeployed, **then** both Tariff Savings Radar and Pattern Detective's threshold reflect the change identically (FR-14).

**Not explicitly written above but required for the system to work end-to-end (project-context.md's "the dev agent owns this" rule) — see Dev Notes' "Edge cases beyond the stated ACs":**
- No current Tariff configured yet (a household could reach this screen having never used Story 5.1's form) — nothing exists to compare against.
- Candidate field validation (negative/absurd inputs) — mirror Story 5.1's `TariffValidation` discipline.

  - [ ] Call `GetCurrentStatus.ExecuteAsync(householdId, cancellationToken)`. If `null`, return `null` (AC #3).
  - [ ] Annualize the pace: `annualPaceKwh = statusResult.PaceToDateKwh * 365m / (decimal)statusResult.ElapsedDays`. This extrapolation is **new logic** — nothing in `PatternDetectiveCalculator`/`GetCurrentStatus` does this today (Status only ever compares pace-to-date against baseline-to-date over the *same* elapsed window; it never needs an annualized figure). `ElapsedDays` is guaranteed `> 0` whenever `GetCurrentStatus` returns non-null (`PatternDetectiveCalculator.ComputePaceToDate` returns `null` for `totalElapsed <= TimeSpan.Zero`), so no divide-by-zero guard is needed here.
  - [ ] Compute `currentAnnualCost = currentTariff.MonthlyBaseFee * 12 + currentTariff.PricePerKwh * annualPaceKwh`.
  - [ ] Compute `candidateAnnualCostNoBonus = candidateMonthlyBaseFee * 12 + candidatePricePerKwh * annualPaceKwh`.
  - [ ] **Bonus-Decay Normalization call (AC #4, #5) — the exact shape, verified against the mockup's own worked numbers (see Dev Notes):** `var bonusNormalizedCandidateAnnualCost = BonusDecayNormalizer.NormalizeToDate(candidateAnnualCostNoBonus, candidateSwitchingBonus, TimeSpan.FromDays(365));`. At `elapsed = 365 days` exactly, `elapsedFractionOfYear = 1`, so the function's rate term reduces to `candidateAnnualCostNoBonus * 1` (unchanged) and its bonus term reduces to `candidateSwitchingBonus * (1 - 1) = 0` (fully decayed) — the *whole point* of an "annual" (one full year out) projection is that a one-time switching bonus should contribute nothing to it, which is exactly what this call produces. **Do not "simplify" this to `bonusNormalizedCandidateAnnualCost = candidateAnnualCostNoBonus` and skip the call** — that would bypass AD-5's single shared implementation (AC #4) even though the numeric result happens to be identical today; a future change to the decay formula (e.g., a non-linear decay curve) must still reach this call site automatically (AC #5).
  - [ ] Compute `bonusNormalizedAnnualSavings = currentAnnualCost - bonusNormalizedCandidateAnnualCost` (positive = switching saves money; negative = candidate costs more). This sign convention is what Story 5.3 will build its "Worth switching"/"Not worth it" verdict and its breakeven tie-break (`== 0` → not worth it) on top of — keep it exactly this way round.
  - [ ] Return `TariffComparisonResult(CurrentMonthlyBaseFee, CurrentPricePerKwh, CurrentCurrency, CandidateMonthlyBaseFee, CandidatePricePerKwh, CandidateSwitchingBonus, AnnualPaceKwh, CurrentAnnualCost, CandidateAnnualCostBonusNormalized, BonusNormalizedAnnualSavings)`.

## Dev Notes

- **The math was verified line-for-line against `mockups/key-tariff-radar.html`'s own worked example (lines 276-314), not invented from scratch — trust these numbers, they're not illustrative filler:**
  - Current: `€12.50/mo` base fee, `€0.3200`/kWh. Candidate: `€14.90/mo` base fee, `€0.3150`/kWh, `€350` one-time switching bonus. Pace: `3,200 kWh/yr`.
  - `currentAnnualCost = 12.50*12 + 0.3200*3200 = 150 + 1024 = 1174.00`
  - `candidateAnnualCostNoBonus = 14.90*12 + 0.3150*3200 = 178.80 + 1008 = 1186.80`
  - Bonus-normalized (this story's output): `bonusNormalizedCandidateAnnualCost = candidateAnnualCostNoBonus` (decayed bonus is `0` at `elapsed = 365 days`, see Task 1) `= 1186.80`. `bonusNormalizedAnnualSavings = 1174.00 - 1186.80 = -12.80` → mockup's own "About €13/yr more, not less" line, rounded for display. **This story renders only this number.**
  - Bonus-included (Story 5.3's job, not built here, shown only for context/validation of the design): `bonusIncludedCandidateAnnualCost = candidateAnnualCostNoBonus - 350 = 836.80`. `bonusIncludedAnnualSavings = 1174.00 - 836.80 = 337.20` → mockup's "Save about €337 this year" line.
  - This cross-check is what gives confidence the `BonusDecayNormalizer.NormalizeToDate(candidateAnnualCostNoBonus, candidateSwitchingBonus, TimeSpan.FromDays(365))` call shape in Task 1 is correct, not a guess at how to reuse a kWh-named function for money.

- **Why `BonusDecayNormalizer`'s parameters are named `annualRateKwh`/`bonusTermsKwh` but this story passes money, not kWh — and why that's fine, not a bug to "fix":** the function is unit-agnostic pure decimal arithmetic (`rate * elapsedFraction + bonus * decayFactor`) — nothing about its implementation actually requires kWh, the naming is just a historical artifact of Pattern Detective (Story 2.x) being the *first* caller. AD-5's own text describes it generically: "a pure function of (rate, bonus terms, elapsed time)." **Do not rename the parameters** as part of this story — the function is called positionally everywhere (`BonusDecayNormalizerTests.cs` confirms no named-argument call sites depend on the `Kwh` suffix), so a rename is technically safe, but it touches a file Pattern Detective (already shipped, done) also depends on for zero functional benefit — out of scope. If a future story finds the naming genuinely confusing, that's a separate, deliberate cleanup, not something to fold into this one.

- **Edge cases beyond the stated ACs (project-context.md's "the dev agent owns this" rule):**
  - **No current Tariff configured yet.** FR-11 assumes a current Tariff exists to compare against, but nothing stops a household from reaching Tariff Radar having never used Story 5.1's create form. `CompareTariff` returns `null` for this case too (see Task 1) — the same nullable-result contract as the no-pace case, since neither AC text nor the mockup ever shows this state explicitly (the mockup's Frame 2 "compare-empty" state already assumes a current tariff exists). The frontend gating recommendation in Task 3 is what actually prevents a household from hitting this in normal use.
  - **Candidate currency:** not a candidate field at all — see Task 2. Don't add a currency selector to the candidate form by copy-pasting `tariff-configuration-form.tsx`'s currency `Input` field; that field doesn't belong on this form.
  - **Partial-year pace extrapolation:** a household with only, say, 60 days of reading history has a valid `PaceToDateKwh`/`ElapsedDays` from `GetCurrentStatus`, but a "kWh/yr" figure requires extrapolating that short window out to a full year (`* 365 / elapsedDays`) — this is new logic this story introduces (see Task 1); nothing existing in `PatternDetectiveCalculator`/`GetCurrentStatus` does this today, because Status never needs an annualized figure (it always compares pace-to-date against baseline-to-date over the *same* window). A short elapsed window (e.g. 5 days) will extrapolate noisily — that's an accepted, known limitation of "actual pace, not a generic assumed figure" (FR-12's own explicit trade-off), not a bug to guard against with a minimum-elapsed threshold this story wasn't asked to add.

- **Story 5.1's own review found and fixed a real currency-formatting bug — don't repeat it here.** `tariff-history-list.tsx`'s `Intl.NumberFormat(locale, { maximumFractionDigits: 4 })` had no `minimumFractionDigits`, so `12.50` rendered as `12.5`, contradicting NFR6's "fixed-decimal, never floating-point" display requirement (caught in Story 5.1's code review, `_bmad-artifacts/implementation/5-1-tariff-configuration.md`'s Review Findings). Any new currency-figure formatting this story adds (the savings amount, the current/candidate annual cost figures if shown) must set **both** `minimumFractionDigits` and `maximumFractionDigits` explicitly (`2` for money figures — this story never displays a 4-decimal per-kWh price itself, only annualized money totals).

- **Closest existing analogs to build from:**
  - `GetCurrentStatus.cs` — the AD-7 single-live-computation-seam pattern this story's `CompareTariff` must plug into as a dependency, not reimplement.
  - `tariff-configuration-form.tsx` — field-level UI patterns (`UnitInput` with currency suffix, validation-before-submit, `ApiError`/error rendering) to mirror for the three candidate fields.
  - `status-card.tsx`'s `!status` branch — the exact empty-state markup/i18n-key shape AC #3 requires reusing verbatim.
  - `status-api.ts`'s `fetchCurrentStatus` — the empty-body-is-null fetch parsing shape `compareTariff` must copy (not `tariff-api.ts`'s existing `fetchTariffHistory`/`createTariff`, which always expect a populated JSON body).
  - `TariffRepository.GetHistoryForHouseholdAsync` — the exact `OrderByDescending` tie-break chain the new `FindCurrentForHouseholdAsync` must reuse (plus its own `<= now` filter, which the existing method doesn't have).
