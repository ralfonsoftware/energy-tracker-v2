## Story

As a self-hoster or future maintainer,
I want the single-instance assumption written down and observed,
so that no one raises the replica count without knowing what breaks (audit A1, AD-24).

## Acceptance Criteria

1. **Given** `docs/self-hosting.md` and the Bicep `maxReplicas` description, **when** this story is done, **then** they state the invariant, list the process-local components, and point to AD-24.
2. **Given** two instances whose DB heartbeat rows overlap for more than 15 minutes, **when** this is detected, **then** a warning is logged. Shorter overlaps during deploys produce nothing, and startup is never blocked.
3. **Given** each process-local mechanism, **when** this story is done, **then** it carries a one-line comment pointing to AD-24.
4. **Implied (what "state the invariant, list the components" has to contain to be useful; AC #1 is not met by one sentence):** `docs/self-hosting.md` gets one section, "Run exactly one instance" (placed after "Put a reverse proxy in front", before "Members and access"), that says: (a) the rule in plain words: one active instance per database, on Azure `maxReplicas` stays 1, on self-host one `api` container per database (never `docker compose up --scale api=N`, never a second stack on the same database); (b) what "one instance" means: one replica at a time, **not** one long-lived process (Container Apps scales to zero when idle and replaces the replica on every deploy, so its disk is not stable; AD-24, "One instance does not mean a stable disk"); (c) a table of the seven bound mechanisms, each with a plain name, the class in parentheses, and **what goes wrong with a second instance** (see Dev Notes, "What breaks with a second instance"); (d) the accepted deploy-overlap loss: an upload, restore confirmation or running import in flight across a revision swap may fail with "upload again" or `job-interrupted`, and the member retries; (e) what the warning looks like (the exact log text), where an Azure operator finds it (Log Analytics), and what to do (scale back to one, deactivate the extra revision); (f) that the Azure Storage Queue adapter existing does **not** make several replicas supported (temp files, registry, lock and rate limiter are still process-local); (g) what lifting the invariant requires: the shared-state list of `ARCHITECTURE-SPINE/deferred.md` ("Multi-instance shared state (lifting AD-24)"), stated as a prerequisite and not as a how-to; (h) the existing sentence in "5. Stopping and restarting" ("Run exactly one app container per database...") now points to this section.
5. **Implied (the Bicep half of AC #1 is two places, plus the values must not move):** the `@description` of `maxReplicas` in `infra/modules/container-app.bicep` **and** of `containerAppMaxReplicas` in `infra/main.bicep` say that the app is correct only with one active instance, name the process-local components in a short clause, and point to AD-24 and `docs/self-hosting.md`. `main.bicepparam` carries a one-line comment above `containerAppMaxReplicas` pointing to AD-24. **The values stay `1`** in all three files (`@minValue(1)` on main stays). `infra/README.md` gets two or three lines under its scale-to-zero mention pointing to the same section. An executable guard (AC #11) pins both the descriptions and the values.
6. **Implied (the instance heartbeat: what is written, by whom, how often; AD-24 says "a short-lived DB heartbeat row keyed by instance id"):** a new entity `AppInstance` (`Id` = the instance id, a `Guid` generated once per process start; `StartedAtUtc`; `LastSeenAtUtc`) in a new table `AppInstances`, created by **one expand-only migration** for both providers through `scripts/add-migration.sh AddAppInstances` (a new table cannot break the previous image). The table is **not** Household data: no `HouseholdId`, no query filter (an AD-3 exemption, recorded in `project-context.md` next to `HouseholdMember`/`HouseholdInvite`/`DataProtectionKeys`), and it is neither exported nor restored. Every `InstanceHeartbeatTimings.Interval` (1 minute, the same cadence as the job heartbeat of AD-6) the process: (a) upserts its own row (`ExecuteUpdateAsync` on `Id`, and an insert when zero rows were affected, so a row removed by another instance's housekeeping comes back with the process's real `StartedAtUtc`); (b) deletes rows whose `LastSeenAtUtc` is older than `RetainFor` (24 hours; set-based `ExecuteDeleteAsync`), so the table stays at a few rows; (c) lists the **other** rows that are alive (`LastSeenAtUtc` within `AliveAfter`, 3 minutes, of now).
7. **Implied (the overlap rule, decided here so the warning is neither noisy nor blind; see Q2):** for each other alive row, `overlap = min(self.LastSeenAtUtc, other.LastSeenAtUtc) - max(self.StartedAtUtc, other.StartedAtUtc)`. A pure function `InstanceOverlapCalculator` in `Domain/Calculations` (no clock, no I/O) computes it; a negative or zero value means no overlap. The warning fires when `overlap > OverlapWarnAfter` (15 minutes, **strictly greater**; exactly 15 minutes does not warn). It is logged **once per other instance id per process** (an in-memory set; observation only, so it needs no durability), at `Warning`, with both instance ids, the other's start time, the overlap in minutes, and the pointer "Energy Tracker supports one active instance (AD-24); see docs/self-hosting.md, 'Run exactly one instance'". A stale row (not alive) never warns, however long it overlapped. A short overlap (a deploy swap, seconds to a few minutes) writes **no** `Warning` or `Error` line; `Information` lifecycle lines are allowed (AC #9).
8. **Implied ("startup is never blocked" and "never crashes the host" are the hard parts of AC #2):** (a) the heartbeat is a `BackgroundService` (`InstanceHeartbeatService`) whose first `await` happens before any database work (`await Task.Yield()` first), so `StartAsync` returns at once and `/health` is never delayed; (b) every failure of a beat (table missing because migrations have not run yet on a self-host install, database unreachable, cancellation that is not shutdown) is caught and logged once as `Warning` for the first failure of a run of failures, with an `Information` line when a beat succeeds again, and the loop continues; an exception never escapes `ExecuteAsync` (a faulted `ExecuteAsync` stops the host by default, see `InProcessChannelJobProcessingService`); (c) the app **never** refuses to start, retries a lock, or fails `/health` because of this check, and `/health` stays liveness-only (AD-19); (d) on graceful stop (SIGTERM at a revision swap or scale-in) the process removes its own row best-effort, with a short bound (5 seconds) and its own error handling, so a stuck database cannot delay shutdown; a killed process leaves a row that goes stale after `AliveAfter` and is purged after `RetainFor`.
9. **Implied (AD-7 consistency and what an operator can see):** nothing else reads the heartbeat: no status, no job, no endpoint, no health check. The only consumer is the warning log line, so a missed beat can never change a result (AD-7: "no timer decides anything"; this one only produces evidence). The service logs `Information` "Instance heartbeat started for instance {InstanceId}" after the first successful beat and "Instance heartbeat stopped for instance {InstanceId}; row removed" on graceful stop; Part R reads these lines. The timer does not keep a scaled-to-zero replica awake (Container Apps scales on HTTP requests, not on in-process timers) and costs one small write a minute; the docs say so in one sentence.
10. **Implied (AC #3 is "each mechanism has a one-line AD-24 comment"; comments that say the opposite are part of the same defect):** (a) the seven bound mechanisms (Dev Notes, "The process-local mechanisms") each carry a one-line `AD-24` pointer at the declaration; the ones that already have it keep exactly one such line (no duplicates); (b) comments that **contradict** the invariant are corrected in the same pass: `HouseholdImportEndpoints.cs` (the comment above the active-restore check claims the check "holds across replicas"; it is a database check-then-enqueue that serialises through the single consumer, Story 11.14 adds the DB guard), `BackgroundJobProcessor.cs` (header says Container Apps "can scale to zero/multiple replicas"), `HouseholdRecomputeLock.cs` (header says "hardcodes maxReplicas = 1": it is a default, not hardcoded, and the pointer is AD-24), `MemoryHouseholdImportUploadRegistry.cs` (header "no evidence of horizontal scale-out") and `docs/data-import-restore.md` (the "one process, one container" paragraph and the closing "disclosed future concern" sentence) now point to the invariant instead of arguing it locally (AD-24: "keep a one-line comment ... instead of re-arguing"). Comments stay one to three lines of *why*.
11. **Implied (drift guard in this repo's style: prose rules die, executable ones do not):** `tests/EnergyTracker.Architecture.Tests/SingleInstanceInvariantIsDocumentedTests.cs` (text scan with comments handled as in `HouseholdImportIsStreamedTests`/`DataProtectionKeyVaultInfraTests`; each scanned file must still exist and still contain what it is scanned for): (a) every file under `src` (excluding `Migrations`, `obj`, `bin`) that contains one of the process-local patterns (`ConcurrentDictionary<`, `SemaphoreSlim`, `Channel.Create`, `IMemoryCache`, `AddRateLimiter`, `Path.GetTempPath`) is in an explicit allow-list, and every allow-listed file contains `AD-24` in a comment, so a **new** process-local mechanism fails until it is listed and commented; (b) `docs/self-hosting.md` contains the section heading, `AD-24`, and a plain-name for each of the seven mechanisms; (c) both Bicep `@description`s and the `main.bicepparam` comment contain `AD-24`, and the three values are `1`; (d) the heartbeat classes (`InstanceHeartbeatService`, `RecordInstanceHeartbeat`) name `AD-24`; (e) the failure message names AD-24 and the `deferred.md` shared-state list. Mutation-checked in Task 7.
12. **Implied (AD-24 and project-context must say what now exists):** `ARCHITECTURE-SPINE/invariants-rules.md` AD-24 gets one `[IMPLEMENTED 2026-10-24, Story 11.13]` line under "Observed, not hard-enforced" naming the table, the 1-minute interval, the 3-minute alive window, the stateless overlap rule and the once-per-instance warning; `_bmad-artifacts/project-context.md` gets one bullet under "Framework-Specific Rules" (the invariant, the seven mechanisms, the heartbeat and its rules, the `AppInstances` exemption, the guard test, "raising `maxReplicas` is an architecture decision, not a config change") and a bumped "Last Updated"; the `HouseholdMembershipDbContext`/exemption list wording stays untouched.

## Dev Notes

### What this fixes and why it is safe to change

- **A1 (Medium, verified).** Correctness depends on exactly one process in at least six places, and only a Bicep default enforces it. AD-24 decided the answer on 2026-10-10: keep one active instance, write it down, observe it, and defer the shared-state alternative (blob uploads, DB-backed registry and lock, job leases, a distributed rate-limit store) until a real need. This story is the "write it down, put a pointer at each mechanism, and observe" half. It changes no behaviour of any mechanism.
- **Why the heartbeat is safe.** It is a new table and a new hosted service whose only output is a log line. It reads and writes nothing of any Household, adds no endpoint, no claim, no query filter and no status input. It cannot fail a request: a beat that fails is caught and logged. It cannot block startup: the first `await` precedes the first query. It cannot fail `/health`: the health check is untouched (AD-19).
- **Why AD-7 still holds.** AD-7 forbids a timer that *decides* a Status or Reminder. This timer decides nothing; it records liveness evidence, like the job heartbeat of AD-6 (written by the worker, judged on read). The `MemoryHouseholdImportUploadRegistry` comment "No IHostedService/Timer: scale-to-zero hosting doesn't reliably run one" is about *correctness* depending on a timer; here nothing depends on it, and a replica that is scaled to zero has no instance to observe.

### What breaks with a second instance (content for the docs table, AC #4c)

1. **Upload registry (validate, then confirm):** the confirm request can land on the other instance, which has never heard of the token and answers "no pending import found"; the member re-uploads. The temp file of the first instance stays behind.
2. **Recompute lock:** two instances can recompute the same Household's Status at once; the locks do not see each other, so the writes can interleave (duplicate or out-of-order `StatusSnapshot` rows). Smart Plug writes are protected separately by database advisory locks and are not affected.
3. **Temp-file payloads:** the instance that dequeues a job may not be the one that holds its file; the job ends terminally `Failed` with `upload-missing` ("upload again"), never retried (AD-6, Story 11.3).
4. **In-process queue:** a job enqueued on one instance runs only on that instance; the other has its own empty queue. Fine for correctness on its own, but together with #5 it is unsafe.
5. **Startup sweep:** a starting in-process instance fails every `Queued`/`Processing` row of every Household as `job-interrupted`, including the ones another live instance is running right now.
6. **Registry expiry sweep:** each instance sweeps only its own map, so an upload abandoned on instance A is never cleaned up by B.
7. **Rate limiter:** limits are counted per instance, so the effective limit is the configured one times the number of instances (sign-in, upload, export, invite and removal throttles).

Also true, not a separate row: the restore-confirm "one active restore" check is check-then-enqueue against the database; with one consumer it serialises, with two it could run two restores at once (Story 11.14 adds a database guard, which is independent of this invariant).

### Design decisions already made (do not re-litigate; Ralf can override at review; none changes an epic AC)

- **Q1 a table, not a log scrape or a heartbeat column on `BackgroundJobs`.** AD-24 and the epic AC both say "DB heartbeat rows ... keyed by instance id". One small instance-level table also fits the 2026-10-10 review's suggestion that a later AD-6 staleness check could reuse it.
- **Q2 the overlap is computed from the rows, with no extra state column.** `min(last seen) - max(started)` against each alive other needs only `StartedAtUtc` and `LastSeenAtUtc`; a "first seen the other at" column would add a write and a migration for nothing. The cost is that it trusts the instances' clocks: two replicas of one container image on one Container Apps environment agree within seconds, and the threshold is 15 minutes, so skew is irrelevant. Say so in a one-line code comment on the calculator, not in the docs.
- **Q3 the numbers are code constants, not configuration.** 1 minute, 3 minutes, 15 minutes and 24 hours are operational constants like `JobLifecycleTimings` (AD-15 does not apply). A self-hoster has no reason to tune them; tests inject short values.
- **Q4 warn once per other instance per process, not every beat.** A warning per minute would drown the log the operator reads; one line per offending instance is the signal. A restart of the observing process warns again if the overlap still exists, which is the right behaviour.
- **Q5 the heartbeat runs for both queue providers and regardless of environment.** An Azure deployment with the Storage Queue adapter is exactly where a second replica is plausible; a self-host in-process deployment is where a second container on one database is plausible. Development runs it too (one row; harmless).
- **Q6 Part R is a gate.** Not an Auth0 gate (no auth path changes), but a new hosted service plus a migration on every boot is the kind of change the `/health`-only deploy gate cannot see. Ralf can drop R3 (self-host) and accept R2 as "observed at the next deploy".

### Technical details the dev must get right

- **Upsert order:** `ExecuteUpdateAsync(set LastSeenAtUtc where Id == self)`; if it returns 0, `Add` + `SaveChangesAsync`. A unique-key race cannot happen (the id belongs to this process only), but wrap the insert so a failure is a normal beat failure, not a crash.
- **Timestamps:** pass UTC values; the global `UtcDateTimeOffsetConverter` normalises both providers (Npgsql accepts only offset 0). Compare with `<` and `>=` against values computed in the use case; never `DateTimeOffset.UtcNow` in SQL expressions.
- **`PeriodicTimer(interval, timeProvider)`** (.NET 8+) honours the injected `TimeProvider`; `WaitForNextTickAsync(stoppingToken)` returns false/throws on cancellation, which is shutdown, not an error. Do the first beat **before** the first wait so the row appears at start.
- **Scope per beat:** resolve `RecordInstanceHeartbeat` (and so `IAppInstanceRepository` and the DbContext) from a fresh scope each beat and dispose it; do not keep a DbContext for the life of the service. `JobHouseholdContext` is never set (no Household), and the accessor's job path returns null for the unfiltered table, which is fine; do not touch `JobHouseholdContext`.
- **Graceful stop:** `BackgroundService.StopAsync` cancels `stoppingToken`, then waits for `ExecuteAsync`; override it to run the row delete after the base call, with its own `CancellationTokenSource(TimeSpan.FromSeconds(5))` (not the host's already-cancelled token) and a catch-all that logs at `Debug`/`Warning` and swallows. Container Apps gives a terminating replica about 30 seconds.
- **Log text is part of the contract:** the warning template of AC #7 and the two `Information` lines of AC #9 are what Part R and the docs quote. Use structured placeholders (`{InstanceId}`, `{OtherInstanceId}`, `{OtherStartedAtUtc:o}`, `{OverlapMinutes:F0}`); instance ids are random Guids and not secrets.
- **Test hosts:** `EnergyTrackerApiFactory` runs the real `Program` against Testcontainers; the new service starts in every `WithWebHostBuilder` host. Many hosts share one test database, so rows from earlier hosts accumulate with start times minutes apart at most; the real-time overlap threshold (15 minutes) is never reached in a test run. Do not "fix" a flake by shortening `Default`.
- **Convention checks:** file-scoped namespaces, one top-level type per file, primary constructors for DI, ports in `Application/Ports` and adapters in `Infrastructure/Adapters`, `Snake_case_with_underscores` test names, Shouldly, NSubstitute against ports (and a `TimeProvider` substitute), `TestContext.Current.CancellationToken`, a `/// <summary>` on the new public use case, comments of one to three lines of *why*.
