# Story 4.3: Correcting a Meter Reading

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Household member,
I want to correct a Meter Reading I entered incorrectly, with the original value preserved and Status history brought up to date,
so that a mistake doesn't leave my trend permanently wrong or silently hidden.

## Acceptance Criteria

1. **Given** an existing Meter Reading, browsed via Trend History (Story 4.1), **when** I edit its value, **then** the original value is preserved and shown as a visible correction note alongside the edit, never silently overwritten, via the shared `AuditCorrection` mechanism (NFR8, AD-11).
2. **Given** two Household members editing the same Meter Reading concurrently, **when** both submit, **then** the second writer receives a 409 conflict rather than silently overwriting the first (AD-4, NFR10).
3. **Given** a corrected Meter Reading, **when** the correction is saved, **then** `IStatusRecomputeService` recomputes Status forward from the corrected reading through to the present, and the affected `StatusSnapshot` rows are updated to reflect the corrected value — history before the corrected reading is left untouched (AD-7).
4. **Given** a Meter Reading that is currently excluded from baseline computation by an unresolved regression prompt (Story 2.3), **when** it is edited, **then** the edit does not bypass or resolve the open regression prompt — the reading remains excluded until the prompt is classified.

**AC #3 is the one genuinely net-new piece**, and it is bigger than it looks. The literal epic wording ("the affected `StatusSnapshot` rows are updated") collides with an explicit, load-bearing invariant already in the codebase: `StatusSnapshot.cs`'s own doc comment says *"Immutable, insert-only... there is deliberately no Version column: nothing ever updates a row after it's inserted."* Confirmed with Ralf during story creation: build this as the literal full historical walk anyway — immutability is preserved by **superseding via append**, not by relaxing the invariant. Tasks 1–4 below are the concrete design; follow them exactly, they resolve a subtlety (which "clock" to filter on) that is easy to get wrong.

**AC #4 needs no code change** — `EditMeterReading` has no dependency on `IMeterRegressionPromptRepository` today and this story doesn't add one, so it structurally cannot resolve/bypass a prompt. Task 6 adds the missing test that proves it.

## Dev Notes

- **The two clock types are the whole story.** `ReadingTimestamp` (domain: when the meter was actually read, user-editable/backdatable) and `CreatedAtUtc`/`ComputedAtUtc`/`EffectiveAtUtc` (wall-clock: when the system did something) are different axes that happen to usually move together but are not guaranteed to. Every filter added in Tasks 2 and 5 must use the wall-clock family, never `ReadingTimestamp` — that's the one mistake most likely to produce a story that passes a shallow test but silently corrupts history for any household that has ever backdated an entry.
- **`StatusSnapshot` immutability is preserved, not relaxed.** No row is ever updated in place; a correction's effect is a *new* row that wins a read-time "latest `ComputedAtUtc` per `EffectiveAtUtc`" tiebreak (Task 4). The superseded row still exists in the table for anyone querying it directly (audit trail intact) — it's simply not the one `GetStatusHistory`/`StatusSnapshotRepository.GetForHouseholdAsync` surfaces to the Trend History chart anymore.
- **Frontend is out of scope for AC #1–#2 — verified by reading the actual current code**, not assumed from the epic text (which still describes editing "via Trend History" as if it needed building; it doesn't, Story 4.1 already did it). `web/src/components/meter-reading/meter-readings-card.tsx` has the Edit button, `edit-meter-reading-dialog.tsx` has the 409 handling (`err instanceof ApiError && err.status === 409` → `meterReadingHistory.conflictError`) and the correction-note rendering is driven by `item.correctedFromKwhValue` from the existing `GET /api/meter-readings` history endpoint. Re-verify this is still true when you start (a stale story shouldn't be trusted blindly either), but do not plan frontend work assuming otherwise.
- **AD-7's "one `IStatusRecomputeService`" rule is about one writer class, not one method.** Adding `RecomputeForwardFromAsync` as a second method on the *same* existing service/port is the correct shape — it is not "a second snapshot writer," which is what the invariant actually forbids (see the existing `IStatusRecomputeService.cs` comment referencing AD-7's "exactly one application service" wording).
- **Regression-prompt state used by a historical `asOfUtc` recompute is always the *current* open prompt, never a point-in-time reconstruction of what was open back then.** No versioned-prompt-history schema exists anywhere in this codebase, and building one is well out of this story's scope. This is an accepted, documented simplification — same spirit as several already-accepted "pre-existing pattern extended, not yet a measured problem" entries in `deferred-work.md`. Flag it again there after this story if it isn't already framed clearly enough.
- **No pagination/perf bound added to `RecomputeForwardFromAsync`'s affected-points walk.** Correcting a very old reading in a long-lived household could mean recomputing many historical points sequentially. This mirrors the exact class of already-accepted risk in `deferred-work.md`'s Story 4.1 entry ("`GetStatusHistory`... reads a household's entire `StatusSnapshot` lifetime with no pagination... a latent NFR1 perf risk... not yet a measured problem at current data volumes") — don't build batching/pagination here; if you want to flag it, add a matching `deferred-work.md` entry rather than solving it.
- **`IHouseholdRecomputeLock` must guard `RecomputeForwardFromAsync` the same way it guards `RecomputeAsync`.** A `CreateMeterReading` racing a concurrent `EditMeterReading` for the same household must still serialize — reuse the existing lock port, don't introduce a second locking mechanism.
- **Migration discipline (AD-2):** always `scripts/add-migration.sh`, never `dotnet ef migrations add` against a single provider project. The backfill-then-NOT-NULL sequence in Task 3 is required because this table has real rows in every existing environment (local dev, self-host, Azure) — a naive non-nullable `AddColumn` will fail migration application against those.
- **UnitOfWork boundary:** `EditMeterReading`'s existing `unitOfWork.ExecuteInTransactionAsync` wraps exactly the value update + `AuditCorrection` write (unchanged, Story 2.8's design). The new `RecomputeForwardFromAsync` call happens strictly after that transaction commits, best-effort/non-fatal on failure — identical philosophy to why `CreateMeterReading` calls `RecomputeAsync` after its own write commits, not inside a shared transaction: a recompute failure must never roll back or fail an already-successful correction.
