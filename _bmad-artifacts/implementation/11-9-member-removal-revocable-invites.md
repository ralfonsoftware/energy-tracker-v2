## Story

As a household member,
I want to remove a member, leave the household, and see and revoke open invites,
so that we can cut off someone who should no longer have access (audit A2, S10).

## Acceptance Criteria

1. **Given** Settings, **when** a member opens the members section, **then** they see current members and open invites, and can remove a member, leave, or revoke an invite (de-DE and en-US).
2. **Given** a removal or leave, **when** it runs, **then** one transaction deletes the membership, expires every open invite of the Household and increments `Household.Version`. Removing or leaving as the last member is rejected, and of two concurrent removals one gets 409 (concurrency test). A structured log event records who removed whom (AD-26).
3. **Given** any lookup by member id, **when** it runs, **then** it goes through one repository method scoped to the current `HouseholdId`, which returns 404 for another Household's member. An architecture test guards this.
4. **Given** a removed member with a still-valid cookie, **when** they make their next request, **then** they land in the household-creation flow (live check with two Auth0 accounts).
5. **Given** a new invite, **when** it is created, **then** its token is 32 random bytes encoded as base64url, and only a SHA-256 hash is stored. Lookup tries the hash first and the legacy plaintext column second. A follow-up entry in `deferred-work.md` records that the plaintext column is dropped at least 7 days after release.
6. **Given** `docs/self-hosting.md`, **when** this story is done, **then** it states that any member can remove others, and that recovering a fully removed household is an operator-level task.
7. **Implied (the epic names the behaviour but not the wire contract; the dev needs one, and the frontend, the guards and the live check all depend on it):** the API is exactly this, all inside the `/api` group (so authenticated, CSRF-filtered), with `Results.Problem` bodies and a stable `errorCode` extension the SPA localizes (AD-18; the `EventEndpoints.Problem(...)` helper is the precedent):
   - `GET /api/household-members` -> `200 { members: [{ id, displayName, isCurrentMember, joinedAtUtc }] }`, ordered by `joinedAtUtc` then `id`. Never `externalIssuer` or `externalSubjectId` (AD-25's reason applies to this response as much as to the export).
   - `DELETE /api/household-members/{id:guid}` -> `204` on success, for removing another member **and** for leaving (`id` equals the caller's own member id). One route, one use case; the log event says which it was. `404` `member-not-found` when the id is not a member of the caller's Household (including another Household's member: never `403`, never a hint that the id exists elsewhere). `409` `last-member` when the Household has exactly one member. `409` `members-changed` when the concurrency guard fired (the SPA reloads the list and says so). `403` with the existing "does not belong to a Household" detail when the caller has no Household.
   - `GET /api/household-invites` -> `200 { invites: [{ id, createdAtUtc, expiresAtUtc }] }`: only invites that are neither consumed nor expired, newest first. It never returns a token or a hash (it cannot return a new invite's token: only the hash is stored).
   - `DELETE /api/household-invites/{id:guid}` -> `204`. `404` `invite-not-found` when the id is not an **open** invite of the caller's Household (unknown, another Household's, already consumed, already expired or already revoked). The SPA treats a `404` as "already gone" and reloads the list.
   - `POST /api/household-invites` keeps its request and its response shape (`{ token, expiresAtUtc }`), so `InviteGeneratePanel`'s parsing and the `/join/{token}` link are unchanged; the token is shown once, at creation, and can never be shown again.
   - The two `DELETE` routes carry `RateLimitPolicies.MemberRemoval` (identity-keyed, 10 per 10 minutes, registered by Story 11.7 and unused until now). The two `GET` list routes are not throttled (they are cheap, member-only reads; list them in `RateLimitedRoutesTests.UnthrottledByDesign`).
8. **Implied (AD-26: no roles; "full, equal trust"):** no endpoint or use case invents an Owner, an admin check, a "cannot remove the person who invited you" rule or a "cannot remove someone newer" rule. Any member can remove any other member, and the UI offers the same actions to everyone. The only refusals are the last-member rule and tenant scoping.
9. **Implied (revocation needs a representation; the epic does not say which, and a new column would be an avoidable schema change):** **revoking an invite sets its `ExpiresAtUtc` to now and bumps its `Version`** (the same mechanism removal uses to "expire every open invite"). No `RevokedAtUtc` column. Preview (`GET /api/household-invites/{token}`) and accept already answer `409` for an expired invite, so a revoked link behaves exactly like an expired one (the SPA's "no longer valid" copy), and a revoked or expired invite drops out of the open list because the list filters on `ConsumedAtUtc is null && ExpiresAtUtc > now`. Rows are never deleted (history stays; no sweep exists for them, see the deferred entry in Task 12).
10. **Implied (S10's other half: the same cross-Household risk that AD-26 names for member ids applies to invite ids, which are now client-supplied for the first time):** `HouseholdInvite` is also an AD-3 query-filter exception, so the revoke and the open-list lookups carry an explicit `HouseholdId` predicate inside the repository, and a test proves that Household A cannot revoke or see Household B's invite (404 / absent). The same architecture test as AC #3 (or a sibling in the same file) fails if a new file queries `HouseholdInvites` by id without that predicate.
11. **Implied (hashing is worthless if the plaintext leaks through a side door the old code left open):** (a) `HouseholdInviteNotFoundException` and `HouseholdInviteExpiredOrConsumedException` stop putting the token in their message (today `detail: ex.Message` echoes the presented token into the ProblemDetails body, and an unhandled throw would write it to the log); the exception takes no token at all. (b) No new log line, exception message or response carries a token or a hash. (c) The presented token is length-checked before it is hashed or compared (reject anything over 128 characters with the same `404` an unknown token gets), so a multi-kilobyte path segment cannot become a database parameter. (d) Record, in Completion Notes and a `deferred-work.md` entry, whether the effective logging configuration writes the request path (`/api/household-invites/<token>/accept`, `/join/<token>`) at `Information` (ASP.NET Core's hosting diagnostics do by default). The token in a URL path is the existing design (Story 1.8) and out of scope to change here; the finding is to be recorded, not fixed.
12. **Implied (the migration must be safe for the previous image, project-context "Migrations"):** one additive migration, created for both providers by `scripts/add-migration.sh AddHouseholdInviteTokenHash`: add `HouseholdInvites.TokenHash` (nullable `nvarchar(64)`/`varchar(64)`, lowercase hex of the SHA-256 of the UTF-8 token, with a plain **non-unique** index: a 256-bit random hash needs no uniqueness constraint, and legacy rows have a NULL hash, so a unique index would add a second NULL-handling dependency on SQL Server) and relax `HouseholdInvites.Token` to **nullable** (its `HasMaxLength(32)` and unique index stay, for legacy rows). Nothing is dropped, renamed or narrowed. Verified on **both** engines: two hash-only invites (both `Token` NULL) can coexist (SQL Server treats NULLs in a plain unique index as equal; EF's SQL Server provider adds the `IS NOT NULL` filter itself for a unique index on a nullable column, and the generated migration must show it), and the previous image keeps working against the migrated schema (its lookup `WHERE Token = @t` never materializes a NULL-token row; an invite created by the old image has `Token` and no `TokenHash`, which the new lookup finds through the legacy path).
13. **Implied (a removed member's other open surfaces, so the story leaves the system working end to end and not just the happy path):** (a) **Leaving** navigates the leaver out of the dead `ready` state: after a successful leave the SPA does a full navigation to `/` (`window.location.assign('/')`), which reloads `/api/session`, answers `hasHousehold: false` and shows the household-creation flow. (b) **AMENDED 2026-10-17, Ralf's decision at create-story review (Q6): warn, and discard on proceed.** A leaver who still has **unsynced offline Meter Readings** for that Household is told before the leave is confirmed (the logoff flow's `checkPendingReadingsBeforeLogoff(householdId)` already flushes and counts them; reuse it, do not copy it): the confirm step warns that the readings that could not be synced will be deleted from this device if they continue. If the member confirms, the leave request is sent and, once it succeeds, those queued readings (only entries whose `householdId` is the left Household; other Households' entries stay) are removed from IndexedDB through `lib/offline-queue.ts` (`listPending` + `remove(idempotencyKey)`; add one small `removeForHousehold(householdId)` helper there, with a test). If the leave request fails, nothing is deleted. ~~(b) ... the confirm step warns that the count will stay on this device and will not sync unless they are invited back. Nothing is deleted from IndexedDB.~~ (c) A removed member's **other open tab** keeps its stale `ready` state until reload (accepted, Q3: Ralf's condition is that **every API request from that tab fails**). Every household-scoped route answers a non-2xx status (today `403` via the endpoint's no-Household check) and no write succeeds; a sweep test (Task 2.4) enforces this for every `/api` route, so a future route cannot quietly work for a removed member. Recorded in `deferred-work.md`; the next page load lands in the creation flow (AC #4). (d) Jobs the removed member queued keep running (AD-26: jobs belong to the Household); `BackgroundJobs.QueuedByHouseholdMemberId` is `SET NULL` on delete (already so since Story 7.2/11.1), so job history shows the existing "a household member" fallback instead of the name (`settings`/job list `queuedByFallback`). A test deletes a member who has a job row and asserts the row survives with a null `QueuedByHouseholdMemberId` on both providers.
14. **Implied (the display name is nullable and must never be fabricated, UX-DR21):** a member without a `DisplayName` renders a translated generic label ("Household member" / "Haushaltsmitglied"), and the aria-labels and confirm dialogs use the same fallback. The caller's own row is marked "You" / "Du" (from `isCurrentMember`, not by comparing names). Two members with the same display name must stay distinguishable in a confirm dialog: the dialog names the member and the row it was opened from is the one acted on (the request carries the id, never the name).
15. **Implied (destructive actions need a confirmation the member cannot trigger by accident, and the confirmation must say what actually happens):** removing and leaving each open a confirm dialog (existing `Dialog` + `GLASS_MODAL_CLASSNAME` pattern, as the logoff dialog). The remove dialog says that the person loses access immediately, that **every open invite link stops working**, and that the household's data stays. The leave dialog says the member loses access to this household's data, is taken to set up or join a household, and that all open invites stop working. While a request is in flight the buttons are disabled; a failure shows an inline `role="alert"` line in the dialog and leaves it open (the 11.8 logoff-error precedent); a `409 last-member` shows its own copy; a `409 members-changed` reloads the list, closes the dialog and shows a polite status line. A member who is the only one sees no Remove buttons and a disabled Leave with a visible reason, not a hidden control.
16. **Implied (a11y and structure; the Settings page has a Tab-order guard):** members and invites render as lists (`<ul>`), every icon-only action has an accessible name that includes the member (`aria-label="Remove {{name}}"`), the section announces completed actions through a polite live region, and after a removal or revoke the focus moves to the section heading (the row that held it is gone). DOM order stays reading order (WCAG 2.4.3); `web/e2e/tab-order.spec.ts` is extended for the Settings page if the Household section's layout changes, and `locale-theme-sweep.spec.ts` gets the new section in both locales and both themes.
17. **Implied (docs that would otherwise go stale):** `_bmad-artifacts/project-context.md` (the AD-26 rules below), `docs/self-hosting.md` (AC #6), `ARCHITECTURE-SPINE/invariants-rules.md` (one clarification sentence under AD-26: revoke = expire; the list never returns tokens; leaving also exits the SPA's ready state), the UX spine (`EXPERIENCE.md` Settings row + the new mock, Task 1), `deferred-work.md` (Task 12), and the sprint status.

## Dev Notes

### What this fixes and why it is safe to change

- **A2 (Medium, verified):** a Household has no way to cut off a former member: `HouseholdMembers` rows are only ever inserted. Removal "already invalidates access effectively, because `CurrentHouseholdAccessor` resolves membership on every request" (audit S13 text): the work is the missing operation, its guard rails and the UI, not a new auth mechanism. Nothing is cached in the cookie (AD-17 amendment), so a deleted row means `HouseholdId == null` on the very next request and every household-scoped endpoint answers 403 or an empty list.
- **S10 (Low, verified):** invite tokens (`Guid.ToString("N")`, 122 random bits, plaintext in `HouseholdInvites.Token`) cannot be revoked, and a database read yields working join links. After this story new tokens have 256 bits, only the hash is at rest, and members can list and revoke open invites; removal expires them all. The throttling half of S10 shipped in 11.7 (`InviteCreate`/`InviteRedeem`).
- The behavioural risk is concentrated in four places, which is why Task 11 and Part R exist: **the migration** (relaxing `Token`, a unique index that must ignore NULLs on SQL Server), **tenant scoping of two new id-based lookups** (member ids and invite ids), **the concurrency guard** (a read-then-write that is only correct because of the `Household.Version` token), and **the removed member's experience** (stale tab, queued readings, jobs).

### Design decisions already made (do not re-litigate)

- **No roles, no Owner** (AD-26, epic, audit A2 option 2): any member can remove any member; recovery of a fully removed household is operator-level and documented.
- **One DELETE route for remove and leave**; the log event carries `Leaving`.
- **Revoke = expire** (AC #9); no new column; rows are kept.
- **Plain SHA-256, hex, no salt** of a 256-bit random token (AD-26). Hash first, plaintext second; plaintext column dropped later (deferred entry), not in this story.
- **Concurrency guard = `Household.Version`** inside a single `SaveChanges`; 409 for the loser (epic AC); the SPA reloads and says so.
- **Removal is not offline-capable**: it is a mutation outside the Meter Reading offline queue (AD-16 says do not extend that pattern); offline it fails like any other request and shows the generic error.
- **404, never 403, for another Household's id** (AD-26).

### Technical details the dev must get right

- **`init` properties and EF:** `HouseholdInvite.ExpiresAtUtc` is `init` today and must become `set`. `HouseholdMember` stays `init`; deleting it needs the tracked entity (`dbContext.HouseholdMembers.Remove(entity)`), which is exactly what `FindMemberInHouseholdAsync` returns (tracked, not `AsNoTracking`).
- **`SingleOrDefaultAsync` on `TokenHash`/`Token`:** `Token` is unique, so `Single` is safe there; `TokenHash` is a non-unique index, so use `FirstOrDefault`; a hash row and a legacy row for the same plaintext cannot both exist for real invites (a new token's plaintext is never stored), the "prefers the hash row" test only pins the order.
- **`Base64Url` namespace:** `System.Buffers.Text.Base64Url` (BCL since .NET 9, present in 10). Do not hand-roll `Replace('+','-')`. Its output for 32 bytes is exactly 43 characters. The frontend's `INVITE_PATH_PATTERN = /^\/join\/([^/]+)\/?$/` already accepts `-` and `_`.
- **SQL Server and unique indexes over nullable columns:** a plain unique index treats NULLs as equal, so a second row with a NULL key fails. EF Core's SQL Server provider adds `WHERE [Col] IS NOT NULL` to a unique index on a nullable property by default; do not trust it, read the generated migration and run the two-NULL-row test on the SQL Server container (AC #12, Task 2.3h and 3.4). Postgres allows many NULLs in a unique index.
- **Expand/contract and rollback:** the previous image reads `HouseholdInvites` only with `WHERE Token = @t` and inserts rows with a `Token`. It never selects an unfiltered list, so a NULL-`Token` row cannot break it. Invites created by this release have no `Token`, so a rolled-back image answers 404 for them; that is the accepted consequence (PR body, AC #12).
- **Last-member and the race:** read AC #2 and Task 5.2 together. The count is for the friendly error; the `Version` token is the guarantee. A test that only checks "the last member cannot be removed" proves nothing about the race, which is why Task 2.3(e) has both a deterministic stale-tracked test and a looped parallel one. In the stale-tracked test the member count must still be above one after the first removal (hence three members), or the second call fails with `LastHouseholdMemberException` before it ever reaches the version check.
- **Logging:** structured properties, no PII: the member and Household ids only. Do not log display names, e-mail addresses, issuer, subject, tokens or hashes (project-context "Security").
- **No `TimeProvider` here**, no new `DateTime`: `DateTimeOffset.UtcNow`, as the sibling use cases do (Story 11.17 migrates them together).
- **Endpoint filters and binding:** the new `DELETE`s have no body; the CSRF filter answers 400 for a header-less call as for any `/api` mutation. Route constraints: `{id:guid}` (a non-guid id then falls through to the SPA/404 pipeline like the other id routes; test one).
- **Don't split the work into a second migration "for later" now:** the plaintext drop is a *later release*, so it is a deferred entry, not part of this PR.
