# Story 3.4: Incremental Smart-Plug Import (Resource-Efficient Re-Import)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Household member who re-uploads a Smart Plug export periodically,
I want the import to only process data newer than what's already stored,
so that re-uploading an export with overlapping history doesn't reprocess (or duplicate) data I've already imported, and stays cheap regardless of how large the file has grown.

## Context (why this is needed)

Both vendors can hand back data the household already imported, for different reasons. Eve Home's export is **cumulative, not incremental** — every download contains the device's *entire* history, growing on every export (confirmed against `sample-data/eve`'s three dated HiFi samples, gitignored/local-only: 108,715 rows on 2026-06-20 → 114,815 on 2026-08-01 → 117,782 on 2026-08-22, still reaching back to the plug's first-ever reading on 2023-05-27). Meross instead lets the household pick an arbitrary export date range by hand — with no record of the last import's end date surfaced anywhere, picking a range that overlaps a prior import is the expected normal case, not a rare mistake. Either way, a household that re-uploads periodically re-parses and re-persists data it already has today, and because `SmartPlugReading` carries no uniqueness constraint, each overlapping re-upload silently **duplicates** already-stored rows, inflating `SmartPlugGapDetector`'s daily kWh totals and the Status-sharpening signal a little more with every re-import.

This story closes a requirement gap surfaced during its own architecture planning (2026-08-22 correct-course, see `_bmad-artifacts/planning/sprint-change-proposal-2026-08-22.md`), not a stakeholder pivot: PRD NFR10 was broadened to cover "no-silent-duplication on repeated writes" and a new architecture invariant **AD-20** was added specifically for this.

## Acceptance Criteria

1. **Given** an Eve Home import for a device tag that already matches an existing, unarchived Power Point with at least one prior stored `SmartPlugReading`, **when** the file is processed, **then** the Power Point match is resolved from the file's header (device/room rows) before the data body is read at all, and only rows newer than that Power Point's latest stored `IntervalStart` are parsed and persisted — rows at or older than that watermark are never materialized into memory (AD-9).
2. **Given** Eve Home's data rows are strictly newest-first (confirmed against the sample files), **when** the watermark is reached during parsing, **then** parsing stops immediately rather than continuing to filter the remaining (already-imported) rows (AD-9).
3. **Given** a Meross import for a device tag that already matches an existing, unarchived Power Point with at least one prior stored reading, **when** the file is processed, **then** rows are filtered against that Power Point's stored watermark before persisting — not early-stopped, since Meross's CSV row order carries no documented ordering guarantee, unlike Eve Home's (AD-9).
4. **Given** a device tag with no existing Power Point match (`AwaitingPowerPointMapping`) or a Power Point with no prior stored readings yet (first-ever import), **when** the file is processed, **then** the full file is parsed exactly as it is today — this story only optimizes the repeat-import path, not the first import, and never changes `AwaitingPowerPointMapping`/first-import behavior.
5. **Given** the Eve Home parser's current full-DOM row load (`worksheet.Descendants<Row>().ToList()`), **when** a file's rows still need reading past the watermark point (e.g. a first-ever import, or the small newest slice of a repeat import), **then** parsing uses a forward-only streaming reader instead of materializing the whole worksheet into memory, so peak memory scales with rows actually read, not the file's total historical size.
6. **Given** any row a parser produces (regardless of the watermark optimization above), **when** it's persisted, **then** a uniqueness guard — a DB constraint on `(PowerPointId, IntervalStart)` plus an upsert/ignore-on-conflict write, not the watermark filter alone — prevents a duplicate `SmartPlugReading` row from ever being written, so an out-of-order file, a clock-adjusted overlap, or any other path that bypasses the watermark can't silently double-count a day's kWh in gap detection or Status sharpening (AD-2: portable relational subset, added via `scripts/add-migration.sh` to both provider projects per AD-2's dual-provider rule).
7. **Given** an incremental re-import of a large, long-lived Eve Home export, **when** processing completes, **then** it finishes well within Tier 3 async expectations (NFR1) regardless of the file's total historical row count, since only the genuinely new slice is read, parsed, and written.
8. **Given** the new `(PowerPointId, IntervalStart)` uniqueness constraint above, **when** its migration is written, **then** it includes a one-time data-cleanup step that runs before the unique index is created (same migration, cleanup first) — grouping existing `SmartPlugReading` rows by `(PowerPointId, IntervalStart)` and deleting every row in a group but one, so the index creation itself never fails against data already duplicated by pre-this-story imports.
9. **Given** a duplicate group found during that cleanup, **when** deciding which row survives, **then** the row belonging to the most recently-created `SmartPlugImport` (by `CreatedAtUtc`) is kept — Eve/Meross re-exports are treated as superseding older ones, rather than an arbitrary/first-inserted row surviving.
10. **Given** the cleanup migration, **when** run against Postgres and SQL Server, **then** it's verified on both providers via a Testcontainers integration test (matching this project's existing migration-testing discipline) before being treated as safe to ship — a duplicate-finding query (e.g. `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)`) is supported by both engines but isn't guaranteed byte-identical in a raw-SQL migration step, unlike EF's normal portable `migrationBuilder` calls.

## Dev Notes

### This story requires you to design several implementation-level decisions the epic's ACs describe only behaviorally — read this whole section before writing code

Unlike most prior Epic 3 stories, this one's ACs specify *observable behavior* (watermark filtering, early-stop, DB uniqueness) but not the exact interface/algorithm shape needed to get there. The recommended defaults below are this story's own proposal — confirm with Ralf before/during dev-story activation, same "propose → confirm" pattern Stories 2.4/3.2/3.3 already used, then move the answers into Completion Notes.

### Open Design Questions for Ralf — confirm before/during dev-story activation

1. **`ISmartPlugParser` interface shape (Task 1).** Recommended default: add `ReadDeviceTag(stream, fileName, ct)` (header-only, no data-body read) plus a `watermark` parameter on `Parse`. Alternative rejected: keep `Parse` as-is and have `ProcessSmartPlugImport` peek at `readings[0].DeviceName` after a full parse, exactly as today — this satisfies none of AC #1/#2/#5 (there's no way to resolve the Power Point/watermark "before the data body is read at all" if the body must be fully parsed first to learn the device tag).
2. **Insert-time conflict handling for the new unique constraint (Task 3, AC #6's "upsert/ignore-on-conflict write").** No portable EF Core "INSERT ... ON CONFLICT DO NOTHING" exists across Npgsql/SqlServer without either a new third-party dependency (not currently in `Directory.Packages.props`) or provider-specific raw SQL (against AD-2's spirit). Two options:
   - **(A, recommended)** Keep `AddAsync`'s current one-`SaveChangesAsync` shape as the fast path (the watermark filter already removes virtually all real duplicates before they're built, so this path succeeds in the overwhelming common case). On `DbUpdateException`, fall back to: **(1) first `SaveChangesAsync` the `SmartPlugImport` row alone, on its own, before touching any reading** — this must complete before step 2 begins, or the *first* colliding reading's failed save would roll back the still-pending import insert too, silently losing the whole import (row + every reading) on one collision, worse than today's duplication bug; **(2) then loop per-reading** `try { add; save } catch (DbUpdateException) { detach; skip; }`, isolating and ignoring only the genuinely conflicting row(s) — this is the literal "ignore-on-conflict" behavior AC #6 asks for, at the cost of splitting what's currently one atomic import+readings transaction into two steps for this rare fallback case only.
   - **(B)** Treat any leftover constraint violation as a genuine anomaly and let it flow into the existing `catch (Exception)` → `PersistFailedImportAsync` path unchanged (simpler, consistent with existing error handling, but doesn't literally implement "ignore-on-conflict" — a legitimate but rare race would surface as a Failed import instead of a silently-deduplicated success).
   Recommend (A) since AD-20's own text frames the DB constraint as protecting "paths the optimization can't reach," implying graceful tolerance, not a hard failure.
3. **Postgres NULL-uniqueness gap for `AwaitingPowerPointMapping` rows.** SQL Server's composite unique index treats two rows as duplicates only when *every* indexed column matches, including matching `NULL`s — so two `PowerPointId == null` rows with the same `IntervalStart` (e.g. the same still-unmapped import re-uploaded twice) *are* correctly rejected there. **Postgres never compares `NULL` as equal to `NULL` for uniqueness, even in a composite key** — so on Postgres, rows with `PowerPointId == null` are *never* caught by this constraint, regardless of `IntervalStart`, leaving a genuine (narrow) gap in AD-20's stated goal specifically for the pre-mapping window on that provider. Recommended default: **document this as a known, accepted limitation** (same "deferred, pre-existing-class-of-tradeoff" pattern as Story 3.3's own deferred concurrent-import race) rather than solving it — a fix would need either a provider-conditional filtered index (arguably against AD-2's "no provider-specific feature" rule, and `IEntityTypeConfiguration<T>.Configure` has no clean way to detect which provider it's compiling for anyway) or a broader redesign (e.g. a non-null synthetic grouping key) outside this story's literal AC scope. **Verify this reasoning empirically against real Postgres/SQL Server behavior via the Task 4/6 Testcontainers tests** rather than trusting this note alone — ANSI NULL semantics for composite unique constraints are exactly the kind of thing worth confirming against a real engine, not just documentation.
4. **`UpdateMappingAsync`'s set-based UPDATE (Story 3.2) can now hit the new unique constraint too, and has zero exception handling around it.** Scenario: an `AwaitingPowerPointMapping` import sits with a reading at the same `IntervalStart` a *different*, already-mapped import for the *same* target Power Point already holds (e.g. genuinely overlapping data that arrived via two separate uploads before ever being mapped). When later manually mapped, `UpdateMappingAsync`'s blind `ExecuteUpdateAsync` would throw a unique-constraint `DbUpdateException`, surfacing as an unhandled 500 on `POST /api/smart-plug-imports/{id}/power-point-mapping`. **This story's ACs only cover the initial-parse insert path, not this later mapping-UPDATE path** — recommend flagging this explicitly as a **known non-goal/deferred item** for this story (same discipline as #3 above), not silently expanding scope to fix it. If Ralf wants it addressed now, it needs its own AC — don't invent one speculatively here.
